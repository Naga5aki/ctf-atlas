拿到的是服务器检材：可能是运行中的主机、磁盘镜像、容器导出，或几份日志。本页是全模块导读：先把链路画出来，再把每一步送到对应的专页。原始材料保持只读；活机命令只在已获授权的目标上执行。

**分清材料 → 画出服务链路 → 有活机先建现状清单 → 按登录、请求、执行、数据追访问 → 容器、云、集群转对应专页 → 把结论和缺口按顺序写出来。**

<span id="01-先画出服务链路"></span>

## 01 分清材料后，先把服务链路画出来

拿到服务器检材，还不知道手里是运行中的服务器、磁盘镜像、容器导出，还是几份日志。先分清材料，再按连接顺序把已经发现的服务记下来。

**先分清材料类型 → 再按入口到数据库把链路写下来 → 暂时找不到的环节留空。**

**1. 先看手里有什么。** 拿到服务器检材，先看手里有什么：运行中的服务器、磁盘镜像、容器导出，还是几份日志？先分清材料，再选查看方法。离线镜像里没有可直接查询的“当前进程”，活机上的状态也不等于过去的状态。手里只有日志时，按日志所属服务进对应专页：Web 访问与错误日志去 [Web 应用取证 §04](/knowledge/fic-case-04/)，系统、登录与 journal 日志去 [服务取证 §06、§07](/knowledge/forensic-server-services/)。

**2. 把已发现的服务按连接顺序记下来。** 入口域名/IP → 反向代理 → Web 服务 → 数据库。遇到容器或虚拟机，再记它属于哪台宿主机、数据实际存在哪个目录。涉及云服务时，把云账号和日志位置也记上。暂时找不到的环节留空，后面查配置补齐。

**3. 开始查询前先保存范围。** 保存主机时区、采集时间、实例/容器 ID、镜像标签与摘要，以及各份检材的哈希。活机查询也会留下记录；优先保存快照和日志副本，再继续分析。

**4. 不知道先翻哪类记录时，用下表定位。** 表里某一层没有材料时留空，不要用另一层的日志补上。

<details>
<summary>展开五层证据定位表</summary>

| 层次 | 第一批证据 | 要解决的问题 |
|---|---|---|
| 身份与主机 | 登录日志、账户、SSH 公钥、sudo 记录 | 谁在何时获得哪类访问 |
| 服务入口 | 反向代理和 Web 访问/错误日志 | 哪个请求到达了哪项服务 |
| 应用与数据库 | 配置、应用日志、审计日志、数据文件 | 请求触发了什么动作与数据变化 |
| 容器与编排 | 容器配置、日志驱动、挂载、事件 | 实际运行的镜像、参数和数据卷是什么 |
| 云控制面 | API 审计、实例/磁盘/网络流记录 | 谁修改了资源，快照覆盖到何时 |

</details>

材料类型和已写上的环节留在链路图里；留空的环节不拿别层的日志补上。时区、采集时间、实例/容器 ID、镜像标签与摘要、各份检材的哈希先保存，再继续查。

<span id="02-有活机时建立最小现状清单"></span>

## 02 连上活机后，先建最小现状清单

终端已经连上，还要确认它就是目标服务器。下面的命令只用于已获授权的运行中 Linux；离线镜像改读镜像里的文件。

**先确认是目标会话 → 再记下时间、监听和服务 → 没有监听时改查历史日志。**

**先确认终端连接的就是目标服务器。** 下面的命令用于已获授权的运行中 Linux 检材；拿到离线镜像时，应读取镜像里的配置和日志，别在分析机上照跑后当成检材结果。先记录时间、主机信息、监听端口、服务列表和近期日志。把完整输出与执行时间一起保存；此时不要重启、安装工具或清理日志。最后一条命令中的日期要换成调查起点。

```bash
date -Is
hostnamectl
ss -tulpn
systemctl list-units --type=service --all
journalctl --since '2026-01-01 00:00:00' --no-pager
```

**1. 先看时间和现在的监听。** `date -Is` 留下采集时间。`hostnamectl` 看主机信息。`ss` 的 `-tulpn` 查看采集瞬间的 TCP/UDP 监听，不是全部已建立连接，也不是历史端口。`systemctl list-units --type=service --all` 列服务单元。`journalctl --since` 的日期要换成调查起点，`--no-pager` 直接输出。命令若在分析机上跑，结果不能当成离线镜像的状态。`systemctl` 和 `journalctl` 只适用于 systemd 发行版；OpenRC、sysvinit 等环境没有这两条命令，改读 `/etc/init.d/` 与 `/var/log/` 下的文本日志，先确认发行版再选命令。

**2. 看到端口后，把 PID 对到服务。** 在端口对应行找 PID，再核对进程的启动命令、执行文件和运行用户。找到它所属的 systemd 单元，读启动参数和配置路径。这样才能把“一个端口”对应到“一个实际服务”。端口行没有进程字段时，先查采集权限。

**3. 没有监听，不等于过去没运行。** 接着查 journal、轮转日志、服务单元和应用日志，找历史启停记录。`journalctl` 的时间输入按主机本地时区解释。不同主机的日志要先换算到同一时区，同时保留原始时间，别只按屏幕上显示的时分秒排序。

采集时间、监听端口与 PID/单元的对应，建立在“终端确属目标服务器”之上。命令、执行时间和原样输出留在一起；没有监听的，接着查 journal、轮转日志和历史单元记录。

<span id="03-从登录与请求追到数据变动"></span>

## 03 按登录、请求、执行、数据四步追一次访问

要查一次可疑访问做了什么，登录成功还不能写成数据已被修改。按进来、访问、执行、数据四步往下对。

**先对认证和会话 → 再对请求和执行 → 对上共同标识之后才写数据变化。**

**1. 先找人从哪里进来。** 把失败尝试、成功认证、会话和提权记录放在一起，核对账户、来源和时间。需要检查 SSH 配置、日志、账户、密钥或 FinalShell 时，使用 [SSH与远程访问取证](/knowledge/fic-case-03/#051-ssh与远程访问取证)中的对应步骤。只有失败记录时，先不要写已经进入系统。

**2. 再找访问了什么。** 从 Nginx/Apache 或应用日志摘录时间、源地址、Host、方法、路径、状态码、请求 ID 和上游。先看代理/NAT 配置：日志里的地址可能是代理地址，任意 `X-Forwarded-For` 也不能直接当作真实来源。

**3. 继续查服务器执行了什么。** 看进程、systemd 单元及覆盖配置、cron、timer，再查 Web 目录里的文件变化，保存可疑文件哈希。只有单元文件，还要找运行日志，才能判断任务是否启动过。

**4. 最后核对数据有没有改变。** 用请求 ID 和时间去找数据库审计、事务日志、对象版本、上传文件及备份。HTTP 200 表示返回了这个状态码，不直接证明数据库写入成功。

**5. 每接上一步，记下靠哪个字段对应。** 请求 ID 对应用日志、会话 ID 对用户、容器 ID 对挂载、文件路径对数据库主键。保留原始日志行或记录位置。只有时间接近时，先列为候选关系，继续找共同标识；找到之前，不把几条记录写成已证实的完整执行过程。

四步里已经靠共同字段接上的才写成链；只有时间接近的列为候选，继续找请求 ID 或会话 ID。HTTP 200 没有被写成数据库写入成功。原始日志行、对应字段和可疑文件哈希留下来。

<span id="04-容器场景转入专门的证据链"></span>

## 04 服务在容器里时，转入容器证据链

发现服务跑在容器里，只保存镜像还会漏掉挂载里的数据库和上传文件。先记下运行时和容器 ID，再把路径和端口对到宿主机。

**先记运行时和容器 ID → 再对路径和端口 → 涉及集群或网站重构时进入对应流程。**

**1. 先记下运行时、容器 ID，以及日志和数据不一定在镜像里。** 再找配置、日志、可写层、数据卷和网络。不要只保存镜像：数据库或上传文件可能在挂载目录里，应用日志也可能不在容器标准输出中。

**2. 把容器内路径对到宿主机持久化目录。** 核对容器配置、挂载和日志位置。具体身份与配置检查集中在 [Docker 取证 01](/knowledge/docker-evidence-01/)。对不上挂载时，先不要只在可写层里下结论。

**3. 把外部访问端口对到容器端口。** 再与宿主机、云平台记录核对。端点与端口映射步骤集中在 [Docker 取证 05](/knowledge/docker-evidence-05/)。

**4. 集群和网站各自转到已有正文。** 如果是集群，先确定服务在哪个节点、哪个工作负载里，再找它的存储、配置和业务依赖。[Kubernetes 集群取证](/knowledge/forensic-kubernetes-cluster/)保留完整操作，不在这里再复制一套。需要打开网站核对页面或业务时，再在隔离副本中做[网站重构](/knowledge/forensic-website-reconstruction/)：依次核对入口与运行环境、数据库、程序配置。宝塔、PHP 备份恢复和 Java 站库分离各按实际部署处理。重构后产生的新访问、账户和缓存另行记录；判断历史情况时，仍回到未修改的材料。

容器路径、端口与宿主机挂载的对应来自容器配置，不来自猜测；只保存镜像不算完成。重构副本里产生的新访问另行记录，没有写进历史材料。

<span id="05-云与虚拟化再补控制面"></span>

## 05 涉及云或虚拟化时，补控制面与父盘核对

实例名已经接上了，同名实例却可能已经重建；只读实例里的日志，也回答不了“谁创建或删除了资源”。这两类问题在云专题里有完整正文，本页只做识别和转接。

**先确认材料涉及云或虚拟化 → 资源表、控制面分层、父盘核对进入云专题 → 拿回的结果用资源 ID 和 UTC 接回本页链路。**

云资源表按 `账号/角色 → 区域 → 实例 → 磁盘/快照 → 网络/对象存储` 逐层列出并记资源 ID；同名实例重建怎么分、控制面与主机/网络/应用四层记录怎么分开、虚拟磁盘父盘与增量盘怎么核对，唯一正文在[云与虚拟机取证](/knowledge/forensic-cloud-vm/)：先按它的 §01 建资源表，按 §02 分开控制面与数据面，按 §04 核对磁盘挂接与父盘。本页不再复制这套步骤。

从云专题拿回的结果接进本页 §06 的时间表时，对应用资源 ID 和 UTC 时间，不用同名实例名。父盘或增量盘不齐时，后续写入不在这份磁盘里，照样写进 §06 的缺口。

<span id="06-输出结论与缺口"></span>

## 06 把结论和缺口按事件顺序写出来

链路已经查到一些事件，接不上的位置还空着。按登录到清理排开，每个缺口写明它影响哪段判断。

**先按顺序排事件 → 再检查轮转、时钟和代理 → 说明“没有找到”所覆盖的材料范围。**

**1. 把查到的事件按顺序排列。** 按 `登录 → 请求 → 执行 → 文件/数据变化 → 外联或清理` 排列。每一步写明原始日志位置、关键字段、哈希，以及能相互印证的另一条记录；暂时接不上的位置直接留出缺口。

**2. 最后检查这些缺口。** 日志是否轮转、容器是否已删除、各主机时钟是否一致、地址是否经过代理、云权限是否足够、快照时间是否一致。写清每个缺口影响哪段判断。

**3. “没有找到”只表示当前材料没找到。** 材料没有覆盖目标时间，或日志已经缺失时，不把结论写成“没有发生”。

每一步旁边有原始日志位置和另一条印证记录；空位保持为空，并写明影响哪段判断。“没有找到”只覆盖当前材料范围。

<span id="07-不同服务架构如何归入同一条主线"></span>

## 07 认出实际服务后，回到对应证据链

浏览器都能打开，不代表后面是同一种服务。先用配置和进程识别实际服务，再按下表找它自己的数据和日志。

**先识别实际服务 → 再按表回到证据链 → 分别核对多节点关系和数据库结构。**

**1. 先用配置和进程识别，不要因为都能通过浏览器访问就套同一种恢复方法。** 表里从 Web、数据库、文件服务、负载均衡写到编排和数据处理。认不出实际产品时，先停在“先识别”一列。

<details>
<summary>展开七类架构识别对照表</summary>

| 架构或服务 | 先识别 | 回到证据链的方式 |
| --- | --- | --- |
| Web 应用 | PHP、Java、ASP、JavaScript 等实际部署与版本 | 配置、代码、访问/错误日志、进程、数据库及上传文件关联；配置与日志步骤见 [Web 应用取证](/knowledge/fic-case-04/) |
| 关系型数据库 | MySQL、PostgreSQL、SQL Server、Oracle 或云数据库 | 数据目录/导出范围、schema、事务/审计、备份和账户；恢复方法不能互套，恢复与统计见[数据库恢复与统计](/knowledge/forensic-database-recovery/) |
| 文档、键值与其他数据库 | MongoDB、Redis、NoSQL 产品及持久化配置 | 逻辑对象、序列化、持久化/备份、日志和同步范围分别核对 |
| 文件与同步服务 | NFS、Rsync、Web 管理面与共享目录 | 服务配置、访问身份、路径映射、会话和目标文件变动 |
| 负载均衡与高可用 | LVS、Nginx、HAProxy、Heartbeat、Keepalived | 请求分流、代理信任、节点切换、时间差和各节点日志 |
| 编排与基础设施 | Kubernetes、OpenShift、Nomad、Swarm、Mesos、OpenStack | 控制面、资源/任务标识、运行节点、实际存储；Kubernetes 详解见[服务器集群](/knowledge/forensic-kubernetes-cluster/)，其他环境沿对应容器与云专题分析 |
| 数据处理与集群 | Spark、Hadoop、云服务器与 VMware 等环境 | 任务、节点、存储、账号、日志、备份及控制面记录；云环境另见[云与虚拟机取证](/knowledge/forensic-cloud-vm/) |

</details>

**2. 遇到多节点，先找请求实际去了哪台。** 高可用、负载均衡和科学计算集群做的事不同，同一个请求或任务也可能经过多个节点。不要只看一台主机就结束分析。

**3. 准备查库或关联表，先核对结构。** 保存 schema、连接键和时间字段，再做查询、联合查询、结构检查、恢复或关联分析。同名对象不一定是同一个对象；重复行和时区差异也会造成错误对应。

**4. 需要往 Linux 底层继续查时，按问题找位置。** 找系统或服务配置：先确认发行版和包管理，再核对用户/系统配置、启动加载器、systemd、桌面环境和日志的实际路径。找数据盘或删除文件：先核对分区，再看超级块、inode、权限，以及数据和元数据。不要只凭文件名认定内容完整。看缓存、swap 或网络材料：分别记清采集范围。无线、VPN、防火墙和抓包还要说明观察的是哪段网络、哪段时间。发现可疑 ELF、内核模块、凭据或动态库：把磁盘记录与 [Unix 内存](/knowledge/forensic-memory-unix/)中的运行痕迹对应起来，不按工具名称再建重复分类。

识别依据是配置和进程；多节点里先定位请求实际到的那台；schema、连接键和时间字段先保存再查库。恢复方法没有从另一种数据库套过来。

<span id="08-实战从一个-web-请求追到数据库变化"></span>

## 08 实战：把一个 Web 请求追成数据库变化

现在手里有反向代理日志、应用日志、相关数据库记录和主机配置。要判断一次上传是否成功，还不能重新调用上传接口。以下操作在日志和数据库副本上进行。

**先从代理日志挑出请求 → 再对应用、文件和数据库 → 用提交记录和文件实体核实业务结果。**

**1. 先查现成记录，不重新调用上传接口制造一条新记录。** 从代理日志挑出目标请求。保存原始时间、Host、方法、路径、状态码、字节数和请求 ID。再核对源地址属于客户端、代理还是负载均衡节点。

**2. 找到处理请求的应用。** 读反向代理配置，确认上游；用请求 ID 或已确认的会话标识找应用日志。跨节点没有共同标识时，时间、路径和参数只能帮助筛选候选记录，先标明尚未确认。

**3. 去查实际文件和数据。** 从应用配置找到上传目录与数据库连接对象。记录文件哈希、数据库主键，再核对创建/变更字段，以及事务、审计或应用日志。

**4. 容器里找不到文件时，查挂载。** 按容器配置把应用路径对应到宿主机持久化目录；不要只搜容器可写层。

**5. 把几个时间分开记录。** 登录、请求、应用处理、数据库提交、文件写入各列一项，注明时间单位和证据位置。

**6. 看到 HTTP 200，先看应用是否只有“接收请求”。** 没有数据库提交或完整文件时，只能确认请求到达并得到响应。继续按同一请求 ID 找应用成功记录，再核对数据库对象和内容一致的实体文件。这几项能对应，才支持相应上传业务完成。

**7. 最后复核六件事。** 资源/实例是否相同、请求/会话是否相同、记录是否覆盖目标时间、写入是否成功、是否有重试或异步处理、时钟是否一致。缺哪一环，就在时间表里标哪一环，不凭常见架构补成事实。

同一请求 ID 下的代理记录、应用记录、数据库对象和内容一致的文件能对上，才写上传完成；缺的那一环标在时间表上。没有靠重新调用上传接口补一条记录。
