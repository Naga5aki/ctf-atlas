手里是云平台审计导出、虚拟机磁盘镜像（QCOW2/VMDK/VHD/E01）、PVE 节点目录或对象存储记录。本页回答：材料属于哪个资源 ID、控制面操作与主机内活动怎么分开、差分盘父链怎么找全、如何在隔离差分层开机仿真。原始材料保持只读。

**先建云资源表并固定范围 → 分开控制面与数据面 → 核对虚拟机挂接配置与父盘链 → 对齐五类记录的 UTC 时间 → 在独立差分层挂载仿真并关联云审计事件。**

<span id="01-先画资源边界"></span>

## 01 先建云资源表并固定采集范围

拿到云审计、虚拟机磁盘、对象存储或平台导出，还不知道这份材料属于哪一个资源。先把资源边界画出来，再打开文件。

操作顺序：先填资源表，再记采集时间和校验值，将结论限定到对应资源与采集时点。

**1. 先建资源表。** 填入账号/租户、区域、实例 ID、磁盘/卷 ID、对象桶、容器集群和日志服务。实例名放在备注里：同名资源可能已经重建、迁移、自动伸缩或删除，名字相同不代表还是同一个实例。对不上实例 ID 时，先不要用同名实例继续。

**2. 每份材料记下采集范围。** 再为每份材料记下采集时间、时区、可读取范围和快照/导出校验值。只有一台虚拟机镜像，就先分析这份镜像覆盖的主机活动，不把结果扩大到整个云账号。

本节已核对这份材料对应的账号/租户、区域和实例或卷 ID；只有一台虚拟机镜像时，云账号里的其他资源还没有材料。资源 ID 和校验值写在同一行，实例名只在备注里，一并留存资源表、采集时间、时区和快照/导出校验值。

<span id="02-分开看控制面与数据面"></span>

## 02 分开保存云平台控制面与主机数据面记录

问题可能是“谁删了实例”，也可能是“实例里执行了什么”。两层证据不在同一处，先按问题选记录，再靠资源 ID 和时间接起来。

操作顺序：先按表分开四层，再各层单独保存，对上资源 ID、请求 ID 和时间。

<details>
<summary>展开控制面与数据面四层证据对照表</summary>

| 证据层 | 主要问题 | 常见证据 |
|---|---|---|
| 控制面 | 谁创建、变更或删除资源 | 审计事件、API 调用、身份与角色变更 |
| 主机层 | 实例上运行了什么 | 磁盘快照、系统日志、进程与服务配置 |
| 网络层 | 与谁通信 | 流日志、负载均衡日志、DNS 与防火墙规则 |
| 应用层 | 请求触发了什么 | Web、数据库、容器和对象存储访问日志 |

</details>

**1. 按问题选层，不要把来宾系统里的操作写成云平台操作。** 要找“谁删了实例”，先看平台审计；要找“实例里执行了什么”，再看主机。表里的“控制面”就是云平台上的资源管理操作；它和来宾系统里的操作不是同一层。某一层没有材料时，在表上留空。

**2. 先把各层记录分开保存。** 后面再靠资源 ID、请求 ID 和时间对应。对不上同一个资源 ID 时，先不要排成一件事。

本节已核对控制面、主机、网络、应用各自回答的问题，以及能接上的资源 ID；只有主机磁盘时，控制面“谁删除了资源”仍然没有记录。各层记录分开保存，对应时用的是资源 ID、请求 ID 和时间，一并留存四层原始导出，以及后来的对照字段。

<span id="03-分析顺序"></span>

## 03 按资源变更、快照归属、跨层关联和旧版本推进

资源边界已经有了，还不知道先查变更、镜像归属，还是旧版本。按下面四步走，当前找不到文件时不要停在“没有过”。

操作顺序：先看资源变过没有，再确认镜像属于谁，对上平台记录、主机记录和旧版本。

**1. 先看资源变过没有。** 从控制面事件里找目标时间段内的实例、存储和身份变更。时间段还没统一时，先不要解释先后。

**2. 再确认镜像属于谁。** 保存磁盘快照与导出文件的哈希，记录快照对应的实例，不用同名实例替代资源 ID。

**3. 把平台记录和主机记录接起来。** 对照云审计、主机日志、应用日志里的请求 ID、资源 ID、源地址，统一时间后再排序。没有共同 ID 时，先标成候选。

**4. 当前找不到文件，继续查旧版本。** 检查对象版本、生命周期规则、备份和删除标记；当前不可见，不等于从未存在。

本节已核对目标时间段内的资源变更、快照所属实例，以及能接上的请求 ID 或资源 ID；对象版本、生命周期、备份或删除标记还没查时，不能把当前空列表写成从未存在。快照哈希和实例 ID 是同一条；排序用的是统一后的时间，一并留存控制面事件、快照哈希、对照过的请求 ID 和仍要查的旧版本。

<span id="04-虚拟机常见陷阱"></span>

## 04 核对虚拟机挂接配置与完整父盘链

目录里有好几个磁盘文件，还不能按文件名或修改时间决定打开哪一个。先读虚拟机或实例配置，看它实际挂接哪一个盘。

操作顺序：先读挂接关系，再沿着父盘往回查，对上内存和磁盘是不是同一次采集。

**1. 先从虚拟化配置或云平台记录确定实际挂接的顶层盘，再读磁盘元数据沿着父盘关系往回查。** 常见挂接配置位置包括：VMware 的 `.vmx`（如 `scsi0:0.fileName`、`nvme0:0.fileName`）、KVM/libvirt 的 `/etc/libvirt/qemu/<vm>.xml`（`<disk>` 下的 `<source file=...>`）、PVE 的 `/etc/pve/qemu-server/<vmid>.conf`（`scsi0:`、`virtio0:` 等卷标识）以及云平台控制台导出的实例卷挂载列表。不要按文件名编号或修改时间猜最新盘；父盘路径打不开时，先列出缺口。

**2. 每一层都记下路径、格式、大小、哈希和采集范围。** 只打开基础盘，会漏掉差分层中的后续写入。

**3. 单独核对内存、休眠文件和磁盘快照的采集时间。** 有磁盘快照，不代表同时保存了内存。

**4. 缺材料时先写影响范围。** 父盘、日志或权限缺失时，先列出缺口以及受影响的数据范围。单条日志不足以补齐整台虚拟机的活动。

本节已核对配置里实际挂接的顶层盘，以及父盘链上每一层的路径和哈希；父盘、内存、休眠文件或权限缺失时受影响的数据范围。打开的盘来自挂接配置，不是文件名或修改时间最新的那一个，一并留存每一层的路径、格式、大小、哈希、采集范围，以及内存快照有没有同时保存。

<span id="05-先做资源与时间对照表"></span>

## 05 摘录五类记录字段并对齐 UTC 时间

开始排时间线前，记录还散在审计、快照和日志里。先摘字段，资源 ID 用来认对象，显示名称只方便阅读。

操作顺序：先按表摘字段，再保全原始导出，对上时区换算前后的两列时间。

<details>
<summary>展开五类云与虚拟化记录字段速查表</summary>

| 记录项 | 要摘录的字段 | 后续核对 |
|---|---|---|
| 身份审计 | 调用者 ID、角色、会话、源地址、事件时间、请求 ID | 身份是否经临时凭证或角色切换 |
| 实例事件 | 实例 ID、区域、创建/停止/删除时间、镜像 ID | 目标时间点实例是否存在 |
| 磁盘快照 | 卷 ID、快照 ID、父快照、创建与完成时间 | 快照链是否完整，是否覆盖目标时间 |
| 网络记录 | 源/目的、端口、动作、流量与采样时间 | 允许连接与实际业务请求能否区分 |
| 对象存储 | 桶/对象键、版本 ID、请求 ID、删除标记 | 旧版本是否仍可恢复 |

</details>

**1. 先保全原始导出，再抄字段。** 先保全原始导出格式并记录哈希，再复制字段做分析表，不直接改原记录。哈希对不上时，先停止使用这份分析表。

**2. 时间先留原值，再加统一时间。** 接着检查时间：云审计往往用 UTC，主机日志可能用本地时间，应用日志还可能没写时区。每条记录保留原时间，再加一列换算后的统一时间；时区未确定的先标明，别只按格式化后的显示时间排序。

本节已核对每类记录要摘的字段，以及原时间和换算后的统一时间；时区未确定的记录；它们先标出来，不参加先后排序。分析表是从带哈希的原始导出抄出来的，原记录没有被改，一并留存原始导出、哈希，以及带两列时间的对照表。

<span id="06-回答问题时按证据层级写"></span>

## 06 按当前证据所属层级限定结论边界

已经看到一条 API、一条流日志或一份空列表，还不能直接写成最终结论。按证据能回答的那一层停住，缺的下一层继续查。

操作顺序：先看这条记录属于哪一层，再决定下一份要打开的日志，说明当前证据能支持到哪一层。

**1. 有“创建快照”API。** 先看请求结果，再查快照状态、所属卷和数据能否读取。有请求，不等于快照已经完成。状态未完成时，先不要读磁盘。

**2. 流日志里有 allow/deny。** 可以判断网络流被允许或拒绝；要知道访问了哪个 HTTP 路径，继续查 Web 或负载均衡日志。

**3. 对象存储列表是空的。** 接着查版本和删除标记，不能据此认定从未存过文件。

**4. 手里只有虚拟磁盘。** 可以分析主机和应用；云账号做过哪些操作，仍要取得云审计，别从来宾系统日志补猜。

本节已核对这条证据直接能回答的那一层，例如请求已接受、流被允许或拒绝、当前列表为空、或只有主机磁盘；快照完成状态、HTTP 路径、对象版本，或云审计。结论停留在已经打开的那一层，没有用另一层的日志补猜，一并留存这条原始记录，以及还要打开的下一层材料。

<span id="07-磁盘仿真的分层流程"></span>

## 07 在独立差分层转换并挂载虚拟磁盘仿真

静态读取可能已经够用，也可能必须开机看界面。先判断需不需要开机；要转换或新建写入层时，只动工作副本。

操作顺序：先判断要不要开机，再查盘链并转换，对上新写入层和证据盘是分开的。

**1. 先判断需不需要开机。** 静态读取系统、分区和启动方式后，若已能回答问题，就先保存结果；确需看界面或验证程序行为，再做仿真。

**2. 准备能回退的工作盘。** 【仅在副本/仿真/授权环境执行】复制工作盘，准备差分盘或快照，把新写入层与证据基础盘分开放。检查虚拟机实际挂接的路径和写入模式，不启动唯一镜像，也不挂接宿主真实磁盘。先记录宿主和来宾时间、网络状态，后面每次修改都记入实验记录。仿真生成的日志与历史日志分开。

**3. 查清格式和盘链，再转换。** 先固定输入磁盘链，再使用 `qemu-img`。盘正在被虚拟机或其他进程改写时，查询结果也可能不一致；转换和修改都不对使用中的盘进行。下面第一条查看盘链，后两条会创建文件。先准备输出目录，并确认没有同名文件。同名文件已经存在时，先换输出路径，不要覆盖。

```bash
qemu-img info --backing-chain ./work/disk.qcow2
qemu-img convert -f raw -O vmdk ./work/disk.raw ./output/disk.vmdk
qemu-img create -f qcow2 -F raw -b "$(realpath ./work/disk.raw)" ./output/session.qcow2
```

**4. 看参数时注意这三处。** `convert -f raw` 表示输入格式是 RAW，`-O vmdk` 表示输出为 VMDK。这里是大写 `-O`，不是小写 `-o`；输入格式也要实际确认，不能只看扩展名。`create -f qcow2` 创建新的 QCOW2 写入层，`-F raw` 指定基础盘格式，`-b` 指向基础盘。这个新层离开基础盘就不完整，不是全量副本。E01 先用 `ewfinfo` 与 `ewfverify` 核对分段及校验，再通过 `ewfmount ./evidence/disk.E01 ./mnt/ewf` 只读暴露 `/mnt/ewf/ewf1` 原始字节流（或导出 RAW 副本），记录导出校验、逻辑扇区大小和快照链。转换后文件容器和哈希通常会改变，不能仅因哈希不同就认定磁盘内容不同；按逻辑磁盘内容复核，同时保存命令、工具版本、输入/输出哈希。

**5. 在 VMware 里挂接副本。** 【仅在副本/仿真/授权环境执行】按这个顺序操作：新建虚拟机 → 自定义（高级） → 稍后安装操作系统 → 按镜像匹配 BIOS/UEFI、控制器和系统类型 → 挂接核对过的副本盘 → 建立快照 → 关闭外部网络 → 启动。网络先隔离。需要从宿主访问时，再按实验网络检查 IP 和路由，不默认桥接到实际网络。

**6. 用 FTK Imager 挂载时，先认准设备。** 打开“文件 → 镜像挂载”，核对镜像、加载方法和 Drive，再让 VMware 选择对应设备。Writeable 模式的写入层要实际检查，常见为 `.adcf`。界面写着“物理磁盘”并不证明原镜像只读，更要防止把宿主磁盘选进去。出现“物理磁盘已被使用”时，先看挂载结果到底是文件还是设备，再查占用它的宿主程序，不直接解除设备锁。

**7. 需要手工描述符或 EWF 映射时，再查这一段。** 优先使用转换后的完整虚拟磁盘，或者已核对的副本映射。确需手写描述符，逐项核对扇区数、偏移、控制器、路径和 VMX 指向，别照抄另一台机器的文件。描述符引用原始设备时，尤其要检查是否误指向宿主磁盘。使用 `ewfmount` 时，核对它输出的 RAW 视图（常见 `ewf1`）与 VMDK 描述符引用一致，并保持挂载进程运行。RAW 视图不是额外复制的全量盘；VMware 新写入必须落在已核验的差分层中。

本节已核对盘链、转换命令的输入输出哈希，以及新写入层和证据基础盘是分开的；父盘不在、挂载指到宿主磁盘，或 EWF 的 RAW 视图和描述符不一致时，先停住。`qemu-img info --backing-chain` 的依赖链，和大写 `-O`、`-b` 指向的基础盘一致，一并留存命令、工具版本、输入/输出哈希、实验记录里的宿主和来宾时间、网络状态。

<span id="08-pve-集群与-ceph-的入口"></span>

## 08 定位 PVE 集群配置、pmxcfs 库与 Ceph 存储映射

离线镜像里可能有 PVE 配置，也可能 `/etc/pve` 是空的。先找配置和集群数据库，再从虚拟机追到实际存储；Ceph 不能把一块宿主磁盘当成整盘。

操作顺序：先定位配置和 config.db，再从虚拟机追到存储，缺节点时先列待补材料。

**1. 先找这些配置，并保存集群库和日志。** 先找 PVE 配置：`/etc/pve/corosync.conf`、`storage.cfg`、`qemu-server/*.conf`、`lxc/*.conf`。同时保存 `/var/lib/pve-cluster` 和 `/var/log/pve`。离线镜像的 `/etc/pve` 是空的时，它在运行时可能是 pmxcfs 挂载点。继续找 pve-cluster 数据库和相关备份，不凭空目录就认定没部署 PVE。

**2. 在工作副本中定位这些文件。** `find` 在 `./work` 里按文件名和路径找 `corosync.conf`、`storage.cfg`、`qemu-server/*.conf`、`lxc/*.conf` 和 `config.db`。没有结果时，先扩大采集范围，不要改搜索名去碰别的产品。

```bash
find ./work -type f \( -name corosync.conf -o -name storage.cfg \
  -o -path '*/qemu-server/*.conf' -o -path '*/lxc/*.conf' -o -name config.db \)
```

**3. 找到后按虚拟机、存储配置、实际数据往下查。** 从 corosync 记录集群名、节点名/ID 和 ring 地址，先确认节点身份。打开 VM/LXC 配置，摘出存储 ID 和卷/磁盘标识。在 `storage.cfg` 中找到同一存储 ID，记录存储类型、节点限制、路径或池名。最后核对实际卷数据及备份范围。配置里有磁盘名，只说明有定位线索，不等于数据已经拿全。存储 ID 对不上时，先停在配置，不要猜一个池名。

**4. Ceph 先列缺的节点。** 如果存储是 Ceph，数据可能分布在多个节点。一块宿主磁盘不能直接当成完整虚拟盘。缺父盘、节点或存储数据时，先列待补材料，不在唯一检材上启动集群，也不猜参数重建。

本节已核对节点身份、虚拟机上的存储 ID，以及 `storage.cfg` 里同一 ID 的类型和路径或池名；空的 `/etc/pve` 还没找到 `config.db`，或 Ceph 缺节点、父盘时的待补材料。VM/LXC 配置里的存储 ID 和 `storage.cfg` 是同一条；磁盘名没有被当成数据已经拿全，一并留存corosync、存储配置、虚拟机配置、`/var/lib/pve-cluster`、`/var/log/pve` 和 `find` 输出。

<span id="09-仿真副本中的口令恢复"></span>

## 09 仅在隔离仿真副本内用 chroot 重置实验账户口令

PVE 7.2 隔离仿真副本进不去。系统盘、实验卷和快照都确认后，再重置实验账户。重置是设置新口令，不是找回原口令。

操作顺序：先保存认证文件，再在救援环境确认卷，确认 passwd 操作落在副本的 chroot 中。

<details>
<summary>展开救援环境 LVM 激活与 chroot 口令重置步骤（仅限隔离仿真副本）</summary>

【仅在副本/仿真/授权环境执行】先保存配置、认证文件和哈希，记录 LVM 卷及挂载目标。`passwd` 会改认证数据，开机和登录也会写新日志；这些改动都要单列，不能拿新登录证明原口令或历史行为。

**1. 进入救援环境，确认卷。** 从安装介质选 Advanced Options → Debug mode，按界面提示继续，然后检查 PV/VG/LV。示例使用 `pve` VG、`pve-root` LV，实际名称以 vgs/lvs 为准。多盘或同名 VG 先比 UUID；加密卷要先满足解密条件，别误激活或挂载宿主的其他卷。名称对不上时，先不要执行下面的挂载。

**2. 挂载实验系统，再改这个系统里的口令。** 顺序是激活已确认的实验 VG → 挂载实验系统卷 → chroot → passwd → 退出并卸载。下面把关键步骤放在独立子 Shell 中，避免中途失败后误改救援环境账户。

```bash
# 【仅在副本/仿真/授权环境执行】
# 括号内是独立子Shell；任一步失败不能落回救援环境执行passwd。
(
  set -eu
  vgs
  lvs
  if mountpoint -q /mnt; then
    printf '%s\n' '/mnt已有挂载，先核对来源，不覆盖。' >&2
    exit 1
  fi
  # 仅激活已确认的实验VG；事先确认/mnt是空挂载点。
  vgchange -a y pve
  mount /dev/mapper/pve-root /mnt
  # passwd只作为chroot的子命令执行，不在救援环境直接执行。
  status=0
  chroot /mnt /usr/bin/passwd root || status=$?
  if ! umount /mnt; then
    printf '%s\n' '/mnt卸载未完成，检查占用并记录当前挂载。' >&2
    exit 1
  fi
  exit "$status"
)
```

**3. 看结果，再验证启动。** 【仅在副本/仿真/授权环境执行】挂载失败时，这组命令会停止；chroot 失败后，也不会在救援环境另跑 passwd。先按报错检查挂载和系统布局，不直接修改宿主账户。`/mnt` 已有挂载或卸载未完成时，脚本会停下来并写到标准错误。正常卸载后再验证副本启动和登录。记录重置时间、文件差异和新增登录，保留修改前后的 shadow 与日志。分析历史时，仍以静态提取结果为基线。

本节已核对实验 VG/LV 的名称或 UUID，以及 passwd 只在 chroot 的 `/mnt` 里执行过；挂载或卸载失败时，救援环境和宿主账户都还不能改。子 Shell 的退出状态、卸载结果，以及修改前后的 shadow 差异，一并留存配置和认证文件的原始哈希、重置时间、新登录记录；历史分析仍用静态提取。

</details>

## 10 实战：关联云审计事件、磁盘快照与来宾日志

现在有云审计导出、磁盘快照和实例日志，要判断一次资源变更影响了哪台实例。演示标识还不能直接当成检材里的 ID。

操作顺序：先从审计认对象，再核对卷和快照是否可用，云角色操作另用控制面审计验证。

下面的标识是演示用值，实际分析时换成检材里的资源 ID。

**1. 先从审计认出操作对象。** 摘录调用者/角色、区域、实例 ID `vm-example`、卷 ID `volume-example`、请求 ID、原始时间、操作和结果字段。显示名称只作备注。字段缺请求 ID 时，先不要和主机日志硬接。

**2. 确认当时挂在哪台实例上。** 核对卷—实例映射及生命周期。实例重建或名称复用时，按资源 ID 和时间区间分别登记。

**3. 确认快照是否可用。** 记录创建时间、完成时间、状态、所属卷、父链和导出哈希。有创建请求，不等于快照完成；快照也不一定覆盖目标事件后的全部写入。

**4. 再读磁盘里的日志。** 在完整快照链的工作副本中提取主机与应用日志，统一时区后与云审计排序。实例日志只反映来宾系统，不能代替云角色操作记录。

**5. 常见结果按表写，差分盘先看依赖链。**

常见的几种结果，分别这样写：

| 示例证据组合 | 可以支持的结论 |
| --- | --- |
| 创建快照请求被接受，但状态未完成 | 发现创建请求，快照完成与数据可读性尚未确认 |
| 快照已完成并明确映射到目标卷 | 取得该卷在快照条件下的一份状态，仍须注明快照时间和一致性范围 |
| 来宾文件在快照后发生变化 | 当前快照不能直接证明变化后的内容，应查后续快照、对象版本或日志 |

遇到差分虚拟盘，用本页 `qemu-img info --backing-chain` 记录依赖链；父盘缺失时，先标明数据不完整。确需仿真，再另建写入层，记录快照、网络隔离和口令变更。新生成的认证、系统日志不并入历史事件时间线。【仅在副本/仿真/授权环境执行】仿真和口令变更只在写入层上进行。

本节已核对审计里的实例 ID、卷 ID、请求 ID，以及快照状态和所属卷；快照未完成、父盘缺失，或只有来宾日志、没有云角色记录。表中的证据组合和实际字段一致；`vm-example`、`volume-example` 已换成检材里的资源 ID，一并留存审计摘录、快照哈希和父链、统一时区后的排序，以及仿真新日志的单独记录。
