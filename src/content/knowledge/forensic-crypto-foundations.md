## 区块链核心概念

先建立“恢复材料 → 密钥与授权 → 钱包组织 → 交易执行 → 账本与资产”的关系，再阅读后面的取证流程。以下概念用 Bitcoin 与 EVM 网络作主要例子；其他链的密码算法、账户规则和备份格式可能不同。

**验证边界说明：** 本页所有助记词、公私钥、地址与派生路径示例均为教学构造材料，用于演示密码学校验与证据判读逻辑，不代表已对真实涉案钱包执行恢复，也不将链上地址或密钥材料直接等同于自然人身份。

### 00.1 区块链、账本与状态：先确定对象是什么

**区块链**（blockchain）既是一种用密码学承诺和父子链接组织记录的结构，也常指围绕这种结构运行的分布式账本系统。完整系统还包括通信、交易有效性规则、执行规则和共识。哈希相连的文件集合本身，不足以证明它是目标网络认可的历史。

| 概念 | 专业含义 | 与相近概念的区别 |
| --- | --- | --- |
| 账本 ledger | 按网络规则保存的交易记录及相关数据 | 不等于某个交易平台的内部用户余额表 |
| 区块 block | 在协议规定位置组织的一批交易及元数据 | 区块高度是位置，区块哈希是内容标识；同高度可出现不同候选 |
| 状态 state | 在指定锚点执行历史后得到的当前数据，例如UTXO集合、账户余额和合约存储 | 历史流水与某一时点的余额是不同对象 |
| 节点 node | 运行网络协议、接收或验证数据并提供相关服务的参与者 | 钱包、浏览器和索引服务可以连接节点，但不必自身完整验证账本 |
| 共识 consensus | 在有效性规则与参与条件下确定共同接受的历史和状态的机制 | 不负责证明链外商品、真实身份或输入数据的真实性 |
| 网络/链标识 | 区分主网、测试网及其他链的参数和标识 | 同一个地址字符串在多条链上可对应不同余额和历史 |

区块链、数字货币与钱包各处在不同层次：区块链提供记录与验证机制，资产按相应账本规则存在，钱包组织密钥、授权和查询。一个钱包应用可以连接多条链，一条链可以有多种资产；不能按应用名字直接确定币种或网络。

**阅读顺序：** 先理解下节的公私钥和地址，再看助记词与密钥派生、钱包分类、合约与交易、资产与链外数据。后面的第02节继续解释区块承诺、Merkle证明、共识、节点历史能力和两类账本，第03节开始把概念转成证据流程。

### 00.2 私钥、公钥、数字签名、地址与keystore

**私钥**（private key）是签名算法使用的秘密参数；**公钥**（public key）是公开验签依据。以常见的 secp256k1 椭圆曲线为例，私钥可表示为满足 `1 ≤ d < n` 的整数，通常按32字节保存；公钥点由 `Q = dG` 得到，其中 `G` 是规定的基点、`n` 是其阶。这里是椭圆曲线标量乘法，不是对私钥作一次普通哈希。

从私钥计算公钥是规定的正向运算；在正确参数与安全密钥条件下，由公钥逆推出私钥在计算上不可行。任意64位十六进制字符串也不自动是有效私钥：它可能是摘要、随机数据或超出有效范围的数值。识别时还要看材料结构、所属算法及地址对应关系。

**数字签名**（digital signature）将签名密钥与规定消息绑定。签名者按算法生成签名，验证者用公钥、原消息和同样的编码/摘要规则检查。签名不是“用私钥把交易加密”，链上的交易内容通常仍可公开读取。Bitcoin传统花费与Taproot可以采用不同签名规则；常见公钥的压缩编码为33字节，未压缩编码为65字节，BIP340的x-only公钥为32字节，不能把这些长度与20字节EVM地址混为一谈。

签名覆盖范围依协议、交易类型和签名模式决定。验证通过支持特定消息满足该密钥对应的签名条件；交易有效还要检查余额或UTXO、nonce、脚本或合约授权等规则。签名不能独自证明自然人身份、签名发生在哪台设备或准确时刻。控制权核对使用已保全的签名与权限材料，并区分满足某项签名条件与完整转出能力。

**地址**（address）是按目标链规则构造的账户或花费条件标识。EVM的普通EOA地址按公钥的Keccak-256摘要规则取20字节；合约地址则按创建规则确定。Bitcoin地址可以编码公钥摘要、脚本摘要或见证程序，不统一等于“公钥的哈希”。因此公开地址一般不足以恢复完整公钥，更不能恢复私钥；有些交易花费后会公开特定公钥或脚本，但仍需按对应格式解释。

| 对象 | 常见用途 | 发现它之后应怎样解释 |
| --- | --- | --- |
| 私钥或私有派生材料 | 满足相应签名条件 | 先核对算法、密钥范围、钱包实例与实际授权条件，不扩大为所有账户的单独控制 |
| 公钥或扩展公钥 | 验签、观察或派生允许的公开分支 | 可有地址关联与隐私价值；仅有公钥不代表能独立签名 |
| 地址 | 定位收款条件、账户和活动 | 先补网络与资产身份；通讯录或二维码记录不证明地址控制权 |
| 签名 | 验证某个规定消息的密码学授权 | 保全原消息、编码、算法、签名及相应验证锚点；不可只凭界面“已签名” |
| keystore/vault | 封装并通常加密保存秘密材料 | 看具体产品与版本；文件名、地址字段或可解析JSON均不等于已解密成功 |

**keystore**通常指密钥保存容器；例如Web3 Secret Storage V3将秘密材料密文、密码派生参数、加密参数和MAC放在JSON中。解锁密码先经KDF生成解密所需密钥，再按格式核对MAC并解密；它与链上的私钥、BIP39恢复口令不是同一个参数。**vault**常指钱包应用保存的一组加密账户或恢复材料，其内容与算法依产品而定，不能仅凭名称套用V3格式。

**构造实战：** 设备导出包含收款二维码、一个加密keystore和一条签名请求。二维码先支持“该设备保存过某地址”；keystore要继续识别版本、所属实例及是否能验证秘密材料；签名请求还要取得实际签名与原消息。三种材料有不同作用，不能只把字符串长度匹配当成“已经控制并完成支付”。更深入的载体保全、钱包格式和派生核对见[钱包取证](/knowledge/forensic-crypto-wallets/)，地址与脚本可见性见[Bitcoin取证](/knowledge/forensic-crypto-bitcoin/)。

### 00.3 熵、助记词、种子与恢复口令

**助记词是秘密材料的可读备份表示，种子是后续确定性派生的输入；二者不等同于某个地址的一把私钥。** 在 BIP39 中，软件先生成不可预测的随机位，再把它们编码成有顺序的单词。熵在这里指原始随机材料及其不确定性，不是单词的“难记程度”；用名言或自己编的句子代替随机生成，会改变安全前提。不是所有单词备份都采用 BIP39，其他词体系和秘密共享备份有各自词表、字段与校验规则，不能仅凭“看起来像英文单词”就套用。

BIP39 先对 ENT 位原始熵计算 SHA-256，取开头 `CS = ENT / 32` 位作为校验位，附在熵后面；再每 11 位切一组。每组可表示 0—2047，作为 2048 词表中的索引。因此词数为 `(ENT + CS) / 11`，顺序也参与编码。

| 原始熵 ENT | 校验位 CS | 总位数 | 助记词词数 |
| --- | --- | --- | --- |
| 128 位 | 4 位 | 132 位 | 12 |
| 160 位 | 5 位 | 165 位 | 15 |
| 192 位 | 6 位 | 198 位 | 18 |
| 224 位 | 7 位 | 231 位 | 21 |
| 256 位 | 8 位 | 264 位 | 24 |

校验位用于发现部分抄写或排序错误，不增加原始随机性，也不认证钱包归属。全部单词都在词表内，仍可能无法通过校验；校验通过，只说明符合这套编码规则。**24 词对应 256 位原始熵，并非 256 位 seed，也不能从词数独自断定随机生成是否可靠。**

从助记词到种子是另一步：BIP39 使用 PBKDF2，伪随机函数为 HMAC-SHA512，迭代 2048 次；将助记词句子作为 password，将固定字符串 `mnemonic` 与 passphrase 拼接后作为 salt，输出 64 字节，即 512 位 seed。这里 password 是算法参数名称，不是钱包登录密码。输出更长不代表凭空增加到 512 位不可预测性。

助记词与 passphrase 都按 UTF-8 NFKD 处理。NFKD 是 Unicode 兼容分解规范化，使规定范围内的字符表示统一；它不是翻译、转小写或随意清理空格。取证时保留原始字符与顺序，规范化只在验证副本中按标准实施。将词翻译成另一语言的对应词，也可能改变 seed，因为派生输入包含实际词句。

| 材料 | 改变它会影响什么 | 不能与什么混同 |
| --- | --- | --- |
| 助记词及顺序 | 熵/校验和后续 seed | 单个地址、单个私钥 |
| BIP39 passphrase | 同一词句生成的 seed 与后续密钥树 | 钱包解锁密码、设备 PIN；也不要求是词表中的“第25词” |
| 钱包解锁或文件加密密码 | 打开本地受保护材料的条件 | 不当然参与 BIP39 seed 派生，须看实际格式 |
| 秘密共享备份的份额 | 达到阈值后按相应协议恢复秘密 | 不是把一套助记词平均剪成几段，也不等于多签 |

未使用 passphrase 时取空字符串。空口令与不同非空口令都会生成有效 seed，通常指向不同密钥树；助记词校验无法判断哪一个是目标钱包。恢复必须继续结合已知公有地址、网络、路径和账户来源核对，不能把“导入成功”当作命中。

**构造判读：** 一份笔记中的 24 词候选通过校验，备份界面却显示余额为零。先确定词体系和原顺序，再分别记录 passphrase 是否已知、所用派生条件及查询范围。若未知 passphrase，零余额只描述当前测试条件下的观察；即使某路径匹配已知地址，也只支持该派生关系。

### 00.4 HD钱包、派生路径与扩展密钥

**HD（分层确定性）钱包把一份种子按确定规则展开为密钥树。** “确定性”表示相同输入与条件产生相同结果；“分层”表示树中不同节点管理不同子树。可以把种子理解为起始材料，把派生路径理解为树中路线，但路线本身不是秘密，且并非所有钱包都使用同一种树或路线约定。

BIP32 从 seed 计算主私钥和 32 字节 chain code，再逐层派生。扩展私钥包含私钥与 chain code；扩展公钥包含公钥与同一节点的 chain code。chain code 是派生参数，不是链编号或解锁密码。序列化还记录深度、父指纹和子索引；BIP32 主网常见编码前缀为 `xprv`、`xpub`，其他版本前缀可能不同，不能只凭前缀确定全部用途。

| 材料 | 可推导的范围 | 取证限制 |
| --- | --- | --- |
| 普通私钥 | 对应密钥的公钥和相应签名能力 | 缺少派生参数，不能当作整棵树的备份 |
| 节点扩展私钥 | 该节点的后代私钥、公钥 | 若节点不在树根，不能自动覆盖祖先或其他子树 |
| 节点扩展公钥 | 沿全非强化路径派生后代公钥 | 无法跨越强化边；还需脚本规则才能生成相应地址 |
| seed 或主扩展私钥 | 对应确定性树 | 不涵盖另行导入的私钥、其他 seed、外部签名器或全部本地元数据 |

**非强化派生**允许父扩展公钥推导子公钥，方便联网程序生成收款地址而不持有签名私钥。**强化派生**在计算中用到父私钥，父扩展公钥不能完成该步。路径中的 `'` 通常表示强化；部分表示法用 `h`。这不是在普通路径上随意加符号，两种派生会产生不同结果。

例如 `m/44'/0'/0'/0/5` 在 BIP44 的 Bitcoin 主网约定下，表示从主节点 m 依次进入用途、币种、账户、外部收款分支和地址索引。前三层采用强化；账户索引从 0 起，最后的 5 是索引 5，不是“第5个账户”。`change=0` 常指外部收款，`1` 指内部找零。这只是特定约定，其他用途、脚本或产品路径须分别确认；地址外观无法还原完整路线。

一个账户 xpub 可帮助关联范围内的收款与找零地址，公开它会削弱隐私。更深的风险是：**父 xpub 与其已知全非强化派生路径上的某个后代私钥一起泄漏，可推回该父节点的扩展私钥，暴露整个对应子树。** 直接子层的关系可简写为 `子私钥 = 父私钥 + 派生偏移（模曲线阶）`；父 xpub 与子索引使偏移可计算，因而已知子私钥可反求父私钥。强化边阻断这条公钥派生路径。不能扩大为“拿到任意私钥和任意 xpub 都能还原全钱包”，也不能把 xpub 当作毫无风险的公开标签。

备份范围还要区分“可以数学派生”与“软件已经发现”。恢复界面的扫描路径、账户顺序与地址 gap limit 可能使部分历史账户未显示；余额为零也不等于没有交易历史。密钥树不保存所有账户名、备注或导入关系。短父指纹可能碰撞，而且 xpub 序列化不包含完整祖先路线，仍需账户配置、密钥来源或描述符补足。

**构造判读：** 应用列出三个账户，其中两个来自同一 HD 根，第三个由单独私钥导入。第一账户 xpub 能派生出截图中的地址，只支持该子树与地址匹配；不能据此恢复第二账户的强化分支，也不能把根备份当作第三账户备份。记录 `根来源 / 路径 / 分支 / 索引范围 / 脚本 / 网络` 后，再判断实际覆盖范围。

### 00.5 钱包类型、账户与控制权

**钱包是管理或调用签名材料、组织账户并查询账本的工具；资产状态记录在链或平台账本上。** 钱包文件可能保存秘密，也可能只有地址、交易缓存和外部签名器配置。把钱包文件复制到另一台电脑，复制的是材料与配置；删掉界面也不等于链上资产消失。

钱包、账户和地址分别回答“用什么工具”“管理哪个对象”“用什么标识”。账户链的链上账户、HD 树的账户层、应用列表中的账户以及平台登录账户属于不同语境；Bitcoin 的一个 HD 账户还可管理多个收款与找零地址。统计账户数时写出口径，不能用地址数、最高账户编号或平台用户名代替。

钱包类型需要按不同维度描述，以下各行可以组合：

| 维度 | 类型与主要机制 | 应核对的控制条件 |
| --- | --- | --- |
| 谁掌握资产授权 | 托管：服务方执行链上操作、用户向其提出业务请求；非托管：用户按相应规则管理授权材料 | 登录权、签名权、恢复权与服务方权限分别确认；名称不证明用户独立控制 |
| 秘密与联网环境的关系 | 热钱包的签名材料在联网环境可用；冷存储使秘密生成、保存或签名保持相应离线隔离 | 实际生成、使用、备份与传输流程，不能只看采集时是否断网 |
| 签名材料所在位置 | 软件钱包使用软件保护材料；硬件钱包把关键签名操作放在专用设备 | 主机侧公开材料、设备关联、备份位置和设备内签名条件 |
| 本机具有什么能力 | 仅观察钱包追踪公开材料；签名钱包或外部签名器提供相应授权 | 有无秘密或可调用权限，不能从余额或“发送”按钮推断 |
| 授权怎样组合 | 多签由规则要求多个密钥的有效授权；常见 MPC 阈值签名由多方份额协同计算签名 | 实际阈值、参与方、份额、恢复和其他授权入口，不把单份材料当作充分条件 |
| 链上如何接受操作 | 普通密钥账户按签名规则授权；合约钱包按程序及状态验证授权 | 目标网络与历史区块下的规则、授权者和可用执行入口 |

硬件钱包可以与联网电脑或手机交换请求和签名；关键区别是相应私钥在设备内使用，而非“从不连接任何设备”。仅观察程序也可构造交易、接收外部签名并广播。手机可以承担离线签名角色，但临时关闭网络不能证明秘密此前未上传、备份未同步或设备未被控制，需要完整流程证据。

多签与 MPC 都可分散控制，机制却不同。典型链上多签把多个密钥及阈值写进脚本或合约规则；常见 MPC 阈值签名可在不先合并完整私钥的情况下，用份额协同产生由对应公钥验证的签名。单看普通链上签名未必能识别背后的 MPC 参与者。秘密共享备份通常讨论“怎样重建秘密”，阈值签名讨论“怎样共同完成计算”，不能互相替代。服务方持一份 MPC 份额，也不能仅凭这个事实判定托管与否，要核对阈值、恢复权及实际权限。

**构造判读：** 电脑应用显示两个地址：一项只保存 xpub，另一项标为外部硬件签名；平台应用另有一个登录账户。前两项支持该电脑记录和管理过公有账户资料，平台项支持服务账户关联。当前材料未证明电脑持有两项私钥，也未证明平台登录者能直接控制充值地址。若另取得“2-of-3”规则和一把参与私钥，只确认其中一个授权条件，完整转出能力仍须核对其他密钥或执行入口。

钱包目录、加密封装、手机备份与硬件、多签、合约账户的深入操作见[钱包与本地痕迹](/knowledge/forensic-crypto-wallets/)。

### 00.6 智能合约、EOA、合约账户与DApp

**智能合约是由区块链协议执行的程序及其状态。** 在 EVM 网络中，合约通常以某地址上的运行时代码、持久化数据和执行规则共同发挥作用：收到有效调用后，节点按相同规则计算结果。名字里的“合约”不表示它天然具有法律合同效力；“自动执行”指触发后的规则处理，不表示程序能每天定时自行醒来。写了到期条件的程序，仍需要交易、其他合约调用或网络特定机制触发执行。

EVM 是执行字节码、计算资源消耗和状态变化的虚拟机及规则环境；Solidity 是编写合约的一种高级语言，源代码经过编译才形成可执行字节码。ABI 是函数、参数、返回值和事件的字节编码与解释约定，帮助应用与程序沟通。源码、字节码和 ABI 承担不同作用：一个熟悉的函数名，不能独自证明目标地址实际执行了哪段代码。

| 概念 | 准确定义 | 识别时的边界 |
| --- | --- | --- |
| 地址 | 在指定网络中定位账户的标识 | 同样字符串可以出现在不同链；地址不是应用，也不直接标明自然人 |
| 账户 | 链状态中的对象，具有余额、nonce、代码或存储等字段 | 原生余额与合约内代币余额分属不同记录位置 |
| EOA，外部拥有账户 | 以对应密钥签名授权外部交易的账户 | 支持 EIP-7702 的网络允许有效授权后的 EOA 委托代码执行，不能断言所有 EOA 永远无代码 |
| 传统合约账户 | 经创建过程建立、按程序响应调用的账户 | 没有一把可像普通 EOA 那样直接替该合约地址签外部交易的私钥 |
| 合约钱包 | 以合约逻辑验证和执行资产操作的钱包账户 | 控制者可用密钥、多签、模块或恢复机制满足规则；控制者私钥不等于合约地址的普通私钥 |
| 钱包应用 | 管理账户、组织签名请求、查询和展示数据的界面 | 一款应用可以管理多种账户；安装应用、添加观察地址都不等于具备控制权 |

部署通过初始化过程建立合约及初始状态；部署请求、初始化代码与最终驻留代码不是同一份对象。调用已有合约可以读取数据、修改存储、调用其他程序或发出事件。**storage 是持久化状态，事件是执行产生的日志记录**；事件可以通知前端，但不会替代余额、权限或所有权状态。事件名可以被自定义，必须结合发出地址和程序含义解释。可升级代理还会使固定地址在不同时间采用不同逻辑。

DApp 是利用链上合约提供部分核心功能的应用。前端负责页面和请求组织；链外后端可能负责索引、账户服务或业务协作；RPC 是应用向节点读取或提交请求的通信入口；合约层按链规则执行。四层可以由不同主体维护，也不一定全部存在。网页写“兑换完成”、后端生成订单、节点接收请求和合约完成兑换，是四种不同证据；前端停服也不直接等于链上合约消失。

**构造证据判读：** 材料只有网页订单“已支付”、钱包地址甲和合约地址乙。先保存网页记录、请求内容、网络及地址，再区分甲是签名账户、观察账户还是合约钱包；把乙关联到实际包含交易、回执和对应状态。若甲是合约钱包，还需区分发起操作的控制者与提交交易的账户。单凭页面按钮或两个地址，不能推出付款已生效，更不能推出某人单独控制乙。

### 00.7 交易、调用、gas与链状态

**交易是提交给网络、按协议验证和排序的状态变更请求；调用是程序执行中的交互。** 一笔外部交易可以触发多次合约调用、多个资产动作和多条事件，调用次数不是交易笔数。生成交易标识只定位请求，等待、被区块包含、执行成功和获得最终性仍要分别判断。

| 对象 | 回答的问题 | 不能替代的对象 |
| --- | --- | --- |
| 交易正文 | 请求向哪里发送原生价值、执行什么输入、使用哪些序列和费用参数 | 执行结果与实际资产变化 |
| 调用过程 | 哪些程序按什么顺序参与，哪些步骤成功或回滚 | 规范链包含证据与最终状态 |
| 回执及事件 | 某笔已包含交易的执行状态、结算用量和保留下来的日志 | 之后的账户状态或链外履约 |
| 链状态 | 指定锚点下账户余额、nonce、代码和存储是什么 | 哪个自然人操作、完整业务历史 |

gas 是协议对计算、存储访问等资源计价的**用量单位**，不是交易金额，也不是币的市场价格。gas limit 是允许消耗的上限；gasUsed 是用于结算的该笔用量；每单位 gas 的实际价格再把用量换成费用。提高上限不表示一定按整个上限收费，也不保证程序逻辑成功。费用上限、实际单价、区块累计用量和本笔用量必须分开。普通 Ethereum 执行费由本笔结算用量乘实际单价求得；blob 交易和部分二层网络还可能存在其他费用成分，不能把这一式子当成所有网络的总费用规则。

已包含但执行失败的普通交易仍可能付费并消耗发起账户 nonce；普通执行中的写入和日志可回滚，费用和协议序列变化依规则保留。支持 EIP-7702 时，有效代码委托授权的处理也可能在外层执行失败后保留，因此“失败”不能扩大解释为整个交易对账户毫无影响。

nonce 的含义必须附上对象和协议域。普通 EVM 外部交易使用本链发起账户的序列值；代币签名授权可以使用该合约自己的防重放计数与签名域；合约钱包操作也可采用自己的序列规则。这些值不能相互替换。不同网络中地址和 nonce 相同，不能据此认定交易互相冲突；当前账户 nonce 也不能直接当成收款次数或成功付款次数。

`view` 表示函数承诺不修改状态，仍会读取和计算；进入链上交易的执行路径时，这些工作仍消耗 gas。`eth_call` 则是在节点选定的状态和输入条件下模拟执行消息调用：程序确实运行，但不会因此广播一笔交易或把模拟变化提交到规范链。它也能模拟原本会写状态的函数，所以“只读”描述对链的影响，不意味着所有被调用函数都是 view。模拟成功不保证将来的交易成功，余额、权限、排序和执行环境都可能变化。

状态查询通常描述某个区块执行完毕后的快照；同一区块早期交易发生时，账户状态可能不同。记录网络、区块 hash、查询时点和所采用的状态范围，再把快照与目标回执区分：回执回答该笔执行怎样结束，快照回答该锚点保存了什么。当前余额也不能直接替代历史交易执行后的余额。

**构造证据判读：** 页面先模拟“可支付”，实际请求的 gas limit 为 80,000，已包含回执显示失败、结算用量为 45,000。应报告模拟结果、失败执行和实际费用三个事实；不能按 80,000 当实际用量，也不能写“支付已成功”或“未付任何费用”。之后的余额查询另附状态锚点。具体回执、调用与费用核对见[账户链与合约交易](/knowledge/forensic-crypto-account-chains/)。

### 00.8 原生币、代币、NFT与链外数据

原生币由所在网络的基础协议账本直接记录和处理，例如 Ethereum 的 ETH；合约代币由合约定义发行、余额、授权和转移规则。它们都可被钱包展示，但数据位置不同。原生转账的 value、合约代币的数量和支付的网络费用不能混成一个金额；“账户有代币”也不自动表示它有足够原生币支付普通交易费用。

| 类型 | 计量或标识方式 | 资产身份与常见误读 |
| --- | --- | --- |
| 原生币 | 协议定义的最小单位整数 | 网络加原生资产类型；不能只保存名称 |
| ERC20 | 合约按地址管理同质数量余额 | 网络加合约；decimals 是可选的展示换算字段；缺失时不能擅自假定精度 |
| ERC721 | 每个 tokenId 区分一项非同质代币 | 网络加合约加 tokenId；编号不是付款金额 |
| ERC1155 | 同一合约内按 id 区分种类，每种又有数量 | 网络加合约加 id；一个 id 可有多单位，不同 id 不可直接混加 |

coin/token 是账本层面的分类；稳定币描述维持某种目标价值的设计，包装资产描述对另一资产的表示机制。在 Ethereum 上，稳定币和桥接包装资产通常作为合约代币记录，不能因为挂钩美元或映射另一链原生币，就当成 ETH。原资产、包装表示和平台账内权益需要分别辨识。名称、symbol、图标乃至相似合约地址都不保证资产相同；桥接关联须有协议映射和两端证据，不能由同名或近似金额直接建立。

链上程序不能仅凭自身执行规则直接知道互联网价格、天气或现实交付。预言机（oracle）通过链外采集、报告、聚合或证明，再由交易、合约验证和更新等机制把外部信息提供给链上程序。预言机不是“链自动知道真相”：需要核对数据源、报告者、聚合规则、更新时间、验证条件和控制权限。共识能确认程序按所接收输入执行，不能独自保证输入符合现实；真实来源也可能提供过时数据。链内时间、数据采集时间与更新包含时间分别保留。

NFT 的链上标识和持有状态，与描述文件、图片、视频是不同材料。metadata 可能在链上，也可能通过 URI 指向链外文件；URI 和文件内容还可能依实际实现改变。IPFS CID 以内容及其编码结构建立标识，取得材料后可按相应规则核对内容完整性。CID 不是简单的文件摘要，也不是存放位置；它不能保证始终有节点保存和提供数据。持续可获取依赖保存、固定和服务可用性，完整性与在线性要分别验证。

链上 NFT 持有记录也不自动证明图片作者、现实物品归属或关联作品版权；token 状态、文件内容、现实对象和约定权益应分列，不由“拥有 NFT”扩大推导。取证中保存当时 URI、metadata、所引用文件及其各自取得时间，并说明可核对到哪一层。

**构造证据判读：** 两条链都展示名为 ART 的代币，一条链的 ERC721 编号 42 指向某 CID，另一条链展示同图标的 ERC20 余额 42。它们是不同资产、不同计量。若 NFT 在指定区块归地址丙，但文件暂时无法获取，可以确认到该 token 的链状态层；不能把编号当作 42 个代币，不能写文件已被篡改，也不能仅凭持有记录确认丙拥有图像版权。

## 01 先确定题目问的是哪一层事实

虚拟币取证连接设备、应用、链和平台四类材料。先把问题拆为“某字段在哪里”“某交易是否生效”“某段时间收到多少”“谁能够控制某地址”，再选择材料和统计口径。四类材料相互补足：钱包界面显示的数字、平台登记的余额和链状态并不总相同。

| 对象 | 可观察内容 | 提交结论需要的验证 |
| --- | --- | --- |
| 设备与文件 | 钱包目录、配置、助记词载体、聊天、笔记与图片 | 原位置、所属用户/应用实例、摘要、时间字段含义 |
| 钱包应用 | 账户、网络、导入方式、发起请求、缓存交易状态 | 版本与账户类型，关联已知地址、实际回执和历史 |
| 链上记录 | 花费关系、交易执行、日志、区块包含关系 | 网络、完整标识、资产、索引、区块锚点与查询时点 |
| 平台账本 | 充值、提现、成交、账内划转、用户及订单 | 平台字段与业务状态，充值映射，银行/支付及链上互证 |

**常见考点：** 地址、交易哈希、账户数量、助记词位置及次序、发起时间、失败原因、有效转入次数、收款总额和后续流向。问“第三个单词”与问“完整正常次序”需要不同结果；问“地址页创建时间”与问“钱包建立时间”也不能混答。

## 02 理论：账本、资产与钱包

### 02.1 三个模型

| 模型 | 金额落在哪里 | 分析对象 |
| --- | --- | --- |
| Bitcoin 的 UTXO | 尚未花费的输出，由锁定脚本约束花费 | 前序输出、当前输入、新输出、手续费与可能找零 |
| EVM/TRON 的账户与合约 | 原生余额在链状态；代币由对应合约状态管理 | 外部交易、执行回执、代币事件、调用路径和原生费用 |
| 中心化平台账本 | 平台记录用户权益与内部业务变动 | 用户ID、订单、充提币、成交、账内划转与余额对账 |

钱包负责保存或调用签名材料、管理派生账户并展示数据。地址可以被公开保存或观察；币的状态由对应账本记录。观察钱包、硬件签名账户或平台登录账户，均不必然意味着本机保存全部私钥。

公链是伪名交易网络：地址和交易图可公开，但自然人姓名通常不在交易中。确认、最终性和历史快照需要按网络说明；不能把“区块链不可改”当作省略重组和节点验证的理由。

### 02.2 资产身份先于符号

记录 `网络标识 + 原生资产/合约标识`，再记录显示名称、symbol、decimals。不同链上同名 USDT、同一链上的假同名币、跨链包装资产都不可未经解释地合并。稳定币的名称也不保证任意时点可按固定法币价值兑换。

金额保留最小单位整数：`1 BTC = 100,000,000 satoshi`，`1 ETH = 10^18 wei`，`1 TRX = 10^6 sun`。代币精度按实际资产核验，不能全部默认 8、6 或 18 位。ERC20 的名称、符号和精度接口可缺失；未知精度时保留整数并标明未知。

普通 BTC 非 coinbase 交易的输入总值减输出总值是手续费。地址余额取决于尚未花费且满足目标控制/观察范围的输出，不能用任意一笔交易的输入减输出替代余额。

### 02.3 地址格式与标识

| 表达 | 可以先识别 | 仍须补足 |
| --- | --- | --- |
| `bc1…`、`1…`、`3…` | Bitcoin 常见主网地址候选 | 完整编码/校验、脚本类型、实际网络与钱包证据 |
| `0x` 加40位hex | EVM的20字节地址候选 | chain ID及链环境，大小写校验与账户/合约语义 |
| `T…` 或 `41` 加40位hex | TRON Base58Check/hex候选表达 | 两种编码是否对应同一地址、实际网络与代币合约 |
| 扩展公钥/描述符 | 可派生或观察地址的公开材料 | 路径、脚本、范围、是否包含私有材料、外部签名条件 |

TRON 主网及常见测试网都可能使用 `41`，不能凭前缀确定网络。EVM 同一20字节地址可出现在多条链。完整交易hash用于查询和关联；前几位仅适合展示，不适合唯一去重。

不要尝试从公开地址反推出私钥。助记词通常结合可选口令形成种子，再经派生路径、脚本类型和账户索引得到不同地址；“助记词→唯一地址”忽略了这些条件。具体处理见[钱包与本地痕迹](/knowledge/forensic-crypto-wallets/)。

### 02.4 账本、区块与节点：先看懂记录怎样串起来

把账本想成一套按规则登记的流水，把区块想成一次装订的一批记录，节点则是接收、检查和保存这些记录的参与者。钱包像查询和签字的窗口，浏览器像整理好的目录。窗口显示一行“已付款”，不等于所有参与者已经认可该行。

一条区块链至少有两种关系：**区块之间的父子关系**，以及**交易内部的资金或状态关系**。父哈希将新区块连接到其父区块；Bitcoin 的交易输入又引用前一笔交易的特定输出。不要把这两种“前序”混为一谈。

| 观察字段 | 表达的事实 | 取证用途与限制 |
| --- | --- | --- |
| 区块hash、父区块hash | 当前区块标识及其连接对象 | 核对连续链；同一高度可能出现竞争区块，高度不能独自唯一定位 |
| 高度/number | 在所观察分支中的位置 | 限定范围、排序和计算深度；跨网络高度没有统一时间意义 |
| 交易列表及交易索引 | 该区块包含的交易及排列 | 固定交易所在位置；不要用浏览器显示顺序替代协议顺序 |
| Merkle root、transactions root | 对交易集合或结构的摘要承诺 | 核对包含关系；不同链的树、编码与哈希规则不能通用 |
| state root、receipts root | 对执行后状态及回执的摘要承诺 | EVM 中状态、交易和执行结果是不同对象，不能互相替代 |

验证的基本流程是“识别网络与规则 → 校验区块及交易 → 确认父子连接 → 判断所跟随分支 → 在该锚点解释金额和状态”。只校验哈希链条，仍可能面对一条按错误规则生成的链或脱离实际网络的私有分支。

**小案例：** 两份响应都把交易记在高度 H，却给出不同区块hash。先保留两份响应、查询时刻与父哈希，再核对节点同步状态和当前分支。正确结果可能是一次重组，也可能是查错网络；不能直接删掉其中一份并写“证据矛盾已消除”。

### 02.5 哈希、公钥、地址与签名：四种作用分开判断

哈希像文件指纹：用于比较内容；公钥像公开的验签依据；地址像账本中的收款或条件标识；签名像对指定内容作出的密码学授权。它们有关联，但既不是同一个字符串，也不承担同一种证明任务。

| 对象 | 核心作用 | 能支持什么、不能推出什么 |
| --- | --- | --- |
| 哈希 | 对按特定规则编码的数据求摘要 | 支持完整性、关联和承诺核验；不是加密，不能用摘要直接还原输入，也不证明输入内容真实 |
| 私钥/公钥 | 私有签名材料与公开验证材料 | 满足相应签名验证条件；公开公钥或地址不等于取得私钥 |
| 地址 | 标识账户或编码花费条件 | 定位目标；Bitcoin 地址可编码公钥摘要、脚本摘要或见证程序，并非统一等于“公钥hash” |
| 数字签名 | 将签名材料与指定消息绑定 | 验证某密钥对应的授权；不直接说明自然人、设备、签名时刻、主观意愿或合法来源 |

同一交易字段用不同编码、字段顺序或哈希算法处理，得到的摘要可以不同。证据文件的 SHA-256、Bitcoin 交易标识和 EVM 交易hash各有计算范围；文件摘要相同与链标识相同是两种核验。签名也有明确的覆盖范围，不能从“验签通过”扩大为“界面展示的全部内容都被签过”。

**取证考点：** 把“发现地址”“本地保存公钥”“具备签名材料”“某签名满足链规则”“某人实施操作”分别列为不同结论。多签、脚本条件、硬件签名及委托权限还可能使一个对象的控制依赖多方或多项条件。

**小案例：** 一台手机保存了收款二维码，链上出现对应地址花费。二维码支持设备与地址内容关联；链上验证支持花费条件曾被满足。二者仍不足以证明手机用户独自生成该签名；需要钱包实例、控制材料、操作痕迹或平台记录补足。

### 02.6 Merkle树与proof：包含证明不是万能真实性证明

Merkle树像一套层层汇总的目录校验：底层记录先求摘要，相邻摘要再组合求摘要，最后形成一个根。验证某条记录时，只需其自身与路径上的配对摘要，就能逐层算到根，不必拿到所有其他记录。

以四条记录 A、B、C、D 为示意，根为 `H(H(H(A), H(B)), H(H(C), H(D)))`；证明 C 的路径需要 D 的摘要和 A/B 合成后的摘要，同时保留左右位置。这里 H 和组合写法只是原理示意，真实验证必须采用目标协议的编码、哈希、奇数叶处理及索引规则。Ethereum 的交易、回执和状态采用相应树结构，不能直接套用这个二叉树示意。

**证明材料至少固定：** 目标记录原始字节或协议标识、叶子/键及位置、完整proof、目标根、区块hash、网络与验证算法。先复算包含路径，再确认根属于一个经验证且满足所需最终性条件的区块；一份自报根值的proof，只能证明它与该根自洽。

| 已验证的对象 | 可以支持 | 仍不能单独支持 |
| --- | --- | --- |
| 交易包含proof | 该交易属于指定区块的交易承诺 | 全链有效、当前仍在主分支、收款人身份、此后未再花费 |
| 回执/状态proof | 指定锚点下对应回执或状态值 | 其他高度的状态、完整历史、链外业务履行 |
| 链上登记的文件摘要 | 指定区块中登记了该摘要 | 文件内容真实、作者身份、实际创建时刻及采集过程可靠 |

普通包含proof不能证明“这个地址从未有其他交易”；“未找到”需要完整覆盖范围或适用于目标数据结构的非存在证明。Bitcoin 的SPV可核对区块头与交易包含关系，但不等同于自行执行所有交易验证。

**小案例：** 对方提供一条交易的proof和高度，却没有区块hash。即使路径复算成功，也应先确认所用根来自哪一分支，并核对其当前状态；不能直接据此宣称“资产已永久到账”。

### 02.7 交易生命周期：发起、等待、包含、执行与最终性

交易像一份提交办理的申请：写好并签字只是申请完成，送到窗口只是窗口收件，登记进账本才是进入已认可记录。账户链还要检查执行回执，才能判断申请中的动作是否实现。

| 阶段 | 应寻找的材料 | 结论边界 |
| --- | --- | --- |
| 构造/签名 | 本地请求、原始交易、签名、网络参数 | 可以已生成hash但从未广播；创建时间不等于上链时间 |
| 广播/接收 | 节点接收结果、本地或服务日志 | 单一节点接收不保证全网传播，也不保证随后打包 |
| mempool/pending | 某节点在某时点的待处理视图 | mempool是节点本地集合；可能被替换、驱逐、冲突淘汰或一直未入块 |
| 区块包含 | 区块hash、高度、交易索引及包含核验 | 已证明指定区块包含；当前分支归属另行核对，账户链交易仍可能执行失败 |
| 执行结果 | 回执状态、日志、费用和必要的调用/状态核验 | 成功回执还要判断业务动作；失败交易可能已上链并消耗费用 |
| 确认/最终性 | 当前链头、确认深度或最终性检查点 | 描述回滚风险；不能把统一的“若干次确认”套给所有网络 |

Bitcoin 常用确认数包含交易所在区块本身：交易在高度 h，当前有效链头高度 H，则常见口径为 `H - h + 1`，前提是该区块仍在该链上。确认深度增加通常降低回滚风险，但不产生数学上的绝对不可逆保证。

**重组（reorg）** 是节点改跟另一条有效分支，旧尾部区块被替换。原交易可能在新分支再次包含、回到pending，或因冲突而不再有效。更新结果时保留旧区块hash与观察时点，并记录新状态；不要把两次包含计成两次独立付款。

**小案例：** 钱包10:00显示“发送成功”，10:03节点记录pending，10:06交易进入区块且回执失败。可分别说明本地提交、等待和链上失败；不能把请求金额计入收款。若10:08发生重组，还需复核此前回执是否属于当前分支。

### 02.8 共识：规则怎样确定共同历史

共识像多人按共同程序选定有效账页：先确认账页符合规则，再决定竞争账页中跟随哪一条。参与者投票或投入资源，解决的是共同历史与状态问题；不会自动验证聊天中的真实身份或链外收据。

| 类型 | 如何参与和选定历史 | 取证要看什么 |
| --- | --- | --- |
| PoW工作量证明 | 对区块头反复求哈希以满足目标；Bitcoin 跟随累计工作量最多的有效链 | 区块有效性、累计工作量、确认深度、分支；不是“节点数量最多”或单纯“区块数最多” |
| PoS权益证明 | 按质押及协议规则提议区块、作出证明/投票，并处理违规行为 | 当前分支与已最终确定检查点、验证者证明、具体网络和协议时期 |
| 许可链 | 获授权成员参与；读、写、出块权限可以分别受限 | 成员/证书、授权与变更历史、共识阈值、组织节点及可见数据范围 |

PoS是一类机制，不能一律等同Ethereum。Ethereum 的分支选择与检查点最终性分工不同；最终性依赖符合规则的质押投票，关键门槛按质押权重计算，而不是简单数机器。出现严重共识故障时，不能继续把已过时间换算成“必定finalized”。

工作量、质押和成员授权也不使任意交易自动有效：诚实验证节点仍检查花费条件、签名与状态转移。持有大量出块资源不等于能直接推导他人私钥；改变历史、审查交易、伪造签名是不同问题。

**小案例：** 两个服务都称“已确认”，一个仅表示最新区块包含，另一个表示已落在最终确定检查点之前。报告应写出各自状态依据和区块锚点。许可链的导出表还要说明导出成员能看见哪些交易，不能假设一份表覆盖全网。

### 02.9 全节点、归档、轻客户端与索引：查询能力并不相同

把节点理解为检查账页的参与者，把归档理解为保存较完整历史版本，把索引理解为额外制作的检索目录。能确认今天的账正确，并不意味着手头仍保存每一页旧账或每个时点的余额。

| 数据提供者 | 常见能力 | 常见缺口 |
| --- | --- | --- |
| 全节点 | 按协议验证并跟随链；维护所需当前状态 | 保存范围、同步方式及附加索引不同，未必能立即回答所有历史问题 |
| Bitcoin裁剪节点 | 验证后保留所需数据及部分近期区块 | 老区块原始数据可已删除；这不表示老交易没有发生 |
| Ethereum归档节点 | 保存历史状态，便于按过去区块查余额、代码或存储 | 要核对起始范围及服务开放能力；归档不自动等于地址活动索引或任意trace均可用 |
| 轻客户端/SPV | 获取区块头或摘要，并按相应规则验证所请求证明 | 不保存完整历史；证明能力、完整性与安全假设须按实现说明 |
| 浏览器/索引服务 | 汇总地址活动、标签、代币、调用路径 | 可能延迟、截断、漏索引或重新解释；展示字段不一定是原始协议字段 |

“归档”在不同链上的对象不同：Bitcoin 常指保留全部历史区块；Ethereum 常指历史状态。历史区块、历史状态、交易索引、地址索引和执行trace应逐项问明，不能只问“是不是全节点”。

**只读核验顺序：** 保存同步高度和状态 → 核对网络、目标区块hash与时点 → 明确请求的数据种类 → 查看裁剪、索引和范围限制 → 用独立查询或原始区块交叉检查。空数组、缺失状态、权限拒绝与服务错误分开记录，均不能直接转写为金额0。

**小案例：** 当前余额能查到，但较早区块的余额查询失败。先核对历史状态保留与服务范围；若只是历史状态缺失，就保留“该服务无法回答此高度”，而非“该地址当时不存在”。节点是否能重建历史，还取决于可获得的历史数据与执行条件。

### 02.10 UTXO与账户模型：同一笔“转账”怎样落到证据

UTXO像若干张一次性使用的付款凭据：花费时消耗旧凭据，生成新的凭据。账户模型像每个对象的一组状态：交易按次序执行，余额、计数器及合约存储随之变化。二者都会产生交易图，但“从哪来、剩多少”需要不同算法。

| 问题 | UTXO模型 | 账户模型 |
| --- | --- | --- |
| 资金对象 | `前序txid + 输出索引`定位一个输出 | 指定区块下的账户余额或合约记录 |
| 一次消费 | 旧输出整体被花费，再分配到新输出 | 按交易执行修改状态；计数器/nonce约束交易次序 |
| 余额 | 指定范围内尚未花费输出的集合 | 指定锚点下余额；代币余额通常由对应合约管理 |
| 收入明细 | 选定收款脚本/地址的输出及索引 | 原生价值移动、有效代币事件及所需状态核对 |
| 易错推断 | 把所有新输出都算作对外付款，或把可能找零当成确定归属 | 把交易`value`当成所有代币金额，或只看最外层`to`判定收款人 |

**UTXO小案例：** 普通交易花费120,000 satoshi，生成70,000与49,000两个输出，差额1,000是手续费。若目标收款条件只对应70,000输出，则该笔目标收款为70,000；49,000可能是找零，也可能支付另一对象，仅凭数值不能确定。

**账户小案例：** 账户发起一次代币调用，外部交易的原生`value`为0，成功回执内却有目标代币转移。这里“没有附带原生币”不等于“没有资产移动”。相反，只有批准额度的动作没有产生该笔代币付款。余额差还可能混入其他交易、费用或特殊资产规则，不能用两张余额截图替代逐笔核对。

### 02.11 智能合约：请求、执行、状态和事件四层证据

智能合约像由网络按同样规则执行的程序：输入是请求，执行过程是程序跑过的路径，状态是执行后保存的数据，事件是程序发出的结构化记录。交易请求可以提出付款，却可能失败；一条事件也可能只是通知或授权，不能脱离合约语义解释。

| 层次 | 典型对象 | 分析问题 |
| --- | --- | --- |
| 请求 | `to`、`value`、输入数据、nonce、费用参数 | 调用了什么；参数说明意图，是否实际执行仍待核验 |
| 执行 | 回执状态、调用路径、消耗费用 | 顶层是否成功；内部调用可失败后被处理，需看具体路径 |
| 状态 | 余额、存储、代码及权限 | 指定锚点下是什么；查询当前状态不能代表事发时状态 |
| 事件/log | 发出日志的合约地址、topics、data、log索引 | 哪个合约记录了什么；同名事件与同名资产均可由其他合约仿造 |

代币是对应网络中某合约规则所管理的资产。ERC20 的 `Transfer` 与 `Approval` 分别表达转移和额度批准；名称、符号、精度属于展示或接口信息。成功回执、正确日志发出合约和资产规则应共同核对；异常或非标准合约还需检查代码/状态，不能仅见熟悉事件名就认定目标资产到账。可升级代理还需记录事发区块下实际生效的实现与权限，避免用今天的解释套到过去。

**小案例：** 浏览器列出两条同名稳定币“收入”，发出日志的合约地址不同。先分别建立资产身份，再核对整数金额、索引与成功状态。即使名称、图标和精度一致，也不能把第二个合约自动合并到第一个资产。

### 02.12 L1、L2与桥：一个动作可以分散在多个账本

L1像独立维护的主账本；rollup型L2像先处理并排序一批操作，再把相应数据或证明提交给L1的处理层。桥像两套账之间传递消息并按规则完成锁定、铸造、销毁或释放的连接程序。资产通常没有以同一个原始对象“跳过去”，而是在两边发生相关但不同的状态变化。

| 概念 | 需要理解的机制 | 最小取证记录 |
| --- | --- | --- |
| L1 | 自身共识、网络和原生状态 | 网络/创世标识、交易与区块锚点、最终性 |
| rollup型L2 | 本地执行排序，再向L1提交批次、状态承诺或证明 | L2交易/区块、L1批次或承诺、对应关系与各阶段状态 |
| optimistic / ZK rollup | 分别依赖相应争议处理或有效性证明规则 | 批次、提交/验证状态、适用协议和退出条件，不能通用一个等待时间 |
| 侧链 | 独立共识，通过桥等机制连接其他链 | 按独立网络采集；不能因兼容EVM就默认继承Ethereum最终性 |
| 桥 | 源链动作与目标链动作由消息/证明或其他机制关联 | 双方网络、合约、资产映射、消息标识、两端交易及状态 |

L2排序器显示“成功”、L1已接受提交、状态达到所需最终性以及提款可完成，是不同阶段。跨链时还要保存目标链资产身份、费用和数量变化，避免同名币、包装币与原生资产混算。

**小案例：** 源链已成功锁定，目标链尚无可验证释放或铸造。当前只能说明源链动作生效与目标动作待核验，不能直接写“目标地址已收到”。仅按相近时间和金额配对也不足以建立跨链关系，应补消息标识与协议映射。逐跳方法见[资金追踪与平台记录](/knowledge/forensic-crypto-tracing/)。

### 02.13 时间与可信边界：链上顺序不是操作人的时钟

区块时间像账页标注的登记时间，设备时间像窗口本地记录的时间，平台入账时间像平台完成记账的时间。它们描述不同事件；链上先后关系也不等于自然人的操作顺序。

Bitcoin 区块头时间由出块者填写，并受先前区块中位时间及未来偏移等协议规则约束；它不是可信机构为每笔交易签发的精确时间戳，也不要求每个相邻区块时间严格递增。Ethereum 在PoS阶段的执行载荷时间与共识slot相关，规则不同，但仍不能代表用户点击或节点首次收到请求的准确时刻。

**排序与交叉验证：** 同一已锚定分支先按高度和父子关系，再按交易索引及日志/输出索引定位。一个区块中的交易共享区块时间，不能据此判断谁先广播；不同链的高度不可直接比较。跨设备时间线应保留原值、单位、时区、时钟偏差和事件含义，并允许传播、排队、执行及平台记账延迟。

**小案例：** 聊天10:00称“已转”，区块时间10:04，平台10:09登记充值。三项可以共同支持一段候选过程；若没有请求/接收日志，不能把10:04写成用户签名时刻，也不能把10:09写成链上发生时间。

最后把证明强度拆开：**完整性**说明记录是否改变，**链有效性与最终性**说明记录在哪条被认可历史中，**业务语义**说明动作与金额，**身份归属**说明谁与对象相关。链上公开记录便于追踪，但伪名不等于不可查；抗篡改也不等于输入真实。真实身份、线下交付和控制意愿仍需要设备、应用、平台及其他材料互证。

## 03 第一轮取证顺序与最小记录

1. 写明问题、材料编号、目标对象、时间区间和输出格式。统计转入时明确是否包含零金额事件、自转和不同资产。
2. 在只读证据范围识别系统用户、钱包/浏览器/手机应用、分身实例、备份与容器。保留应用版本、扩展ID和数据库伴随文件。
3. 从聊天、配置、二维码、笔记、图片和钱包记录提取候选地址与hash。为每条线索保存路径、表/主键、消息ID或文件偏移。
4. 确认网络、资产和钱包类型；账户列表与派生范围单独记录，不用账户最大编号替代实际数量。
5. 保存链查询的原始响应、参数、节点/服务、UTC查询时间、区块范围和最终性锚点。区分请求、pending、失败、已生效及被重组记录。
6. 对平台材料分别列用户ID、订单ID、充提币ID、状态、费用、内部划转和法币支付。一个链hash可能对应平台批量提现中的多个业务记录。
7. 建立规范明细与排除表，再逐笔、逐资产核算；输出可复查的证据定位和未验证环节。

**材料固定示例：** 假设已经按采集流程得到只读镜像导出的三个文件；以下命令只识别类型和生成摘要，结果本身不证明来源或采集完整性。

```bash
mkdir -p work
file evidence/wallet.dat evidence/messages.db evidence/ledger.csv
sha256sum evidence/wallet.dat evidence/messages.db evidence/ledger.csv > work/input.sha256
```

需要分析 SQLite 时，完整采集主库和实际存在的 WAL/SHM 后在工作副本读取；LevelDB 需采集整目录的 MANIFEST、CURRENT、日志与表文件，不能只挑一个 `.ldb`。钱包文件不要导入联网钱包作为第一步，避免同步、升级、派生或广播改变观察范围。

### 03.1 证据表建议字段

| 分组 | 保存字段 |
| --- | --- |
| 采集 | 材料编号、原位置、摘要、工具版本、采集方式及时间 |
| 对象 | 网络/chain ID/创世标识、地址原值与规范值、钱包/应用实例 |
| 交易 | 完整hash、区块hash/高度、事件或输出索引、交易与执行状态 |
| 金额 | 资产标识、原始整数、decimals及来源、方向、手续费 |
| 时间 | 原始值、单位、时区、UTC值、事件含义与可能时钟偏差 |
| 关联 | 消息ID/订单ID/账户ID/数据库主键、关联依据与反例 |

区块时间、钱包发起时间、平台入账时间、照片保存时间和笔记对象创建时间分别表达。保留原值，统一时区后比较；不能因为两个时间相近就自动认定同一操作。

## 04 实战：从二维码和聊天定位交易

**场景与材料：** 手机聊天数据库、邮件附件图片、笔记数据库与指定网络的链响应。目标是确定收款候选并核对是否到账。

1. 保留邮件附件的 MIME 结构、文件摘要和聊天消息ID。二维码可以是裸地址、付款URI或网站链接，先离线解析载荷并保存原字符串，不直接访问编码后的未知网址。
2. 对OCR/二维码结果核对原图；二维码中的金额参数是请求内容，不是到账证明。URI中的网络/资产提示仍需验证。
3. 地址从多层Base64/hex等内容解出时，每层保存输入/输出摘要、长度和转换顺序；不能把自动“Magic”结果当作确定的应用行为。
4. 按网络和完整hash检查链记录；仅有地址时，从有明确范围和分页记录的历史查询寻找候选，再逐笔核验。
5. 对比资产、有效事件/输出、目标对象、整数金额、状态和区块。聊天中重复发送同一地址，只增加消息次数，不增加地址数或交易数。

**判读：** 两份设备材料保存相同地址可证明内容关联；成功回执和对应资产移动支持实际到账。地址控制者与设备用户关系需要另行验证。链记录没有查到时先检查网络、范围、分页、索引和节点能力，不能立即写“从未转账”。

## 05 实战：问题驱动的考点表

| 问法 | 先找什么 | 验证与常见失分点 |
| --- | --- | --- |
| 地址/助记词藏在哪里 | 聊天附件、图片、文档尾、笔记历史、分身应用目录、加密容器 | 保留层级与载体摘要；修复副本后验证结构，不能只抄OCR |
| 第N个词或正常词序 | 三段原词、每段顺序和指定位置、已知地址及派生条件 | 原排列与正常排列分开；checksum通过还需目标地址匹配 |
| 钱包有几个账户 | 账户实际条目、导入/硬件/观察类别、版本及实例 | 去重且定义账户口径；最高编号不等于条目数 |
| 何时发送、为何失败 | 本地请求记录、交易体、回执、区块、错误字段 | 本地发起不等于上链；失败请求不等于已上链失败 |
| 收到多少、几次 | 正确网络资产的成功移动及完整事件/输出索引 | 请求金额、Approval、重复、自转、失败与平台账分列 |
| 收币后去哪、终点是谁 | 逐跳交易图、充值归集、平台账、桥消息/目标链记录 | 观察终点不等于最终持有人；交换/桥接不只按金额时间配对 |
| 与谁有关 | 设备账户、聊天、订单、登录、控制材料及可解释时间线 | 标签与启发式用于线索；不得仅凭共同输入或平台标签定身份 |

证据题通常同时考介质恢复、应用数据库、编码/隐写和资产语义。先完成载体提取再分析币种；不必把所有文件都送入链分析工具。

## 06 结果与验证边界

回答优先给材料定位、解释字段、验证步骤、结论和限制。金额题同时交付选中明细、精确整数/小数、展示舍入、事件数、去重键及排除原因。身份题分开写“设备中发现”“能够按条件派生或验证控制”“平台账户关联”和“自然人身份判断”。

链浏览器和分析工具适合定位及可视化，截图要与原始响应、区块锚点和本地证据互证。一个标签、一段聊天、一张余额截图或一笔借条金额不能独自替代整条证据链。无法核验的本地记录明确称为登记/显示/候选值。

账本练习与实战场景使用构造材料；区块头练习另含公开创世区块固定向量，用于核对格式、哈希与包含关系。真实钱包、设备镜像和真实链请求仍需在对应材料上复核。继续阅读[Bitcoin交易与UTXO](/knowledge/forensic-crypto-bitcoin/)、[EVM与TRON交易](/knowledge/forensic-crypto-account-chains/)、[资金追踪与平台记录](/knowledge/forensic-crypto-tracing/)及[账本复核与实战](/knowledge/forensic-crypto-practice/)。
