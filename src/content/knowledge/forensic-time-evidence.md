## 01 先读字段含义，再换算

每个时间记录保留 `证据位置、表/字段、原值、纪元、单位、时区、精度、转换公式`。10/13/17/18 位只能帮助提出候选，不能单靠位数判定格式；数值也可能是 ID、单调计数或特殊值。

| 类型 | 常见纪元与单位 | 换算要点 |
| --- | --- | --- |
| Unix | 1970-01-01 UTC，秒/毫秒/微秒/纳秒 | 根据字段确认单位，不能只截取前几位 |
| Chromium/WebKit | 1601-01-01 UTC，微秒 | 转 Unix 秒：`value / 1e6 - 11644473600` |
| Windows FILETIME | 1601-01-01 UTC，100 纳秒 | 小端结构先解析整数，再换纪元；0/最大值可能是哨兵 |
| Apple Absolute Time | 2001-01-01 UTC，常见秒 | 转 Unix 秒加 `978307200`，部分字段为纳秒或小数 |
| 日志文字 | 本地时间或 UTC，可能无年/无时区 | 用启动、轮转、时区配置与独立事件校准 |

关机时间、程序创建、消息发送、服务器接收、本地入库和备份完成不是同一事件。时间一致也不自动证明是同一行为，继续核对账户、对象 ID、文件哈希、会话和路径。

## 02 整数时间的离线换算

下面保存为自己的分析辅助脚本，仅处理已确认类型的整数。Python datetime 显示到微秒；更细的余数与原值继续保存，不伪造更高精度。

```python
from datetime import datetime, timedelta, timezone

FORMATS = {
    'unix_s': (1970, 1),
    'unix_ms': (1970, 1_000),
    'unix_us': (1970, 1_000_000),
    'unix_ns': (1970, 1_000_000_000),
    'webkit_us': (1601, 1_000_000),
    'filetime': (1601, 10_000_000),
    'apple_s': (2001, 1),
    'apple_ns': (2001, 1_000_000_000),
}

def convert_timestamp(raw, kind):
    year, scale = FORMATS[kind]
    value = int(raw)
    seconds, remainder = divmod(value, scale)
    micros = remainder * 1_000_000 // scale
    result = datetime(year, 1, 1, tzinfo=timezone.utc) + timedelta(
        seconds=seconds, microseconds=micros)
    return result.isoformat()

print(convert_timestamp(1704067200000, 'unix_ms'))
print(convert_timestamp(13348540800000000, 'webkit_us'))
print(convert_timestamp(133485408000000000, 'filetime'))
print(convert_timestamp(725760000, 'apple_s'))
```

四个示例都应得到 `2024-01-01T00:00:00+00:00`。带小数的 Apple 秒应另用保留精度的解析，不能直接 int 截断；二进制 FILETIME 先确认字节序。溢出或不合理年份时回到字段定义，不能通过盲目除 10 把结果“调到合适年份”。

## 03 校准时区、漂移与启动周期

1. 从系统配置和日志确认目标时区、夏令时和是否发生时钟修改。
2. 以一条可独立确认的事件校验转换；最好再核对另一时间点，区分固定偏移与逐渐漂移。
3. 保留 UTC 统一时间与原始显示，注明采集机/分析机时区。
4. journal 等包含启动 ID/单调时间时，在对应启动周期内关联；不同启动的单调值不能直接比较。
5. 无年份日志用轮转序列、文件记录和前后事件限定年份，不默认为分析当年。

## 04 建立事件表与结论

事件表包含 `统一时间、原始时间、时间类型、设备、账户、对象、动作、记录ID、证据位置、可信范围`。时间相近但字段冲突时保留多种记录，不强行合并。复制/恢复文件会产生新的文件时间，应与内容、内部记录和历史元数据分开。

一条完整链示例：认证 → 进程启动 → 文件写入 → HTTP 请求 → 数据库变更。每一步都必须有对应记录与关联标识；缺失环节明确停在可证实的范围。

## 05 实战：关联浏览器时间、Windows 事件与服务器日志

**场景与材料：** 浏览器保存微秒整数，EVTX 中有 UTC 时间，服务器访问日志带 `+0800`。需要核对一个下载与后续程序活动，以下值仅用于演示换算。

### 05.1 先建立时间字典

| 记录 | 示例原值 | 按已确认格式解释 |
| --- | --- | --- |
| Chromium visit_time | `13348540800000000` | 1601 纪元微秒，得到 2024-01-01 00:00:00 UTC |
| Windows SystemTime | `2024-01-01T00:00:02Z` | 已含 UTC 标识，不再重复加时区 |
| 服务日志 | `01/Jan/2024:08:00:03 +0800` | 得到 2024-01-01 00:00:03 UTC |

1. 每个字段先记录格式、单位、精度和对象，不因时间接近就认定同一行为。
2. 沿本页转换脚本保存 UTC 与原值；有 100ns/ns 余数时单独保存，避免显示到微秒后丢掉排序依据。
3. 用下载 ID、路径/哈希、进程会话与请求对象建立关联，再按统一时间排序。
4. 以独立可确认事件校验时钟偏移，在前后两个时点检查固定偏移和漂移。必要时同时记录未经校准与校准后的时间及误差范围。

### 05.2 示例判读与交叉核验

三条时间相差数秒，只说明它们可能位于同一阶段。浏览器访问不等于下载成功，进程创建要确认具体文件，请求日志要确认对象与返回。若服务日志没有时区或年份，应先用配置、轮转与其他事件限定，不能默认为本地时区或分析当年。

日志时钟修改、备份后的文件 mtime 和进程单调时间都单独处理。统一时间后，按记录 ID、文件哈希、账户或会话标识核验事件关系，并逐项确认字段代表访问、创建、接收还是提交；只有时间接近时保留为候选关联。交付时间线保留连接条件、冲突记录与缺失环节，使另一分析者可以重算而无需相信排序结果。
