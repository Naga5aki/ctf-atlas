## 01 从离线账本复核开始

先练习“同一批材料能否被另一名分析者重算”，再处理多跳图、平台账户与身份关联。可下载[离线复核脚本](/practice/crypto-forensics/crypto_ledger.py)和[演示账本](/practice/crypto-forensics/movements.csv)，放到同一目录。演示地址、交易标识与代币用于构造练习，不代表已查询实时网络或真实资产价值。

```bash
mkdir -p result
sha256sum crypto_ledger.py movements.csv > ./result/input-sha256.txt
python3 crypto_ledger.py movements.csv \
  --target TARGET \
  --start 2026-01-01T00:00:00Z \
  --end 2026-01-02T00:00:00Z \
  --out result
python3 -m json.tool ./result/summary.json
```

脚本只对输入表执行离线校验、冲突隔离、去重与统计，输出 `summary.json`、逐行判读 `decisions.csv` 和问题表 `issues.csv`。查看实际汇总口径及每条排除原因；有输出、退出成功或问题表为空，都不能单独证明链上记录、标签或账户身份真实。字段约定和预期值可下载[练习说明](/practice/crypto-forensics/README.txt)。

目标是确定时间范围内，指定目标的**已确认成功链上转账**。时间范围采用 `[start,end)`：包含起点，不包含终点，适合相邻区间分别统计后拼接。平台记录保留用于对接，不直接加入链上汇总；手续费按资产单列。后续将自己的原始响应规范化为相同字段时，另留输入证据编号及字段映射，不能直接覆盖演示材料或原始检材。

## 02 认识字段与来源层次

| 字段 | 要核对的含义 | 错误处理 |
| --- | --- | --- |
| `source_ref` | 证据文件、页码、记录/行号或响应位置 | 缺失时无法从汇总回到具体材料，补清单 |
| `source_kind` | `chain` 或 `platform` | 不将平台流水伪装成公开链上交易 |
| `chain` | 具体链/网络，不能只写代币简称 | 同地址跨链分别处理 |
| `asset_id` | 原生资产标识或网络中的代币合约/明确资产键 | 同名不同资产分开；先复核合约身份 |
| `decimals` | 已核实的最小单位精度 | 保留取得依据，冲突时不擅自改到“合理金额” |
| `tx_hash`、`event_index` | 来源命名空间中的交易/事件标识 | 一笔交易可有多个事件；不能只按哈希删除 |
| `block_hash` | 记录当时纳入的区块，平台材料可不适用 | 区块不同或重组历史单列核查 |
| `event_type` | 本练习支持 `transfer`、`fee`、`approval` | 其他类型先单独分析，不擅自映射成转账；授权不当作到账 |
| `from`、`to` | 明确方向的链上地址或平台对象 | 不用备注名代替真实对象 |
| `status` | 已确认成功、失败、待确认等规范化状态 | 同时保留原始状态与映射规则 |
| `raw_amount` | 整数最小单位 | 不先转二进制浮点数再相加 |
| `timestamp_utc` | 带明确时区的 ISO8601，统一到 UTC 比较 | 无时区值拒绝统计；原值、原时区和精度在映射表中保留 |

平台表中的 `tx_hash` 栏若承载内部记录 ID，必须通过来源类型和映射说明区分；它并非链上哈希。对于多个未成交订单、多次成交和内部转账，另建业务表，不强行塞成一条链上转账。

数量示例：`raw_amount=30000000`、`decimals=6` 表示 30 个资产单位，`raw_amount=1` 表示 0.000001 个资产单位。显示时可以增加分隔符，计算时保留整数。相同简称的仿冒 Token 即使也有 6 位精度，仍是另一个资产。

## 03 去重、冲突和统计要分三步

### 03.1 先保全重复，再判断是否相同事件

演示脚本用以下组合标识重复候选：

```text
(source_kind, chain, asset_id, tx_hash, event_index)
```

保存同键行的全部 `source_ref`。两个分页响应包含同一事件时，只保留一条参与汇总记录，证据位置可有多处。相同哈希的两个不同事件索引仍是两个事件；平台来源和链上来源即使表示同一笔业务，也先分别保留，以对接表关联。

规范化前核对标识的语义：BTC 输出应有输出索引；代币日志应有日志位置；费用使用独立事件类别与索引约定。标签、币种简称或表格行序号不能代替稳定事件标识。重复候选的资产身份本身仍需人工复核，不能用错误的 `asset_id` 把冲突藏成两个资产组。

### 03.2 同键矛盾不能采用“最后一行覆盖”

同键的数量、精度、地址、状态、区块或时间不一致时，保留原始行，整组进入待核查清单，暂不加入确定汇总。数量 100 与 200 不能相加，也不能选一个顺眼的；待确认与成功两条记录需要有版本、查询时点及区块材料解释，不能自动挑成功状态。

平台记账、链上回执与钱包缓存之间也可能有差异。先检查字段是不是同一事件、缓存是否陈旧、平台是不是只显示申请量、是否发生重试/替换或链重组，再决定是否产生新的规范化版本。保留旧表、修订依据和新结果。

### 03.3 去重后再按问题过滤

确定转账汇总应满足来源为 `chain`、状态为 `confirmed_success`、事件类型为 `transfer`、目标及 UTC 时间范围匹配，并且事件未被隔离。失败、待确认、授权、平台行、自转、其他目标、范围外事件及有冲突的组均需要解释其去向。失败执行可能仍支付原生币费用；检查已验证的 `fee` 行，不能因付款失败而认定费用为零，也不能将费用混入转账额。

零数量转账如果本身是有效事件，应按题目或报告约定决定是否计入事件次数；它对资金数量的贡献为 0。次数、非零付款次数、独立发送者数和收款地址数分别计算，不能用消息条数或 CSV 行数替代。

脚本的 `net_flow_raw` 按每个资产组计算 `incoming_raw - outgoing_raw - fee_raw`，费用组可能显示负净流。已上链失败的转账金额被排除，真实回执已确认扣取的 `fee` 则可在 `confirmed_failed` 状态下计入费用。费用须先由回执正确规范化，不能把失败请求量改成费用行。本练习共有22行，预期重复1行、冲突4行、无效整数1行，`issues.csv` 共5条、`review_status=needs_review`；这些异常需要人工复核。

## 04 必须先声明金额口径

| 指标 | 可复核定义 | 不能直接替代 |
| --- | --- | --- |
| 地址流入量 | 指定范围内有效转账到达目标的数量，按链和资产分组 | 受害损失、余额或销售收入 |
| 地址流出量 | 指定范围内有效转账离开目标的数量 | 包含未成交订单的申请总额 |
| 转账净变动 | 同资产已确认流入减已确认流出，自转按约定处理 | 全部余额变化，因费用/铸造/销毁等可能未覆盖 |
| 费用 | 已核对付款方、费用资产和交易结果的实际费用 | Token 转出数量或订单服务费 |
| 平台账户变动 | 期初 + 记账增加 − 记账减少 = 期末，按资产复核 | 平台热钱包全部余额 |
| 控制集对外净流量 | 经证据支持的控制范围跨边界增减，排除内部转移 | 全图边权相加 |
| 损失或业务数额 | 按明确事实范围与材料支持计算的特定经济口径 | 所有币种数量相加或多跳累计 |

资产兑换同时改变两种资产余额。需要法币价值时注明计价时间、价格取得方式、币种和是否为实际成交价；不能默认稳定币永远严格等于一单位法币，也不能把 BTC、TRX、USDT 的单位数量直接相加。分析工具的资金关联模型与法定数额认定也分别说明。

## 05 实战一：重复页、状态冲突和同名资产

**材料与位置：** `movements.csv` 是规范化演示表；每行的 `source_ref` 指回构造的响应页或平台记录。下载脚本及账本后按本页命令复核指定目标和时间范围。本场景不需要联网、钱包密钥或真实平台账户。

练习先完成四张清单：全部输入行、重复组、有冲突的组、最终参与汇总的事件。再检查数量与次数能否同时复算。

| 构造情况 | 应做的判读 | 核查位置 |
| --- | --- | --- |
| `demo-evm-1` 中 `token:K` 精度为 6 | 原始整数相加后除以 10^6；成功流入 30、流出 4、转账净变动 26 | `asset_id`、`decimals`、`raw_amount`、`from/to` |
| 第二页重复第一页面的事件 | 去重一次，同时保留两处证据定位 | `source_ref` 与完整事件键 |
| 零数量成功事件 | 流入共 3 个事件，其中正值 2 个；零事件贡献数量 0 | `event_type`、状态、数量 |
| 失败或待确认转账 | 排除确定汇总，保留状态和原因 | `status`、关联回执或状态材料 |
| Approval 与自转 | 授权不计入付款；自转不产生目标对外净流量 | `event_type` 与 `from/to` |
| 同名仿冒 Token 和另一条链的 K | 700 个假同名资产与其他链 7.5 个 K 分组；同一资产的精度矛盾另隔离 | `chain`、`asset_id`、`decimals` |
| 同键数量 100/200 或状态互相矛盾 | 整组隔离，不任选、不求和 | `issues.csv` 与全部对应输入行 |
| `native:ETH` 费用、平台内部记录 | 费用 0.001600000000000000 ETH 单列且含失败执行费用；平台 100 独立保留，不加入链上汇总 | 来源类型、费用类型及资产键 |

**验证顺序：** 从 `summary.json` 看分组和统计范围，再逐条读取 `issues.csv`，最后回到输入行人工复算 `token:K` 的流入 30、流出 4 与净变动 26。事件次数包括零数量记录，同时另列正值事件次数。费用组只有费用行，不能当成 ETH 收付数量；同一费用也不能从回执和规范化费用行重复计入。两组冲突分别是金额矛盾和状态矛盾，各自整组隔离。检查非目标资产和平台行能否各自解释，而不是把它们静默丢弃。没有证据位置、字段映射或区块响应时，结论只限于这份输入表的内部一致性。

变式练习可在副本中增加一条完全重复行、把一个事件数量改一单位、改变目标/时间、增加同哈希不同事件索引或改成平台来源。预测哪些统计应该改变，再运行比较；不要直接修改唯一的原始演示文件。

## 06 实战二：设备钱包、平台账本与法币对接

以下是可自行构造的材料设计，用于练习跨来源印证；这些文件不是上面的下载附件，数量与时间也不是实时网络查询结果。

```text
evidence/
  device/wallet-state.json        钱包账户对象、账户类型及本地交易状态
  device/app-transactions.json    发送请求、失败原因、交易哈希与本地时间
  communication/chat.csv         收款指令、订单号及付款确认上下文
  platform/deposits.csv           UID 与充值事件对接
  platform/ledger.csv             账内增减、费用、期初与期末
  platform/orders.csv             委托、修改、取消及订单状态
  platform/fills.csv              实际成交、成交 ID、交易对与费用
  platform/p2p.csv                对价、托管、放币和支付参考号
  payment/bank.csv                法币到账与账户信息
  chain/transfers.json            成功转账、输出/日志索引和回执
```

构造一个账户的资金变化：向平台充值 1000 个演示资产 U；账内转出 200 U；实际成交支付 400 U 换得 0.2 E，另付成交费 0.4 U；P2P 卖出 200 U；提现到账 199 U，平台扣提现费 0.6 U。另加一个未成交后取消的 100 U 委托和钱包中一条发送失败记录。

| 账户 U 资产方向 | 数量 | 依据 |
| --- | --- | --- |
| 期初 | 0 U | 平台期初账本 |
| 充值增加 | +1000 U | 充值记录、链上事件及 UID 映射 |
| 平台内部划转 | −200 U | 账本记录 ID 和对手 UID，不要求链上哈希 |
| 已成交兑换及费用 | −400 U、−0.4 U | `fill_id`、结算记录及费用资产 |
| 已完成 P2P 放币 | −200 U | 订单与账本记录；对价另查银行流水 |
| 提现及费用 | −199 U、−0.6 U | 提现 ID、实际链上到账及费用 |
| 期末 | 0 U | 1000 − 200 − 400 − 0.4 − 200 − 199 − 0.6 |

E 的余额为另一资产账本中的 +0.2 E。未成交的 100 U 委托不再扣一次，钱包失败请求不计作成功付款。上述对账只解释这个账户在已覆盖业务中的记账变化；没有 E 的后续记录时，不把它说成已提现或丢失。

为 P2P 订单另设实际到账 1410 个演示法币单位，使用相同支付参考号关联银行流水。这只是构造对价，不是市场报价。加入一张重复付款截图、一个标记“已付款”但无实收的取消订单，要求区分付款声明、银行到账、平台放币和交易完成。

### 06.1 从钱包材料回答账户与交易问题

1. 解析 `wallet-state.json` 中真实账户对象；记录地址、网络、类型、导入/派生/观察标识及材料位置。账户标签最大编号不等于数量，删除残留和只读观察账户单列。
2. 从 `app-transactions.json` 找目标地址、时间原值、发送状态、错误、哈希及重试关联。网络发送前失败与上链后执行失败分开；有失败记录不表示金额已经离开。
3. 在 `chain/transfers.json` 对照哈希、具体事件及执行结果，不把钱包里“提交”或截图中的余额当成链上确认。
4. 用钱包状态、受控恢复材料的离线派生结果、平台 UID 与交易记录印证地址关联。发现某恢复材料能派生地址，不直接推出当时机主亲自点击了发送。
5. 聊天中的收款指令按地址集合去重；分别统计使用过的地址、成功收款次数、来源人数和实际数量。重复发送同一地址的消息不增加地址数。

若材料中有欠条、合同或口头描述的币数量，单列为债务/业务声明；实际已收付数量仍需交易或账本材料。图片记录助记词的文件哈希用于识别该文件，不能代替其生成过程、完整性和派生参数核验。

### 06.2 对接链、平台与银行

充值用 `网络 + 资产 + 事件哈希/索引 + 地址 + memo/tag + 数量` 接到 UID；账内划转用 `ledger_id` 与源/目标 UID；成交用 `order_id → fill_id → 结算`；P2P 用 `订单 → 放币/托管记录 → 银行支付参考号`。每种关联写清条件与材料位置。

对提现，明确平台扣减量、费用和接收地址实际到账量；批量链上付款只取对应输出/事件。对银行对价，核对币种、户名、账户、数额、支付状态和时间，不用一条同额流水自动拼接所有订单。

**复核限制：** 按表成功对账只证明该范围内记录之间的数量关系。平台认证账户可能借用，设备可能共享，登录 IP 可能来自代理或共享出口；现实操作者仍需要独立事件与身份材料。材料未覆盖的历史、后续交易和平台内部环节均列为未知。

## 07 延伸练习：桥、混币与多跳终点

在场景二之后，可增加 `chain/bridge-source.json`、`chain/bridge-destination.json` 和 `bridge/mapping.csv`。设定本练习桥按每1 A对应发行1 B的数量规则映射，源端支付10 A，其中扣桥费0.1 A，剩余9.9 A对应目标端发行9.9 B；链上gas另列。记录协议消息 ID、接收人、数量映射及费用来源。若实际协议采用兑换率，须取得当笔报价与结算记录，不能直接将两种资产数量相减解释为费用。核对两端成功状态后再建立关联，也不能把10 A与9.9 B相加成为19.9个“损失单位”。

另放两笔同额候选目标交易，其中只有一笔具有匹配消息 ID，让分析者比较“时间金额近似”与“协议标识对接”的证据强度。加入仅存入成功、目标释放失败或待完成的桥记录，检查是否被错误画成已到账。

当路线进入混币或隐私交易，明确展示已确认入口、候选出口和信息缺口；没有可验证对接就停止。CoinJoin 候选交易不能直接用全部输入归为一名控制者。资金多跳后的余额停留地址只是材料截止点的观察，不能凭余额、交易次数或大额特征就判定它是长期最终存储地址。

## 08 报告字段与交付格式

| 报告部分 | 必需字段 |
| --- | --- |
| 任务与范围 | 要回答的问题、授权对象、设备/账户/链/资产、起止时间、采集方式、可见范围 |
| 输入清单 | 证据编号、实际位置、文件大小、SHA-256、采集人/时间、工具及版本、导出范围和缺失项 |
| 解析与规范化 | 原表/字段、原值、单位、精度、时间语义、状态映射、资产标识依据、转换规则 |
| 数据审查 | 总行数、重复组、冲突组、隔离原因、参与事件与排除项、分页/截止区块 |
| 资金与账户 | 分资产数量、次数口径、手续费、余额公式、平台/链对接条件、控制范围证据 |
| 路径与归因 | 每条图边的记录 ID、桥/兑换对应、标签版本、推断假设、反例和替代解释 |
| 时间线 | 原值、原时区、UTC、字段类型、时钟校准、误差和事件关联标识 |
| 结论与限制 | 已直接观察、多材料印证、仅推断、待核实项、无法回答的问题及补充材料需求 |

交付可包含 `evidence-list.csv`、`field-map.csv`、`movements.csv`、`issues.csv`、`account-link.csv`、`timeline.csv`、`fund-flow.svg` 和报告正文。不要只提交一张带标签的箭头图或一个最终金额。

结论句应包括对象、时段、动作、数量、证据位置和限制，例如：“在所列链上记录截止点内，目标地址收到某资产的已确认转账合计 X，按事件索引去重并排除列出的冲突组；平台账户及现实操作者尚无对应材料。”数额、币种和标识应由实际结果填写，不能把示例中的占位内容当成已核实事实。

## 09 最后复核的常见考点

| 问题 | 应提交的证据与口径 |
| --- | --- |
| 钱包有多少账户 | 账户对象与类型、去重键、删除/观察账户处理，不用编号猜数 |
| 向哪一地址收款或付款 | 完整地址、网络、设备记录位置、成功交易或明确指令 |
| 某次发送何时发生 | 本地发起、链上区块、平台到账分开，注明时区与时间精度 |
| 为什么发送失败 | 错误记录及对应阶段；不能用后续成功交易覆盖失败历史 |
| 一个地址收款多少次/多少币 | 按事件去重与状态过滤；次数和数量分别计算 |
| 收到后流向哪里 | 逐跳事件、兑换/桥/平台对接及材料截止点，未知出口明确停止 |
| 哪些地址关联同一恢复材料 | 离线派生参数、实际地址比对及账户类型，不扩张为全部历史 |
| 欠款数额和到账数额是否相同 | 文书声明与实际交易各自引用证据，不能相互替代 |
| 谁掌管或操作资金 | 控制权限、平台/设备/会话的独立印证，标签和 IP 只提供限定线索 |

授权采集、原始封存、完整性校验和保管交接都记录到证据清单。普通练习只在材料副本和离线环境中解析、计算与验证；具体案件的程序适用应按调查权限、辖区及正式规定核对，不能将一次练习流程当成所有场景的法定操作要求。

## 10 区块头与 Merkle 证明的离线实战

### 10.1 从真实格式理解哈希、字节序与包含关系

下载[区块头核对脚本](/practice/crypto-forensics/blockchain_header.py)、[公开创世区块向量](/practice/crypto-forensics/genesis-proof.json)、[三叶教学分支](/practice/crypto-forensics/constructed-merkle-proof.json)和[字段及边界说明](/practice/crypto-forensics/blockchain-header-README.txt)。脚本只使用 Python 标准库，读取本地 JSON，不访问节点、不创建钱包、不签名、不广播。

第一个向量使用 Bitcoin 主网创世区块的公开固定数据，第二个是构造的三叶 Merkle 树，**不是实际挖出的区块，也不包含真实付款交易**。两者用途不同：前者检查真实格式与已知哈希，后者演示树分支、末节点复制，以及包含关系不能替代工作量或活跃链验证。

```bash
mkdir -p result
sha256sum blockchain_header.py genesis-proof.json constructed-merkle-proof.json \
  > result/header-input-sha256.txt
python3 blockchain_header.py genesis-proof.json > result/genesis-check.json
python3 -m json.tool result/genesis-check.json
# 教学分支的包含关系匹配，但其区块头未完成对应工作量；预期退出码为 1。
python3 blockchain_header.py constructed-merkle-proof.json > result/branch-check.json
python3 -m json.tool result/branch-check.json
```

输出另存到 `result/`，不要用重定向覆盖输入。退出码 `0` 表示所给区块头满足它自己声明的 target，且所给分支重算结果匹配头中的根；`1` 表示上述局部条件至少一项不匹配，仍保留计算结果；`2` 表示输入格式错误。任何退出码都不能单独表述为“已完整验证一个 Bitcoin 区块”。

### 10.2 按字段解释核对结果

Bitcoin 区块头固定为 80 字节：4 字节版本、32 字节父哈希、32 字节 Merkle 根、4 字节时间、4 字节 `nBits`、4 字节 nonce。整数以小端表示；哈希在序列化和内部拼接中的字节顺序，与浏览器展示的十六进制顺序需要转换。

| 核对项 | 本练习的操作 | 成功结果能支持什么 |
| --- | --- | --- |
| 区块头哈希 | 对完整 80 字节执行两次 SHA-256，并转换为显示顺序 | 得到这份区块头的标识；公开向量与固定创世区块标识相符 |
| 父哈希 | 读字节 4–35，保留完整 32 字节 | 说明声明连接到哪一个父区块；脚本不检索或验证该父区块 |
| 时间 | 读 4 字节 Unix 秒，再显示 UTC | 解释该头声明的时间；不代表钱包点击时间或节点首次看见时间 |
| `nBits` 与 PoW | 将紧凑编码还原为目标，再比较区块头哈希的数值 | 只说明满足此头声明的目标；未核验该高度实际应采用的难度、网络上限或累计工作量 |
| Merkle 分支 | 将目标 TXID 和每层兄弟哈希转为内部字节序，按左右位置拼接再双哈希 | 所给叶哈希、路径和树宽度假设可以重算到所给头中的根 |
| 最终状态 | 查看 `active_chain_checked`、`confirmations` 等边界字段 | 本工具没有连接节点，活跃链检查为 false、确认数为 null；不能自行补成“已确认” |

三叶树中，最后的叶 C 没有同层伙伴，需要先与自己配对；再与 A/B 形成的父节点配对。脚本列出 `merkle_steps`，可核对第一步的 `duplicated_last_node` 与第二步的左右位置。兄弟哈希列表按“离叶最近的一层 → 根”排列，不能倒置。把显示形式的 TXID 当 ASCII 文本拼接、漏掉反向转换或只执行一次 SHA-256，都会算出不同的根。

输入中的 `target_txid` 是待核对的叶哈希，脚本**没有取得或解析原始交易字节来重新计算该 TXID**；也没有执行输入脚本、检查签名、判断重复花费或验证 witness commitment。`transaction_count` 和索引来自输入材料，80 字节头没有单独提交交易笔数；脚本只能检查这些声明与分支长度/末节点规则相容，不能独立证明完整区块的叶数及无歧义结构。

### 10.3 用反例检验结论是否越界

1. 在副本中修改 nonce 的一个字节：交易叶和 Merkle 根可以保持不变，但区块哈希改变。说明“包含关系未变”不等于“区块标识未变”。
2. 将所给 TXID 的显示顺序直接反转：头的公开标识仍可匹配，而包含关系失败。先查字节序，不能立即声称交易原件被篡改。
3. 检查三叶教学输入：可以匹配 Merkle 根，却不能将它叫作实际链上区块。即使另一个自造头满足宽松 target，也没有证明它满足目标网络当时的难度规则。
4. 换成真实调查材料时，补齐原始交易、完整区块或可靠分支、可信区块头锚点、连续头链/节点状态及查询时点；交易有效性和活跃链最终结果还需进一步验证。

**交付时的准确表达：** 哪些字节产生了哪个哈希，所给分支是否匹配哪一个区块头，采用了什么字节序和算法，还有哪些全节点或历史状态检查没有做。不要把 SHA-256 文件摘要、交易 TXID、区块哈希和 Merkle 根都称为同一个“证据哈希”。

## 11 用区块链原理解释实战问题

| 观察到的问题 | 先用哪个原理解释 | 需要核对的材料 | 可接受的结论边界 |
| --- | --- | --- | --- |
| 两个浏览器在同一高度显示不同区块 | 分支、重组和查询时点 | 网络、区块哈希、父哈希、节点高度/同步状态、采集时间 | 先区分分支与滞后；不能只按高度覆盖旧记录 |
| 钱包记录了一笔后来查不到的交易 | 本地构建、广播、交易池和确认是不同阶段 | 原始交易、请求/响应、首次观察、替换或冲突记录、最终区块 | 区分未广播、未收录、被替换、查询缺口；“查不到”不等于不存在 |
| 支付代币，但顶层 `value` 为零 | 合约调用与代币状态转换 | 指定网络的回执、正确合约的事件、ABI、精度及必要状态 | 原生币为零不否定代币移动；伪造同名事件也不自动证明真实资产到账 |
| 出现 Approval 或 Permit，但没有即时转账 | 授权改变与资产移动分离 | 结构化消息/调用、spender、额度、期限、nonce、后续转账 | 可先描述权限变化或签名请求；未生效的本地消息不算链上支出 |
| L2 钱包显示成功，但 L1 提现未完成 | 执行、批次提交、证明/挑战和消息执行分阶段 | L2交易、批次/输出标识、L1提交与桥事件、目标端实际执行 | L2执行成功不替代L1结算或到账确认；不套用一个固定等待时间 |
| 多个输入合成一笔付款 | UTXO消费关系与资金分配假设 | 每个前序输出、具体新输出、手续费、协作交易及钱包记录 | 先报告交易事实；同一控制者与来源比例另列推断条件 |
| 合约发生多次递归调用或大额借还 | 调用树、状态与权限条件 | 历史代码、调用结果、状态变化、余额及实际移动 | 递归或闪电贷是行为线索；不能单凭它们认定漏洞已被利用 |

对合约安全事件，先固定事件发生时的网络、区块、实现代码和 ABI，再检查成功调用路径、权限/存储状态及实际资产变化。静态扫描发现风险是候选，模拟结果依赖选定状态；两者都不能代替历史交易中的利用证据。普通回执没有完整调用树或状态差分时，应说明需要的补充材料，而不是猜出缺失路径。
