手里是一份 Linux 服务器检材：可能是离线镜像、已挂载目录、运行现场采集或隔离仿真副本。镜像能挂上，还不表示系统身份、根分区、服务清单和账户活动已经对上。

**分清分析环境 → 读系统身份并对上根分区 → 列服务清单并分清安装与运行 → 沿家目录追账户活动与启动配置 → 离线不够再做隔离仿真 → 把结果填进可复查的表。**

写入性操作只在已经做好快照的副本上做；原始材料保持只读。

<span id="01-分析目标与操作顺序"></span>

## 01 先分清环境，再按四个问题推进

系统、根分区、装过的服务和留下的操作记录都还没分开。现在就开机或在分析机上装工具，回答不了这四个问题：**这是什么系统？根分区是哪一个？装过哪些服务？留下了哪些操作和运行记录？**

**读系统信息 → 对上分区 → 列服务和账户痕迹 → 离线不够再做隔离仿真。**

**1. 读系统信息。** 找发行版、主机名和时区，后面据此选择包管理记录、服务配置和日志路径。查到一项就记录路径和结果。

**2. 对上分区。** 把挂载配置里的标识与实际文件系统比对，避免分析错盘。

**3. 列服务清单。** 分别看软件包、配置、数据目录和日志，不把“安装过”当成“正在运行”。

**4. 查账户做过什么。** 从命令历史、SSH 配置、定时任务和自启动项找线索，再回到服务文件与日志验证。

**5. 有必要再仿真。** 离线材料不足以观察启动行为时，再建立隔离副本，单独记录仿真产生的变化。

四个问题各自记下读取路径和已经看到的结果；还没读到的项先空着，不靠开机补。发行版、分区标识、服务清单和账户痕迹的原始输出连同路径一起保存。

### 01.1 先区分三种分析环境

命令已经能跑，但还不知道终端看的是离线镜像、已采集的运行现场，还是隔离仿真副本。看错对象，进程和软件包都会记成分析机自己的。

**先对上现在的环境 → 把路径指到检材 → 软链跳出根目录就停。**

**1. 先看自己现在处于哪种环境。** 避免命令查错对象：

| 环境 | 可以观察什么 | 结论范围 |
| --- | --- | --- |
| 离线镜像或已挂载目录 | 系统配置、包管理记录、持久化日志、用户文件 | 镜像保存时留下的状态与历史痕迹 |
| 已采集的运行现场 | 当前进程、监听端口、内核与网络连接 | 采集时刻的运行状态 |
| 隔离仿真副本 | 启动后实际加载的服务、界面与程序行为 | 仿真条件下的表现，需与离线痕迹交叉核对 |

**2. 假设检材已只读挂载到 `/mnt/evidence`，先设置路径并确认目录。** 后续在同一终端操作。路径和输出只是示例，使用时替换成实际检材：

```bash
EVIDENCE_ROOT=/mnt/evidence
ls -ld "$EVIDENCE_ROOT/etc" "$EVIDENCE_ROOT/var" "$EVIDENCE_ROOT/home"
```

**3. 命令能运行，不代表查的是检材。** `uname -a`、`ss -tlnp`、`dpkg -l` 默认看当前机器。在分析机上执行，显示的就是分析机，而不是挂载的镜像。

**4. 离线分析，把读取路径指向检材。** 要查当前进程或监听，先确认终端进入了目标会话。读配置前也要检查软链目标，别让路径跳出检材根目录。目录对不上或软链指向检材根以外时，先改读取位置，不要把分析机文件当成镜像内容。

这一步结束时，应当能写清：这次操作属于三种环境中的哪一种，`$EVIDENCE_ROOT` 下的 `etc`、`var`、`home` 是否在。终端还在分析机上时，`uname -a`、`ss -tlnp`、`dpkg -l` 的结果不能写成镜像状态；软链目标必须仍在检材根内。环境说明、`EVIDENCE_ROOT` 和目录检查输出一起保存。

<span id="02-系统身份与文件系统对应"></span>

## 02 读出系统身份，把根分区对上挂载配置

发行版、主机名和根分区还没对上，后面的包记录和日志路径会选错。这一节先把系统身份和根文件系统对应起来。

**读发行版、主机名和时区 → 再把挂载标识对到实际分区。**

### 02.1 实战：识别发行版与版本

要确定系统是什么版本，镜像还没启动，`os-release` 在不在、是不是软链也还没看。先找文件，不用先启动镜像。

**看文件和软链 → 只读检材根里的那一份 → 按字段记下名称和版本。**

**1. 看文件在不在，是否是软链。**

```bash
ls -ld "$EVIDENCE_ROOT/etc/os-release" "$EVIDENCE_ROOT/usr/lib/os-release"
readlink "$EVIDENCE_ROOT/etc/os-release"
```

按看到的结果选择读取位置：

1. `/etc/os-release` 是普通文件：优先读它。
2. 它是软链：先看指向哪里，再从检材根目录内读取。目标若是 `../usr/lib/os-release` 或 `/usr/lib/os-release`，实际读取的都应是 `$EVIDENCE_ROOT/usr/lib/os-release`，不是分析机上的同名文件。
3. `/etc/os-release` 不存在：再找 `/usr/lib/os-release`。两份独立文件不一致时，保存差异，以 `/etc/os-release` 为优先依据，不拼接字段。

**2. 提取名称和版本。** 下例已经确认软链指向 `/usr/lib/os-release`；若 `/etc/os-release` 是普通文件，就把路径换成它：

```bash
grep -nE '^(ID|PRETTY_NAME|VERSION_ID|VERSION_CODENAME)=' \
  "$EVIDENCE_ROOT/usr/lib/os-release"
```

例如看到下面这些字段（命令实际输出还会带行号）：

```text
ID=debian
PRETTY_NAME="Debian GNU/Linux 13 (trixie)"
VERSION_ID="13"
VERSION_CODENAME=trixie
```

逐项看，不自行补版本号：

<details>
<summary>展开 os-release 字段逐项判读</summary>

| 字段 | 含义 | 示例判读 |
| --- | --- | --- |
| `ID` | 发行版标识 | `debian` 表示 Debian 系统 |
| `PRETTY_NAME` | 便于阅读的完整名称 | 保留 `Debian GNU/Linux 13 (trixie)` 的完整字符串 |
| `VERSION_ID` | 发行版版本标识 | 记录为 `13`，不自行补成 `13.0` |
| `VERSION_CODENAME` | 版本代号 | `trixie`，用于辅助核对 |

</details>

**3. 结果这样记。** 检材 `/usr/lib/os-release` 中系统名称为 Debian GNU/Linux 13 (trixie)，版本字段为 13，`/etc/os-release` 指向该文件。把读取位置和软链关系一并保存，别人才能照路径复查。字段对不上或两份文件不一致时，保存差异，不把字段拼成一份新的版本说明。

**4. 如果题目问的是内核版本，分开记。** 发行版版本和内核版本不是一回事。镜像 `/boot` 中的文件名只能提供已安装内核的线索；运行现场的 `uname -a` 或 `/proc/version` 才描述那个会话的运行内核。读取字段就用文本方式，不执行检材中的配置文件。分析机上的 `uname -a` 不是镜像里的历史内核。

版本字段按原文记录，`VERSION_ID` 不自行补成 `13.0`；字段对不上或两份文件不一致时保存差异，不拼成一份新的版本说明。内核版本不在这里回答，另看 `/boot` 或目标会话的 `uname -a`、`/proc/version`。`ls -ld`、`readlink` 和带行号的 `grep` 输出连同软链关系一起保存。

### 02.2 主机名与时区

发行版已经有了，主机名和日志时区还可能对不上。接着读主机名、解析记录和时区链接。

**读 hostname 和 hosts → 看 localtime 指向哪 → 再查 timezone 和各日志自己的时区。**

**1. 读这三个位置。**

```bash
cat "$EVIDENCE_ROOT/etc/hostname"
cat "$EVIDENCE_ROOT/etc/hosts"
readlink "$EVIDENCE_ROOT/etc/localtime"
```

**2. 主机名看哪里。** 对照 `/etc/hostname` 和 `/etc/hosts`。不一致就保留差异，解析别名不能单独证明主机身份。

**3. 时区怎么看。** `localtime` 若指向 `zoneinfo/Asia/Shanghai`，记下这个配置线索。若它是普通二进制文件，`readlink` 会没有目标输出；继续比对检材时区数据，不把空输出写成“没有时区”。

**4. 还要查什么。** 部分系统保存在 `/etc/timezone`。整理日志时再分别核对：有的日志使用 UTC，有的应用自己指定时区，不一定跟系统相同。对不上时，保留系统配置和这条日志各自的时区，先不要按屏幕上的时分秒排序。

主机名差异保留，不合并；时区写成配置线索，`readlink` 空输出不写成“没有时区”。日志时区可能和系统不同，整理时间线前逐条核对。三个命令的原始输出和后来核对到的日志时区一起保存。

### 02.3 实战：核对根文件系统 UUID

已经找出疑似根分区，还不知道它是否与系统挂载配置对应。这里的 `root-partition.dd` 是**单个文件系统分区镜像**，不是整块磁盘。

**读 fstab 的有效行 → 探测分区元数据 → UUID 相同再查挂载点和标识类型。**

**1. 把两边 UUID 对上。** 例如 `fstab` 的根目录项写着 `UUID=3231e52f-5e15-44c4-b224-e29cb4201c0e`，分区探测输出相同 `UUID` 和 `TYPE=btrfs`。这能说明配置中的文件系统标识与该分区元数据一致。

```bash
# 读取挂载表中未注释的有效条目
grep -nEv '^[[:space:]]*(#|$)' "$EVIDENCE_ROOT/etc/fstab"

# 直接探测已定位分区的文件系统元数据
blkid -p -o export ./root-partition.dd
```

`blkid -p` 直接探测指定对象，不依赖普通缓存查询；`-o export` 以 `键=值` 输出。保存原始 UUID 和文件系统类型，再逐项比较。

**2. 没有结果或报错，就先检查输入。** 同时保存错误提示和退出状态，区分“没有可识别结果”“读文件失败”“多个冲突签名”。先查分区边界和文件可读性，再按提示处理，不为得到一个结果去擦除签名。

**3. UUID 相同也要再查四处。**

1. 挂载点是不是根目录 `/`？`/home` 和数据目录可能是另外的文件系统。
2. 两边是不是同一种标识？`UUID` 是文件系统标识，`PARTUUID` 是分区标识，不能混着比。
3. 是 Btrfs 时，可再用超级块的 `fsid` 复核。相同 UUID 只是显示不同，可统一大小写、去掉连字符后比较，但要保留原始值。
4. 对不上时，检查选错分区、克隆副本、过期配置或多设备文件系统。即使 UUID 相同，也不能凭这一项认定唯一主机，或认定历史挂载成功。

**4. 完全探测不到文件系统时，回查边界。** 回查分区起点、长度和提取对象，别把整盘直接当根文件系统。确认边界后再探测；具体定位操作保留在[镜像与文件系统取证](/knowledge/fic-case-02/)。

原始 UUID、文件系统类型、错误提示和退出状态留在一起。标识相同仍要核对挂载点是不是 `/`、比的是 `UUID` 还是 `PARTUUID`；相同 UUID 不单独证明唯一主机或历史挂载成功。探测失败时先回查分区边界。`fstab` 有效行、`blkid -p -o export` 输出，以及 Btrfs 时的 `fsid` 一起保存。

<span id="03-服务清单与状态判定"></span>

## 03 列出服务清单，分清安装、初始化与运行

包名已经出现，还不能写成服务器当时正在跑这个服务。安装、初始化、历史运行和当前运行要分开记。

**先看装了什么 → 再看配置和数据 → 最后才用日志或现场进程判断是否跑过。**

### 03.1 分开判断“安装、初始化、运行”

找到一个数据库包名，还不能直接写“服务器运行了这个数据库”。按照证据往下确认，缺哪一层就停在哪一层。

**对安装记录 → 对配置和数据目录 → 再对历史日志或当前进程。**

**1. 按四层往下看，不跳层。** 四层依次是：安装记录、配置与初始化、历史运行、当前运行。每层支持的结论和仍需核对的项：

<details>
<summary>展开四层判断表</summary>

| 判断层次 | 优先证据 | 可以支持的结论 | 仍需核对 |
| --- | --- | --- | --- |
| 安装记录 | 软件包数据库、可执行文件 | 某个组件被登记安装或存在于检材中 | 是否只是客户端、是否为残留文件 |
| 配置与初始化 | 服务配置、数据库目录、实际数据文件 | 存在部署配置或初始化数据 | 是否复制而来、路径是否仍有效 |
| 历史运行 | 启停日志、应用日志、相关访问记录 | 某时刻有对应运行活动 | 时间范围、日志完整性与时区 |
| 当前运行 | 目标会话的进程、监听端口 | 观察时刻有进程或监听 | 进程身份、实际服务、宿主机或容器归属 |

</details>

**2. 端口也只能先当线索。** 默认端口可以修改。把端口、进程、包记录、配置和数据目录放在一起判断；缺哪一项就记哪一项，不假设所有材料都应该齐全。只有端口、没有进程和配置时，不写成这个服务正在运行。

每个组件停在安装、配置、历史运行、当前运行中的哪一层，要写得出来；表里“仍需核对”列空着的项就是缺口。端口单独出现只是线索。四层各自的证据路径和明确写上的缺口一起保存。

### 03.2 离线查询安装记录

Debian 系镜像里的包数据库还没按检材路径查过。命令若在分析机执行又不指定目录，查到的是分析机的软件包。

**指定检材的 dpkg 数据库 → 看包名、Status 和版本 → 没有命中再查路径和别的安装方式。**

**1. 先查检材自己的 dpkg 数据库。**

```bash
dpkg-query --admindir="$EVIDENCE_ROOT/var/lib/dpkg" \
  --show --showformat='${binary:Package}\t${Status}\t${Version}\n' \
  '*postgresql*' '*mysql*' '*mariadb*'
```

**2. 先看输出的三列：包名、`Status`、版本。** `install ok installed` 表示这份数据库登记该包已安装。配置残留、未完整安装和没有命中，要分开记录。

**3. 两个参数别漏。** `--admindir` 指定检材的包数据库，`--showformat` 决定显示哪些字段。包名通配符的单引号也要保留，让 dpkg-query 匹配包名，不让 Shell 提前展开当前目录文件。

**4. 没查到时，先分清原因。** 先分清是没有匹配包，还是数据库路径不存在/不可读；再查手工部署、容器内安装和包数据库缺失的可能。保存完整输出、错误和退出状态，不运行检材中的安装或维护脚本来“补全”记录。

**5. RHEL 系换它自己的包数据库。** RHEL 系运行现场可用 `rpm -qa` 清点软件包；离线镜像要读取目标自己的包数据库，别把分析机的结果填进去。

`install ok installed`、配置残留、未完整安装和没有命中分开记录。分析机上的 `dpkg-query` 或 `rpm -qa` 不能填进离线结果；完整输出、错误和退出状态一起保存。

### 03.3 实战：识别数据库服务与客户端

同时看到了 PostgreSQL、MySQL/TiDB 文件和 `mariadb-client`，还分不清哪些是服务端、哪些只是连接工具。目录不存在也要先记下来。

**先看候选目录 → 再定位 PostgreSQL 配置 → 按证据组合决定下一份要核对的材料。**

**1. 先查看候选目录，再定位 PostgreSQL 配置。** 目录不存在也要如实记录：

```bash
# 查看候选配置与数据目录；不存在的目录需如实记录
ls -ld "$EVIDENCE_ROOT/etc/postgresql" \
  "$EVIDENCE_ROOT/var/lib/postgresql" \
  "$EVIDENCE_ROOT/var/lib/mysql" \
  "$EVIDENCE_ROOT/db/tidb"

# 在已发现的 PostgreSQL 配置目录内定位关键配置
find "$EVIDENCE_ROOT/etc/postgresql" -type f \
  \( -name postgresql.conf -o -name pg_hba.conf \) -print
```

**2. 按看到的证据继续查。**

| 观察到的证据组合 | 判读与下一步 |
| --- | --- |
| PostgreSQL 服务端包、`/var/lib/postgresql/17/main`、`postgresql.conf` 与 `pg_hba.conf` | 支持存在 PostgreSQL 服务端部署痕迹；继续核对配置中的实际数据目录、端口及启停日志 |
| MySQL 服务端组件与 `/var/lib/mysql` | 核对数据库文件、配置和日志，区分安装组件与曾经运行的实例 |
| TiDB 程序或配置与 `/db/tidb` 等现场路径 | 核对启动参数、数据布局和日志；路径及常见端口 `4000` 只能辅助定位 |
| 仅有 `mariadb-client` | 支持存在客户端组件；不足以确认 MariaDB 服务端。继续检查服务端程序、配置、数据与日志 |

**3. 同一种数据库也要分实例记录。** 每个实例分别记根文件系统、配置路径和数据目录。宿主机和容器可能各有一套，不能拿宿主机包记录配上容器数据文件，就当成同一个实例。目录不存在时如实记录，不把别的实例的文件补进来。

**4. 发现容器时先确认身份和卷。** 先确认容器身份和卷映射，再回到数据库清单；具体识别步骤见 [Docker 与 LXC 的现场识别](/knowledge/docker-evidence-01/)。

**5. 结果可以这样写。** 发现 PostgreSQL 服务端安装记录、配置和数据目录，支持存在部署痕迹；采集时是否运行，还缺运行记录。仅发现 MariaDB 客户端记录，暂不认定部署了 MariaDB 服务端。

每个实例的根文件系统、配置路径和数据目录写在同一条；常见端口 `4000` 只辅助定位。只有 `mariadb-client` 时不认定 MariaDB 服务端；采集时是否运行还缺启停或进程记录。`ls -ld` 和 `find` 的输出（包括不存在的目录）一起保存。

### 03.4 运行现场的补充核对

已经进入**身份确认过的目标会话或隔离仿真副本**，还没看这一刻的内核、监听和服务状态。离线镜像不跑这组命令。

**先看监听 → 再读服务状态 → 仿真后才出现的端口单独标明。**

**1. 在目标会话里看内核、监听和服务。**

```bash
uname -a
ss -tlnp
systemctl status postgresql --no-pager
```

**2. 先看端口。** `ss -tlnp` 中，`-t/-l/-n/-p` 分别选择 TCP、监听套接字、数字地址/端口和可见进程。记录地址、端口、关联进程、执行环境和观察时间。`ss` 没显示进程字段时，先查权限，不写成“没有归属进程”。配置里的 listen 地址还没出现在这次输出里时，不写成已经能连上。

**3. 再看服务。** `systemctl status` 重点读 Loaded/Active 和下面的日志。单元不存在、没运行、启动失败都可能返回非零；分别记录原因，别把非零一律当“命令没执行”。

**4. 总服务单元不等于每个实例。** systemd 的总服务单元不一定代表每个数据库实例，还要对照实例配置和日志。仿真开机后才出现的监听，注明“仿真时观察”，不拿来证明采集前也在运行。分析机上的 `ss` 和 `systemctl` 不是镜像里的历史状态。

地址、端口、进程、执行环境和观察时间写在同一条。`ss` 没有进程字段时先记权限缺口；非零退出写明是单元不存在、没运行还是启动失败。仿真后才出现的监听标明“仿真时观察”。三条命令的原始输出和观察时间一起保存。

<span id="04-账户活动与启动链路"></span>

## 04 沿家目录追账户活动和启动配置

家目录里的命令和启动配置已经能看见，还不能当成已经执行成功。先从账户找到文件，再去对运行记录。

**从 passwd 找家目录 → 读历史、SSH、定时任务和配置 → 再找有没有真正跑过。**

### 04.1 证据位置与解释边界

检材里各账户的家目录还没从 `/etc/passwd` 读出来。别只看 `/root`，也别把某账户目录里的所有文件直接归到同一个自然人名下。

**读出家目录 → 按位置看命令、SSH、定时任务和应用配置 → 文件在，再去找使用记录。**

**1. 先从检材 `/etc/passwd` 读出各账户的家目录，再逐个检查。**

| 位置 | 关注内容 | 判读边界 |
| --- | --- | --- |
| 用户目录中的 `.bash_history`、`.zsh_history` | 服务安装、存储配置、容器创建和隧道启动命令 | 记录了命令文本，不保证成功执行；时间信息可能缺失或被改写 |
| 用户 SSH 目录及授权材料 | 证据定位与解释统一见[SSH Key取证](/knowledge/forensic-server-services/#146-ssh-key取证) | 本页只沿家目录定位，不另复制信任/授权/实际使用的定义 |
| `/etc/crontab`、用户定时任务、systemd 单元 | 执行账户、计划时间、命令、工作目录和依赖 | 配置存在不等于任务实际运行 |
| 用户目录中的 `.config/` | 应用参数、日志位置和其他配置线索 | 路径依版本、账户和安装方式变化 |

**2. 看见命令、授权文件或启动配置后，下一步都是找对应的使用和运行记录。** 文件存在是一条线索，不自动证明它已经生效或执行成功。SSH 的信任、授权和实际使用不在本页另写一套定义，沿家目录定位后按表中的入口核对。

每个账户的家目录，以及历史、SSH、定时任务、`.config/` 里实际存在的文件，按位置记下内容和判读边界。只有命令文本或启动配置、没有使用和运行记录时，不写成已经执行成功。`/etc/passwd` 里的家目录和这些位置的文件清单一起保存。

### 04.2 实战：从历史命令追踪服务搭建

命令历史和定时任务里还没把数据库、容器、存储和隧道关键词提出来。下面以 root 的历史文件演示，其他账户按上一节找到的家目录分别检查。

**先检索历史和 crontab → 按行找留下的文件 → 再按配置、数据和带时间的日志复核。**

**1. 在命令历史和定时任务里找关键词。**

```bash
grep -nE 'zpool|lxc-create|ngrok|postgres|mysql|tidb' \
  "$EVIDENCE_ROOT/root/.bash_history"

grep -nE 'ngrok|postgres|mysql|tidb' "$EVIDENCE_ROOT/etc/crontab"
```

**2. 这些是待分析的记录，不是让你执行的操作。** 假设发现以下历史片段：

```text
zpool create -f db /data/zfs
lxc-create -n app-db
ngrok http 80
```

按行提取线索，再找它们留下的文件：

1. 第一行涉及存储池 `db` 和 `/data/zfs`，去查对应存储配置与元数据。
2. 第二行涉及名为 `app-db` 的容器，去查容器配置和数据位置。
3. 第三行记录了把本地 80 端口用于隧道的启动意图，再查启动配置和运行日志。

**3. 每一条都按“配置 → 数据目录/元数据 → 带时间的运行日志”复核。** 多项证据能对应，才能说明部署过程。历史文件中的排列只提供顺序线索，不一定有准确执行时间；目录修改时间也不能直接写成安装时间或建库时间。对不上时，停在“历史里有这条命令文本”。

每一行历史命令都按配置、数据或元数据、运行日志复核过再下结论；目录 mtime 不写成安装时间。只有命令文本、没有带时间的运行日志时，停在“历史里有这条命令文本”。带行号的 `grep` 输出和随后核对到的文件路径一起保存。

### 04.3 实战：核对 ngrok 的历史启动方式

默认配置里找不到域名或启动参数，还不知道历史隧道是怎么被拉起来的。接着查定时任务、systemd 单元及相关脚本，别靠重新启动来猜历史配置。

**静态检索启动配置 → 保存命中行和参数 → 再用日志核对历史地址。**

**1. 静态检查启动配置；只检索，不启动隧道。**

```bash
# 静态检查启动配置；只检索，不启动隧道
grep -rInE 'ngrok|ExecStart=' \
  "$EVIDENCE_ROOT/etc/crontab" \
  "$EVIDENCE_ROOT/etc/cron.d" \
  "$EVIDENCE_ROOT/etc/systemd/system"
```

这条递归检索不跟随目录中的软链。命令所列起始路径先检查软链；遇到服务单元软链，也在检材根目录内找到目标后单独读取，防止查到分析机文件。

**2. 找到命中行，连上下文一起保存。** 记下执行账户、程序路径、完整参数和配置文件路径。没有命中时，记下搜过的三个起始路径，不写成从未配置过。

**3. 看到 `ngrok http 80`，先记为启动意图。** 它拟把本地 80 端口作为后端；如果带 `--config`，先读指定配置。

**4. 再查这个账户的默认配置。** 例如 `.config/ngrok/`，但默认位置随版本变化，目录缺失不代表没有使用。

**5. 最后查实际运行记录。** 用应用日志和访问记录核对历史公网地址、启停时间及访问活动。只有启动配置时，就写“发现启动配置，历史公网地址尚未确认”。重新运行 ngrok 可能得到新端点并产生网络活动，所以新得到的地址不能代替历史日志里的地址。

命中行和上下文必须来自检材根内的文件，不是分析机上的同名单元。只有启动配置时，历史公网地址尚未确认；新跑出来的端点不代替历史日志。`grep` 命中、软链目标、指定的 `--config`，以及应用日志里的地址和时间一起保存。

<span id="05-仿真观察与结果复核"></span>

## 05 离线不够时做隔离仿真，并回离线材料核对

离线材料已经能回答系统和部署问题，就先出结果。需要看启动过程或桌面界面时，才做隔离仿真；副本上的新日志不能混进采集前状态。

**先留退路和快照 → 再配置并开机观察 → 回到离线材料核对。**

**1. 先留退路。** 保存镜像标识、哈希、磁盘布局和关键配置，为仿真副本建立快照。

**2. 再配置虚拟机。** 【仅在副本/仿真/授权环境执行】选择匹配的虚拟硬件、启动方式和磁盘控制器。黑屏就查启动日志和兼容性，不把黑屏当正常启动。

**3. 开机后先记现象。** 记录服务加载、报错和界面变化。端口、内核与新增日志标为“仿真后观察”，不混进采集前状态。

**4. 优先读现成文件。** 查看相关账户的桌面、文档、应用配置和日志。发现文本或联系方式，保存完整路径、上下文、时间属性，再判断与目标的关系。

**5. 需要远程连接再查 SSH。** 先分清进入宿主机还是容器，再查服务、监听和认证。安装或启动会改变副本，实验操作和新增日志单独记录。改配置、启停服务之前仍停在副本上，并保留改前哈希。

**6. 回到离线材料验证。** 用原配置、数据和历史日志核对观察结果。副本启动失败就继续离线分析，不能据此认定原系统没有该服务。

仿真里实际加载的服务、界面或报错，要和离线配置、数据、历史日志对应上；端口、内核和新增日志标明“仿真后观察”，实验操作和仿真产生的变化单独列出。黑屏或副本启动失败时，继续查启动日志和离线材料，不写成原系统没有该服务。镜像标识、哈希、磁盘布局、关键配置和仿真快照，以及开机后的现象记录一起保存。

远程要进的是宿主机还是容器、用的是哪个 Linux 账户，都还没分开。sshd 是否在听、用什么认证、日志里有没有这次登录，也不能靠网站目录来回答。

## 06 把结果填进可复查的表

前面各节的路径和字段还散着，缺一项或互相冲突时也不知道写在哪。最后把本页结果填进下表。

**按表填路径和字段 → 冲突与缺失单独写 → 让别人能沿路径复查。**

**1. 每项都保留路径、关键字段和适用时间。** 冲突与缺失单独写明：

| 项目 | 建议记录内容 |
| --- | --- |
| 系统身份 | 发行版、版本字段、主机名、时区、读取位置与软链关系 |
| 存储对应 | 挂载点、文件系统类型、UUID/PARTUUID 类型、对应分区与差异 |
| 服务清单 | 实例归属、软件包状态、配置、数据目录、历史运行日志与当前状态 |
| 账户活动 | 账户与家目录、历史命令、SSH 线索、定时任务及启动链路 |
| 复核与限制 | 已确认事实、待验证推断、证据缺失、时区差异与仿真产生的变化 |

**2. 写结论时按四步。** **写对象和路径 → 摘关键记录 → 列相互印证的材料 → 写结论和未解决问题。** 不只写“已识别系统”或“发现服务”，要让读者沿记录的路径重新查到依据。对不上的项留在“复核与限制”，不把仿真里新出现的状态写成采集前就有。

表中每一项都要填上路径、字段和时间；冲突、缺失、时区差异和仿真产生的变化写进“复核与限制”。结论旁边要有对象、路径、关键记录和另一份能印证的材料。这张结果表和表中引用的原始输出一起保存。
