## 1. 先筛出同一方向的候选流量

TTL 是 IPv4 头字段，普通业务流量也有 TTL；不能导出整个 PCAP 的 `ip.ttl` 后直接逐字节拼接。先记录抓包时间范围和主要通信对，再按**同一发送端、接收端、协议或会话、时间窗口**收窄。请求与响应来自不同设备，应分开；重传和干扰包也要单独标注。

```bash
sha256sum capture.pcap
tshark -r capture.pcap -Y ip -T fields \
  -e frame.number -e frame.time_epoch -e ip.src -e ip.dst -e ip.ttl > ttl.tsv
```

`ttl.tsv` 保留帧号，是为了在发现候选文本时能回到每个包复核。先观察一个方向内的 TTL 值分布和发送间隔：值是否有刻意变化，包的顺序是否稳定，是否存在明显缺包。只见到 `64` 或 `128` 等常见值，不足以断定有隐藏信息。

## 2. 再验证编码假设

对筛出的同一序列，分别检验**直接字节值、固定基准差值、奇偶或低位比特**等假设。每种假设都要声明取包规则、比特顺序与分组长度，并展示完整输出；不能只挑出能组成单词的几帧。

抓到的是**采集点观察到的 TTL**，不一定是发送端设置值。若跨越路由器，同一路径通常会产生相同的跳数差；只有得到路径或独立基准证据后，才能尝试校正。路径变化、负载均衡或不同来源流量混用，会使简单的“TTL = ASCII”失效。候选结果应能在原始帧序列中逐项复现，并与后续文件、密钥或明文校验相互印证。

## 3. 基础概念考点

**TTL全称：** Time To Live（生存时间），位于IPv4头部8位字段，取值范围0~255。

**正常转发规则：** 数据包每经过一台三层路由设备，TTL 通常递减，转发要求至少减 1；转发途中 TTL 降至 0 时，路由器丢弃该包。

**隐写核心原理：** 发送端可自定义初始 TTL 以承载信息；分析时需按会话提取观察值并考虑传输路径，再还原候选数据。

## 4. 两种主流编码模式

**模式1：** TTL数值直接映射ASCII

在未跨路由或已校正跳数时，可尝试将每个包的 TTL 值映射为 ASCII；需回到报文核对。

例：TTL=102→ASCII f，TTL=108→l，拼接得到明文。

**模式2：** TTL二进制提取

TTL是8bit，可以直接使用TTL的比特位承载二进制数据，再转为字符。

## 5. 流量包实战解题步骤

### 1. 流量筛选

**Wireshark过滤器：** ip，只保留IPv4数据包，排除ARP、IPv6等无关干扰包。

### 2. 批量提取TTL值

**方法：** 使用tshark命令批量导出所有ip.ttl字段

```bash
tshark -r capture.pcap -T fields -e ip.ttl
```

得到一串TTL数字序列。

### 3. 编码还原

**方案A：** 只有在采集位置和跳数已明确时，才把校正后的 TTL 当作 ASCII 候选字节；

**方案B：** 若按低位或奇偶承载，应先说明取几位、比特顺序与分组长度，再转换为文本。

## 6. 识别特征与陷阱

### 1. 流量特征

大量独立 ICMP/UDP 小包且载荷很短可以作为候选特征；需对比正常业务流量，确认变化确实发生在 IPv4 TTL 字段。

### 2. 重大陷阱

跨路由采集时，观察到的 TTL 会被逐跳减少；若同一路径的跳数稳定且有独立基准，仍可能还原发送值。不能预设所有题目都在同网段。

### 3. 区分常见 TTL 与异常波动

部分 Windows、Linux 环境常见初始 TTL 为 128、64，但配置与路径会改变观察值；异常波动只是线索，还需按会话验证。

## 7. 常见出题形式

给出 PCAP 后，先筛选同一方向的候选序列，再验证 TTL 编码与完整输出；

干扰包混杂正常通信流量，需要过滤出用于隐写的一组数据包；

**进阶变种：** 利用TTL奇偶代表二进制0/1，组合成信息。
