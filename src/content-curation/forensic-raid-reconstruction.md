## 01 适用场景与分析路线

获得 NAS、工作站或存储服务器的多块磁盘镜像时，单独打开一块盘可能只能看到零散分区、文件头或无法解析的文件系统。RAID 重组的任务是还原成员之间的数据映射，得到可解释的逻辑地址空间，再分析其中的分区、卷和文件。设备来自服务器，并不改变这一步属于磁盘与存储结构分析的性质。

先回答三个问题：**拿到的是独立成员，还是同一镜像的分段；目标数据位于哪一层；成员是否来自同一个阵列、同一采集状态。** 一个 NAS 可以只有单盘，也可以同时包含系统镜像阵列、数据阵列、热备盘和多个卷。不能把镜像文件数直接当成阵列成员数，也不能看到三个文件就套 RAID5。

按下面的顺序推进，每一步保留证据位置和判断依据：

1. 登记成员、分段、容量、哈希、扇区大小和缺失情况。
2. 检查分区与阵列元数据，确定成员范围、编号和有效状态。
3. 确认级别、盘序、数据起点、块大小、校验布局及有效长度。
4. 在工具中建立虚拟阵列；缺少元数据时，用文件系统规律缩小参数候选。
5. 验证校验关系、文件系统结构和跨条带文件，保存重组配置。
6. 按需要导出逻辑镜像、提取文件或在独立副本上仿真。

本页的偏移、文件名、记录编号和示例布局均为说明方法的构造参数。没有取得并复跑具体成员镜像时，不能把示例结果视为实际检材的重组结论。常规分区、文件系统与镜像识别见 [取证镜像与文件系统识别](/knowledge/disk-evidence/)。

## 02 必须分清的存储概念

### 02.1 物理盘、成员、逻辑盘和热备

| 对象 | 含义 | 分析时要记录什么 |
| --- | --- | --- |
| 物理盘 / PD | 实际存储介质；镜像可以覆盖整盘，也可以只覆盖某一区域 | 介质标识、采集范围、大小、逻辑扇区大小、镜像及哈希 |
| 阵列成员 | 参加某个阵列的数据区域，可能是整盘，也可能是盘上的一个分区 | 阵列标识、成员编号、数据起点、有效长度、状态 |
| 虚拟盘 / VD、逻辑盘 / LD | 控制器或软件向上层提供的逻辑地址空间；名称依实现而异 | 与成员阵列的对应关系、容量、分区与文件系统 |
| 热备盘 / HS | 准备接替故障成员的盘；是否已接替要看状态与历史 | spare、replacement、active 等角色及同步进度 |
| 卷、卷组、存储池 | RAID 上下还可能存在 LVM、动态磁盘或文件系统存储池 | 层次、UUID、设备映射、分配关系和缺失对象 |

热备不能未经核对就加入有效盘序。曾经被替换的旧盘可能留下较早数据，替换盘也可能尚未同步完成。RAID 卷数、LVM 卷组数、逻辑卷数和挂载点数回答的是不同问题。

### 02.2 常见级别与缺盘边界

下表设成员容量相同，`N` 是有效成员数，`S` 是每个成员实际可用于阵列的数据长度；容量公式不含控制器保留区、文件系统开销和后续卷划分。

| 类型 | 组织方式 | 常规容量与成员要求 | 恢复边界 |
| --- | --- | --- | --- |
| RAID0 | 数据分块后在成员间交替存放 | `N × S`，通常至少 2 盘 | 无冗余；缺盘时不能保证完整恢复，局部文件是否可取要检查块映射 |
| RAID1 | 保存镜像副本 | 通常约 `S`，至少 2 盘 | 一份完整且处于相符状态的镜像可提供数据；仍需核对副本新旧与坏块 |
| RAID5 | 数据条带化，分布式单校验 | `(N - 1) × S`，至少 3 盘 | 理论上可恢复一个缺失成员；剩余成员完整、状态一致和布局正确是前提 |
| RAID6 | 数据条带化，两组独立校验 | `(N - 2) × S`，至少 4 盘 | 理论上容忍两个成员失效；第二组校验不能当作另一份普通 XOR 校验 |
| RAID10 | 镜像组再条带化 | 常规成对镜像为 `N / 2 × S`，通常至少 4 盘 | 容错取决于故障分布；同一镜像组全部失效时，对应数据仍会丢失 |
| RAID50 / RAID60 | 多个 RAID5 / RAID6 子组再条带化 | 先算每个子组，再汇总 | 先恢复子组关系；不能只按全体缺盘总数判断可恢复性 |
| 线性拼接 / SPAN | 按顺序连接成员地址空间 | 通常为成员有效长度之和 | 不使用 RAID0 的交替块规则；缺失位置影响后续地址和文件 |

JBOD 有时表示独立盘集合，有时工具用它指线性拼接，必须看实际映射。RAID 也不能替代备份：误删除、覆盖、恶意修改和某些一致性故障会影响整个逻辑卷。

### 02.3 实现方式决定先找什么

**硬件 RAID** 由控制器处理映射，操作系统通常看到一个或多个逻辑盘。成员中的控制器头尾、磁盘编号和配置记录是重要线索。**操作系统软件 RAID** 由系统实现，如 Linux MD，其成员常是分区，通常能从超级块获得 UUID、级别和角色。**固件或驱动辅助 RAID** 依赖固件、驱动及厂商元数据，不能简单等同于独立 RAID 控制器。

ZFS RAID-Z、Btrfs 多设备配置和 Storage Spaces 有各自的元数据与映射规则。发现这些结构后应转入对应解析路径，不能全部当作固定条带 RAID5。软硬实现也不决定“必定自动识别”或“必定没有性能提升”。

## 03 重组参数、单位与地址坐标

### 03.1 建立完整参数表

| 参数 | 需要确认的内容 | 常见误判 |
| --- | --- | --- |
| 级别与拓扑 | RAID0 / 5 / 6、镜像组、嵌套子组、拼接关系 | 只凭容量或成员数选择级别 |
| 成员数与角色 | 预期盘数、现有盘数、缺失槽位、有效成员和热备 | 把所有文件或所有分区塞进同一阵列 |
| 盘序 | 成员角色对应的稳定编号与逻辑排列 | 把文件名、添加顺序或 Windows 磁盘编号当作盘序 |
| 成员数据起点 | 每个成员从哪里开始参与块映射 | 把分区起点、超级块位置和数据起点混用 |
| 块大小 `C` | 单个成员每次参与交替的一块，常称 chunk / strip / block size | 与扇区大小、文件系统簇大小或整组宽度混淆 |
| 校验布局 | 校验旋转方向、数据排列、起始相位、延迟或厂商布局 | 只写“左同步”而不保存实际排列 |
| 扇区与有效长度 | 各输入对象的扇区单位、有效数据范围和尾部保留区 | 把所有“扇区”固定按 512 字节换算 |
| 同步与历史状态 | 事件计数、故障、替换、重建、reshape 及采集时点 | 把能读到元数据的旧盘当作最新有效盘 |

### 03.2 单盘块大小与整组条带宽度

设 4 盘 RAID5 的单盘块大小为 `C = 64 KiB`。同一成员地址上的一组包含 3 个数据块和 1 个校验块，因此：

- 单盘块大小：`65,536` 字节。
- 一组成员块合计：`N × C = 262,144` 字节，包括校验。
- 对外连续逻辑数据宽度：`(N - 1) × C = 196,608` 字节。
- 若某工具该字段以 512 字节扇区计，单盘块大小应填 `128` 扇区；若按 4096 字节计，则为 `16` 扇区。

界面中的 stripe、strip、chunk 和“条带”可能使用不同口径。每次记录**字段原名、原值、单位和换算后的字节数**。WinHex / X-Ways 的重组字段可以按扇区表示单盘 strip；其他工具可能用 KiB。不要跨工具照抄数字。

### 03.3 三层偏移必须分别记录

1. **成员所在区域的起点**：例如成员分区在整盘镜像的第 `P` 个扇区开始。
2. **成员数据起点**：例如成员分区内又预留 `D` 个元数据扇区。若 `P` 的单位为 `B` 字节、`D` 的单位为 `U` 字节，则整盘镜像内的数据起点为 `P × B + D × U`。
3. **重组逻辑空间内的分区起点**：阵列重组后，逻辑盘内的 NTFS 分区还可能从另一位置开始。它不应再次填入成员数据偏移。

Linux MD 元数据中的一些 sector 字段以 512 字节为单位，即使底层逻辑扇区是 4096 字节也不能直接改用 4096 相乘；以字段定义和工具显示单位为准。超级块位置也不等于 Data Offset。

**构造换算：** 整盘成员分区从 `2048 × 512` 开始，分区内数据起点又是 `2048 × 512`，则整盘输入对象上的成员数据起点为 `2,097,152` 字节。若已把成员分区单独提取，工具中的起点只剩分区内的 `1,048,576` 字节。若输入的是已重组的逻辑盘，应重新按逻辑盘的分区表确定文件系统起点。

## 04 首轮取证：成员清点与元数据读取

### 04.1 先识别镜像容器与采集范围

保留原件，在新工作目录中进行分析。以下命令以 Kali/Linux 上已经准备好的 RAW 工作副本为例，文件名只表示成员标签，不代表盘序：

```bash
mkdir -p ./output/raid
sha256sum ./work/member-a.img ./work/member-b.img ./work/member-c.img
stat -c '%n %s bytes' ./work/member-a.img ./work/member-b.img ./work/member-c.img
file ./work/member-a.img ./work/member-b.img ./work/member-c.img
mmls -b 512 ./work/member-a.img
```

`-b 512` 仅适用于已确认的 512 字节逻辑扇区；遇到 4096 字节扇区应按实际值调整。没有分区表的成员分区镜像不一定能被 `mmls` 识别，不能因此判定镜像损坏。

E01、E02、E03 可能是同一成员镜像的连续分段，应由支持该格式的工具按一条逻辑镜像载入。不能把三个分段作为三块 RAID 成员，也不能把 E01 容器的文件偏移当作介质偏移。工具不支持该容器时，先验证分段完整性，再导出 RAW 或提供只读逻辑视图；保留转换记录、容器哈希和解码后逻辑数据的校验记录。

### 04.2 Linux MD 优先检查成员超级块

在专门的 Linux 分析环境中使用只读 loop，先记录返回的真实设备名。环境应避免自动组装与自动挂载；下列命令只用于准备和检查工作副本，不执行阵列创建：

```bash
loop_a=$(sudo losetup --find --show --read-only --partscan ./work/member-a.img)
loop_b=$(sudo losetup --find --show --read-only --partscan ./work/member-b.img)
loop_c=$(sudo losetup --find --show --read-only --partscan ./work/member-c.img)
printf '%s\n' "$loop_a" "$loop_b" "$loop_c"
sudo mdadm --examine "$loop_a" "$loop_b" "$loop_c"
cat /proc/mdstat
```

若 MD 位于成员分区内，整盘 `--examine` 没有结果是合理情况。按已核对的分区起点和长度创建区域映射，再检查它。例如下面只演示一个分区区域，数值应替换为实际记录：

```bash
# 示例：成员区域起点 2048 扇区，长度 409600 扇区，每扇区 512 字节
member_region=$(sudo losetup --find --show --read-only \
  --offset 1048576 --sizelimit 209715200 ./work/member-a.img)
sudo mdadm --examine "$member_region"
```

`--examine` 读取成员上的元数据；`--detail` 描述已激活的阵列，二者不能替代。检查结果至少整理为下面的表，再决定是否进入虚拟重组或只读组装：

| 字段 | 判读方式 |
| --- | --- |
| Array UUID、名称、元数据版本 | UUID 是分组的重要依据；名称相似或容量相同不足以认定属于同一阵列 |
| Raid Level、Raid Devices | 记录级别和预期有效成员数，与现有角色逐一对应 |
| Device Role / RaidDevice | 核对成员槽位；编号不能按导入顺序自行重排 |
| Chunk Size、Layout | 记录单盘块大小、实际布局和单位 |
| Data Offset、Super Offset、有效长度 | 分别保存位置，说明相对于整盘还是成员分区 |
| Events、Update Time、State | 比较状态、采集时点和事件差异；较大计数也不能单独保证整盘内容最新且一致 |
| replacement、recovery、reshape 信息 | 判断是否处于替换、未完成同步或布局变更中；不能套一个静态布局覆盖全盘 |

元数据缺失可能来自采集范围不全、头尾损坏、工具不支持或另一种存储体系，不自动证明是硬件 RAID。`mdadm --create`、`--zero-superblock`、强制更新成员信息以及控制器初始化会改变数据或元数据，不能用来试探重组参数。

分析结束后，确认映射未被挂载或用于阵列，再仅释放本次命令创建且记录过的 loop。若已经建立阵列，应先按本次分析记录解除依赖，不能停止其他阵列或全局清理 loop：

```bash
sudo losetup --detach "$member_region"
sudo losetup --detach "$loop_a" "$loop_b" "$loop_c"
```

只执行了整盘检查而未创建 `member_region` 时，跳过对应释放命令。loop 的只读状态也不能代替文件系统层面避免日志回放的设置。

## 05 工具重组：相同参数，不同入口

### 05.1 UFS Explorer

1. 打开每个完整成员镜像，确认容器分段被合并为正确的逻辑对象。
2. 查看每盘的分区、元数据和自动识别出的阵列。系统分区与数据分区分别核对，不把所有可见对象混成一个阵列。
3. 打开阵列配置，记录级别、成员来源与顺序、起点、块大小、布局、缺失槽位和阵列长度。
4. 自动识别失败时，在 RAID 配置中选取正确的成员区域，按参数表建立虚拟 RAID；缺失成员用对应槽位表示。
5. 打开虚拟阵列内的目标文件系统，检查目录、元数据和跨多组条带文件；保存配置后再导出。

自动识别可以提供候选配置，仍须验证。导出时区分整块逻辑盘、某一分区和单个文件；RAW、E01 等格式以当前版本及版本权限支持为准，文件扩展名不能说明导出范围。

### 05.2 R-Studio

1. 用 Open Image 导入成员，在虚拟块 RAID 功能中添加对应对象。
2. 优先使用已记录的参数；需要检测时再使用 Auto Detect，并保存它生成的候选及扫描范围。
3. 在成员列表和参数页核对 RAID 级别、成员顺序、Block size、Offset 与 Blocks order。每个成员起点不同，应分别设置。
4. 应用配置后扫描**虚拟阵列**，检查识别出的分区与文件系统。
5. 导出代表文件并完整检查；参数未固定前保留候选配置，避免反复全盘扫描却没有记录变化。

识别出分区表而文件不能正常解析时，优先回查盘序、块大小、起点和布局。虚拟 RAID 是数据映射，不等于已经向成员写回了阵列配置。

### 05.3 取证大师

先将完整成员作为镜像加入案例，检查自动识别的设备、分区和阵列对象。若只出现未识别对象，先扫描磁盘结构，再在相应成员或阵列对象上使用 RAID 重组功能。记录自动计算出的盘序、块大小、循环方式与状态，然后继续扫描逻辑卷。

本地摘要中的卷、卷组或逻辑盘数量要按其实际定义判读；不能把某个摘要字段直接等同于物理盘数。结构扫描仍不能识别时，回到输入范围和参数分析，不反复依赖同一个按钮。

### 05.4 WinHex / X-Ways

先打开并解释各成员镜像；软件 RAID 的输入可能需要选到成员分区。进入 RAID 重组功能，按正确顺序选择对象，设置单盘 strip、每成员 header / footer 或有效区域，以及实际校验排列。保存为案例证据对象时，同时保存配置与成员对应表。

X-Ways 常见 RAID5 名称可作如下对照，但应继续核对其排列预览：

| 常用布局名 | 常见工具表示 |
| --- | --- |
| 左不对称 / 左异步 | Backward Parity / Left Asynchronous |
| 左对称 / 左同步 | Backward Dynamic Parity / Left Synchronous |
| 右不对称 / 右异步 | Forward Parity / Right Asynchronous |
| 右对称 / 右同步 | Forward Dynamic Parity / Right Synchronous |

Delayed、HP/Compaq、5EE 和某些厂商排列有额外规则，不能只看 forward / backward 就套四种基本布局。版本、许可和输入格式影响可用入口；记录实际软件版本与配置，界面名称仅作为定位提示。

## 06 RAID5 的校验与四种基本布局

### 06.1 XOR 能证明什么

同一组内，RAID5 的校验满足 `P = D0 XOR D1 XOR …`。若只缺一个数据块，可以用校验与其他数据块得到该块，例如 `D1 = P XOR D0 XOR D2`。按相同成员数据坐标取齐所有块，整组 XOR 应为零。

**一字节演示：** 三个数据字节为 `0x12、0x34、0x56`，校验为 `0x70`；缺失 `0x34` 时，`0x70 XOR 0x12 XOR 0x56 = 0x34`。整块恢复是对每个字节重复此关系，而不是寻找相似文件名。

XOR 具有交换律，因此**整组 XOR 为零不能确定盘序、校验盘角色或同步方式**。即使块大小选错，或所有成员一起移动相同字节数，某段逐字节 XOR 仍可能为零；它也不能独立证明块大小和阵列起点。全零区域、未使用空间或高度重复的数据会给出弱证据。应选择包含实际不同内容的多组，再用元数据和逻辑文件连续性验证。

校验块不一定是乱码。例如三个数据块同一位置均为 `FILE` 时，其 XOR 仍是 `FILE`。同样，乱码可能来自加密、压缩或普通二进制内容；“可读文件名”和“出现 FILE”都不能单独区分数据与校验。

### 06.2 左右决定校验位置，对称决定数据起点

下面以成员编号从左到右递增的常用 Linux MD 约定描述 RAID5，`r` 为组号，`N` 为成员数：

| 布局 | 校验位置 `p` | 同一组内的数据读取顺序 |
| --- | --- | --- |
| 左不对称 | `N - 1 - (r mod N)` | 从最低编号成员开始，跳过校验位置 |
| 左对称 | `N - 1 - (r mod N)` | 从校验位置后一成员开始，循环递增，跳过校验 |
| 右不对称 | `r mod N` | 从最低编号成员开始，跳过校验位置 |
| 右对称 | `r mod N` | 从校验位置后一成员开始，循环递增，跳过校验 |

“同步 / 异步”在这里表示块排列，不表示磁盘写入时刻或数据同步进度。若成员显示顺序被反转或厂商起始相位不同，图中的箭头会改变；保存实际排列比只保存中文名称更可靠。

四盘左对称的一个完整周期如下，`D` 是依次编号的逻辑数据块，`P` 是该组校验：

| 组号 | 成员 0 | 成员 1 | 成员 2 | 成员 3 | 数据读取次序 |
| --- | --- | --- | --- | --- | --- |
| 0 | D0 | D1 | D2 | P0 | 0 → 1 → 2 |
| 1 | D4 | D5 | P1 | D3 | 3 → 0 → 1 |
| 2 | D8 | P2 | D6 | D7 | 2 → 3 → 0 |
| 3 | P3 | D9 | D10 | D11 | 1 → 2 → 3 |

相同校验位置下，左不对称的第 1 组则为 `D3、D4、P1、D5`。观察校验从成员 3 移到成员 2，只能约束旋转方向；还需要连续数据块的顺序区分对称与不对称。

## 07 实战：没有阵列元数据时分析 NTFS 成员

### 07.1 场景、目标与先决条件

**场景与材料：** 获得四个完整 RAW 成员副本，元数据缺失；某个候选逻辑区域包含 NTFS 启动结构与连续的文件记录。目标是推导成员数据起点、单盘块大小、盘序及校验布局。

先记录每个输入对象的扇区大小、头尾范围、候选起点和发现位置。容量接近三块成员容量之和只支持四盘 RAID5 作为候选，还要排除保留区、截断、未分配空间、其他级别和拼接。发现某盘首扇区有 MBR，也不能直接证明全部成员起点为零或该盘是逻辑首盘。

### 07.2 从 NTFS 启动结构定位 $MFT

对可信的 NTFS DBR / VBR，关键字段均按其结构解释：

| 字节位置 | 字段 | 用途 |
| --- | --- | --- |
| `0x0B–0x0C` | 每扇区字节数，小端 | 计算分区内部地址 |
| `0x0D` | 每簇扇区数 | 簇大小为该值乘扇区字节数 |
| `0x30–0x37` | `$MFT` 起始簇号，小端 | 是 LCN，不是字节偏移或扇区号 |
| `0x38–0x3F` | `$MFTMirr` 起始簇号 | 区分主表和镜像区域 |
| `0x40` | 文件记录大小的有符号编码 | 负值 `v` 表示 `2^(-v)` 字节；正值表示 `v` 个簇 |

若分区在逻辑镜像中的字节起点为 `V`，簇大小为 `K`，起始簇号为 `L`，则 `$MFT` 首段的逻辑字节位置为 `V + L × K`。这是**重组逻辑地址**，必须再通过 RAID 映射才能定位某个成员上的物理位置。后续 `$MFT` 还可能有多个 data run，不能把全表都当作一个连续区域。

下面只读解析**候选逻辑镜像**中已知位置的启动扇区，打印字段与坐标；它不进行 RAID 重组，也不把一次签名通过视为有效文件系统。`1048576` 是示例分区字节起点：

```bash
python3 - ./work/raid-candidate.raw 1048576 <<'PY'
from pathlib import Path
import sys

path = Path(sys.argv[1])
volume_start = int(sys.argv[2], 0)
if volume_start < 0:
    raise SystemExit("negative volume offset")
with path.open("rb") as stream:
    stream.seek(volume_start)
    boot = stream.read(512)
if len(boot) != 512 or boot[3:11] != b"NTFS    " or boot[510:512] != b"\x55\xaa":
    raise SystemExit("not a complete NTFS boot candidate")
sector = int.from_bytes(boot[0x0B:0x0D], "little")
spc = boot[0x0D]
if sector not in (512, 1024, 2048, 4096) or spc == 0 or spc & (spc - 1):
    raise SystemExit("unsupported sector or cluster geometry")
cluster = sector * spc
code = int.from_bytes(boot[0x40:0x41], "little", signed=True)
record = 1 << (-code) if code < 0 else code * cluster
if record == 0:
    raise SystemExit("invalid zero record size")
mft_lcn = int.from_bytes(boot[0x30:0x38], "little")
mirror_lcn = int.from_bytes(boot[0x38:0x40], "little")
print("sector_bytes:", sector, "cluster_bytes:", cluster)
print("record_bytes:", record)
print("mft_lcn:", mft_lcn, "mirror_lcn:", mirror_lcn)
print("mft_logical_byte:", volume_start + mft_lcn * cluster)
PY
```

例如 `512` 字节扇区、每簇 `8` 扇区、`0x40` 为 `0xF6` 时，簇为 `4096` 字节，记录为 `1024` 字节。记录大小应读取后计算，不能预设所有 NTFS 记录均为 1 KiB。字段合理后，还要验证主表记录、属性结构、USA/fixup、data run 和镜像关系。

### 07.3 用连续记录约束块大小

搜索 `FILE` 可以寻找候选文件记录，但应验证记录头、长度、属性边界、USA/fixup 和实际记录编号，排除旧格式化残留、`$MFTMirr` 与校验偶合。现代 NTFS 记录中的记录编号常位于头部 `0x2C`；不要把 `0x10` 的序列号、日志序列号或 GUI 行号当作编号。

在**已确认的连续、记录对齐的 $MFT 数据段**中，若相邻逻辑数据块在相同块内位置的记录编号稳定相差 `Δ`，且记录大小为 `R`，可提出 `C = Δ × R` 作为单盘块大小候选。差值可能跨越多个块，也可能受到碎片化影响，因此还要验证块边界及其他区域。

**构造观察：** 三个已验证的数据块同一块内位置分别含编号 `128、192、256`，实际记录大小为 `1024` 字节，则相邻候选间距为 `64 × 1024 = 65536` 字节，即 `64 KiB`。这只能约束该连续区域的块大小；第四成员即使同样出现 `FILE`，也要先确认它是否为可解释的数据记录。

随后在每个成员的同一数据坐标上向后移动一个候选块，再记录新的编号和完整结构。若 `C = 65536` 字节，在 512 字节扇区显示下应移动 `128` 扇区；若窗口按字节显示，则移动 `65536`。不按单位核对就跳转，会把错误坐标当作布局变化。

### 07.4 用完整周期、首盘锚点与文件内容确定盘序

至少记录一个完整校验周期，并在非零、不同内容区域复核：每组哪些块能形成连续文件记录、哪个位置承担候选校验、数据块应从哪里开始。以第 06 节四盘左对称表为例，校验位置依次为 `3、2、1、0`，同时逻辑数据起点依次为 `0、3、2、1`，才支持相应布局。

中间区域推导出的排列可能存在整体循环平移。再用逻辑盘起点的可信分区结构、分区范围、NTFS 卷大小、主表及完整文件约束首盘和起始相位。两个成员出现相同 MBR 或文件头时，可能来自镜像、校验巧合、旧结构或重复区域，不能任选其一当作首盘。

将候选配置逐一保存，比较同一组验证对象。若某盘序能识别 NTFS 但跨块文件损坏，另一盘序在相同区域能正确解析元数据、完整解出文件且校验一致，后者获得更强支持。保留失败候选及失败位置，才能解释为什么最终配置更合理。

## 08 实战：NAS 多层存储与缺失成员

### 08.1 带元数据的多盘 NAS

**场景与材料：** 三块 NAS 整盘镜像，每盘有小型系统分区和较大的数据分区；工具自动生成多个阵列对象。目标是还原共享目录和业务文件。

1. 对每盘分别列出分区，记录相同位置上的阵列标识、成员角色和预期盘数。
2. 按 UUID 分组系统阵列与数据阵列。系统分区可以采用镜像，数据分区可以采用另一种布局，不能共享一套盘序与块大小假设。
3. 检查数据阵列上是否还有 LVM；若有，继续建立物理卷、卷组和逻辑卷的对应表，再定位文件系统。
4. 识别实际文件系统；遇到 Btrfs、ZFS 或存储池元数据时，使用对应解析规则，不把“NAS”当作 RAID5 的证据。
5. 提取共享目录配置、目标文件和有关日志，记录所在阵列、卷、路径、元数据地址及导出哈希。

**结果判读：** 系统阵列可读只能说明系统区域被解析；共享目录没有出现时，还要核对数据卷、加密、挂载、快照和缺失范围。共享配置中的路径也不等于该路径下的数据已经完整恢复。

### 08.2 四盘 RAID5 只取得三个有效成员

**场景与材料：** 元数据记录预期 4 个成员，角色为 `0、1、3` 的工作副本可读，槽位 `2` 缺失。其余成员来自相符采集状态，布局和数据起点已有证据支持。

在虚拟阵列配置中保留四个槽位，把缺失对象放在角色 `2`，而不是将剩余三盘改成三盘 RAID5。对每一组，按实际校验位置判断缺失的是数据还是校验：缺数据时由剩余数据与校验计算；缺校验时已有数据可以直接映射。

验证恢复后的文件系统和跨多组文件，同时记录合成块的范围、读取错误、零填充策略和未验证区域。如果另一个有效成员在同组也有坏块，或成员状态跨越了重建过程，单校验不再保证该组可恢复。热备和旧成员只能在核对角色、代际和同步状态后作为候选补充。

**结果边界：** 理论上的“一盘容错”描述冗余能力，不是对本次检材完整性的保证。工具显示 degraded、阵列可启动或部分文件可打开，仍不足以认定全部数据恢复。

## 09 证明重组正确：结构、校验与跨条带文件

### 09.1 分层验证，记录覆盖范围

| 验证层 | 实际检查 | 能支持的结论与限制 |
| --- | --- | --- |
| 输入与范围 | 成员哈希、有效区间、尾部与读取错误 | 说明使用了哪些字节；哈希不能证明镜像采集完整 |
| 阵列参数 | UUID、角色、块大小、起点、完整布局周期 | 说明配置与现有元数据和观察是否相符 |
| 校验关系 | 多个不同内容区域的完整成员块 XOR | 说明抽查坐标上的校验相容；不能独立确定块大小、起点或盘序 |
| 分区与文件系统 | 分区范围、卷大小、主备结构、目录、记录和 data run | 排除只命中魔数或只出现目录的弱配置 |
| 文件内容 | 跨多个成员、多个校验周期的文件，完整格式解析和内部校验 | 证明所选文件可恢复；不自动覆盖未抽查区域 |
| 独立核验 | 同配置在另一解析器的结构和文件结果，或已有可信文件哈希 | 加强交叉证据；两个工具都猜同一参数仍不能代替内容验证 |

选大文件时检查**实际分配 run**，确认跨越多成员和多组，而不只是看文件逻辑长度。稀疏文件、压缩文件及高度重复内容可能让抽样范围不足。某工具预览出一张图片，只证明被解码的部分；应完整解析、检验 CRC/校验字段或与可信副本比对。

### 09.2 只读抽查 RAID5 整组 XOR

以下脚本假设有四个完整 RAW 成员，成员数据起点相同，单盘块为 `65536` 字节，数据从各输入的 `1048576` 字节开始。它读取前 4 组并计算整组 XOR，不写入成员；若起点不同、输入是 E01 容器或阵列正在 reshape，不能套用这个示例：

```bash
python3 - 65536 1048576 ./work/member-a.img ./work/member-b.img \
  ./work/member-c.img ./work/member-d.img <<'PY'
from contextlib import ExitStack
from pathlib import Path
import sys

chunk = int(sys.argv[1], 0)
start = int(sys.argv[2], 0)
paths = [Path(value) for value in sys.argv[3:]]
if chunk <= 0 or start < 0 or len(paths) < 3:
    raise SystemExit("invalid chunk, start or member count")
with ExitStack() as stack:
    streams = [stack.enter_context(path.open("rb")) for path in paths]
    for row in range(4):
        blocks = []
        for stream in streams:
            stream.seek(start + row * chunk)
            block = stream.read(chunk)
            if len(block) != chunk:
                raise SystemExit(f"short read at stripe {row}")
            blocks.append(block)
        xor = bytearray(chunk)
        for block in blocks:
            for index, value in enumerate(block):
                xor[index] ^= value
        mismatches = sum(value != 0 for value in xor)
        all_zero = all(not any(block) for block in blocks)
        print("stripe", row, "nonzero_xor_bytes", mismatches,
              "all_members_zero", all_zero)
PY
```

`nonzero_xor_bytes = 0` 表示该组满足抽查关系，`all_members_zero = True` 提示这组证据很弱。非零结果可能来自各成员的数据坐标未对齐、代际不一致、坏块、缺失区零填充或校验未完成，不应直接断言某一盘损坏。块大小或共同起点错误仍可能通过抽查，要继续核对逻辑结构。抽查应覆盖数据卷中段和末段，实际组号与坐标写入记录。

### 09.3 在已重组的逻辑镜像中提取验证对象

先确认导出对象是整块逻辑盘还是单分区。以下命令用于整盘 RAW 重组结果，示例文件系统起点为 `2048` 个 512 字节扇区：

```bash
sha256sum ./output/raid/raid.raw
mmls -b 512 ./output/raid/raid.raw
fsstat -b 512 -o 2048 ./output/raid/raid.raw
fls -b 512 -o 2048 -r -p ./output/raid/raid.raw > ./output/raid/files.txt
metadata_addr='12345-128-1' # 替换为 fls 实际输出的完整地址及数据流
icat -b 512 -o 2048 ./output/raid/raid.raw "$metadata_addr" > ./output/raid/recovered.bin
stat -c '%n %s bytes' ./output/raid/recovered.bin
sha256sum ./output/raid/recovered.bin
file ./output/raid/recovered.bin
```

单分区导出通常从文件系统偏移 `0` 开始，应重新核对后调整 `-o`。TSK 的 `-o` 是镜像内扇区偏移，`-b` 是底层扇区字节数；不能把它们与成员 Data Offset 混用。`icat` 输出的对象还应核对长度、数据流、格式与内容；只计算恢复件哈希，不能证明恢复件与原文件一致。

## 10 导出逻辑镜像与仿真边界

### 10.1 保存导出范围和复现配置

导出前保留成员清单、阵列参数、区域范围与验证结果。导出后记录逻辑字节数、格式、分段、压缩及读取错误；重新载入输出，核对分区、目标文件系统和代表文件。E01 容器文件哈希与 RAW 文件哈希通常不同，应比较相同范围的解码后逻辑数据，不能只比较两种容器的文件哈希。

工具中的“保存 RAID 配置”可能只是保存成员映射，不能代替完整逻辑镜像；“恢复文件”则不保留整盘未分配空间。根据分析目标明确保存配置、整盘、分区还是文件，以及不包含的范围。

### 10.2 FTK Imager 与 VMware 的作用

FTK Imager 可以提供镜像的逻辑磁盘视图，VMware 可以把相应虚拟或映射磁盘接入虚拟机。它们用于呈现镜像和仿真环境，不能凭挂载动作推导硬件 RAID 的盘序与布局。硬件阵列通常需先导出重组逻辑盘；系统软件 RAID 可能由虚拟机中的原有驱动依据元数据组装。

确有仿真需要时按顺序检查：

1. 先完成静态重组验证，复制一套独立实验镜像或建立可靠的写入覆盖层，记录起始哈希与配置。
2. 将**实验对象**挂载或转换为虚拟机可用磁盘，核对物理磁盘编号与实验对象映射；不要把真实宿主磁盘选作检材。
3. 按原环境确认 BIOS/UEFI、控制器类型、启动盘和全部必要成员。软件阵列应保留成员身份与拓扑，不能用虚拟机控制器端口号替代阵列角色。
4. 在隔离环境启动，记录固件、驱动、阵列、卷和服务报错；需要读写时仅写入实验副本，保留变化记录。
5. 检查目标数据卷和代表文件，并把仿真运行态、静态镜像痕迹与启动后生成的日志分别记录。

系统盘放在 SATA0:0 或调整启动次序只是某些环境的设置，不能作为所有镜像的固定要求。FTK 的读写挂载也不是静态重组的必要步骤；仿真允许写入的对象必须是独立实验副本或覆盖层。

如果操作系统在独立盘上，启动成功时数据阵列仍可能未恢复；如果操作系统位于阵列中，启动失败也可能来自固件、启动文件或驱动不匹配。**能启动不能证明重组成功，不能启动也不能证明数据不可读。** 仿真无法完成时，仍可在可信逻辑卷上静态提取配置、共享数据、用户文件和日志。

## 11 考点与常见故障判读

### 11.1 重点掌握的考查内容

| 考查方向 | 应能完成的判断或操作 |
| --- | --- |
| 成员识别 | 区分 E01 分段、独立成员、单分区、热备与缺失槽位 |
| 级别和容量 | 说明条带、镜像、单/双校验及容量公式的前提，不只按容量猜级别 |
| 参数读取 | 从元数据记录 UUID、角色、块大小、布局、Data Offset、事件与状态 |
| 单位换算 | 在字节、扇区、簇和整组宽度之间换算，并标明地址相对层次 |
| RAID5 排列 | 绘出四种基本布局，分开解释校验方向与数据起点 |
| 手工重组 | 使用可信 NTFS 启动结构、记录长度、连续编号和校验周期提出候选配置 |
| 缺盘处理 | 保留原拓扑与缺失位置；解释单校验为什么不能解决同组两个未知块 |
| 多层 NAS | 区分系统阵列、数据阵列、卷组、逻辑卷和文件系统存储池 |
| 导出和取证 | 导出适当范围，保留原路径/地址、逻辑大小、哈希与错误记录 |
| 成功验证 | 用元数据、校验、文件系统和跨多组文件形成相符证据 |
| 仿真判读 | 说明系统启动、阵列可见、卷可读、服务恢复之间的区别 |

题目涉及“磁盘数、卷组数、条带大小、盘序、循环方式或共享文件”时，分别返回相应层次的对象和证据字段。应给出可复核的参数、位置与过程，不能只交付工具界面显示的一行结果。

### 11.2 按现象回查

| 现象 | 优先排查 | 下一步验证 |
| --- | --- | --- |
| 单成员打不开文件系统 | 是否本来就是条带成员、采集范围、镜像格式 | 分区与阵列元数据，不先执行文件系统修复 |
| 自动检测没有阵列 | 分段是否齐全、成员是否选到分区、元数据/格式支持 | 换只读逻辑视图或手工参数路线 |
| 出现分区但目录混乱 | 盘序、起点、块大小、同步方式 | 相同代表区域的连续记录与跨块文件 |
| 小文件正常，大文件损坏 | 大文件是否跨组、data run、缺盘、坏块、布局 | 完整读取并定位失败逻辑块 |
| 每到固定边界出现乱码 | 块大小、数据起点、扇区单位 | 按候选块边界对照各成员；不能只凭现象确定一种原因 |
| 部分区域正常，后段失效 | 输入截断、有效长度、成员代际、reshape | 检查尾部与状态，并记录不同布局或缺失范围 |
| 同 UUID 成员角色重复或事件不一致 | 旧盘、替换盘、克隆件、采集不同步 | 结合状态和非零内容决定候选集合 |
| 系统能启动但共享数据为空 | 数据阵列、卷管理、加密和挂载依赖 | 检查目标卷本身及静态共享配置 |
| 仿真启动失败 | 固件、启动链、控制器、驱动与阵列依赖 | 继续静态读取，不据此判定镜像无价值 |

## 12 交付一份能够复核的重组记录

每次重组至少保留：

- **输入清单**：成员标签、分段组成、采集范围、字节数、扇区大小、哈希和缺失/坏块说明。
- **成员映射**：阵列 UUID、角色、热备与旧成员处理、实际输入区域及数据起点。
- **参数配置**：级别、拓扑、块大小、每成员有效长度、校验周期、起始相位、工具字段原值和版本。
- **推导过程**：元数据位置、NTFS 字段与计算、记录连续性、候选盘序、失败配置及原因。
- **验证结果**：校验抽查坐标、文件系统结构、跨组文件的实际分配范围、完整解析或可信哈希比对，以及未覆盖区域。
- **输出与变化**：逻辑镜像范围、格式、大小、哈希、错误日志、提取文件路径/元数据地址，实验副本的写入变化。

能够列目录时，只记录“该配置可解析所列目录”；代表文件经过完整核验时，记录具体对象与覆盖范围；只有证据支持时才说明相应数据区域已恢复。已知缺失、校验不一致和工具不支持的范围应随输出一起保留。
