## 01 先判断取得的是哪一层数据

记录设备型号、系统版本、设备时间和时区、锁定状态、提取方式与时间、检材哈希。常见的手机检材包括**本地备份、逻辑导出、文件系统提取、应用容器、云导出或截图**，覆盖范围差别很大。建一张“已取得/未取得/未知”清单，避免把备份中缺少的数据误判为设备上从未存在。设备仍在运行时，网络同步、通知和自动清理可能改变证据；操作前记录屏幕状态和时间，不随意登录、升级或恢复备份。

| 检材 | 通常先找 | 不能直接推出 |
|---|---|---|
| Android 共享存储导出 | `DCIM/`、`Download/`、媒体和应用导出 | 已取得每个应用的私有数据库 |
| Android 完整文件系统提取 | `/data/user/0/<包名>/`、系统及共享目录 | 所有加密内容均可解读 |
| iOS 本地备份 | 清单、应用域、数据库及附件 | 等同于实时完整文件系统 |
| 云端或平台导出 | 账号、会话、服务端时间及导出范围 | 数据都在这台手机上生成 |

## 02 Android：从设备和包名入手

在**设备已授权且允许调试**的前提下，ADB 可帮助确认设备标识、系统版本、安装包名，并提取当前可访问的共享目录。命令结果是采集时的状态，不保证历史完整；没有调试授权时不要把 ADB 报错当成没有数据。

```bash
adb devices -l
adb shell getprop ro.build.version.release
adb shell pm list packages
adb pull /sdcard/DCIM/ ./work/DCIM/
find ./work/DCIM/ -type f -print0 | sort -z | xargs -0 -r sha256sum > dcim.sha256
```

有完整提取时，按包名定位 `databases/`、`shared_prefs/`、`files/`、`cache/` 与外部存储目录。Android 版本、厂商及应用的备份规则会影响可见范围；普通 ADB 权限通常不能读取其他应用私有目录。分析 SQLite 时连同 `-wal`、`-shm` 文件复制到工作目录，避免只读主库漏掉尚未检查点的事务。先看表结构和字段样本，再解释时间戳、消息方向和状态码。

## 03 iOS：从备份清单还原逻辑路径

本地备份先保存完整目录并计算哈希，识别设备信息、备份时间、是否加密、清单数据库和应用域。加密备份可包含未加密备份没有的类别，但也并非完整设备映像；需要已知密码才可正常解读。对已解密的工作副本，可用清单将散列文件名映射到 `domain + relativePath`，再按应用标识追踪数据库和附件。

```bash
file ./work/Manifest.db
sqlite3 -readonly ./work/Manifest.db 'SELECT domain, relativePath, fileID FROM Files LIMIT 20;'
```

示例查询用于**确认结构**；分析结论还需来自实际记录及关联证据。不同备份版本、工具和加密状态可能要求先解析或解密；查询失败应检查数据库是否完整、格式是否相符。iOS 数据库同样要关注 WAL。不能只凭散列文件名判断文件用途，也不能把备份生成时间当成每条记录的事件时间。

## 04 应用消息、附件与定位怎么串起来

先确定包名/Bundle ID、应用版本、账号标识和设备标识；一台手机可能有多账号、多开、卸载重装或从另一设备同步。按稳定 ID 建立关系：`会话 → 消息 → 附件 → 联系人/群组 → 系统通知或服务端记录`。对每条关键记录保留数据库路径、表名、主键、原始时间字段、方向与状态值，避免只截图一个解析界面。

位置证据要写明来源：GPS、图片 EXIF、Wi-Fi/基站、地图搜索和用户手填地点的精度与含义不同。时间字段可能使用 Unix 秒/毫秒、Apple 纪元或应用自定义基准；先取几条已知事件校准，再统一到一个时区。媒体缩略图、缓存和原件分别计算哈希；缓存出现不等于用户实际打开。

## 05 用第二种痕迹复核并报告

通信行为至少核对两层：例如数据库消息与附件文件、应用记录与系统通知、设备记录与云端导出。缺少另一层时，只报告“记录显示”而不推断对方收到、用户读过或人在某地。最终给出提取方式、覆盖区间、账号切换、加密限制、数据库路径、主键、时间换算和缺失项。这样即使某个应用版本改变表结构，分析过程仍可复查。

## 06 设备身份、提取层级与应用分析

设备标识中的 IMEI/MEID、SIM/UICC 的 ICCID/IMSI 和应用账号标识不是同一对象；双卡、多设备和账号迁移需要分别建表。硬件的 RAM、ROM、存储芯片、接口、基带、可移除存储影响可获取范围；不能把“物理提取”理解为一定含可读明文。

逻辑提取、备份、文件系统提取、物理镜像、屏幕记录和云端固定逐项注明范围。ROOT、刷机、恢复、芯片提取等可能改变数据或设备状态，需要匹配设备条件和明确记录；没有对应采集条件时不编造通用解锁步骤。Windows Phone、BlackBerry、Symbian、非智能手机与不同厂商方案也不能套用现代 Android/iOS 的路径。

应用结构分析按包名/Bundle ID、版本和运行框架定位。Android 关注 manifest、DEX、SO 与 Java/原生/混合/Flutter 结构；iOS 关注 IPA、Mach-O、签名和文件系统/备份域。Frida、Xposed、Cydia Substrate、IDA、MachOView、Reveal 等属于不同平台的观察工具，hook、抓包、反编译和动态调试各自提供有限视角；不要把修改后的实验数据与原始提取结果混在一起。数据库、消息、附件和删除残留的主流程见 [应用与通信](/knowledge/forensic-mobile-apps/)，避免按工具名重复建立知识分类。

## 07 实战：把消息记录与附件对应起来

**场景与材料：** 已取得一个应用的数据目录或解密备份，内含消息数据库、相邻 WAL/SHM 及部分附件。目标是核对一条消息的内容、方向、时间和附件，不假定特定应用的表名适用于所有版本。

### 07.1 保全和定位

1. 完整复制数据库及旁文件到同一工作目录，保存各文件哈希；记录应用包名/Bundle ID、版本、账号和提取范围。
2. 查看实际表结构和少量样本，确认会话 ID、消息主键、发送者/方向、时间、类型、状态和附件引用字段。字段名相似时也要验证含义，不凭译名猜测。
3. 对 iOS 备份，先从清单映射逻辑路径；对 Android，沿私有目录与共享存储中的实际附件路径检索。同名附件可能有原件、缩略图、缓存和多个版本。

### 07.2 按关系验证

| 对应关系 | 核对方式 | 不足以推出的事实 |
| --- | --- | --- |
| 消息—会话 | 使用实际主键/外键或经样本验证的关联字段 | 同名联系人就是同一账号 |
| 消息—附件 | 记录引用路径/ID、文件大小与内容哈希 | 缓存文件存在就是用户打开过 |
| 时间—行为 | 保留原始值，验证秒/毫秒/纪元和时区 | 备份生成时间就是消息发送时间 |
| 状态—交付 | 按版本核对发送、接收、已读等字段 | 本地状态一定等于对方实际行为 |

**结论示例：** “应用数据库中存在一条发出方向的消息记录，附件引用可映射到已取得文件；该文件哈希和大小已保存。当前材料未包含服务端交付或对端已读证据，因此不进一步断言对方收到或阅读。”

最后尝试用另一层痕迹验证，如系统通知、同会话附件或合法取得的云导出。关联失败时保留原记录，不删除相互冲突的数据来制造完整链路。
