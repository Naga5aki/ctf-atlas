## 01 校准抓包边界

记录文件哈希、抓包起止时间、时区、接口、链路类型、分包大小和丢包信息。主机、网关与镜像端口看到的方向不同；NAT、代理和负载均衡会改变可见端点。先回答三个问题：**覆盖目标时间吗、覆盖目标链路吗、载荷是否完整**。若覆盖条件未知，后面“未看到某行为”的结论也要限定范围。

```bash
sha256sum capture.pcapng
capinfos capture.pcapng
tshark -r capture.pcapng -q -z conv,tcp
tshark -r capture.pcapng -q -z conv,udp
```

会话统计帮助找大流量、长连接和可疑端点，但同一个业务可能跨多条连接；反过来，单条连接也可能复用多个请求。`-q` 只压低逐包输出，不改变检材。抓包若被截断，协议解析和对象导出都可能只得到片段。

## 02 从五元组缩小范围

先按源/目的 IP、端口、传输协议、时间段列候选会话，再检查建连、请求、响应、断开与重传。TCP 三次握手只证明连接建立，不能证明应用请求成功；看到 HTTP 200 也不代表客户端下载完整。UDP 没有同样的连接语义，需看应用层请求/响应配对。

```bash
tshark -r capture.pcapng -Y 'dns.flags.response == 0' -T fields \
  -e frame.number -e frame.time_epoch -e ip.src -e dns.qry.name
tshark -r capture.pcapng -Y 'http.request' -T fields \
  -e frame.number -e ip.src -e http.host -e http.request.uri
```

以上命令输出帧号，便于回到原始报文。IPv6 抓包应改看 `ipv6.src` 等字段；非标准端口可能需要在 Wireshark 中指定“Decode As”。DNS 查询名与后续连接要核对解析结果及时间，不能只凭域名出现在包里推断访问成功。常见 16 类协议的显示过滤表达式与 `tshark` 导出命令速查见[Wireshark 过滤](/knowledge/forensic-traffic-filters/)。

## 03 按分析目标选择下一步

| 目标 | 观察点 | 实际验证 |
|---|---|---|
| 下载或上传文件 | HTTP 请求/响应、FTP/SMB 会话、分片和长度 | 重组实体，核对文件头、大小、哈希与完整性 |
| 扫描或爆破 | 多端口/多账号尝试、响应码、时间密度 | 与服务认证日志交叉确认是否登录成功 |
| 命令控制 | 周期性连接、相近请求体、固定目标 | 对照 DNS、终端进程和服务器日志 |
| 数据外传 | 异常上行量、编码载荷、长域名或隧道 | 按序还原数据，验证解码结果和传输完成程度 |

用 Wireshark 的 Follow Stream 或 Export Objects 提取时，保存过滤条件、流编号、帧号范围和输出哈希。HTTP 压缩、分块、重传和多路复用可能使“原始载荷”和“还原实体”不同；在报告中说明提取的是哪一层。加密 TLS 没有合法密钥时通常只能分析握手、目标和时序，不把域名或证书字段写成已看到的明文内容。

## 04 与主机侧证据闭环

把报文时间统一到服务器和终端的时间基准，再关联访问日志的请求 ID、状态码、字节数，以及终端的进程、下载文件和 DNS 缓存。若客户端和服务器对同一请求的时间不一致，先核对时区、时钟漂移、代理层和日志缓冲。最终每条结论至少附帧号/会话、原始字段、提取件哈希及另一侧证据；不完整会话、未知抓包点和加密范围要单独列为限制。

## 05 实战：核对一次候选文件下载

**场景与材料：** 已取得一份 PCAPNG，怀疑某个客户端下载了文件。先确定抓包点、时间范围和载荷完整度，再分析请求与响应；以下过程不发送新网络请求。

1. 用本页 `capinfos` 和会话统计记录捕获范围、TCP 端点及候选流。按客户端方向筛选 HTTP 请求，保存帧号、Host 与 URI。
2. 回到同一连接中的响应，核对状态、实体长度、传输编码、分块和重传。若只见请求或握手，应停止于“观察到请求/连接”，不能判定完整下载。
3. 在 Wireshark 中使用 Follow Stream 或 Export Objects，记录实际流编号、帧号范围和导出层次；压缩或分块会使实体长度不同于网络载荷总量。
4. 对导出件执行已有的哈希、文件头与解析器检查流程，再与服务器日志的请求、终端保存路径和文件哈希关联。文件恢复成功也不能单独证明用户手动下载。

**示例判读：** 一个 TCP 流返回 HTTP 200，但抓包在响应中途结束；导出文件只有头部和部分数据。结果应写成“观察到成功状态响应及部分实体，完整传输不可确认”。若完整实体通过格式校验且与终端文件哈希一致，才可进一步支持相同内容已保存。

**易错点：** DNS 解析与访问分开验证；服务器状态与客户端完成程度分开验证；TCP 重传包不重复计入逻辑内容。对 TLS 仅有握手元数据时，仍按加密范围描述，不将 Host 或 URI 的明文分析方法直接套入。
