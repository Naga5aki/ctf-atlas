## 01 阅读路线与首轮调查

Bitcoin 链上取证的基本对象是**交易、被花费的输出和新生成的输出**。先把每个输入准确连接到前序输出，再解释金额、手续费与可能的找零，最后才讨论地址关联和资金去向。

**首轮顺序：** 确定链与网络 → 固定交易和区块 → 补齐输入引用的前序输出 → 用 satoshi 核算金额 → 标出资金移动和可能的找零 → 复核活跃链状态 → 与设备、钱包和业务记录关联。

| 要回答的问题 | 必需材料 | 核心输出 |
| --- | --- | --- |
| 交易在哪条网络上发生 | 节点配置、网络标识、创世块 hash、区块信息 | 网络身份与采集时间 |
| 实际花费了哪些资金 | 交易 vin 与前序交易 vout | 每个输入对应的 txid:vout 和金额 |
| 实际手续费是多少 | 全部输入金额、全部输出金额 | 整数 satoshi 手续费与校验结果 |
| 哪个输出可能是找零 | 输出金额、脚本、钱包记录、后续花费 | 事实与找零推断分开的结果 |
| 钱包有没有关联到某个人 | 钱包配置、设备记录、账户资料、导出记录 | 地址关联证据及可信范围 |
| 资金后续去了哪里 | 完整交易、花费边、区块定位、采集范围 | 可回查的交易图和金额表 |

命令默认使用 Kali/Linux。`/mnt/evidence` 表示只读材料挂载点；当前工作目录必须是自己的分析目录。示例输出写入 `./output/bitcoin`，不要在检材目录启动钱包、导入钱包或改变节点配置。没有可用节点时，直接从保全的交易 JSON、原始交易 hex 与区块信息开始。本文模板说明操作方法；离线案例为自建练习，不代表已经复跑某个真实钱包或真实链案件。

## 02 从 UTXO 理解交易

### 02.1 余额是一组输出的合计

UTXO 是尚未花费的交易输出。钱包显示的余额可以来自多笔历史交易的多个输出。普通交易输入引用前序输出，花费时消耗整个输出金额，并生成新的输出。

```text
前序交易 P                          当前交易 T
P:0 = 120,000 sat  ────────────┐
                             ├─ vin → T:0 = 150,000 sat
P:2 =  80,000 sat  ────────────┘       T:1 =  49,000 sat
                                     差额 =  1,000 sat 手续费
```

图中两项输入分别是 `P:0` 与 `P:2`。输出属于脚本规定的花费条件；脚本能够表示常见地址时，解析器才可能展示 `address`。不能因为输出没有地址字段就删掉它，也不能把脚本地址直接当成自然人身份。

### 02.2 最少需要读懂的字段

| 字段 | 含义 | 取证时的使用方式 |
| --- | --- | --- |
| `txid` | 交易标识 | 引用前序输出和定位交易 |
| `hash` | 节点展示的交易 hash，witness 交易可能与 txid 不同 | 单独保存，不能替代 txid:vout |
| `vin[i].txid` / `vin[i].vout` | 第 i 个输入引用的前序交易及输出下标 | 用两个字段共同连接前序输出 |
| `vin[i].prevout` | 节点可提供的被花费输出详情 | 金额和脚本核算；缺失时补查前序交易 |
| `vout[j].n` | 当前交易输出下标，从 0 开始 | 构造当前 txid:n 的唯一定位 |
| `vout[j].value` | 输出 BTC 金额 | 转为整数 satoshi 后计算 |
| `scriptPubKey.hex/type` | 输出脚本和解析类型 | 保留原始脚本，解释支付或数据输出 |
| `scriptPubKey.address` | 能明确表示时提供的地址 | 仅为脚本的展示形式 |
| `blockhash` / `blocktime` | 所在区块及其时间 | 建立链上包含关系与时间表 |
| `confirmations` / `in_active_chain` | 查询时的确认与活跃链状态 | 记录采集快照，复核重组 |
| `size` / `vsize` / `weight` | 序列化大小、虚拟大小和权重 | 正确解释费用率，注明分母 |

**输出下标与地址出现次数不是同一件事。** 两个输出即使支付同一地址，也仍是两个不同的 UTXO。交易图使用 `txid:vout` 做资金对象，地址图用于辅助展示归属候选，不能省略输出层。

## 03 金额、手续费与找零

### 03.1 普通交易的金额守恒

```text
1 BTC = 100,000,000 satoshi
输入总额 = 各 vin 引用的前序输出金额之和
输出总额 = 当前交易全部 vout 金额之和
普通交易手续费 = 输入总额 - 输出总额
以 vsize 为分母的费用率 = 手续费 sat / vsize vB
```

计算包含全部输出，包括没有可显示地址的输出。不要把支付到自己地址的找零排除后再算手续费。Coinbase 没有普通的前序输入，不能套用上述输入减输出算法；应单列为区块奖励类交易。

JSON 中的 BTC 小数先按十进制精确解析，再乘 `100000000`。若出现不足一个 satoshi 的残余，应检查字段、单位和材料是否错误；不要悄悄四舍五入来掩盖问题。累计计算使用整数，只有展示时再换回 BTC。

### 03.2 找零是一种解释，不是交易内的标签

找零输出把输入中超出支付需求和手续费的余额送回支付方控制的脚本。链上交易通常不会给普通输出写一个可靠的“找零”标志。

| 观察 | 可以提出的候选 | 不能独立证明 |
| --- | --- | --- |
| 一个输出金额较小 | 可能找零，也可能小额支付 | 小额输出一定属于付款方 |
| 某个输出为整额 | 可能是用户指定的付款金额 | 另一个输出一定是找零 |
| 输出脚本类型与输入相同 | 可能沿用钱包输出策略 | 同一钱包或同一人的身份 |
| 地址首次在观察范围出现 | 可能是新找零地址 | 全链第一次出现，或地址控制权 |
| 输出随后与已知钱包 UTXO 共同花费 | 新的地址聚类线索 | 无协作交易时才可成立的前提已经满足 |
| 钱包导出把该输出标为 change | 钱包侧找零证据 | 该导出未经验证就是真实历史 |

找零判定写为“候选 + 支持证据 + 反例检查 + 置信范围”。交易只有一个输出、批量付款存在多个收款输出、钱包使用不同脚本类型、多人协作构造交易等情况，都不能按“第二个输出是找零”处理。

## 04 地址聚类与协作交易边界

### 04.1 共同输入启发式

常见非协作交易由一个控制方选择多个 UTXO，因此共同输入可以形成钱包关联候选。但是，链规则并没有要求所有输入归同一人。多人可以共同构造并签署各自输入。

CoinJoin 把多个参与方的输入和输出放入同一交易；Payjoin 可以让支付方和收款方都提供输入。后一种情况可能在金额和输出形态上很像普通付款，却破坏共同输入和找零推断。因此，**共同输入是带前提的启发式，不能输出“必然同一钱包”**。

### 04.2 图形模式不能替代证据

多个等额输出、很多输入、连续小额输出、归集到一个地址，都值得进一步检查，但不单独证明混币、交易所或某人的钱包。交易所批量付款、多人付款、钱包归集与普通支付都可能形成相似图形。

图中建议区分三类边：

1. **链上花费边：** 前序 `txid:vout` 被当前 `txid:vin_index` 消耗，属于可验证事实。
2. **地址关联边：** 根据共同输入、输出策略或钱包记录提出的候选，须保存理由。
3. **身份关联边：** 地址和设备用户、账户或真实主体之间的关联，须依赖独立材料。

一个输出被花费并不意味着“其全部金额一一流向某个特定输出”。多输入、多输出交易在协议层没有为每项输入指定唯一收款输出。采用比例分配或先入先出等追踪规则时，明确标为分析模型，不要把模型结果写成链规则。

## 05 只读节点查询的启动前提

### 05.1 先确认环境是否能够回答问题

只读查询需要可访问的 Bitcoin Core 节点、对应网络的数据，以及能工作的 `bitcoin-cli` 配置。本文按支持 `getrawtransaction` verbosity 2 的节点语法编写；本机版本不同，先查看本机帮助。历史交易查询需要 `txindex` 或明确的区块 hash；即便有索引，裁剪或 undo 数据缺失也可能使历史交易、前序输出或手续费不可取。

节点同步状态、索引状态与数据范围属于采集条件。`getrawtransaction` 查询失败不能直接推出“交易不存在”。不为完成查询去修改检材节点配置；需要另建分析节点时，由独立环境准备数据，并记录网络、同步边界和版本。

以下命令在自己的分析目录执行。先选好节点网络与配置文件，再运行；`bitcoin-cli` 会使用其已配置的连接及认证信息。不要把密码写入公开命令历史、报告或网站。

```bash
OUT='./output/bitcoin'
mkdir -p "$OUT"
bitcoin-cli --version > "$OUT/client-version.txt"
bitcoin-cli help getrawtransaction > "$OUT/help-getrawtransaction.txt"
bitcoin-cli getblockhash 0 > "$OUT/genesis-hash.txt"
date -u '+%Y-%m-%dT%H:%M:%SZ' > "$OUT/collected-at-utc.txt"
```

将创世块 hash 与预期网络核对。不要只依据钱包界面的“BTC”、地址长相或区块浏览器的页面标题判断网络。

### 05.2 已知 txid 和区块 hash 时

`TXID` 是 64 个十六进制字符，不带 `0x`；`BLOCKHASH` 是包含该交易的完整区块 hash。替换以下占位值，保留双引号。

```bash
TXID='替换为64位交易txid'
BLOCKHASH='替换为64位区块hash'
bitcoin-cli getrawtransaction "$TXID" 2 "$BLOCKHASH" > "$OUT/transaction.json"
bitcoin-cli getblockheader "$BLOCKHASH" true > "$OUT/block-header.json"
```

检查 `transaction.json` 的 txid 与目标相同，`blockhash` 与请求一致；显式传入区块 hash 时检查 `in_active_chain`。`getblockheader` 的 `confirmations=-1` 表示该区块不在主链上，应进入重组或分叉核查，不与当前活跃链记录混在一起。verbosity 2 返回的 `transaction.json` 关键字段结构如下（构造示例）：

```json
{
  "txid": "1111111111111111111111111111111111111111111111111111111111111111",
  "vsize": 200,
  "in_active_chain": true,
  "vin": [{"txid": "aaaa...", "vout": 0, "prevout": {"value": 0.00120000}}],
  "vout": [{"n": 0, "value": 0.00150000, "scriptPubKey": {"address": "bc1qexample..."}}]
}
```

节点不能提供 verbosity 2 的详情时，可读取 verbosity 1，再逐项补齐前序交易。只有索引可用而不知道区块 hash 时，才采用不带区块 hash 的查询；保存返回的区块定位，并随后复核。

```bash
bitcoin-cli getrawtransaction "$TXID" 1 > "$OUT/transaction-basic.json"
```

### 05.3 手工补齐一个前序输出

从当前交易某个输入读取 `vin[i].txid` 和 `vin[i].vout`。用对应前序交易的完整区块 hash 查询，再选择 `vout[n]`，同时核对它的 `n` 字段等于所需下标。

```bash
PREV_TXID='替换为该输入引用的64位txid'
PREV_BLOCKHASH='替换为前序交易所在的64位区块hash'
bitcoin-cli getrawtransaction "$PREV_TXID" 1 "$PREV_BLOCKHASH" > "$OUT/previous-transaction.json"
```

前序金额取自被引用的那一项输出，而不是前序交易的全部输出或浏览器显示的总额。为每个 vin 重复这个关联过程。保存前序交易文件及其 hash，便于别人复算。

### 05.4 复核是否仍在活跃链上

从 `block-header.json` 读取十进制 `height`，替换变量，再查看该高度当前活跃链的区块 hash。

```bash
HEIGHT='替换为区块十进制高度'
bitcoin-cli getblockhash "$HEIGHT" > "$OUT/canonical-block-hash.txt"
sha256sum "$OUT"/*.json "$OUT"/*.txt > "$OUT/SHA256SUMS"
```

把 `canonical-block-hash.txt` 与原 `BLOCKHASH` 比较。不同则停止将旧包含关系视为当前有效，保留两次记录、查询时间和变化原因。确认数随查询时间变化；不要把一个快照值当作永久属性。

## 06 无节点时的离线金额核算

### 06.1 输入材料与脚本范围

准备一份交易 JSON，要求全部普通输入已有 `prevout.value`。它可以来自 verbosity 2，也可以由已保全的前序交易补齐；补齐时另存字段来源映射，不能覆盖原始响应。下面脚本保存为分析目录中的 `check_btc.py`，仅使用 Python 标准库，读取副本，不访问网络。

```python
import json
import sys
from decimal import Decimal
from pathlib import Path

SAT = Decimal(100_000_000)

def to_satoshi(value):
    amount = Decimal(str(value)) * SAT
    if not amount.is_finite() or amount < 0 or amount != amount.to_integral_value():
        raise ValueError(f'金额不能表示为非负整数 satoshi: {value}')
    return int(amount)

tx = json.loads(Path(sys.argv[1]).read_text(encoding='utf-8'), parse_float=Decimal)
if any('coinbase' in item for item in tx['vin']):
    raise SystemExit('Coinbase 单列，不能按普通输入减输出核算')

seen = set()
input_sum = 0
for index, item in enumerate(tx['vin']):
    key = (item['txid'], item['vout'])
    if key in seen:
        raise SystemExit(f'重复输入引用: {key}')
    seen.add(key)
    if 'prevout' not in item or 'value' not in item['prevout']:
        raise SystemExit(f'vin[{index}] 缺少前序金额，手续费保持未知')
    input_sum += to_satoshi(item['prevout']['value'])

output_sum = sum(to_satoshi(item['value']) for item in tx['vout'])
fee = input_sum - output_sum
if fee < 0:
    raise SystemExit('输出大于输入，检查网络、前序引用、金额或数据完整性')
if 'fee' in tx and fee != to_satoshi(tx['fee']):
    raise SystemExit('计算手续费与节点 fee 字段不一致')

result = {'txid': tx.get('txid'), 'inputs_sat': input_sum,
          'outputs_sat': output_sum, 'fee_sat': fee}
if isinstance(tx.get('vsize'), int) and tx['vsize'] > 0:
    result['fee_sat_per_vb'] = str(Decimal(fee) / Decimal(tx['vsize']))
print(json.dumps(result, ensure_ascii=False, indent=2))
```

```bash
python3 check_btc.py output/bitcoin/transaction.json
```

脚本只检验字段、引用是否重复和金额算术。它不能验证签名、脚本执行、真实网络包含关系或输出是否未花费。算术通过应写为“金额核算一致”，不能写成“交易已确认合法且地址归属已证明”。

### 06.2 可手算的离线练习

使用合成网络 `synthetic`，两个输入的 `prevout.value` 分别为 `0.0012`、`0.0008` BTC；两个输出分别为 `0.0015`、`0.00049` BTC；`vsize=200`。

下载[合成交易 JSON](/practice/crypto-forensics/bitcoin-transaction.json)并在练习目录运行 `python3 check_btc.py bitcoin-transaction.json`。标识不是有效链上hash，输出的脚本类型也是教具标记；只用于上述整数算术练习。

| 项目 | 应得到的值 |
| --- | --- |
| 输入总额 | 200,000 sat |
| 输出总额 | 199,000 sat |
| 手续费 | 1,000 sat，即 0.00001 BTC |
| 按 vsize 的费用率 | 5 sat/vB |
| 小额输出归属 | 49,000 sat 仅能列为可能找零，需额外归属证据 |

把其中一个 `prevout` 删掉，正确结果是“金额不完整，手续费未知”；把前序金额故意填错，正确行为是报错或与已保全前序交易冲突。把交易标为 Coinbase，则转入专门核查，不能为了得到数字继续运行普通公式。

## 07 匿名竞赛式实战：从设备线索到资金路径

### 07.1 场景与典型问法

材料包含电脑或手机镜像、聊天导出、浏览器记录、钱包相关文件，以及若干交易 JSON。题目可能问：某次付款的 txid、实际手续费、某地址在限定时间的收款次数和总额、付款之后的一跳去向、钱包账户与设备用户的关系。

先写清题目口径：问“交易次数”“输出次数”还是“收款次数”；是统计单个地址，还是已有证据支持的地址集合；是链上 BTC，还是聊天中约定的金额；时间以 UTC 区块时间还是本地应用时间计算。口径不同，正确数字也可能不同。

### 07.2 证据位置与操作

1. **设备入口：** 在应用记录、支付截图、二维码、聊天文本和浏览器历史中找网络名、地址、txid、钱包名称和时间。保存数据库表、记录 ID、截图位置或文件偏移。
2. **候选提取：** 64 位十六进制字符串仅是候选交易标识，也可能是文件 hash；通过交易结构和区块包含关系验证。二维码可能是含金额参数的付款 URI，参数是请求金额，不等于链上到账。
3. **链上固定：** 保存交易、所在区块、全部前序输出和采集时间。截图旁边保留机器可读响应，避免只抄界面显示的“总金额”。
4. **金额核算：** 用整数 satoshi 复算输入、输出与费用。生成逐项表，再生成合计表。
5. **路径追踪：** 逐一寻找目标 `txid:vout` 被哪个输入花费。地址相同不是花费证明；真正的边来自输入对前序输出的引用。
6. **身份关联：** 把钱包侧记录、账户配置、设备用户、聊天约定与链上事实关联。地址标签记录获得时间和依据，结论保留范围。

### 07.3 接收次数和余额的统计规则

限定网络、地址集合、区块范围和确认状态后，分别输出：唯一交易数、支付到该集合的输出数、累计流入金额、已知花费金额、观察截止点的未花费输出合计。收到两个同地址输出的一笔交易，对交易数贡献 1，对输出数贡献 2。

历史累计收款不等于当前余额。检材钱包显示余额也可能来自不同同步高度、未确认交易或钱包内部口径。时间范围不完整、缺少历史区块或钱包地址集合不完整时，报告“观察范围内”的统计，不写“全部资金”。

## 08 时间、确认与证据唯一键

| 对象 | 建议唯一键 | 附加定位 |
| --- | --- | --- |
| 交易 | 网络标识 + txid | 区块 hash、高度、采集时间 |
| 输出 | 网络标识 + txid + vout.n | 金额 sat、脚本原始 hex |
| 花费边 | 前序 txid:vout → 当前 txid:vin_index | 两端交易和区块证据 |
| 地址关联假设 | 网络标识 + 地址组合 + 假设编号 | 方法、前提、反例、置信范围 |

保留 `blocktime/time` 的 UNIX 秒原值，再转换成 UTC。区块时间不是用户点击发送或聊天发出时间；同一区块内的交易也不能靠同一个时间值建立先后关系。需要精确设备行为时间时，继续核对应用记录、网络日志和系统时间偏差。

Bitcoin 确认数提供查询时的链上深度，不是绝对不可逆承诺。采集后发生重组时，旧交易可能改变包含区块或暂时失去确认。保留旧快照，并使用活跃链区块 hash 和新的包含关系更新统计；不能直接覆盖旧证据。

## 09 结果验证与常见扣分点

交付前逐项验证：网络标识一致；txid 与 witness hash 未混淆；每个输入的前序输出下标正确；所有金额采用相同单位；完整计入全部输出；手续费与节点提供值一致或解释缺失；区块仍在观察时的活跃链；统计范围和去重口径明确。

| 常见错误 | 正确处理 |
| --- | --- |
| 把前序交易总额当成某个输入金额 | 按 vin 的 txid:vout 精确取值 |
| 把找零排除后计算手续费 | 手续费核算包含所有输出 |
| 缺少 fee 字段就填 0 | 补齐前序金额；不完整则保持未知 |
| 将所有共同输入地址标为同一人 | 保留协作交易反例和身份关联限制 |
| 两个同地址输出被去重成一个 | 按 txid:vout 保存，不按地址去重 |
| 累计流入当作当前余额 | 继续核对后续花费与截止高度 |
| 查询失败就认定交易不存在 | 检查网络、同步、索引、裁剪与区块参数 |
| 地址标签当成身份或定性证据 | 与钱包、设备和账户材料交叉验证 |
| 根据图形分配输入到输出 | 说明采用的是追踪模型及其假设 |
| 金额脚本通过即声称完成链验证 | 分别报告算术、链包含和归属验证结果 |

## 10 可复核的交付表

建议同时交付原始响应清单、前序输出表、当前输出表、花费边表和结论表。每条结论能够回到 `网络 → 区块 → txid → vin/vout → 原始文件 → hash`。

```text
金额表：network / block_hash / height / txid / direction /
        input_or_output_index / prev_txid / prev_vout /
        script_hex / address_if_available / amount_sat / evidence_file

结论表：question / scope / calculation / result / unit /
        confirmed_at_utc / supporting_records / uncertainty
```

钱包私钥、助记词、认证凭据和解锁材料不进入公开稿。只读链上取证不需要为了证明控制权而转币、签署链上交易或向未知地址发送资金。没有复跑材料时，区分“已核对语法”“已离线核算”和“已在指定网络取得响应”，不要合并成一个笼统的“验证通过”。

## 11 原始交易、脚本与见证数据

### 11.1 原始交易 hex 是可以重解码的字节证据

原始交易是一段按协议排列的字节；hex 只是把每个字节写成两个十六进制字符。交易 JSON 是节点对这些字节的解释，还可能附加区块定位与确认状态。调查中同时保存原始 hex 和 JSON，可以发现显示层省略脚本、遗漏 witness 或把字段抄错的问题。

普通交易序列化含版本、输入列表、输出列表和 `locktime`。每个输入含前序输出引用、解锁脚本及 `sequence`；每个输出含整数 satoshi 和锁定脚本。SegWit 序列化还包含标记、标志和各输入的 witness。长度与数量通常用 CompactSize 编码，不能简单每隔固定字符切一个字段；它也不是磁盘格式中所有变长整数的通用编码。

| 原始对象 | 解码后的主要字段 | 核对重点 |
| --- | --- | --- |
| 交易版本与时间限制 | `version`、`locktime`、`vin[].sequence` | 影响规则和可纳入区块条件，不是用户操作时间 |
| 前序输出引用 | `vin[].txid`、`vin[].vout` | 以完整 outpoint 关联，不能按地址猜前序 |
| 解锁材料 | `scriptSig.hex`、`txinwitness[]` | 要结合被花费的锁定脚本解释 |
| 输出 | `vout[].value`、`n`、`scriptPubKey.hex` | 原始金额和脚本不可因没有 address 而丢弃 |
| 交易标识 | `txid`、`hash` | 分清不含 witness 与含 witness 的计算对象 |

下面沿用第 05 节的本地分析节点和 `OUT`，从分析副本 `transaction.hex` 解码；文件中只放一笔完整 hex，不放 JSON 或命令。操作不会广播、签名或改变钱包。

```bash
RAW_HEX=$(tr -d '[:space:]' < './transaction.hex')
[[ "$RAW_HEX" =~ ^[[:xdigit:]]+$ ]] && (( ${#RAW_HEX} % 2 == 0 )) || {
  printf '原始交易应为完整偶数长度hex\n' >&2; exit 1;
}
bitcoin-cli help decoderawtransaction > "$OUT/help-decoderawtransaction.txt"
bitcoin-cli decoderawtransaction "$RAW_HEX" > "$OUT/decoded-raw.json"
sha256sum './transaction.hex' "$OUT/decoded-raw.json" > "$OUT/raw-decode-SHA256SUMS"
```

`decoderawtransaction` 能证明字节可被该版本解析，不能证明签名有效、输入可花费或交易已在活跃链。输出通常不含可独立证明包含关系的 `blockhash`、确认数或完整前序金额。继续按第 05 节补链与前序证据。若手工从原始字节提取 txid，还要处理序列化哈希和展示字节序；不要拿文件的普通 SHA-256 与 txid 直接比较。

**取证考点：** 从 hex 找出输入引用和输出脚本，解释解析结果与链上查询的职责差异。解析成功只是结构层验证；在真实网络验证前保持“保存的候选交易”这一结论。

### 11.2 txid、wtxid 与 SegWit 的差别

SegWit（隔离见证）把输入用于满足花费条件的 witness 另列在交易序列化中。它并没有隐藏收款金额，也没有把整个交易加密。公开链上仍可看到输入引用、输出金额和锁定脚本。

`txid` 按不带 witness 的传统交易序列化计算双 SHA-256；`wtxid` 按带 witness 的序列化计算双 SHA-256。Bitcoin Core 的解码字段 `hash` 对应含 witness 的交易标识。没有 witness 的交易通常两值相同；含 witness 时通常不同。前序输出引用始终使用 `txid:vout`，不能改成 `wtxid:vout`。

实际核对时保留 `txid`、`hash`、原始 hex 和 `vin[].txinwitness`，再查看每个输入花费的前序 `scriptPubKey.type`。witness 数组存在不等于每个输入都是 SegWit；一笔交易可以混合不同类型输入。只改变 witness 的候选序列化可以具有相同 txid、不同 wtxid；这不意味着两个候选都合法或都已确认。反过来，修改输入、输出或其他非 witness 字段通常会改变 txid，SegWit 并不让所有交易修改都保持标识不变。

**取证考点：** 钱包与节点两处 hash 不同，先确认它们是不是在展示不同标识，再判断是否为不同交易。金额追踪使用 outpoint；见证完整性另存 wtxid。仅持有 txid 和输出 JSON，不能声称已经检查完整 witness 字节。

### 11.3 锁定脚本决定能看到多少花费条件

锁定脚本可以理解为“这个输出以后怎样才能被花费”。地址只是某些脚本的便于展示形式；不同模板会公开不同程度的公钥、脚本和花费条件。

| 模板/解码类型 | 创建输出时可见 | 花费时继续检查 | 推断边界 |
| --- | --- | --- | --- |
| P2PKH / `pubkeyhash` | 公钥哈希和模板 | `scriptSig` 中公钥与签名 | 哈希或公钥都不是自然人身份 |
| P2SH / `scripthash` | redeemScript 的哈希 | 普通花费的 `scriptSig` 中披露的 redeemScript；嵌套 SegWit 另看 witness | 未花费时仅凭哈希无法恢复完整脚本 |
| P2WPKH / `witness_v0_keyhash` | 20 字节 witness program | witness 中签名、公钥 | scriptSig 可为空，不能因此认定未签名 |
| P2WSH / `witness_v0_scripthash` | 32 字节脚本哈希 | witness 中实际 witnessScript 与满足条件的栈 | 哈希承诺不等于已披露脚本全文 |
| Taproot / `witness_v1_taproot` | 32 字节输出公钥 | 区分 key path 与 script path | 单一输出公钥不证明单签或单人控制 |
| `nulldata` 等数据脚本 | 数据及脚本字节 | 独立解释编码与上下文 | 文字可能是声明或伪造内容，不能单独当付款身份 |

解码时同时看前序输出的锁定脚本和当前输入的解锁材料；只看当前 `scriptSig` 很容易漏掉 SegWit。保存脚本 hex 后再作反汇编说明，未知模板保留未知，不把它强制转换成常见地址。

Taproot（隐去未使用条件的输出方案）允许走公钥签名路径，也允许披露并执行某条脚本路径。依规则先处理可能存在的 annex：若 witness 至少两项且最后一项首字节为 `0x50`，它属于 annex。去掉 annex 后，单一 witness 项用于 key path；script path 会披露脚本、control block 及其余栈项。不要只用未处理的 witness 数组长度判断路径。

key path 看不到完整备用脚本树，聚合公钥也可能代表多人协作；script path 只披露实际使用的叶子及验证所需路径，不会展开所有其他分支。记录“该次花费披露了哪些条件”，不能写成“还原了钱包全部策略”。不解析 annex/control block、未校验脚本与输出承诺时，报告的只是结构分类。

## 12 PSBT、已签名交易与链上支付阶段

### 12.1 PSBT 是协作交易材料，不是付款回执

PSBT（部分签名比特币交易）像一份可以在构造者、补全者和签名者之间流转的交易工作包。即使文件扩展名为 `.psbt`，也要检查实际字节和格式；标准起始魔数为 `70 73 62 74 ff`。Base64 是常见传递形式，不能把它与最终网络交易 hex 混为一谈。

工作包可以包含待交易输入与输出、前序 UTXO、部分签名、最终解锁材料、脚本和派生线索。它可能尚未补齐，也可能已经包含完整签名；“PSBT”这个名称本身不能判断完成程度。

| 字段 | 应做的关联 | 可以证明到哪一层 |
| --- | --- | --- |
| `tx.vin/vout` | 对比各版本输入和输出 | 交易拟使用的资金和拟支付目标 |
| `inputs[].non_witness_utxo` / `witness_utxo` | 对照前序 txid:vout、金额和脚本 | 包内提供的前序资金材料；仍要核对真实性 |
| `partial_signatures` | 对照对应输入、公钥与 sighash 范围 | 存在部分签名候选，不表示所有输入可执行 |
| `final_scriptSig` / `final_scriptwitness` | 对照该输入脚本要求 | 存在最终解锁材料；存在字段不等于已验证合法 |
| `bip32_derivs` / `global_xpubs` | 对照钱包侧路径与指纹 | 钱包关联线索，不能仅凭包内自报字段确定身份 |

从自己的分析副本读取 Base64 PSBT，向本地分析节点解码，不把包含扩展公钥和派生路径的材料提交给不明在线解码站。沿用第 05 节 `OUT`：

```bash
PSBT_B64=$(tr -d '\r\n' < './transaction.psbt.base64')
bitcoin-cli help decodepsbt > "$OUT/help-decodepsbt.txt"
bitcoin-cli decodepsbt "$PSBT_B64" > "$OUT/decoded-psbt.json"
sha256sum './transaction.psbt.base64' "$OUT/decoded-psbt.json" > "$OUT/psbt-SHA256SUMS"
```

按本机支持的 PSBT 版本解释。v0 工作包中的 unsigned transaction 尚无最终解锁材料，其中展示的 txid 不一定就是最后广播交易的 txid：例如传统输入补入最终 scriptSig 会改变 txid。最稳妥的关联是核对输入 outpoint、输出脚本与金额、版本与 locktime，并在已有最终 raw transaction 时比较最终序列化。包内 `fee` 依赖前序金额是否完整，不能让一个不真实的 UTXO 字段替代链上前序输出。

### 12.2 把“完成付款”拆成五个证据阶段

| 阶段 | 需要的证据 | 不能跳过的核对 |
| --- | --- | --- |
| 已构造 | PSBT、unsigned transaction、客户端草稿 | 仅能描述付款意图 |
| 已具备签名材料 | 部分或最终解锁字段、最终 raw transaction | 是否满足每个输入条件、签名实际覆盖哪些字段 |
| 已提交或传播 | 客户端提交记录、本地节点记录、mempool 快照 | 提交成功不保证其他节点接受、也不保证入块 |
| 已入块 | 交易正文、区块 hash、区块包含关系 | 区块是不是当前活跃链的一部分 |
| 在观察点具有确认深度 | 活跃链锚点、确认数及复核时间 | 确认状态可以随重组变化 |

**实战判读：** 设备中发现写着收款人和金额的 PSBT，而链上只找到不同最终金额的交易，不能直接用草稿金额作到账统计。先保全各版本，定位共同输入、变动输出和最终活跃链记录，再解释是否改款、调整费用或未完成。钱包侧“已发送”和链上“已确认”的时间分别建表，禁止覆盖成同一个支付时间。

## 13 冲突、替换与重组：交易版本怎样关联

### 13.1 RBF 是待确认候选的替换，不是修改已确认区块

RBF（按费用替换）让节点在符合其内存池策略时，用新的冲突候选替换未确认交易。候选 A、B 只要花费至少一个相同 `txid:vout`，便存在输入冲突；“同一地址又发一笔”不足以证明替换。B 可以增加输入、改变找零甚至改收款输出，不能按 A 的草稿金额解释 B。

`sequence < 0xfffffffe` 是传统 BIP125 显式可替换信号；未确认祖先还可能让候选继承信号。但是节点策略会变化，支持 full-RBF 的节点可在符合其他条件时接受没有这一显式信号的替换。Bitcoin Core 28.0 已把 full-RBF 默认配置改为启用。调查旧节点或其他客户端时，保存实际版本和策略证据，不从 `sequence` 的大值推导“绝不可能被替换”。

若候选还在自己的分析节点 mempool 中，可只读保存当前条目；查询失败只证明该节点当时没有可返回条目，不证明全网从未见过它。

```bash
bitcoin-cli help getmempoolentry > "$OUT/help-getmempoolentry.txt"
bitcoin-cli getmempoolentry "$TXID" > "$OUT/mempool-entry.json"
```

重点读 `time`（该节点接收时间）、`depends/spentby`（未确认依赖）、费用与大小；某些版本的 `bip125-replaceable` 仅解释信号且已废弃，不是最终性字段。不要把本地 mempool 接收时间当作全网首见时间。若节点已经删除旧候选，当前 RPC 不能恢复完整替换历史，应转向此前保全的快照、钱包数据库和节点日志。

CPFP（子交易为父交易提费）是另一种方式：子交易花费父交易输出，以较高费用影响整组交易的矿工激励。它增加父子依赖，没有把父交易原来的收款输出直接改成新输出。区分两者才能避免把同一支付及其提费动作统计成两次独立对外付款。

### 13.2 用 outpoint 比较候选，再用活跃链定结果

为每个候选建立一行：`候选txid / 输入outpoint集合 / 输出脚本及金额 / 费用 / 首见材料 / mempool状态 / 包含区块 / 采集时间`。先对输入集合求交集，得到明确冲突点；再比较输出，不使用收款人标签替代脚本比较。

| 观察 | 可作的结论 | 保留的限制 |
| --- | --- | --- |
| A、B 同时引用 P:2 | 有冲突花费候选 | 不自动证明是谁发起了替换 |
| B 输入交集非空且费用更高 | 可能是提费替换 | 仍需节点或钱包历史解释因果 |
| A 无确认、B 当前活跃链包含 | 截止点实际花费以 B 为准 | 不把 A、B 两次输出都计为到账 |
| A 旧区块不再活跃、A 进入新块 | 同一交易改变包含位置 | 旧区块和新快照都保存 |
| A 重组后没有新包含证据 | 当前未证实确认 | 不将旧确认数继续累计 |

重组是节点改变所接受的链分支，和 mempool 替换不是同一层次。恢复交易图时不仅复核根候选，也要复核依赖其输出的后继：父交易未生效时，后继不能作为已经完成的活跃链资金路径。要证明某 outpoint 最终被谁花费，仍需最终交易输入中的精确引用和对应活跃链区块。

## 14 Coinbase、币龄与时间锁的调查口径

### 14.1 Coinbase 是区块中的特殊产币交易

Coinbase 是每个区块中的第一笔特殊交易，用于领取允许的区块补贴与手续费；这里的协议术语与同名商业服务无关。其输入表现为 `vin[].coinbase`，没有普通前序 outpoint，因此不能倒查一个“付款人输入地址”，也不能按输入总额减输出总额计算普通手续费。

核查时保存 Coinbase raw transaction、输出脚本和所属区块。领取上限与该高度的补贴规则、区块其他交易手续费有关；不能把全部输出金额一律称为新发行量，也不能把产块奖励输出地址直接等同于所有矿工身份。矿池后续结算可能是一笔普通交易，不能只因付款来自矿池候选地址就把它认作 Coinbase。

Coinbase 输出具有成熟限制：准备纳入的花费区块高度减去其生成高度必须至少为 100。假设在高度 h 生成，最早可花费的候选区块为 h+100；这是高度差检查，别把包含区块计入的界面确认数和高度差混用。后续重组还可能改变生成高度或使产币交易失效，成熟性应连同活跃链一起核对。

### 14.2 币龄是分析量，不是身份标签

币龄通常描述一个输出从生成到观察或花费之间经历的时间或区块数。报告必须说明算法：按区块高度差，还是按两个区块时间之差；是否乘金额形成币天等指标；是否只统计完整材料内的输出。协议不会给每笔输出一个能证明“同一人持有多久”的标签。

读取前序 `txid:vout` 的生成区块和实际花费区块，计算高度差；时间差另列，保留区块时间误差边界。两个输出金额相同、地址相同或币龄相近，都不能证明资产没有换控制方。未花费输出也不意味着实际控制方一直未变；私钥、托管账户或多签权限可能在链下转移。

**取证考点：** 能证明的是“输出在这些活跃链区块之间未被花费”或“观察范围中未找到花费”，二者因数据完整性而不同。所谓老币移动不自动证明账户解锁时间、设备开机时间或持有人的身份。

### 14.3 locktime 与 sequence 不是点击发送时间

时间锁是对交易或脚本何时允许花费的条件。`locktime` 的绝对锁定值、`sequence` 的相对锁定编码，以及脚本中的锁定条件需要按当时协议规则共同解释；`sequence` 还兼有替换信号等用途，不能见到一个整数就转换成秒。

| 检查项 | 解释顺序 | 常见误判 |
| --- | --- | --- |
| `locktime=0` | 无该字段施加的绝对锁定 | 不代表没有脚本侧或相对时间锁 |
| 非零 `locktime < 500000000` | 解释为区块高度条件 | 不能转换为 UNIX 秒 |
| `locktime >= 500000000` | 解释为时间值；现代相关规则按前一区块的 Median Time Past 核对 | 当前墙钟或包含区块 timestamp 不能直接替代判定时间 |
| 全部输入 `sequence=0xffffffff` | 交易级 nLockTime 被禁用 | 非零 locktime 不一定实际限制入块 |
| 版本至少 2，sequence 的 bit31 未置位 | 进入相对锁定解释，取低16位；bit22 区分区块数与每单位512秒 | 将整个 sequence 当作延迟秒数 |

Median Time Past（过去时间中位数）由相关区块及其祖先最近最多 11 个区块时间计算，并非设备时间。对于相对时间锁还要使用前序输出相关区块的规定基准；币龄的普通 timestamp 差不能替代这项共识计算。需要断言最早可纳入的区块时，按实际规则检查严格比较与高度边界，不能只做一遍日期换算。

读取 `version/locktime/sequence`，并结合前序输出脚本及实际包含高度核对。非零 locktime 可能是钱包构造策略，并不一定实际延迟付款；绝对锁定值还要检查输入 sequence 是否启用相关条件。解析器显示某个时间限制，只表明构造的条件，不表明用户就在该时刻签名或广播。身份时间线优先依靠设备记录、服务记录与采集偏差，链上字段用来约束可包含范围。
