## 01 先界定分析目标与检材

把问题拆成可核验的事实：目标设备和账户是什么、需要确定的时间段、文件或程序是什么、需要交付的结论与证据范围是什么。先列检材清单：完整磁盘镜像、单分区镜像、内存镜像、系统日志、浏览器导出、附件等。记录每件检材的名称、字节数、取得时间、哈希与时区；原件只读，所有提取、修复和试验都在工作副本上进行。

```bash
sha256sum disk.dd memory.raw
file disk.dd memory.raw
mmls disk.dd
```

`mmls` 的 Start 是**扇区偏移**，不是字节偏移。下文以 `2048` 为示例占位值，必须替换为目标分区的真实 Start；单分区镜像通常从偏移 `0` 开始。工具不识别镜像时，先确认格式、分段文件是否齐全，不能把读取失败解释为“无文件系统”。

涉及可移动介质时，按[U盘取证](/knowledge/forensic-usb-evidence/)分别建立主机接入痕迹与介质文件证据，核对设备、卷、用户和具体文件，再使用 MFT、日志及恢复结果解释操作。

## 02 从文件系统定位证据

若取得的是多盘阵列成员，先完成 [RAID 重组取证](/knowledge/forensic-raid-reconstruction/) 中的成员、参数和逻辑数据验证，再分析目标卷。

按“分区 → 目录项 → 元数据地址 → 文件内容”逐层收敛。优先查目录、回收站、快照和文件系统日志，再到未分配空间；这样更容易保留路径与时间上下文。

```bash
fsstat -o 2048 disk.dd
fls -r -p -o 2048 disk.dd > files.txt
fls -r -d -p -o 2048 disk.dd > deleted.txt
metadata_addr=12345 # 替换为 fls 输出的完整元数据地址
icat -o 2048 disk.dd "$metadata_addr" > recovered.bin
sha256sum recovered.bin
file recovered.bin
```

`fls` 列出的地址用于 `icat`；如果文件有多个数据流，应核对地址和流编号。恢复件能打开也不足以证明完整：还要核对格式结构、大小、内部校验和其他痕迹。NTFS 重点看 `$MFT`、`$UsnJrnl`、`$LogFile` 与回收站；ext 系列关注目录项、inode、日志与未分配空间。文件系统时间可能被复制、同步、解压或分析操作改变，必须记录时间字段的实际含义。

## 03 还原账户、执行与访问

Windows 镜像可先定位 `Windows/System32/config/`、`Windows/System32/winevt/Logs/` 和 `Users/<账户>/`；Linux 则从 `/etc/`、`/var/log/`、用户目录、systemd 单元与计划任务入手。对每个可疑事件填写四列：**时间及其时区、证据路径、记录字段、可推出的事实**。

| 要回答的问题 | 优先证据 | 复核方式 |
|---|---|---|
| 谁登录过 | Windows Security 日志或 Linux 登录日志 | 账户、登录类型、来源地址与会话时间一致吗 |
| 程序是否运行 | 进程日志、Prefetch、Amcache、服务/计划任务 | 路径、哈希和相邻日志能否互证 |
| 文件是否下载或打开 | 浏览器历史与下载库、快捷方式、最近使用记录 | URL、保存路径、文件哈希及文件系统变动是否连贯 |
| 文件是否删除 | 回收站、目录项、USN/文件系统日志 | 删除时间、原路径和恢复内容是否一致 |

Windows 的 4624 表示一次成功登录事件，但仍须看登录类型；4625 是失败尝试。4688 依赖进程创建审核配置，未出现不能直接推断程序未运行。只拿到浏览器主数据库时，需一并检查相邻 WAL/日志文件。账户活动也不能直接等同于某个自然人操作。

## 04 有内存镜像时再补运行态

磁盘说明“留下了什么”，内存可能补足当时的进程、连接和已退出或未落盘的对象。运行态和磁盘时间未必一致，先分别固定材料与采集条件。

完整识别、首轮命令和反证流程集中于[内存取证模块](/module/forensics/#memory)：从[采集与识别](/knowledge/forensic-memory/)确认系统和符号，再用[进程与攻击行为](/knowledge/forensic-memory-processes/)核对父进程、启动时间、命令行、路径和连接端点。扫描出的孤立对象可能来自已退出进程或残留，不能单凭一次命中认定持续运行；Unix 系统使用匹配内核的分析流程。

## 05 交付可复查的结论

建议输出一张事件表：`原始时间 → 统一时间 → 证据位置 → 原始字段 → 判断 → 独立印证`。例如“下载数据库有记录”只能说明记录存在；若又看到文件系统写入与程序执行痕迹，才能逐步提高判断强度。保留原始值、提取命令、镜像偏移、恢复件哈希和缺失范围。时间冲突时并列展示证据，说明时区、时钟漂移或同步延迟的可能影响。

## 06 macOS 与程序分析的定位

macOS 同样先分清磁盘、文件系统、内存和应用材料。`bundle` 是目录式应用封装，`plist` 是配置或结构化数据，DMG 是磁盘映像；不能只按扩展名套用 Windows 的解析工具。关注文件属性、挂载卷、应用记录、日志、特定痕迹和内存，在支持的解析环境中核对结构。APFS 见 [镜像与文件系统](/knowledge/disk-evidence/)，内核匹配见 [Unix 内存](/knowledge/forensic-memory-unix/)；不足以读取的加密卷单独标明。

需要判断一个程序的行为时，先保存哈希、文件结构和静态信息，再在独立环境做动态观察。可用 IDA、Ghidra、OllyDbg/x64dbg、dnSpy，以及 Process Monitor / Process Explorer 分别观察代码、托管程序、文件/注册表行为和进程；这些工具的角色不同。PE 结构、API、指令、脚本、脱壳与反编译属于辅助分析能力，具体入口集中在 [Reverse](/module/reverse/)。功能分析、相似性比较和“是否运行过”的痕迹判断分别记录，不能互相替代。

## 07 实战：将下载、执行与删除分开验证

**场景与材料：** 分析一份 Windows 磁盘镜像，并取得同一设备的一份内存镜像。目标是判断某文件是否下载到本机、是否执行、是否随后删除。下面的时间与文件名只是示例，不能代替检材记录。

### 07.1 建立三条独立证据线

1. 用分区表确认目标卷，在浏览器下载数据库中摘录 URL、目标路径、记录状态与原始时间字段。不要把浏览历史中的网页访问直接当成下载完成。
2. 用文件系统目录项或删除项定位 `Users/analyst/Downloads/sample.exe`，记录元数据地址；按本页命令提取文件，计算哈希并检验 PE 结构。文件名相同不足以保证是同一份内容。
3. 在可用的进程创建日志、Prefetch 等记录中查询相应路径，核对执行文件、账户与时间；有内存时再核对进程、父子关系、命令行与连接。把采集时仍在运行和历史上曾运行分别描述。
4. 对回收站、USN 或删除目录项单独分析，确定记录是否指向相同路径或文件对象；删除时间不能由当前文件缺失直接推出。

### 07.2 用事件表解释证据强度

| 示例记录 | 可以先描述的事实 | 下一条印证 |
| --- | --- | --- |
| 10:00 的下载记录指向目标路径 | 数据库保存了该下载事件及状态字段 | 文件写入记录、大小与内容哈希 |
| 10:02 的进程创建记录包含目标路径 | 该会话记录了相应程序的进程创建 | 完整命令行、进程身份、执行文件哈希及内存 |
| 10:05 出现相关删除记录 | 文件系统记录了相应对象的删除或移除 | 回收站原路径、元数据地址、恢复内容 |

先统一时间单位和时区，再比对事件先后。仅有下载记录时，结论应止于“发现下载记录”；只有路径、对象/内容和时间关联成功，才将其组合成下载—执行—删除过程。若只有磁盘而无内存，仍可完成持久化痕迹分析，并如实标注当前进程状态不可见。
