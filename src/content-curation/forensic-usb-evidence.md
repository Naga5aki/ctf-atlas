## 01 先建立设备、卷、用户与文件四条证据线

U 盘取证通常面对两种材料：**计算机镜像**回答某设备是否接入、哪个用户留下访问痕迹；**U 盘镜像**回答卷内有什么文件、哪些对象被删除、内容能否恢复。将两者连起来，才能进一步讨论文件是否从计算机复制到 U 盘、是否打开、改名或删除。只有 U 盘镜像时，通常不能确定它接入过哪台计算机、谁执行了复制；只有主机镜像时，也不能据此还原 U 盘全部内容。

| 实战目标 | 首查对象 | 需要补齐的关联 |
| --- | --- | --- |
| 找到设备型号、序列号和卷 | SYSTEM、设备安装日志、卷标识、分区结构 | 设备实例 → 磁盘 → 卷，不能只按盘符合并 |
| 判断接入时段和关联用户 | 设备属性时间、适用事件日志、用户 Hive | 时间字段的真实含义、SID、会话和记录覆盖范围 |
| 找出打开或保存的文件 | LNK、Jump Lists、应用 MRU、浏览器下载、文件系统 | 目标卷标识、路径、对象编号、内容哈希 |
| 解释删除、改名和恢复 | NTFS 的 MFT、USN、LogFile；FAT/exFAT 的目录项和分配信息 | 操作事件与对象身份、是否被覆盖、恢复内容完整性 |
| 判断是否复制到另一介质 | 两端文件、元数据、用户与应用活动 | 内容一致性、目标写入过程和源读取线索；保留其他来源的可能 |

建议记录四组标识：设备实例路径/硬件序列号；镜像、分区与卷标识；主机用户 SID；文件路径、文件引用与哈希。硬件序列号、NTFS 卷序列号、卷 GUID、磁盘签名和历史盘符分别填写，不把不同命名空间里的“序列号”当成同一个值。

### 01.1 首轮操作与材料保全

1. 固定主机和 U 盘镜像的名称、字节长度、哈希、采集时间和坏扇区记录。实际介质采集采用适用的写保护方式，工作输出另存；不把插到分析机之后产生的记录纳入历史。
2. 确认拿到的是整盘镜像、单分区镜像、逻辑文件导出还是镜像分段。整盘通常还要解析分区起始位置；单分区从卷起点解释，不能再次加分区偏移。
3. 识别实际文件系统。NTFS 有 `$MFT`；FAT32 和 exFAT 使用各自目录项及分配结构，**没有 NTFS MFT**。U 盘是可移动介质，不代表它一定使用 FAT32。
4. 主机侧保全 SYSTEM、SOFTWARE、每个相关用户的 NTUSER.DAT/UsrClass.dat 及相邻事务日志，另取设备安装日志、相关 EVTX、Recent/Jump Lists、应用数据和系统卷元数据。U 盘侧保全卷引导区、目录结构、分配信息及需要的 NTFS 元数据。
5. 将“设备接入”“卷可访问”“用户访问路径”“文件内容存在”“操作已发生”分开记录。使用统一 UTC 时间线，另保留原时区、原始时间与显示设置。

在 Kali/Linux 的工作副本上可先查看分区与文件系统；下面的 `2048` 只是构造的分区起始扇区，需替换成实际值，并确认工具所用扇区大小：

```bash
sha256sum evidence.img
mmls evidence.img
fsstat -o 2048 evidence.img
fls -r -p -o 2048 evidence.img > file-list.txt
```

从目录列表取得实际元数据地址后再提取目标；`icat` 的参数必须来自该卷解析结果，不能把 XFW 的内部编号直接代入。`fls -r` 不递归已删除目录，因此还需单独检查删除目录及其他恢复结果。镜像/卷层次、分区和文件系统识别的通用步骤见[镜像与文件系统](/knowledge/disk-evidence/)。

### 01.2 FAT32/exFAT U 盘的分析分支

确认不是 NTFS 后，把分析重点转到该格式的目录项、文件名、起始簇、逻辑长度及分配结构。FAT32 检查目录与 FAT 簇链；exFAT 则联合文件目录项组、Stream Extension、名称条目、Allocation Bitmap 和 FAT。没有 MFT 不是异常，也不能靠改扩展名让 MFTECmd 按 NTFS 解析。

exFAT 的 `InUse` 是目录项 EntryType 的最高位；清除后对应结构是未使用项，其他字段可能残留，但不能当作有效当前文件直接引用。`NoFatChain=1` 表示连续分配，按 FirstCluster 和 DataLength 推算簇数；为 0 时按有效 FAT 簇链解释。它和“整个卷上没有 FAT”不是同一含义。

检查当前分配位图、候选目录项组及目标内容是否互相吻合；恢复旧项时记录覆盖与碎片风险。FAT 系列时间与 NTFS 的 UTC FILETIME 不同；exFAT 还保存 UTC offset/有效性信息，缺失或不可信时保留原始值及解释条件。恢复出的内容都要检查格式、字节长度和哈希，不能只凭名字正确判定成功。

## 02 设备识别：从设备实例关联到历史卷

U 盘镜像能回答介质中有哪些文件、删除记录是否还在；主机镜像能回答系统识别过什么设备、哪些账户留下了相关痕迹。两者应分别分析后关联。只有主机上的 USB 使用记录，不能据此列出 U 盘全部文件；只有 U 盘镜像，也通常不能据此认定谁在某台电脑上复制了文件。

先列出待回答的问题和证据缺口：设备是否接入过这台主机；系统首次安装和最后识别的时间；当时有哪些登录会话；账户是否访问了卷内文件；目标文件是否被写入、删除或重命名。每个结论保存原始路径、设备实例路径或卷标识、记录号、时间类型、原始值、解析工具与版本。不要把不同问题压缩成一个“U 盘使用时间”。

### 02.1 优先导出的主机证据

以下是检材内的 Windows 路径，盘符以原系统为准。将导出的文件放在分析目录，使用离线解析器读取；不要对分析机自己的注册表作查询后误记为检材结果。

| 证据 | 检材位置 | 优先用途 |
| --- | --- | --- |
| SYSTEM、SOFTWARE | `C:\Windows\System32\config\` | 设备枚举、卷挂载、系统时区与账户配置关联 |
| 用户注册表 | `C:\Users\<账户>\NTUSER.DAT` | MountPoints2、最近文档、打开/保存对话框痕迹 |
| 用户类注册表 | `C:\Users\<账户>\AppData\Local\Microsoft\Windows\UsrClass.dat` | ShellBags 和目录交互 |
| 注册表事务日志 | 对应 hive 同目录的 `.LOG1`、`.LOG2` 等 | 在工作副本上恢复一致状态；注明有无日志重放 |
| 设备安装日志 | `C:\Windows\INF\setupapi.dev.log` 及可用的旧日志 | 设备/驱动安装与更新段落 |
| 事件日志 | `C:\Windows\System32\winevt\Logs\` | 设备识别、磁盘分区诊断、会话和已有审计 |
| Recent 快捷方式 | `C:\Users\<账户>\AppData\Roaming\Microsoft\Windows\Recent\` | 文件路径、目标卷、访问线索 |
| 自动 Jump Lists | 上述 Recent 目录下 `AutomaticDestinations\` | 按应用关联的最近文件与 DestList 条目 |
| 自定义 Jump Lists | 上述 Recent 目录下 `CustomDestinations\` | 应用自定义任务、固定项目及嵌入快捷方式 |

若文件系统是 NTFS，另导出主机与 U 盘各自的 `$MFT`、可用的 `$Extend\$UsnJrnl:$J`、`$LogFile` 和回收站内容。卷上没有启用 USN 日志、日志已轮转，或 U 盘是 FAT/exFAT 时，不应写成“缺日志等于没有文件操作”。

### 02.2 设备标识：不要把五种号码当成同一个序列号

| 标识 | 指向什么 | 关联时的边界 |
| --- | --- | --- |
| VID/PID、型号与版本 | 设备类型或产品系列 | 同型号设备可完全相同，不能独立识别一只 U 盘 |
| 设备实例路径、设备报告的字符串 | 某一枚举器下的设备实例 | 可能是设备报告、接口桥接器报告，或与端口有关的生成值 |
| Windows 卷 GUID | 本系统识别的卷/挂载名称 | 与文件系统卷序列号不同，不直接等于硬件序列号 |
| 文件系统卷序列号 VSN | 某个文件系统卷 | 格式化可能改变；复制镜像可能复制；存在碰撞 |
| MBR 磁盘签名、GPT 磁盘/分区 GUID | 磁盘或分区身份线索 | 与设备实例及 VSN 分开记录；克隆和重分区会影响解释 |

USB 外置盒可能报告盒子的标识，而不是盒内硬盘标签上的编号。同一硬盘换转接器后，主机记录的字符串也可能改变。保留每个来源的原字段名；有实体设备时，在证据保护条件下结合标签、描述符和介质结构核对，不能把工具里所有 `SerialNumber` 都改名为“厂商唯一序列号”。

### 02.3 离线枚举 USBSTOR、USB 与 UASP

打开 SYSTEM 工作副本，先读取 `SYSTEM\Select\Current`，确定当前控制集对应的 `ControlSet00n`。离线 hive 通常不能直接把在线别名 `CurrentControlSet` 当作真实键名；也不要默认永远是 `ControlSet001`。将所用控制集记录在报告里。

检查这些分支：

```text
SYSTEM\ControlSet00n\Enum\USBSTOR
SYSTEM\ControlSet00n\Enum\USB
SYSTEM\ControlSet00n\Enum\SCSI
SYSTEM\MountedDevices
SOFTWARE\Microsoft\Windows Portable Devices\Devices
```

在 USBSTOR 中逐个读取设备类型/厂商/型号/版本层及其下面的实例层，保存 `FriendlyName`、`DeviceDesc`、`HardwareID`、`Service`、`ContainerID`、完整实例路径和时间属性。USB 分支补充 VID/PID、父子实例等信息。不同枚举层不必使用完全相同的字符串，后缀还可能包含逻辑单元信息，不能简单按子键个数统计物理 U 盘数。

部分使用 UASP 的 USB 存储设备会在 SCSI 枚举分支留下磁盘层记录。USBSTOR 没找到时，继续查看 SCSI 的磁盘实例，通过 USB 父实例、服务/驱动、设备属性和事件中的父设备路径建立关联。SCSI 里也有内部磁盘，不能把所有 SCSI 实例都归为 U 盘；USB 3 接口也不意味着设备一定使用 UASP。

`ContainerID` 等字段可帮助关联设备组成部分，但应与实例路径和其它证据核对后再归并。最终使用“一只设备—多个实例—一个或多个卷”的表，不用“一行注册表=一个实体设备”的计数方法。

## 03 主机接入时间：安装、到达与移除分别核对

### 03.1 首次安装、最近安装与最近到达是三件事

这组属性以 Windows 8 以后常见布局为主；Windows 10/11 仍按实际 Hive 与事件复核，旧系统可能缺少部分属性。

设备实例的时间属性常见于：

```text
SYSTEM\ControlSet00n\Enum\USBSTOR\<设备类型及型号>\<实例>\Properties\{83da6326-97a6-4088-9453-a1923f573b29}\0064
SYSTEM\ControlSet00n\Enum\USBSTOR\<设备类型及型号>\<实例>\Properties\{83da6326-97a6-4088-9453-a1923f573b29}\0065
SYSTEM\ControlSet00n\Enum\USBSTOR\<设备类型及型号>\<实例>\Properties\{83da6326-97a6-4088-9453-a1923f573b29}\0066
SYSTEM\ControlSet00n\Enum\USBSTOR\<设备类型及型号>\<实例>\Properties\{83da6326-97a6-4088-9453-a1923f573b29}\0067
SYSTEM\ControlSet00n\Enum\USB\VID_<VID>&PID_<PID>\<实例>\Properties\{83da6326-97a6-4088-9453-a1923f573b29}\<属性号>
SYSTEM\ControlSet00n\Enum\SCSI\<磁盘类型及型号>\<实例>\Properties\{83da6326-97a6-4088-9453-a1923f573b29}\<属性号>
```

| 属性编号 | 含义 | 能支持的表述 |
| --- | --- | --- |
| `0064` / `0x64` | InstallDate，实例最近安装/驱动更新的时间 | 最近安装事件；不能无条件当首次接入 |
| `0065` / `0x65` | FirstInstallDate，实例首次安装时间 | 本系统对该实例首次安装的线索 |
| `0066` / `0x66` | LastArrivalDate，最近到达/重新识别时间 | 最近一次系统识别该实例的线索 |
| `0067` / `0x67` | LastRemovalDate，最近移除时间 | 系统观察到移除的线索，可能缺失 |

这些数值按 FILETIME 解析并保留 UTC。不同系统版本可能将数据放在属性键默认值或下一层 `00000000\Data` 中，应按检材结构读取，不能从键 LastWrite 时间替代属性值。键的最后写入只表示键有变化，也可能受安装、更新或其他操作影响。

首次安装不等于设备出厂、首次在任何计算机使用或首次由某人接触。系统重装、删除设备记录后重新识别、端口相关实例变化等，都要作为可能解释检查。设备仍插着时重启，Windows 也可能更新到达时间；遇到与启动时刻相邻的 LastArrivalDate，先核对启动/关机事件。移除值为空时检查是否带盘关机、突然断电、日志或属性缺失，不能直接宣布“现在仍插着”。

时间顺序异常时，先查时间编码、时区、系统时钟变化、实例匹配及版本行为，再考虑篡改。旧系统上验证过的属性更新规则，不自动成为所有新版本的绝对规则。

### 03.2 SetupAPI 提供安装语境，而不是完整插拔账本

`setupapi.dev.log` 记录设备和驱动安装操作。按已知实例字符串、VID/PID 或设备名称检索后，保存完整安装段落，包括段头、Section start/end、实例路径、驱动处理与退出状态。相同设备的驱动更新也可能形成新段，不能把段落数统计为插拔次数。

在 Kali 的工作目录中，可先对导出文本定位：

```bash
rg -n -i -F -C 8 'DEMO-USB-A' evidence/host/setupapi.dev.log
```

`DEMO-USB-A` 是构造占位符，实际使用时替换为检材中读到的设备实例字符串。命中后的固定上下文仅用于定位，应回到日志段落首尾补齐。日志时间一般需要按原机本地时间和当时的时区/DST规则解释；没有显式时区的值不能直接追加 `Z` 当 UTC。

未命中时记录“当前取得的日志中未见匹配段”。日志可能轮转、截断或设备早已安装；这个结果不能排除更早连接。

### 03.3 卷挂载：相同二进制数据可以关联，盘符不宜长期追踪

在 `SYSTEM\MountedDevices` 中保存：

```text
\DosDevices\E:
\??\Volume{<卷GUID>}
```

若两项的完整二进制值相同，可支持它们在该 hive 状态中指向同一卷。保留原始数据，并识别它属于可读设备路径、磁盘签名加分区偏移、分区标识或其它形式；不能把所有值都强行 UTF-16 解码后再搜“序列号”。

这是系统的挂载名称映射，不能直接读出每一次连接时用过的盘符。另一卷可能后来复用了 `E:`，一个卷也可能曾分配不同盘符。建立“卷标识 + 时间窗口”的关联，优先用卷序号、GUID、分区起点和事件互证，而不是看到 `E:\` 就归到某只 U 盘。

### 03.4 EVTX：先看 Provider、频道和原始字段，再解释事件编号

重点检查：

```text
Microsoft-Windows-Partition%4Diagnostic.evtx
Microsoft-Windows-Kernel-PnP%4Configuration.evtx
Microsoft-Windows-DriverFrameworks-UserMode%4Operational.evtx
System.evtx
Security.evtx
```

`Microsoft-Windows-Partition/Diagnostic` 的 1006 事件可能包含磁盘型号、设备报告标识、容量、BusType、父设备路径、分区信息与 `Vbr0` 等卷引导记录片段。这是设备与卷之间的重要桥梁；即使后来格式化，旧事件仍可能保留历史卷信息。该频道也记录内部磁盘，开机、设备变化和移除也可能出现相关事件。不能将“所有1006”直接当作“所有 U 盘插入”；应查 BusType、ParentId、容量、VBR是否存在、同实例前后记录以及启动/移除语境。

每条记录保存 Provider、Channel、EventID、EventRecordID、`TimeCreated/SystemTime` 和设备字段。同一事件编号在不同 Provider 下不是同一个含义。事件 XML 的系统时间通常是 UTC，而查看器可能已显示为本地时间，需防止二次加时区。

1006 内有效 VBR 的卷序号可与 LNK 和 Jump Lists 对照。卷序号在不同文件系统中偏移和宽度不同；NTFS 引导记录中的完整卷序号为 8 字节，而标准 LNK `VolumeID.DriveSerialNumber` 是 4 字节，匹配时明确比较低 32 位，不把其与硬件设备序列号混为一谈。保留完整卷序号和用于关联的32位表示。

事件中的 VBR 可能不完整或为空，不能读取不存在的分区数据。一个设备可能有多个卷，要逐个关联。较早研究仅验证过特定 Windows 版本、MBR/未分区及有限卷数；面对 GPT、多分区、外置 SSD 与转接盒时，按实有字段与介质结构验证，不假定工具能恢复所有历史卷。

Kernel-PnP 可补充设备安装、配置或启动语境；DriverFrameworks 的记录依系统、设备类型和频道是否启用而变化。审计事件 6416 属于 PNP Activity，说明外部设备被识别/启用等；它经常由 SYSTEM 注册设备，事件中的 SYSTEM SID 不是“实际插盘者”。

## 04 用户与文件活动：把访问、复制和删除分别互证

### 04.1 用户关联：MountPoints2 是账户语境，文件痕迹才推进到具体行为

先用 SOFTWARE 中：

```text
Microsoft\Windows NT\CurrentVersion\ProfileList\<SID>\ProfileImagePath
```

确认每个 SID 对应哪个用户配置文件，再分别分析各账户的：

```text
NTUSER.DAT\Software\Microsoft\Windows\CurrentVersion\Explorer\MountPoints2
```

MountPoints2 可能包含卷 GUID、盘符和网络路径。先把卷 GUID 与 SYSTEM 挂载映射关联，确认是目标存储卷，再描述“该账户配置文件留有该卷的挂载/识别痕迹”。不能把每个键 LastWrite 当作一次文件访问时刻，也不能因此单独断定谁亲手插盘。

围绕连接窗口核对 Security 中取得到的登录/解锁与登出事件、日志中的账户 SID、Recent/Jump Lists 所属配置文件。共享账号、远程会话、自动任务以及由服务账户运行的程序，都可能改变“账户=自然人”的解释。

| 用户痕迹 | 优先读取内容 | 合理结论与限制 |
| --- | --- | --- |
| Recent LNK | 目标路径、VolumeID中的VSN/卷标、链接自身时间、目标内嵌时间 | 支持某用户语境中的文件/路径关联；先区分自动与手建/复制过来的快捷方式 |
| Jump Lists | AppID、类型、目标路径、嵌入 LNK、DestList 的条目访问时间/顺序及 PinStatus | 推进到特定应用关联；固定项目、应用任务不直接等于每次打开 |
| ShellBags | 目录路径、Shell Item、MRU序与相关键时间 | 支持目录曾与 Shell 交互；不能单独证明目录内某文件打开或复制 |
| RecentDocs / OpenSavePidlMRU | 相关文件名、路径、MRU位置与键时间 | 佐证最近文档或打开/保存对话框选择；不等于写入完成 |
| 已有文件审计/终端遥测 | 账户、进程、对象路径、实际访问权限、读写/删除事件 | 可推进到具体文件操作；仍需确认操作方向与完成情况 |

ShellBags 中保存的目录元数据时间与注册表键更新时间意义不同；MRU父键的 LastWrite 不可无条件分配给它的所有子目录。选择文件夹也可能产生痕迹，具体行为随版本变化。LNK 的目标创建/修改时间是目标的元数据副本，不能称为“此次打开时间”；链接自身被复制或重建也会影响解释。

USB 外置盘可能报告为固定盘。筛选 LNK 时可以利用 DriveType，但不能只保留 `Removable` 而漏掉已由设备链证实来自 USB 的 `Fixed` 卷。

### 04.2 复制、打开和删除分别怎样互证

“同文件名 + 接入窗口相近”只是调查线索。若主机与 U 盘中都取得完整文件，先比较字节长度与强哈希，再检查版本内容、目录结构与时间窗。强哈希相同支持取得的两份文件字节一致，但不单独证明复制方向、操作时间或操作者。

要支持主机向 U 盘写入，优先形成：目标卷身份已识别 → 对应连接窗口 → 账户/进程的目标文件写入记录 → U 盘目录项/MFT与可用日志中的创建/写入状态 → 文件内容对照。仅有目标卷中新建文件，也应考虑应用直接另存、解压、同步或先前就已存在等解释。

NTFS 目标卷中 `FILE_CREATE`、`DATA_EXTEND`、`DATA_OVERWRITE`、`CLOSE` 等变化可用于构建写入过程，但 USN 本身不保存复制起点的文件路径与操作者，也可能合并原因或因轮转丢失。`CLOSE` 不代表一次完整文件复制事务的独立证明；源卷可能只有读取而没有相应 USN 写变化。不要为了查复制而寻找不存在的统一“COPY”记录。

若取到了已生效的文件/可移动存储审计，Security 4663 能表示某访问权限被实际使用。查看 `ObjectType`、`ObjectName`、`SubjectUserSid`、`SubjectLogonId`、`ProcessId`、`ProcessName`、`HandleId` 和 `AccessMask`：文件对象的 `0x1` 可表示 ReadData，`0x2` 表示 WriteData，`0x10000` 表示 DELETE；对目录对象，某些权限位有列目录/添加文件等不同含义。权限掩码要按位解析，不能只做字符串相等。

把复制起点的文件读、目标文件写、同一会话/进程、文件身份和接入窗口合并，结论才能推进到复制行为。单次 4663 写入也可能是另存或修改，不能写成“已复制完整文件”；4656 请求句柄也不等于对应文件操作已完成。日志没有事前启用或已覆盖时，应说明证据缺口，事后开启审计无法补回过去记录。

证明打开某文件时，以账户下的自动 LNK、应用 Jump List、应用最近文档和文件内容关联互证；保守表述“存在该账户访问/使用该路径的痕迹”，避免自动升级为“阅读过全部内容”。无此痕迹不能排除命令行复制、未维护最近列表的应用或日志清理。

证明删除时，检查 U 盘目录/MFT已删除状态、可用的 USN删除记录及回收站。已删状态不是删除时刻；MFT的常见MACB时间不提供一个通用独立删除时间。若文件经回收站处理，`$I`可提供原路径/大小/删除时间等，`$R`为对应数据；可移动介质可能直接删除，不能要求必有回收站痕迹。恢复出内容还要确认原路径、记录序号、数据是否已覆盖及完整性，不能把恢复成功当成删除者已确定。

### 04.3 交付前核对

每个结论至少附可定位的记录、字段与时间解释。将“直接读到的事实”“多个来源支持的推断”“未取得证据的部分”分开列出。设备识别、卷对应、账户活动、文件读写与删除五个阶段有任何断点，都应在结论中保留，不凭选项、名称或软件汇总标签补齐。

## 05 NTFS 布局与 MFT 的证据范围

MFT（Master File Table，主文件表）是 **NTFS 卷自己的文件系统元数据**。它用记录描述文件、目录和 NTFS 的元数据文件；记录内的属性保存名称、时间、数据流，或指向卷上其他位置的数据。一个文件可以占用一个基础记录和多个扩展记录，因此“一条记录就是一个完整文件”并不总成立。

U 盘可以格式化为 NTFS、FAT32 或 exFAT。**FAT32、exFAT 没有 NTFS 的 `$MFT`、`FILE` 记录与 `$I30` 属性体系**，应按各自的目录项和分配结构分析；在它们的未分配空间发现旧 NTFS 残留，也不意味着当前文件系统变成了 NTFS。
主机系统盘的 `$MFT` 描述主机 NTFS 卷上的对象。U 盘若是 NTFS，它有另一份 `$MFT`；若是 FAT32/exFAT，就不存在可按本节解读的当前 U 盘 MFT。主机 MFT 中发现一个快捷方式、缓存文件或复制到本机的文件，只能先说明该**主机卷上的对象**；它不能替代 U 盘的文件目录，也不能单凭相同文件名证明 U 盘原文件被打开或复制。记录来源时，应同时写明设备、卷、镜像分区偏移和提取路径。

本节偏移表以 **NTFS 3.0/3.1** 为范围，详细字节示例采用 NTFS 3.1、1024 字节记录和 512 字节保护步长。NTFS 版本不是 Windows 产品版本；实际卷的记录大小、簇大小和版本应从该卷核实。

### 05.1 典型基础元数据记录

在 NTFS 3.x 中，MFT 开头的这些记录帮助建立卷布局与解析上下文：

| 记录号 | 对象 | 用途 |
| ---: | --- | --- |
| 0 | `$MFT` | 整张记录表及其记录分配位图 |
| 1 | `$MFTMirr` | MFT 开头关键记录的冗余副本 |
| 2 | `$LogFile` | 文件系统元数据事务日志，不等于所有用户操作日志 |
| 3 | `$Volume` | 卷名称、版本与状态等信息 |
| 4 | `$AttrDef` | 属性类型定义与相关规则 |
| 5 | 根目录 | 当前卷目录树的起点 |
| 6 | `$Bitmap` | 卷簇分配位图 |
| 7 | `$Boot` | 卷引导区与文件系统参数 |
| 8 | `$BadClus` | 标记坏簇的元数据 |
| 9 | `$Secure` | 集中保存的安全描述符及索引 |
| 10 | `$UpCase` | 名称比较使用的大写映射表 |
| 11 | `$Extend` | 扩展元数据对象所在目录 |

前 16 个槽为系统保留范围，其中 12–15 不要猜成用户文件。后续系统对象应按实际名称、属性、目录索引和完整引用定位；不要把某个测试卷中 `$UsnJrnl` 等对象的记录号当作固定常量。这里的 9 号 `$Secure` 适用于 NTFS 3.x，不外推到早期 NTFS。

## 06 读记录：头部、属性、身份与时间

### 06.1 从卷开始找到记录，而不是把整个磁盘都当成 NTFS 卷

先确定文件系统卷在镜像中的起点，再读 NTFS 引导区提供的簇大小、`$MFT` 起始 LCN 和文件记录大小。记录大小常见为 1024 字节，但不可硬编码：NTFS 引导区的记录大小编码和 Windows 对大记录格式的支持都要求按实际值处理。在线卷信息也有 `BytesPerFileRecordSegment` 字段；这只是尺寸的另一种复核来源，不应把分析机卷信息当成证据卷信息。
读到记录 0 后，继续解析 `$MFT` 自身的无名 `$DATA`。这条流才描述整张 MFT 的布局，可能包含多个非连续 run。第 `n` 条记录在 **MFT 逻辑流**中的偏移为 `n × 记录大小`；只有映射结果确认这一段连续时，才能把它换成“卷起点 + MFT 起点 + 记录偏移”。不能拿第一段 MFT 的物理起点一直线性加下去。

下面的多字节整数使用小端序。把 `38 00` 读成 `0x0038`，把 `00 04 00 00` 读成 `0x00000400`，不要按屏幕上的字节顺序直接当成十六进制数值。

### 06.2 FILE 记录头：所有偏移均相对记录起点

| 偏移 | 长度 | 字段 | 实际读法与意义 |
| --- | ---: | --- | --- |
| `0x00` | 4 | 签名 | 通常是字节 `46 49 4C 45`，即 `FILE`；命中签名后仍须验证其他字段 |
| `0x04` | 2 | USA offset | Update Sequence Array 的起点，相对本条记录，不是相对镜像 |
| `0x06` | 2 | USA count | 数组中 16 位字的数量，包含第一个更新序列值；数组字节数为 `count × 2` |
| `0x08` | 8 | LSN | 与 `$LogFile` 元数据事务相关的序列值，不是时间，也不是文件引用序列号 |
| `0x10` | 2 | Sequence number | 本记录的代际序列号；关联当前对象时核对代际，已删除残留结合释放规则 |
| `0x12` | 2 | Hard link count | 基础记录的硬链接计数，不应直接拿 `$FILE_NAME` 属性数量代替 |
| `0x14` | 2 | First attribute offset | 第一条属性的起点，相对本记录；不要假定固定为 `0x38` |
| `0x16` | 2 | Flags | `0x0001` 为正在使用；`0x0002` 表示文件名索引存在，通常用于目录 |
| `0x18` | 4 | Bytes in use | 本记录当前有效区域的大小；它不是文件内容大小 |
| `0x1C` | 4 | Bytes allocated | 记录槽的大小，应与实际记录尺寸交叉核对 |
| `0x20` | 8 | Base file reference | 基础记录为 0；扩展记录保存它所属基础记录的文件引用 |
| `0x28` | 2 | Next attribute ID | 本记录内后续属性实例的编号信息，不能当作全卷文件编号 |
| `0x2A` | 2 | 对齐/保留区域 | NTFS 3.1 常见头部对齐字段，不作为行为证据 |
| `0x2C` | 4 | Record number | NTFS 3.1 中的本记录编号；辅助复核槽位置，不能取代来源和布局验证 |

仅有 `FILE` 字符串不能证明是一条有效当前记录。复制出来的文件、旧记录残留、截断数据和随机内容都可能含有这个字符串。至少检查记录尺寸、USA 范围、属性起点、使用区大小、属性边界，以及记录位置与记录号是否自洽。

### 06.3 USA/fixup：读取属性之前先恢复被替换的尾部字

NTFS 的多步长传输保护把原来的尾部两字节临时存进 USA，再在各保护步长末尾写入同一个更新序列值。它用于检查多段写入是否一致，**不是密码、校验和或文件历史日志**。这里的更新序列值也不要与 `$UsnJrnl` 中的 USN 混为一谈。

读取盘上原始记录时，先保留原始字节副本，再按以下顺序处理：

1. 从 `+0x04` 和 `+0x06` 取得 USA 位置与元素数，确认数组未越过记录边界，且不会与第一个保护尾字冲突。
2. USA 第一个 16 位字是更新序列值。对本节的 1024 字节、512 字节步长示例，检查记录 `0x1FE–0x1FF`、`0x3FE–0x3FF` 是否都等于它；预期有两个保存字，因此元素数为 3。
3. 所有比较通过后，把 USA 后两个保存字分别放回 `0x1FE`、`0x3FE`；在这个修复后的副本上解析属性。不要修改证据原件。

有任一尾字不匹配，就不能宣称完整记录通过验证。先检查获取过程、起点、截断、尺寸以及来源是否已经做过 fixup，再判断损坏情况。提取工具可能提供盘上字节，也可能提供已修复的视图，必须先查明；对已修复字节再次按原始记录处理，会产生误判。本节所述序列步长为 512，不应因为设备标称 4 KiB 物理扇区就自动把此例的检查点改成 4096。

### 06.4 文件引用、扩展记录与硬链接：不要只追记录号

NTFS 的 8 字节文件引用由低 48 位记录号和高 16 位序列号组成。可写为 `记录号-序列号` 便于核对，例如字节 `2A 00 00 00 00 00 07 00` 指向 `42-7`；`FRN & 0x0000FFFFFFFFFFFF` 得到记录号，`FRN >> 48` 得到序列号。
已删除记录的头部序列号可能在释放时已经递增，而解析器的历史目录键可能采用递增前代际。先核对原始头、字段定义和日志时间；不能把所有差一的引用直接判为复用，也不能机械改值强行配对。

删除、释放与复用过程中序列号会改变。按该结构定义，在记录释放时递增；它是循环使用的 16 位值，不能当作无上限的精确复用计数。目录项保存的 `42-7` 若遇到当前槽 42 的序列号为 8，就应标记为**陈旧引用或不一致**，不能把当前槽中新文件的内容配给旧文件名。即使序列号匹配，也要继续核对名称、父目录、属性和分配状态；格式化后遗留记录尤其不能直接套进当前卷的目录树。

文件属性放不进一个槽，或非驻留映射太长时，会使用扩展记录。读到 `Base file reference != 0` 的记录，先验证它指向的基础记录；基础记录的 `$ATTRIBUTE_LIST` 再给出属性所在记录、类型、名称、Lowest VCN 等信息。同一数据流可能横跨多条属性记录，必须按 VCN 范围装配，不能只提取基础记录看得见的第一段。

一个文件可拥有多个名称和父目录关系。Win32 长名与 DOS 短名也可能形成两个 `$FILE_NAME`，它们不是两个独立文件或两个独立硬链接。实际硬链接共享同一文件对象和数据流，只允许位于同一卷；删掉一个名称还可能保留其他链接。重建路径时应枚举所有 `$FILE_NAME` 的父引用和 namespace，允许一个 FRN 对应多个路径，并逐级检查父引用的序列号。

### 06.5 属性头：先分清三个“长度”和两套坐标

每条属性从自己的头开始；**属性长度包含头部、可选名称、值或映射以及对齐填充**。下一条属性通常位于 `本属性起点 + RecordLength`，不是靠搜索下一个 `80 00 00 00` 来猜。属性按 8 字节边界对齐，类型 `0xFFFFFFFF` 是属性结束标记；结束标记不能继续当作完整属性头读取。

| 属性头内偏移 | 长度 | 含义 |
| --- | ---: | --- |
| `0x00` | 4 | 类型：`0x10` `$STANDARD_INFORMATION`，`0x20` `$ATTRIBUTE_LIST`，`0x30` `$FILE_NAME`，`0x80` `$DATA`，`0x90` `$INDEX_ROOT`，`0xA0` `$INDEX_ALLOCATION`，`0xB0` `$BITMAP` |
| `0x04` | 4 | `RecordLength`，本条属性记录的总字节数 |
| `0x08` | 1 | 形式：0 常驻，1 非驻留 |
| `0x09` | 1 | 可选属性名长度，按 UTF-16 代码单元计数，不是字节数 |
| `0x0A` | 2 | 可选属性名偏移，相对本属性起点；名称长度为 0 时不要依赖该值 |
| `0x0C` | 2 | 属性标志：低字节为压缩形式；`0x4000` 加密，`0x8000` 稀疏 |
| `0x0E` | 2 | 属性 instance，在该记录内区分属性实例 |

**常驻**（resident）的值直接放在 MFT 记录内，其附加头为：

| 属性头内偏移 | 长度 | 含义 |
| --- | ---: | --- |
| `0x10` | 4 | `ValueLength`，值的字节数 |
| `0x14` | 2 | `ValueOffset`，值起点，相对本属性起点 |
| `0x16` | 2 | 索引标志/保留与填充区域；不作为内容长度使用 |

若属性起点为 `0x110`，`ValueOffset=0x18`，则内容起点是记录内 `0x128`，不是 `0x18`。应先验证 `ValueOffset + ValueLength <= RecordLength`。常驻 `$DATA` 表示内容在 MFT 内；不能因为没有外部数据簇就判定文件内容丢失，也不能用固定“700 字节以下必常驻”之类阈值判断。

**非驻留**（non-resident）的属性记录仍在 MFT 中，实际值通过外部簇存储。常见布局为：

| 属性头内偏移 | 长度 | 含义 |
| --- | ---: | --- |
| `0x10` | 8 | `LowestVcn`，本属性记录覆盖的起始 VCN |
| `0x18` | 8 | `HighestVcn`，覆盖的最高 VCN，端点包含在范围内 |
| `0x20` | 2 | runlist / mapping pairs 偏移，相对本属性起点 |
| `0x22` | 1 | 常见压缩单元指数；`2^指数` 为一个单元的簇数 |
| `0x23` | 5 | 保留/对齐区域，不能据此拼接数据 |
| `0x28` | 8 | allocated size，分配长度信息 |
| `0x30` | 8 | data size，逻辑值长度 / 文件流 EOF |
| `0x38` | 8 | initialized size / valid data length，已初始化的逻辑长度 |
| `0x40` | 8，可选 | 压缩/稀疏布局的额外实际分配长度信息；普通无压缩头不能一律读取这里 |

压缩/稀疏头部存在变体。必须依据标志、头长度和映射偏移识别变体。尺寸字段只应从 `LowestVcn=0` 的首段作全流解释；后续段的同位置字节不能重新当成整个文件大小。逻辑长度、分配长度、初始化长度也不是同一个量：不要把簇尾 slack 或 EOF 之后内容加入文件；未初始化逻辑范围按文件系统语义读出零值，底层可能残存的字节需要另作物理残留报告。压缩、稀疏情况下还须区分逻辑分配长度与实际物理占用。
属性名称与文件名称不同：`$FILE_NAME` 值内的 `evidence.txt` 是目录中的名字；`$DATA` 头内的可选名字是数据流名。无名 `$DATA` 是默认内容流；命名 `$DATA` 是其他数据流（ADS）。列流时分别记录名称、形式、长度和映射；同一文件有多条 `$DATA` 不等于多个文件。

### 06.6 `$SI` 与 `$FN` 四时间：相同格式，不同更新背景

`$STANDARD_INFORMATION`（简写 `$SI`）和 `$FILE_NAME`（简写 `$FN`）都通常提供创建、内容修改、元数据修改、访问四个时间。先通过常驻属性的 `ValueOffset` 找到**属性值起点**，下面的偏移再相对该值计算；不能直接加到 `FILE` 记录头上。

| 意义 | `$SI` 值内偏移 | `$FN` 值内偏移 | 解释边界 |
| --- | --- | --- | --- |
| Creation time，创建 | `0x00` | `0x08` | 文件对象的创建时间；不自动等于内容最初产生时间、首次插盘或首次打开时间 |
| Last write / data modification，内容修改 | `0x08` | `0x10` | 数据流内容的修改时间；不能单凭它区分编辑、复制或程序写入 |
| Change / entry modification，元数据修改 | `0x10` | `0x18` | 元数据或对象变化相关时间；不要与上一行的内容修改混同 |
| Last access，访问 | `0x18` | `0x20` | 受访问时间策略、延迟写回和程序行为影响；不自动等于用户最近双击时间 |

各值为 8 字节小端 FILETIME，表示自 `1601-01-01 00:00:00 UTC` 起的 100 纳秒单位。转换时使用整数运算：`整秒 = ticks // 10000000`，`秒内余数 = ticks % 10000000`，小数秒保留七位。不要先转浮点数或只保留毫秒；例如 `134339328000000007` 应得到 `2026-09-15 08:00:00.0000007 UTC`。保留原始整数；若另显示北京时间，明确标注 `UTC+08:00`。存储精度并不代表行为推断能达到 100 纳秒精度。

`$FN` 的时间与大小是名字/目录索引关联的重复元数据，可能落后于 `$SI` 和实际数据流；多个硬链接的目录展示也可能不同步。不要把两组时间不一致直接判成篡改，不要把 `$FN` 定义成永不变化的“原始时间”。更新时间规则要以目标 Windows 版本和实际操作验证。判断事件时，应对照文件引用、命名操作、相关日志和已知程序行为。
访问时间尤其需要版本边界：NTFS 最多可延迟一小时写回访问时间；较新 Windows 还可采用系统管理策略，是否更新不能只凭操作系统名称推定。取证时核对证据主机的版本与当时配置；分析机当前设置只说明分析机。
`$FN` 值的后半部分还需要读取：

| 值内偏移 | 长度 | 字段 |
| --- | ---: | --- |
| `0x00` | 8 | 父目录的完整文件引用，含序列号 |
| `0x28` | 8 | 重复存储的分配大小，不保证等于当前数据流状态 |
| `0x30` | 8 | 重复存储的实际大小，不应取代 `$DATA` 的逻辑长度 |
| `0x38` | 4 | 文件属性标志，与 `FILE` 头的使用/目录位不是同一套位域 |
| `0x3C` | 4 | EA / reparse 相关字段，按对应标志解释 |
| `0x40` | 1 | 文件名长度，以 UTF-16 代码单元计 |
| `0x41` | 1 | namespace：0 POSIX，1 Win32，2 DOS，3 Win32 与 DOS 共用一个名称 |
| `0x42` | `2 × 文件名长度` | 文件名，UTF-16LE，无须以 NUL 结尾 |

namespace 为 3 不是第三条路径，它说明这个名字同时适用于 Win32 与 DOS。namespace 为 2 的短名也不能自动当作另一个用户文件。解析器应按长度处理 UTF-16 字节并保留异常码元的原始表示，不要用替换字符悄悄合并本来不同的名字。

### 06.7 runlist：把流内 VCN 映射到卷内 LCN

VCN 是**某条属性流内部**的簇编号；LCN 是**该 NTFS 卷内**的簇编号，卷起点的簇号为 0。相同 LCN 在另一卷上没有相同对象意义，也不是整盘的 LBA。

从属性头给出的 mapping pairs 起点读取 runlist，每个 run 的首字节拆成两部分：低 4 位是“簇数量”字段字节数，高 4 位是“LCN 位移”字段字节数。簇数量是正的无符号小端数；LCN 位移是按其字段宽度符号扩展的有符号小端数。首个有物理位置的 run 以 0 为 LCN 累加起点，后续位移相对前一个有物理位置的 run 的**起始 LCN**，不是相对该 run 的结束簇。VCN 则从本属性记录的 `LowestVcn` 开始，随各 run 的簇数累加。首字节为 `00` 时结束。
高 4 位为 0 时没有 LCN 位移字段，表示该范围没有物理 run。对普通稀疏流，这段逻辑内容返回零；它不是指向 LCN 0，也不要因此清零前一个物理 run 的 LCN 累加状态。压缩流同样可能含这种 run：压缩单元中“若干已分配簇 + 剩余无物理映射簇”用于表示压缩后节省的空间，不能把后半段直接零填充后当成解压结果。必须按压缩标志、压缩单元和压缩格式完整还原；NTFS 压缩与 EFS 加密也不能混为一谈。
映射成镜像字节时，公式为 `卷在镜像中的字节起点 + LCN × 每簇字节数`。若读的是分区卷镜像，其起点一般是该文件的 0；若读的是整盘镜像，要加入分区偏移。始终按 **VCN 的逻辑顺序**输出内容，不能把 run 按物理 LCN 从小到大排序。后续扩展属性段要按各段的 `LowestVcn` 及其 runlist 独立解码，再装配同一流。

### 06.8 `$I30`、三类位图与 `$MFTMirr`

目录的 `$I30` 是文件名索引的**属性名称**，不是一个普通用户文件名。目录的 `$INDEX_ROOT` 保存常驻索引根；容量不够时使用 `$INDEX_ALLOCATION` 的索引块，盘上块常见签名为 `INDX`，也有 USA 保护。索引项保存子对象文件引用和 `$FILE_NAME` 形式的索引键；可以拿来复核父子关系、长短名和旧名字，但它不是文件内容备份。解释已分配节点与节点 slack 中的残留时须分开，残留项不能不加说明地加入当前目录列表。

| 对象 | 管理什么 | 不能据此推出什么 |
| --- | --- | --- |
| `$MFT` 的无名 `$BITMAP` 属性 | 哪些 MFT 记录槽当前分配使用 | 某个数据簇内容是否仍完好 |
| 卷元数据文件 `$Bitmap` 的无名 `$DATA` | 哪些卷簇当前分配使用 | 一个未分配簇一定属于哪个已删除文件 |
| 目录中的 `$BITMAP:$I30` 属性 | 哪些索引分配块当前使用 | 每个目录项是否当前有效或何时删除 |

名字都含 bitmap，却不能互换。记录头的 in-use 位、MFT 位图、数据 run 对应的卷位图应交叉核对；冲突可能来自陈旧残留、截取时刻不一致或结构损坏，不能只取其中最方便的一项。
`$MFTMirr` 是 MFT 开头关键记录的冗余副本。通常涵盖前四条，大簇布局可能扩大镜像范围，应以实际 `$MFTMirr` 流长度核验。**它不是整张 MFT 的备份，也不是所有已删除文件的恢复库**。其价值首先是复核/补救 MFT 开头的关键结构；对任意用户记录 42 的恢复，不能期待镜像必然包含它。

### 06.9 删除、格式化与复用：把可证明的事实分层写

删除后 MFT 槽会被标记为空闲并可能复用，MFT 文件本身不因每次删除而缩短。名称、属性或 runlist 的旧字节有机会残留，但“有机会”不等于必然。还应先排除删除的是单个硬链接、文件尚处删除等待状态、或者只发生了改名。
| 观察 | 可作的初步解释 | 仍须核对 |
| --- | --- | --- |
| `FILE`、USA、属性完整，in-use 位为 0 | 一条空闲槽中存在可解析记录残留 | 属于哪个文件系统代际、名称引用是否陈旧、记录是否已部分复用 |
| 完整旧 `$FN`，但无可用 `$DATA` 映射 | 可能恢复文件名或目录关系线索 | 内容不能从名字自动推出；不要承诺完整恢复 |
| 旧常驻 `$DATA` 值仍在有效残留属性范围内 | 有机会直接提取记录内内容 | 长度、USA、属性边界、复用覆盖情况和内容格式 |
| 旧非驻留 runlist 完整 | 得到候选内容簇位置 | 各 run 是否越界，当前簇归属、覆盖、TRIM、压缩/加密及 EOF |
| 旧目录项指向的槽已换序列号 | 旧引用与当前槽不同代 | 不能把当前新文件的内容拼给旧名字 |
| 只有未分配空间里的 `FILE` 或内容签名 | 候选雕刻命中 | 原卷位置、记录尺寸、fixup、字段自洽，以及是否为文件内嵌副本 |

快速格式化会重建/移除旧文件表和根目录等结构，不能等同于“只是把全部记录 in-use 清零”；旧 MFT 是否残留、留在哪、覆盖多少要直接检查镜像。格式化还可能改变文件系统类型、簇大小、卷序列信息与记录布局。之后解析旧 NTFS 残留时应保留**旧布局假设**，不能直接使用新 exFAT/FAT32 的簇坐标，或把不同代际的记录拼成同一目录树。

TRIM/UNMAP 会把已释放簇信息通知底层设备；通知开关、设备支持、USB 桥接转发及控制器执行情况都会影响逻辑读取结果。不能笼统声称“所有 U 盘都支持 TRIM”，也不能笼统声称“U 盘永远没有 TRIM”。格式化过程也可能发送释放通知，快速格式化不能直接等同于可恢复性保证。对取证得到的逻辑镜像，控制器没有提供的旧闪存页不在该镜像内；MFT 映射无法凭空重建其内容。
即便候选内容能导出，也应分开报告“名字/路径恢复”“部分内容恢复”“完整逻辑内容恢复”和“无法核验”。新生成的哈希可用于固定导出结果；没有原文件哈希时，它不能证明导出内容与删除前完全相同。复杂压缩、缺失扩展记录、加密或覆盖应明确列出限制。

## 07 构造字节实战：常驻记录与 runlist

以下数据全部为独立构造的教学样例，不来自真实设备；它验证字段解读，不能代替 Windows 上的创建、复制、改名或删除行为实验。它也不是可以挂载的完整 NTFS 卷。没有给出的字节均置零，数值均为小端。

### 07.1 样例一：记录 42 的常驻 `evidence.txt`

设记录大小为 `0x400`，序列号为 7，基础记录引用为 0，使用标志为 1，属性从 `0x38` 开始。头部及 USA 的构造字节如下：

```text
0000  46 49 4C 45 30 00 03 00 00 00 00 00 00 00 00 00
0010  07 00 01 00 38 00 01 00 38 01 00 00 00 04 00 00
0020  00 00 00 00 00 00 00 00 03 00 00 00 2A 00 00 00
0030  AA BB 00 00 00 00 00 00
01FE  AA BB
03FE  AA BB
```

读 `+0x04` 得 USA 起点 `0x30`，读 `+0x06` 得 3 个字。`AA BB` 是本例更新序列值，两个尾字都匹配；保存字均为 `00 00`，所以修复后的两个尾字还原为零。注意记录内 `+0x10` 的序列号是 `07 00`，它与 USA 更新序列值不同。

三条属性按下面布局放置：

| 属性起点 | 类型 | 总长度 | 值起点 | 值长度 | 下一位置 |
| --- | --- | --- | --- | --- | --- |
| `0x38` | `$SI`，instance 0 | `0x60` | `0x50` | `0x48` | `0x98` |
| `0x98` | `$FN`，instance 1 | `0x78` | `0xB0` | `0x5A` | `0x110` |
| `0x110` | 无名 `$DATA`，instance 2 | `0x20` | `0x128` | `0x08` | `0x130` |
| `0x130` | 结束标记 | 4 个 `FF`，后补 4 个零用于对齐 | — | — | 使用区结束 `0x138` |

这三个常驻属性头分别为：

```text
0038  10 00 00 00 60 00 00 00 00 00 00 00 00 00 00 00
0048  48 00 00 00 18 00 00 00

0098  30 00 00 00 78 00 00 00 00 00 00 00 00 00 01 00
00A8  5A 00 00 00 18 00 01 00

0110  80 00 00 00 20 00 00 00 00 00 00 00 00 00 02 00
0120  08 00 00 00 18 00 00 00
0128  55 53 42 2D 44 45 4D 4F
0130  FF FF FF FF 00 00 00 00
```

`$DATA` 的八个内容字节是 ASCII `USB-DEMO`。读者应能在未查看 `$FN` 前，仅凭常驻头算出内容范围 `[0x128, 0x130)`。

在 `$SI` 值起点 `0x50` 放入四个时间，以下列字节复核 UTC 解码：

| 记录内偏移 | 字节 | UTC 意义 |
| --- | --- | --- |
| `0x50` | `00 00 CE 34 E8 44 DD 01` | 创建：2026-09-15 08:00:00 |
| `0x58` | `00 5E 9E E7 E8 44 DD 01` | 内容修改：2026-09-15 08:05:00 |
| `0x60` | `00 EA 24 2F E9 44 DD 01` | 元数据修改：2026-09-15 08:07:00 |
| `0x68` | `00 BC 6E 9A E9 44 DD 01` | 访问：2026-09-15 08:10:00 |

在 `0x70` 放 `20 00 00 00` 作为 archive 属性，其余 `$SI` 值字节置零。这里的四时间是为了区分偏移而设置的样例，不能反推真实系统一定按这个顺序发生了四次操作。

在 `$FN` 值起点 `0xB0` 放父引用 `05 00 00 00 00 00 02 00`，它指向根目录记录 `5-2`；在 `0xB8`、`0xC0`、`0xC8`、`0xD0` 放相同创建时刻的字节 `00 00 CE 34 E8 44 DD 01`。`0xD8` 的重复分配大小设 0，`0xE0` 的重复实际大小设 8（`08 00 00 00 00 00 00 00`），`0xE8` 放 archive 标志 `20 00 00 00`。

最后放名称长度、namespace 和 UTF-16LE 名称：

```text
00F0  0C 01
00F2  65 00 76 00 69 00 64 00 65 00 6E 00 63 00 65 00
0102  2E 00 74 00 78 00 74 00
```

`0C` 表示 12 个代码单元，后续 24 个字节得到 `evidence.txt`；namespace 为 1。`$FN` 值长度因此为 `0x42 + 2×12 = 0x5A`，加常驻头 `0x18` 后是 `0x72`，再对齐到属性总长度 `0x78`。这正是 `0x98 → 0x110` 的由来。

这份孤立样例没有提供父目录记录 5、目录索引或 MFT 位图，所以只能读出“样例声明父引用为 `5-2`”；不能宣称已经验证路径存在。若只把头部使用位改成 0，可用来测试解析器如何显示空闲残留，但那只是一个标志变体，**不是对真实 Windows 删除流程的完整模拟**。

### 07.2 样例二：含负位移与稀疏区的非驻留映射

另构造一份**未压缩的稀疏流**，其属性标志含 `0x8000`，`LowestVcn=0`、`HighestVcn=8`，逻辑长度为 9 簇，簇大小为 4096 字节。这里只演算映射，不提供内容区。runlist 为：

```text
21 03 20 01  11 02 F0  01 04  00
```

| 字节组 | 字段解释 | VCN 范围 | 物理映射 |
| --- | --- | --- | --- |
| `21 03 20 01` | 1 字节长度 3；2 字节位移 `0x0120` | 0–2 | LCN `0x120–0x122` |
| `11 02 F0` | 长度 2；1 字节有符号位移 `F0=-16` | 3–4 | 起点 `0x120-0x10=0x110`，即 LCN `0x110–0x111` |
| `01 04` | 长度 4；没有 LCN 位移字段 | 5–8 | 稀疏洞，逻辑读取产生四簇零值 |
| `00` | runlist 结束 | — | — |

最高 VCN 是 8，总长度是 `3+2+4=9` 簇，而不是 8 簇。物理区间在卷内起点为 `0x120×0x1000=0x120000` 和 `0x110×0x1000=0x110000`。若卷在整盘镜像内从字节 `0x100000` 开始，两段镜像起点分别为 `0x220000`、`0x210000`。第二段物理地址更低，导出时仍应接在第一段后面，因为逻辑 VCN 顺序是 0–2、3–4、5–8。

本例逻辑长度为 `0x9000`（36864）字节，真正映射了五个物理簇。不要因为四簇没有物理映射，就去 LCN 0 提取四簇；不要把此例的零填规则直接用于带压缩标志的流。末尾不是整簇的真实文件，还必须按 `$DATA` 的逻辑长度裁切 EOF，不能把簇尾填充算进原文件。

## 08 复核：把一条结论落到可复查的字节与关系上

1. **范围复核**：写明这份 MFT 属于主机卷还是 U 盘卷、当前文件系统还是旧 NTFS 残留；记录镜像卷起点、簇大小、记录大小、版本和原始/已 fixup 来源。
2. **结构复核**：保存原始记录偏移与字节；核对 `FILE`、USA、头部尺寸、有效区、属性长度与对齐。修复仅作用于解析副本。
3. **身份复核**：报告完整 FRN；父目录、索引项、属性列表和基础/扩展记录都核对记录号与序列号，避免跨卷或跨代际配对。
4. **内容复核**：枚举无名与命名 `$DATA`；常驻值按 value 边界导出，非驻留值按 VCN 顺序装配，处理稀疏、压缩、初始化长度和 EOF。目录索引不当作文件内容。
5. **状态复核**：把头部 in-use、MFT 位图、目录索引和卷簇位图分别记录。空闲不等于空白，旧分配映射也不等于内容未覆盖。
6. **时间复核**：保留 `$SI`、每个 `$FN` 和目录索引中的时间及来源，不合并成一组“标准时间”；先检查版本、访问时间策略、命名行为，再讨论异常。
7. **结果复核**：对教学样例逐项核对头部、三条属性边界、四时间和 runlist；对真实镜像另检查导出内容格式、实际长度、跨 run 连续性及可获得的原始校验信息。结构样例通过不能宣称真实设备恢复成功。

建议离线演示同时展示原始记录、fixup 后记录、字段树和 VCN/LCN 映射，并加入 USA 不匹配、序列号不匹配、属性越界和仅清使用位四种变体。其价值是让读者看见解析器何时必须停止或降低结论强度；要研究真实复制、删除或格式化的更新时间，则另外使用可重复的 Windows 测试卷，并记录系统版本、操作过程和前后镜像。

## 09 XFW：从目录条目回到真正的 FILE 记录

XFW 指 **X-Ways Forensics**。它适合在同一个案件里浏览主机和 U 盘镜像、检查文件系统结构、导出目标及元数据。界面语言和版本会改变菜单文字，以下以英文功能名配中文说明；实际操作先在 Help/About 确认版本与授权。20.1 等旧版的功能与较新版本未必相同，不把新版本能力默认套到旧安装。

### 09.1 加载镜像与建立可比较的视图

建立案件，分别添加主机镜像和 U 盘镜像为证据对象，记录校验值与分区信息。打开目标卷，确认卷起始位置、文件系统、扇区/簇大小和卷序列号。第一次目录视图来自文件系统分析，`Volume Snapshot` 是 XFW 保存的分析视图，不能当成原设备某一历史时点的完整备份。

在目录浏览器显示名称、路径、状态/属性、逻辑大小、ID、FS offset、主要时间与哈希等列。清楚当前是整卷递归浏览、某个目录还是过滤后的结果。相同名称、相同扩展名只是候选；对 NTFS 对象还应记录序列号、所属卷及多条名称关系。

**ID 与 Int. ID 分开看：** ID 可能是文件系统标识，硬链接或历史版本可以出现相同值；Int. ID 是分析快照内部对象编号。后者方便在案件中导航，不能当成磁盘上的 MFT record number 或完整 FRN。无文件系统身份的雕刻对象，也不能仅凭一个界面编号和 MFT CSV 合并。

### 09.2 用 Details 比较 $SI 与 $FN，用原始字节验证

选中候选 NTFS 文件，切换 `Details`，查看文件系统元数据，比较 `0x10` 与 `0x30` 属性时间。目录浏览器的常规时间列主要用于筛选；必要时启用对应的第二组时间列，或在 Details 中逐项记录。两组一致也要记明来自哪个属性；不一致要考虑复制、解压、改名、程序设置时间、系统版本及历史残留。

然后在该对象右键的 `Navigation` 中选择定位 `FILE record` 的功能，或利用 `FS offset` 定位定义该对象的结构。也可在已识别 NTFS 的卷上使用 `Go To FAT Entry/FILE Record` 按记录号跳转。到达后检查开头是否为 `46 49 4C 45`，读取记录号/序列、使用标志、属性起点和记录长度，核对正在查看的是当前 MFT、历史记录、目录索引还是文件内容。

特别注意三个位置：**FILE 记录所在位置、文件内容第一段所在位置、工具导出逻辑文件内的位置**。对大文件，元数据所在簇与数据所在簇通常不同；对驻留数据，内容可能直接在 FILE 记录内部。查到记录后直接从这里向后读“文件大小”字节，通常会把别的属性、slack 或下一条记录拼进去。

### 09.3 使用 NTFS FILE Record 模板的正确方法

将光标放在目标 FILE 记录的第一个字节，打开模板管理器，选择 `NTFS FILE Record` 并 Apply。记录头中的第一属性偏移指向一串属性；按每个属性自己的 Length 前进，核对 `$STANDARD_INFORMATION`、所有 `$FILE_NAME` 和 `$DATA`，而不是固定假设某属性总在 `0x38`。

模板只是辅助解释。已核对的 20.1 随附模板明确说明**不处理 fixup 字节**，属性数量或类型改变时，直接推进到相邻记录也可能解释错位。模板显示异常时，要先复核起点、扇区大小、USA 校验及属性边界；先跳到下一条记录的真实起点，再重新应用。不能把模板输出当成比原始字节更高一级的证据。

若 `$DATA` 非驻留，进入对应属性，按 Mapping Pairs Offset 找到 runlist；再列出或导出该文件分配簇，和手工解码的 VCN/LCN 对照。压缩、稀疏、加密或多 extent 的文件应由支持该结构的逻辑恢复方式重建。`First sector` 仅能提示起始位置，不能代替整条 runlist；部分列表若用省略号缩短，也不能据此统计完整簇数。

### 09.4 删除项、旧记录与恢复结果

先对当前快照中可见的已删除候选记录做核验；不足时再按目标卷运行 `Refine Volume Snapshot` 中的深入文件系统结构搜索。适用选项可能从日志、旧 FILE 记录、索引残留或卷影副本补出对象。每个新候选注明来源，避免把历史分区里的记录当成当前卷文件，或把前后两个版本当成两次复制。

选中目标使用 `Recover/Copy` 输出到新目录，保存原路径、文件系统对象、导出大小与哈希。然后检验文件头、内部结构、内容和预期长度；图片可再看分辨率和 EXIF，文档可看容器完整性。一个能显示的缩略图不等于整张图片恢复成功；导出全零、固定填充或读取失败提示，也不能包装成原文件内容。

仅名称和时间残留、没有可用数据簇的对象，可以证明“发现相应元数据”，不能证明恢复了内容。`$MFTMirr` 仅镜像关键起始记录，也不能替代完整用户文件的 MFT，更不能恢复全盘文件数据。

### 09.5 在同一案件中接上主机侧痕迹

主机卷里定位 SYSTEM 与用户 Hive，用集成 Registry Viewer 搜索实际设备实例、卷 GUID、盘符映射和 MountPoints2；需要时根据 `Reg Report Devices.txt` 等定义生成报告。报告是候选汇总，再回到键路径、原始值与键 LastWrite 验证，尤其避免把一个键的更新时间误当成其中每个值的更新时间。

定位用户 Recent/Jump Lists 中包含目标卷与文件路径的对象，逐条检查目标路径、卷信息、文件时间和应用关联。将用户 SID、设备/卷映射与 U 盘的具体文件对应；主机自身 `$MFT` 只列主机卷上的对象，通常不会直接列出 `E:\` U 盘内的所有文件。

输出时用 `Export List` 保留候选对象列表，另保存 Details/原始记录摘录、注册表键值、恢复文件和哈希。标注数据来自哪个证据对象和哪个卷。工具生成的事件列表是多类时间字段的集合，必须逐行说明“接入”“文件属性时间”“应用记录”“删除事件”的不同语义。通用案件设置与导出见[X-Ways 工具指南](/tool/forensic-xways/)。

## 10 MFTECmd：先确认输入和版本，再选择输出

MFTECmd 用于解析 NTFS 元数据。先从只读镜像的正确 NTFS 分区导出 `$MFT` 的完整逻辑文件，以及存在时的 `$Extend\$UsnJrnl:$J` 数据流。导出过程要处理文件的数据运行列表和扩展属性，不能把 `$MFT` 的首个物理簇当作整个文件，也不能把分区镜像、目录列表、CSV 或 `$MFTMirr` 改名当成完整 `$MFT`。记录镜像哈希、分区起始扇区、扇区大小、导出文件长度和哈希，再在工作副本上解析。U 盘如果使用 FAT/exFAT，则没有 NTFS 的 `$MFT`，应返回相应文件系统流程。

以下参数按实际检查的 **MFTECmd 2026.5.0** 维护。先运行 `MFTECmd.exe -h` 与 `MFTECmd.exe --version` 保存本机版本证据。程序按数据结构识别输入，导出件可以叫 `sample.mft`、`sample.usn`。它的 `-f` 输入包含 `$MFT`、`$J`、`$Boot`、`$SDS`、`$I30`；不要因旧参数表提及 `$LogFile` 就假设现有版本支持它。

| 参数 | 实际用途、组合和限制 |
| --- | --- |
| `-f FILE` | 待解析文件。单字母参数使用一个连字符；路径必须指向真实导出件。 |
| `-m MFT` | `-f` 为 `$J` 时加载同一卷的 `$MFT`，辅助解析日志记录的父目录路径。 |
| `--csv DIR` | CSV 输出目录，不是输出文件。与 `--json`、`--body`、`--de` 等按任务选择。 |
| `--csvf NAME` | 自定义 CSV 文件名；目录仍由 `--csv` 指定。使用新的输出目录避免覆盖。 |
| `--json DIR` / `--jsonf NAME` | JSON 输出目录及文件名。MFT JSON 是逐行记录，读取时按 JSON Lines 处理，不假设是一个 JSON 数组。 |
| `--body DIR` / `--bodyf NAME` | 导出 bodyfile 时间线；必须同时提供 `--bdl`。不能把其中的占位 MD5 当作内容哈希。 |
| `--bdl E` | bodyfile 中使用的逻辑盘符，只传 `E`，不用 `E:` 或路径。这是路径标签，不是自动证明的历史盘符。 |
| `--blf` | bodyfile 使用 LF 换行；默认 CRLF。 |
| `--de ENTRY` / `--de ENTRY-SEQ` | 显示指定记录的完整属性。支持十进制或 `0x` 十六进制，例如 `42-2`、`0x2a-0x2`。 |
| `--fls` | 配合目录的 `--de` 列出关联的子项；对普通文件忽略。与 Sleuth Kit 的独立 `fls` 命令不同。 |
| `--dd DIR` / `--do VALUE` | 导出单个 FILE 记录。`--dd` 目标目录先创建；**此版 `--do` 存在帮助与实现差异，见下一节，不直接照抄字节偏移。** |
| `--ds ID` | 当 `-f` 指向 `$SDS` 时按 Security Id 输出安全描述符详情，支持十进制/十六进制；不是 MFT 的记录号筛选。 |
| `--dt FORMAT` | 显示时间的格式，默认 `yyyy-MM-dd HH:mm:ss.fffffff`；格式不是时区转换参数。 |
| `--sn` | 包含 DOS 文件名类型；同一文件的长名、短名不能直接统计为不同文件。 |
| `--fl` | 生成简化文件列表，要求 `--csv`；它不包含完整 CSV 的全部证据字段。 |
| `--at` | 输出所有 `$FILE_NAME`（0x30）时间。默认仅在与 `$STANDARD_INFORMATION`（0x10）相应时间不同等情况下输出。 |
| `--rs` | 检查 FILE 记录 slack 中残留的索引信息；对 `$I30` 无效。不是恢复卷上所有已删除文件内容。 |
| `--dr` | 将 `$MFT` 的驻留数据导出到输出目录的 `Resident` 子目录；文件名含 Entry、Sequence、Attribute 编号和文件名，并以 `.bin` 结尾。 |
| `--ir` | 在 CSV/JSON 中加入驻留数据的 Base64、Hex、可显示文本字段。 |
| `--re '.txt,.ps1,.bat'` | 对 `--ir` 加入的数据按扩展名过滤；带前导点、逗号分隔。不是记录号、正则表达式或恢复模式。不能据此假设 `--dr` 只导出这些扩展名。 |
| `--rm 1024` | `--ir` 可加入的驻留数据大小上限，单位字节；默认 1024，帮助列出的最大值是 1024000。 |
| `--vss` | 处理 `-f` 所在盘上的现存卷影副本；需要管理员权限及可访问的 VSS 环境。离线镜像不是自动提供本机 VSS。 |
| `--dedupe` | 按 SHA-1 去重输入及 VSS 副本，首次发现者优先；不是文件内容的法证采集哈希流程。 |
| `--debug` / `--trace` | 更多处理信息，用于调查识别、记录偏移、路径或属性错误；同时保留完整日志。 |
| `--recover` | **此版没有这个参数。** 恢复任务分别看 `--dr`、`--rs` 及镜像的数据簇恢复工具，不混为一个开关。 |

## 11 一组可直接调整的命令与输出检查

MFTECmd 的 Windows 示例使用 PowerShell。文件路径里的字面量 `$MFT`、`$J` 用单引号；双引号会尝试展开 PowerShell 变量。下面假设导出件已放到工作目录，工具位于当前目录。

```powershell
# 常规 MFT 全字段CSV：保留全部FN时间及UTC偏移
& .\MFTECmd.exe -f 'C:\Case\export\$MFT' --csv 'C:\Case\out\mft' --csvf mft.csv --at --dt 'yyyy-MM-ddTHH:mm:ss.fffffffzzz'

# JSON与简化列表；建议每次输出到新目录
& .\MFTECmd.exe -f 'C:\Case\export\$MFT' --json 'C:\Case\out\json' --jsonf mft.json --at
& .\MFTECmd.exe -f 'C:\Case\export\$MFT' --csv 'C:\Case\out\listing' --fl

# 查看记录及目录；42-2、24-1必须替换为实际记录标识
& .\MFTECmd.exe -f 'C:\Case\export\$MFT' --de 42-2
& .\MFTECmd.exe -f 'C:\Case\export\$MFT' --de 24-1 --fls

# 驻留字节导出与CSV内嵌数据分别执行，便于核对
& .\MFTECmd.exe -f 'C:\Case\export\$MFT' --csv 'C:\Case\out\resident' --csvf mft.csv --dr
& .\MFTECmd.exe -f 'C:\Case\export\$MFT' --csv 'C:\Case\out\inline' --csvf mft.csv --ir --re '.txt,.ps1,.bat' --rm 1024

# bodyfile及FILE slack检查
& .\MFTECmd.exe -f 'C:\Case\export\$MFT' --body 'C:\Case\out\timeline' --bodyf mft.body --bdl E --at --blf
& .\MFTECmd.exe -f 'C:\Case\export\$MFT' --csv 'C:\Case\out\slack' --csvf mft.csv --rs --debug

# USN日志；与MFT输出分目录
& .\MFTECmd.exe -f 'C:\Case\export\$J' -m 'C:\Case\export\$MFT' --csv 'C:\Case\out\usn' --csvf usn.csv --dt 'yyyy-MM-ddTHH:mm:ss.fffffffzzz'

# SDS是不同输入，ID取自待核对记录的SecurityId
& .\MFTECmd.exe -f 'C:\Case\export\$SDS' --ds 256
```

`--do` 的版本差异必须单独核对：本机 2026.5.0 帮助写“记录偏移”，实现却把参数值乘 FILE 记录大小，然后读取 1024 字节。构造流中 entry 42 位于字节偏移 `0xA800`；传 `--do 0xa800` 得到空文件，而 `--do 42` 得到与第 42 个记录逐字节相同的 1024 字节文件。以下仅是这一版、1024 字节连续记录流的验证用法，不能推广到其他版本、异常记录布局或整个卷的偏移：

```powershell
New-Item -ItemType Directory -Path 'C:\Case\out\record' -Force | Out-Null
& .\MFTECmd.exe -f 'C:\Case\export\$MFT' --dd 'C:\Case\out\record' --do 42
```

先用 `--de` 或 `--debug` 确认记录大小和真实字节偏移，再检查导出件非空、长度正确、头部为 `FILE`，并与输入工作副本的相应范围比较。优先使用 `--de` 查看属性；不要为定位一个条目猜测偏移。构造测试还发现参数错误或处理错误有时仍返回退出码 0，因此“退出成功”和“打印已导出”都不能代替实际输出核对。

## 12 CSV：把记录身份、名字、数据流和时间分开读

先保留完整 CSV，使用 CSV 解析器读取，不能按文本行数数记录：驻留文本及 `ZoneIdContents` 可包含换行。本版实测表头有 `InUse`、`ReferenceCount`、`HasAds`、`IsAds`，没有名为 `IsDeleted` 或 `HardLinkCount` 的列。

| 字段 | 证据含义与判读 |
| --- | --- |
| `EntryNumber` + `SequenceNumber` | FILE 记录位置编号和记录序列号；关联跨时间材料时保存两者及所属卷。相同 EntryNumber 不保证是同一代文件。 |
| `ParentEntryNumber` + `ParentSequenceNumber` | 当前 `$FN` 中引用的父记录标识。不要只用父记录号关联，也不要用现在的盘符推定过去路径。 |
| `ParentPath` + `FileName` | 根据可用 MFT 记录重建的父路径和当前行名字。`PathUnknown` 等结果表示链缺失，不能补成一个已证实路径。 |
| `InUse` | `True` 为记录使用中；`False` 表示空闲/已删除候选。它不证明内容可恢复，也不给出删除时间。损坏及未初始化记录另看处理日志。 |
| `ReferenceCount` / `NameType` | 输出计数按非DOS名字与父引用的组合去重计算，并非直接复制FILE头部引用计数；另看名字类型及完整 `--de`。多名字可能来自硬链接、短名或不同名字属性，不能把CSV多行都当成多个文件。 |
| `HasAds` / `IsAds` | 前者提示主记录含命名数据流；后者标记当前行自身为 ADS。常见名字形如 `report.txt:Zone.Identifier`，不能再将此行当普通独立文件。 |
| `FileSize` / `IsDirectory` | 当前数据或数据流的大小、目录标记；目录大小和文件内容恢复要分开解释。 |
| `Created0x10` / `Created0x30` | `$SI` / `$FN` 的创建时间。`LastModified` 是内容修改；`LastRecordChange` 是记录修改；`LastAccess` 是访问，各有 0x10/0x30 两组。 |
| `UpdateSequenceNumber` / `LogfileSequenceNumber` | `$SI` 中的 USN 值和 FILE 头的日志序列号。不要把它们当时间戳、MFT SequenceNumber 或 fixup 校验编号。 |
| `SecurityId` / `ZoneIdContents` | 安全描述符索引和可取得的 Zone.Identifier 文本。ZoneId 提示来源区域，不独自证明USB插拔、复制或特定操作者。 |
| `SI<FN` / `uSecZeros` / `Copied` | 工具依据时间关系产生的调查线索。分别观察 SI创建早于FN、毫秒部分为零、内容修改早于创建等现象；都不是“改时间”或“复制”的独立证明。 |
| `ResidentDataBase64` / `ResidentDataHex` / `ResidentDataASCII` | `--ir` 加入的驻留字节及可显示文本；以 Base64/Hex 核验原始字节，文本为空不代表没有二进制数据。 |
| `SourceFile` | 当前解析输入路径。仅作为导出件追溯信息，不能替代原镜像/原卷的身份记录。 |

默认 `0x30` 时间为空时，先加 `--at` 或查看 `--de`，排除“与 0x10 相等而省略”。无效时间、缺失属性和解析异常也必须区分。NTFS FILETIME 表示 UTC 时间；此版在本机 UTC+08:00 时区下，构造输入 `2026-01-02T03:04:05.1234567+00:00` 的默认 CSV 仍为 `2026-01-02 03:04:05.1234567`，只是没有显式时区。加入上述 `--dt` 后为 `2026-01-02T03:04:05.1234567+00:00`。保留原 CSV；报告若转换到北京时间，另列为 `2026-01-02 11:04:05.1234567+08:00`，注明转换规则，不能再次加八小时。

构造例中 `report.txt` 与 `alias.txt` 共享 entry 42、sequence 2、ReferenceCount 2；每个名字还有一行 ADS，所以四行只代表一个 FILE 记录的两个名字及命名流。已删除记录的 CSV 保存头部序列号，而此版内部目录键可能采用序列号减一：构造 record 43 的 CSV 是 sequence 3，`--fls` 显示键 `43-2`，`--de 43-2` 显示头部 `0x2B-0x3`。查空闲记录先用单个 entry（例如 `--de 43`）取得详情再核对，不强行把这些序列表示当成矛盾或自动连接到另一代文件。

## 13 USN关联、恢复边界和练习范围

本版实际支持 `$J`。应导出 `$UsnJrnl` 的 **`$J` 命名流**，不是无名流，也不是 `$Max`。`-m` 只帮助利用 MFT 重建父路径；当前 MFT 路径未必是事件发生时的完整历史路径，父目录重命名、丢失、复用和日志截断都要另行核对。

USN CSV 的实测字段是 `Name`、`Extension`、`EntryNumber`、`SequenceNumber`、`ParentEntryNumber`、`ParentSequenceNumber`、`ParentPath`、`UpdateSequenceNumber`、`UpdateTimestamp`、`UpdateReasons`、`FileAttributes`、`OffsetToData`、`SourceFile`。按同一卷、文件引用的记录号与序列号以及 USN顺序，检查 `RenameOldName` / `RenameNewName` 的前后名字和父目录；再与 `FileCreate`、`FileDelete`、`DataExtend`、`DataOverwrite`、`Close` 等组合解释。`Close` 不是删除，原因位可以累计；MFT空闲状态不能代替 USN删除事件时间。日志可被禁用、回卷、截断或清除，没有某事件不等于没有发生。

`--dr` 可以取出驻留在 FILE 记录里的数据，包括未被覆盖的已删除驻留数据和命名流；导出 `.bin` 后核对 Attribute 编号、大小、内容和哈希。`--ir` 内嵌的数据不能代表所有 ADS，ADS另看对应行与 `ZoneIdContents`、属性详情、驻留导出。若同时提供 CSV与JSON，驻留目录实际优先落到 JSON输出位置。非驻留文件只有运行列表和元数据在 MFT中，恢复内容还需要完整镜像的数据簇及压缩、稀疏、加密和覆盖状态检查；MFTECmd解析成功不等于非驻留内容恢复成功。

练习件是人为构造的 **FILE记录流与USN V2记录流**，用于学习参数、字段和输出检查。MFT部分含45个1024字节槽位，其中有效记录的物理槽位与EntryNumber一致；它不是完整NTFS卷，运行列表不提供可恢复的真实磁盘内容。可以交给MFTECmd；十六进制取证软件可以查看FILE头、属性和fixup，但不能据此声称已验证整卷目录、分区或真实U盘恢复。实际检查得到9行MFT CSV、3行USN CSV及驻留字节输出；参数表中的SDS、VSS和真实附件恢复没有借构造练习宣称实测。

## 14 离线练习：记录解析、驻留内容与改名日志

可以下载[构造 MFT 记录流](/practice/usb-forensics/sample.mft)、[构造 USN V2 记录流](/practice/usb-forensics/sample.usn)及[尺寸与校验清单](/practice/usb-forensics/manifest.json)。这些小文件不含真实设备数据，**不是完整磁盘、分区或 NTFS 卷**；用于观察 FILE 记录、属性、CSV、驻留导出与日志引用。非驻留映射指向虚构簇，不能拿它练习真实内容恢复。

下载到 Windows 工作目录，按本机工具位置调整命令。以下以 MFTECmd 2026.5.0 为例，输出另存；先把文件大小、SHA-256 与清单比较：

```powershell
Get-FileHash -Algorithm SHA256 -LiteralPath '.\sample.mft', '.\sample.usn'
& .\MFTECmd.exe -f '.\sample.mft' --csv '.\out\mft' --csvf sample.csv --at --dt 'yyyy-MM-ddTHH:mm:ss.fffffffzzz'
& .\MFTECmd.exe -f '.\sample.mft' --de 42-2
& .\MFTECmd.exe -f '.\sample.mft' --de 24-1 --fls
& .\MFTECmd.exe -f '.\sample.mft' --csv '.\out\resident' --dr
& .\MFTECmd.exe -f '.\sample.usn' -m '.\sample.mft' --csv '.\out\usn' --csvf sample.csv
```

先观察完整 CSV，再回到属性验证，不只比较行数：

- `report.txt` 与 `alias.txt` 的 Entry/Sequence 相同；检查父目录、两个名字和命名 `$DATA`，解释为何 CSV 有多行而不是多份独立文件。
- 检查 `gone.txt` 的使用标志与驻留字节，比较 CSV 中的头部序列号、工具历史目录键和 USN 删除引用。此例演示释放后的序列表现，不能把所有真实历史引用都机械减一。
- `large.bin` 只提供非驻留元数据；从 MFT 里看到长度和 runlist，不代表取得了外部内容。比较它与驻留导出目录中的结果。
- 比较 `Created0x10` 与 `Created0x30`，确认 `--at` 是否保留相同时间；检查 UTC 偏移与七位小数，不把保存精度当作事件发生精度。
- USN 有旧名、新名与删除原因的构造记录，按完整引用和 USN 顺序分别解释。它们的时间被刻意设为相同，不能借此推断一次真实操作过程的持续时间。

这份练习使用 45 个 1024 字节槽位，六个有效 FILE 记录；其他槽位为空。所验证版本通常导出 9 行 MFT CSV 和 3 行 USN CSV。CSV 的多行规则随解析器改变，核验重点应落到原始记录身份和内容。

在 XFW/WinHex 中把 `sample.mft` 作为**普通文件**查看，从 `42×1024=0xA800` 定位记录 42 的原始字节，检查 `FILE`、序列号、属性头与 fixup。该文件缺少完整卷结构，不能添加为磁盘镜像后期待正常卷目录。它与前面的孤立 `evidence.txt` 字节示例是两组不同的构造材料，不混用名称、序列号和时间。

## 15 实战：把接入、复制、打开与删除逐项验证

### 15.1 一台主机与一份 NTFS U 盘镜像

**构造场景：** 主机用户为 analyst，目标文件为 `E:\Projects\budget.xlsx`，U 盘卷内随后只剩删除记录。目标是判断文件是否在这台主机上被访问、是否曾存在于这个卷，以及能否解释删除。以下时刻只说明推理方法，实际答题使用检材字段。

| 示例证据 | 首先能说明什么 | 下一步核验 |
| --- | --- | --- |
| 09:58 目标设备实例出现一次 arrival 记录 | 系统记录了该实例的到达 | Provider、字段、卷映射、完整日志范围 |
| 用户 Recent 的 LNK 指向目标路径并保存卷标识 | 用户目录内有指向该卷和文件的访问相关痕迹 | LNK 目标元数据、Jump List/应用 MRU、SID 与会话 |
| U 盘 MFT 存在文件名与有效数据映射，记录现为未使用 | 这个卷留下相应文件对象的删除候选元数据 | FRN 序列、父引用、数据覆盖状态及日志；已删除记录结合释放后的序列变化 |
| 同卷 USN 中与候选对象代际相符的引用有 FILE_DELETE 原因 | 文件系统日志记录相应对象的删除变更 | 原因组合、CLOSE、先后 USN 与覆盖范围 |
| 恢复件与主机复制起点的文件 SHA-256 相同 | 两份可读内容一致 | 文件来源、目标写入记录、其他同内容副本的可能 |

1. 用设备实例串和卷信息建立主机到 U 盘的桥梁，记录历史 `E:` 只是当时的映射。不要仅因当前 U 盘也分配了 E: 就合并。
2. 导出用户痕迹，确认 LNK 指向目标卷；区分 LNK 文件自己的时间、保存的目标时间和应用使用事件。发现 LNK 并不自动确定“打开时间=目标访问时间”。
3. 用 XFW 导出 U 盘逻辑 `$MFT` 与 USN `$J`，保留镜像/卷范围和提取哈希；用 MFTECmd 分别解析。对候选记录检查完整 FRN、父目录、两组时间与每个 `$DATA` 流。
4. 按 runlist 恢复正文，验证 XLSX ZIP 结构和必要成员，计算哈希，和主机候选复制起点的文件比较。元数据中的 FileSize 与恢复字节数不符时，先报告损坏或不完整。
5. 将有依据的事件排到时间线上：记录到达、用户访问痕迹、目标对象存在、删除变更、内容一致性。若缺少源读取和复制程序记录，结论可写“支持同内容文件曾位于目标卷并有相关访问/删除痕迹”，不把一次具体复制动作和自然人身份写成已唯一确定。

### 15.2 改名、硬链接和记录复用的区分

**构造场景：** USN 先后出现 `draft.txt` 的旧名称与 `final.txt` 的新名称。若同一卷、完整 FRN 一致，并能按 USN 顺序关联 `RENAME_OLD_NAME`/`RENAME_NEW_NAME`，可以支持同一个对象改名或移动；同时记录两次父引用，解释是否换目录。

若两条 MFT 导出行名字不同但 Entry/Sequence 相同，先检查多个 `$FILE_NAME`、命名空间和父目录，可能是硬链接或长短名称。它们不一定是两份内容。如果 Entry 相同而 Sequence 不同，则要考虑槽位复用；不能把旧文件的删除日志拼到新文件的访问事件上。卷不同的相同 FRN 更无跨卷身份意义。

### 15.3 快速格式化之后的旧文件

**构造场景：** 现在是 exFAT 卷，未分配空间中还能找到结构合理的旧 NTFS FILE 记录。先检查当前引导结构、旧卷起点与旧簇大小，区分当前目录与历史文件系统残留。旧 runlist 的 LCN 必须按旧卷几何解释，不能按当前 exFAT 参数读数据。

深入搜索、旧元数据恢复与按格式雕刻可分别尝试；每个恢复对象记录方法和来源范围。雕刻通常不能保留原路径、对象编号或完整时间，也未必能处理碎片。发现可解析的 FILE 残留说明存在历史 NTFS 结构候选；不能据此认定该文件目前仍在 U 盘，或仅凭残留推定格式化的具体时间和操作者。

## 16 考点、答题字段与最终复核

| 考点 | 答题时写清楚的单位/身份 | 常见失分原因 |
| --- | --- | --- |
| 厂商、型号、设备实例和序列号 | 原始键/日志字段，硬件与生成实例的区别 | 将尾部 `&0` 或卷序列号直接当硬件序列 |
| 首次安装、最近到达、最近移除 | 时间属性名称、UTC/本地、Provider/版本 | 用 USBSTOR 键 LastWrite 代表全部插拔时间 |
| 盘符与关联用户 | 历史卷映射、SID、用户 Hive 和会话 | 把当前 E: 或某用户键存在直接当人证 |
| 文件名、路径和 MFT 编号 | 卷、Entry、Sequence、父引用、FN 命名空间 | 只按名称或 Entry 合并历史对象 |
| SI/FN 四时间 | 属性类型、四字段语义、原始值和显示时区 | 将访问时间视作每次打开记录，将 MFT 变更视作删除时间 |
| 驻留/非驻留、ADS 与 runlist | 属性名称、VCN/LCN、簇大小、逻辑/分配/初始化长度 | 把 Mapping Pairs Offset 当段数，把簇号当扇区 |
| 已删文件恢复、首末位置 | 完整所有 extent、分区起点、字节/扇区单位 | 只看第一簇，忽略碎片、稀疏区和末簇有效长度 |
| 复制、改名和删除过程 | 内容哈希、完整 FRN、USN 原因和独立痕迹 | 将内容相同或文件缺失直接视作某次特定操作 |
| 图片或文档内部信息 | 恢复件哈希、格式完整性、内部元数据语义 | 将拍摄/编辑时间当 U 盘写入时间 |

交付一张可回查的证据表：`镜像哈希 → 卷标识 → 用户/设备 → 文件引用 → 原始字段与偏移 → 统一时间 → 判读 → 独立印证 → 缺失范围`。恢复件另外记录字节长度、哈希、原路径、恢复方式与完整性验证结果。

最终复核时清除工具筛选条件，检查输入是否完整、日志是否循环覆盖、旧记录是否归错卷、序列号是否匹配、路径是否可靠，以及导出文件是否含预期内容。两个解析器一致通常支持解析结果，但它们若读取同一份 MFT，仍只是一类原始证据；不同来源的主机痕迹、卷元数据和应用记录才能进一步增强行为判断。

**目录交互专项：** ShellBags 的层次、MRU、时间推导、Windows 版本差异及 ShellBags Explorer 操作集中在 [ShellBags 取证](/knowledge/forensic-shellbags/)，本页保留注册表或 U 盘的通用证据链。


## 17 引导扇区损坏后，用特征字节定位

引导扇区被填成 `0x00` 或 `0xFF` 时，BPB 里的张数、保留扇区和 MFT 簇号是空的，挂不上盘符也正常。分区个数看分区表或扫描结果。扇区字节数用工具读到的物理扇区。

FAT32 只在本分区范围内搜 `F8 FF FF 0F`。互不重叠的表头有几处，就有几张 FAT。保留扇区数等于 FAT1 的整盘扇区号减去本分区起始扇区。要整盘扇区号时，用减法之前的那个数。

NTFS 先搜 `46 49 4C 45`。靠前的一份通常是 `$MFTMirr`，它只镜像开头若干条记录。从这份记录取一段特征再向后搜，卷中部再次出现并且后面连续有大量 `FILE` 记录的位置，是 `$MFT`。在目标记录类型 `0x80` 的 `$DATA` 非驻留运行里读起始簇。相对扇区号等于整盘扇区号减去分区起点，再除以每簇扇区数。用起始簇乘每簇扇区数，加回分区起点，应回到原来的整盘扇区。

键名形如 `##<主机>#<共享名>` 时，`##` 表示 UNC 的两个反斜杠，第一段是当时连接的主机。盘符保留冒号。比较文件大小时，逻辑大小是字节长度，占用空间按簇对齐。
