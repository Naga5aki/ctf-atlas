### 01.1 先保住副本，再找回 `/www`

先给系统盘、数据盘和数据库所在虚拟机做快照，限制副本外联，只保留操作机和副本之间需要的连接。后面的配置修改、口令重算和代码调整都在这里进行。原文件、原账号记录另存；备份不要放进网站公开目录。

从浏览器历史或桌面记录找到宝塔地址。面板地址包含端口，有时还包含安全入口；**面板账号不是商城后台账号**。

有宝塔，先进入 **文件**，查看 `/www/wwwroot/`；不要因为 **网站** 列表为空就添加站点。

若 `/www` 也是空的，到服务器终端分别查看：

```bash
lsblk -f
```

```bash
cat /etc/fstab
```

```bash
findmnt /www
```

对照分区 UUID、容量和原挂载点：

- 数据盘没有接入：先在虚拟机设置中接入对应的副本磁盘。
- 数据盘已接入，`fstab` 明确把它挂到 `/www`：核对 UUID 后执行：

```bash
mount /www
```

- 原挂载点在别处：沿原路径找源码，不要把任意分区直接挂到 `/www`。
- 显示 LVM、阵列或文件系统错误：先恢复对应卷的可见性；不要格式化，也不要在空目录建立替代商城。

**进入下一步的结果：** 能看到原程序、上传目录及原服务器配置；至少确认这是一份 PHP 程序，而不是只有 HTML 的前端。

**三格回填：入口＝待查；程序＝已找到实际目录；数据库＝待查。**

### 01.2 让网站配置指向真正的入口

有宝塔，进入 **网站 → 目标站点 → 设置**，依次看：

1. **域名管理**：域名、端口。
2. **网站目录**：源码所在目录。
3. **运行目录**：浏览器请求实际进入哪一层。
4. **PHP 版本**：原站点使用的版本。
5. **配置文件、伪静态**：原来的入口转发规则。

宝塔的“网站目录”和“运行目录”是两项设置；源码根目录与公开入口目录可能不同。[宝塔目录说明](https://docs.bt.cn/user-guide/site/php/site-config/website-directory/)

网站列表为空、文件已经找回时，先检查 `/www/server/panel/vhost/` 中的原站点配置。配置仍在就核对加载情况；配置确实缺失，才按原域名和已有源码目录添加站点，**不自动创建新数据库、不覆盖原入口文件**。

只打开与实际框架对应的配置：

| 已确认的程序 | 真正要看的位置 | 运行目录与伪静态 |
|---|---|---|
| ThinkPHP | 先从入口确定版本和加载路径。常见为 `/www/wwwroot/shop/application/database.php`、`/www/wwwroot/shop/config/database.php`；旧项目也可能在模块配置中 | 有 `public/index.php` 才选 `/public`；恢复原 ThinkPHP 规则，检查它使用 PATH_INFO 还是 `s` 参数 |
| Laravel | `/www/wwwroot/shop/.env`；再核对 `/www/wwwroot/shop/config/database.php` 如何读取变量 | 指向 `/public`；普通路由回到 `index.php`，保留查询参数 |
| WordPress | `/www/wwwroot/shop/wp-config.php`，包括数据库、表前缀 | 通常指向包含 `index.php`、`wp-admin` 的目录；使用该站的 WordPress 规则，区分普通站、子目录安装和多站点 |

不要因为目录里有多个数据库配置，就逐个改一遍。顺着入口和配置加载代码确定生效的那份。

Laravel 修改 `.env` 后仍连旧库，先看是否存在配置缓存。需要清除时，在项目目录使用与网站相同版本的 PHP 执行：

```bash
php artisan config:clear
```

不要顺手执行数据库迁移或重新生成 `APP_KEY`。Laravel 的公开目录和配置缓存处理有明确要求。[Laravel 部署说明](https://laravel.com/docs/12.x/deployment)

没有宝塔，查看原 Nginx 站点配置中的 `listen`、`server_name`、`root`、`fastcgi_pass` 和伪静态包含文件；已有站点就修这一份，不另装面板。


原站使用 Apache 时，先从原服务启动参数确认实际二进制和配置；系统 Apache 与宝塔 Apache 是不同实例，`which httpd` 的结果不证明它就是当前站点。宝塔仍在 **软件商店 → 已安装** 管理原实例，不另启系统 Apache。没有面板时，使用原实例的配置检查；宝塔路径确实存在且未用启动参数覆盖配置时，例如：

```bash
/www/server/apache/bin/httpd -t
```

```bash
/www/server/apache/bin/httpd -S
```

`-t` 通过后才重载原服务；`-S` 用于核对域名和端口命中的虚拟主机。启动参数带 `-f`、`-d` 时，诊断也带同一组参数。改了另一实例的 `DocumentRoot`，当前网站不会跟着改变。

**进入下一步的结果：** 域名能对应到一个站点配置，站点配置能对应到确实存在的 PHP 入口。

**三格回填：入口＝已登记域名和端口，待访问；程序＝已确定入口和 PHP 版本；数据库＝已找到配置，待连接。**

### 01.3 先确认库里有旧数据，再启动业务程序

在生效配置中记录：数据库主机、端口、库名、用户名、表前缀。

有宝塔：

- **软件商店 → 已安装**：查看原 MySQL/MariaDB 服务和版本。
- **数据库**：管理已有库、查看表；不要把面板列表为空当作数据库为空。
- **文件**：核对数据库配置和原数据目录。

只有 SQL 备份时，导入到副本中的对应库；只有原数据库数据目录时，优先恢复原版本服务和原数据卷，不把零散 `.ibd` 文件直接塞进新库。

按配置中的业务账号测试连接，而不是仅用数据库管理员账号证明“数据库正常”。没有面板时，例如：

```bash
mysql -h 127.0.0.1 -P 3306 -u shop_user -p shop
```

连接后：

```sql
SELECT DATABASE();
```

```sql
SHOW TABLES;
```

核对是否有用户、订单等原业务表，并能读到旧记录。

失败只查数据库这一格：

- **连接超时、拒绝连接**：查主机、端口、服务监听和副本网络。
- **Access denied**：查账号、口令和账号允许的来源主机。
- **Unknown database**：查库名、实例及导入目标。
- **表不存在或空表**：查表前缀、是否连到新建空库。
- **配置写 `localhost`**：先确认是否使用 Unix 套接字；改成 `127.0.0.1` 会改变连接方式，别把它当作必做步骤。

库确认后，到 **软件商店 → 已安装** 启动站点指定的 PHP，再启动原 Web 服务。没有面板，使用原服务单元；例如实际服务确为这些名称时：

```bash
systemctl start mysql
```

```bash
systemctl start php7.4-fpm
```

```bash
systemctl start nginx
```

不要为凑命令另装一个不同版本。

**进入下一步的结果：** 业务账号能读取正确库中的旧记录，PHP 和 Web 服务启动日志没有阻断错误。

**三格回填：入口＝待浏览器验证；程序＝原运行环境已启动；数据库＝业务账号读到旧数据。**

### 01.4 用原域名打开，并按现象只查一格

在操作机的 hosts 中，把原域名指向副本站点 IP：

```text
192.168.56.10 shop.test
```

hosts 只写 IP 和域名，不写协议、端口或路径。浏览器访问表中登记的完整地址；原站使用 HTTPS，就保留原域名、HTTPS 绑定和证书配置，不为方便改成 IP 登录。

| 现象 | 先查哪一格 | 具体看哪里 |
|---|---|---|
| 超时、连接拒绝 | 入口 | 站点 IP、监听端口、防火墙；站点访问日志有没有本次请求 |
| Nginx 欢迎页或别的网站 | 入口 | 域名是否命中该虚拟主机；配置是否加载；命中后再核对 `root` |
| 浏览器下载 PHP 源码 | 程序 | PHP 请求是否进入 FastCGI 处理规则；站点是否误设成静态 |
| 502 | 程序 | PHP-FPM 日志；`fastcgi_pass` 与实际端口或套接字是否一致；套接字访问权限 |
| 500、白屏 | 程序 | PHP 错误日志、扩展、依赖和目录权限 |
| 数据库连接错误 | 数据库 | 第 3 步的连接参数、账号和原库 |
| 首页正常、内页 404 | 程序 | 原路由、运行目录、对应框架的伪静态 |

有宝塔，日志从 **网站 → 设置 → 日志** 查看；部分版本显示为“网站日志”。没有面板，就打开该站配置里 `access_log`、`error_log` 指定的文件。

伪静态缺失时，不直接选一个看起来相似的模板：

- ThinkPHP：先用入口文件加实际路由验证。显式入口能通、去掉入口才 404，才修伪静态。
- Laravel：确认请求转到 `/public/index.php`；不要把源码根目录公开。
- WordPress：核对固定链接及原安装路径；子目录、多站点沿用对应规则，不套普通单站规则。[WordPress Nginx 配置说明](https://developer.wordpress.org/advanced-administration/server/web-server/nginx/)

**进入下一步的结果：** 首页和一个实际业务内页均由这份程序处理，而不是只得到 HTTP 200。

**三格回填：入口＝原域名命中目标站；程序＝首页及内页已验证；数据库＝已连通，待页面核对。**

### 01.5 找到正确后台，只处理实际挡住的登录条件

从浏览器历史、站点日志和路由配置找后台入口，再在 **文件** 中打开对应控制器。先区分会员登录与管理员登录，确认各自查的是哪张表。

按本项目代码的实际顺序看：验证码、账号状态、口令校验、来源地址、角色权限。页面提示“登录失败”不等于口令错误。

需要重设口令时：

1. 保存目标管理员这一行的原口令字段、自己的 `salt` 及相关状态值。
2. 找到实际口令比较语句和调用的哈希函数。
3. 按原算法、编码、拼接次序和该用户自己的 `salt` 重算。全局密钥与用户 salt 是两回事。
4. 在本地使用原校验函数确认新明文能通过。
5. 在 **数据库** 中只更新该主键对应的一行，核对影响行数为 1，再登录。

例如，**只有代码明确写着** `md5(sha1($password).UC_AUTH_KEY)`，且没有其他处理时，才采用同样的两层计算；这不是所有 ThinkPHP 商城的通用算法。使用 bcrypt、Argon2 或框架哈希器的站点，调用该项目对应实现，保留它要求的完整编码结构。

MD5 是摘要计算，不是解密。不要把别人的摘要或 salt 复制给目标管理员，也不要通过网页错误提示输出摘要；代码难以单独调用时，在副本的本地调试器中调用原函数。

其他阻断分别处理：

- **图形验证码**：先修会话、验证码存储和 Cookie，再按页面输入。
- **账号禁用**：根据代码确认允许值，只改目标账号，不猜 `0`、`1` 的含义。
- **来源 IP 限制**：先看程序实际读取的客户端地址；反向代理传递错误就修代理。确为固定白名单时，只加入操作机的副本地址，不删除全部判断。
- **登录后立即退出**：查会话存储、Cookie 域名、HTTPS 和系统时间，不继续换口令。

**进入下一步的结果：** 目标管理员能进入正确后台，刷新后仍保持会话，并能打开业务列表。

**三格回填：入口＝后台域名、路径正确；程序＝登录和会话已验证；数据库＝目标账号正确，业务记录待核对。**

### 01.6 用一笔旧订单验收

从后台打开一笔恢复前已存在的订单，记录订单编号、金额、状态。到已确认的数据库，按同一编号查询对应行。

查询模板中的表名、字段名和编号换成现场值：

```sql
SELECT order_no, amount, status
FROM orders
WHERE order_no = '待核对的旧订单编号';
```

金额先核对“元还是分”“总额还是实付”；状态先看代码中的枚举映射。页面显示“已支付”、数据库存数字时，要通过代码证明二者对应。

再退出、重新登录，重新打开这笔订单。若金额或状态不同，只查数据库这一格：实例、库名、租户、表、缓存来源；若页面请求到了另一接口，回查程序这一格。

**验收结果：** 原域名进入正确商城，正确 PHP 程序处理请求，页面与库中同一旧订单的编号、金额、状态一致。首页 200、面板运行中、欢迎页均不单独计为完成。

**三格回填：入口＝已验证；程序＝已验证；数据库＝同编号旧记录已核对。**

## 02 Java：恢复站点机与数据库机

<span id="073-java-站库分离恢复入口应用与依赖网络"></span>


| 三要素 | 填表示例，现场按实际替换 | 从哪里确认 |
|---|---|---|
| 浏览器入口 | `https://admin.test:443`；接口为 `https://api.test:443` | Nginx 配置、浏览器实际请求 |
| 实际程序 | `/srv/portal/portal.jar`，活动 profile 为 `prod`，监听 `127.0.0.1:9098` | 原启动参数、服务配置、启动日志 |
| 实际数据库 | `db.test:3306/portal`，域名指向数据库副本；Redis 另记地址和库号 | 生效配置、数据库连接结果 |

### 02.1 从原启动方式认准程序，不先解压所有 JAR

先给站点机、数据库机及其数据卷做快照，限制外联。停止与页面查看无关的短信、支付回调和定时业务任务；所需连接仅指向副本。后续改配置、账号、Redis 或 class 均在副本上进行。

有宝塔，先看 **网站 → Java 项目**；部分版本为独立“Java 项目”入口。记录项目路径、JDK、工作目录、启动参数、端口、运行用户和日志位置。面板账号与业务后台账号分别记录。

没有宝塔，查看现有进程和原服务：

```bash
pgrep -af java
```

已找到服务名时：

```bash
systemctl cat portal
```

程序未运行，再检查原运行用户的命令历史、启动脚本和日志。历史命令是线索，当前服务配置才决定下一次怎样启动。

活动 profile 先认启动参数：

```text
-Dspring.profiles.active=prod
```

或：

```text
--spring.profiles.active=prod
```

同时查看服务环境中的 `SPRING_PROFILES_ACTIVE`、外部配置位置和配置导入。基础配置、活动 profile 配置、外部配置可能叠加；不要只抽出一个 `application-prod.yml` 就认定全部参数。最后用启动日志确认实际激活的 profile。[Spring Boot 外部配置说明](https://docs.spring.io/spring-boot/reference/features/external-config.html)

**进入下一步的结果：** 确定唯一的业务 JAR 或 WAR、工作目录、JDK 和实际配置来源。

**三格回填：入口＝待查；程序＝包、启动方式、profile 已确定；数据库＝待读生效配置。**

### 02.2 把域名、前端和后端连成一条实际路径

有宝塔：

- **网站 → 设置 → 域名管理、SSL**：记录浏览器入口。
- **网站 → 设置 → 反向代理、配置文件**：记录后端地址和路径处理。
- **文件**：打开前端目录及 JAR/WAR 副本。
- **Java 项目**：核对项目端口与反向代理目标。

没有面板，查看原 Nginx 站点配置中的 `listen`、`server_name`、`root`、`proxy_pass`。

以压缩工具打开 JAR 副本，查看 `BOOT-INF/classes/` 下的基础配置、活动 profile 配置；外部文件和服务环境中的覆盖项也要一并记入。至少记录：

- 数据库主机、端口、库名、用户名。
- Redis 地址、认证方式、逻辑库号。
- 日志中实际阻断启动的注册中心、消息队列等依赖。
- 对象存储地址及本地附件是否齐全。

对象存储缺失可以先继续恢复页面和数据库，但要把附件功能记为待验收，不能据此宣布整个业务完整。

#### 如果拿到的是 WAR

仍用原 Tomcat，不把普通 WAR 当作独立 JAR 启动。

依次看：

- 原服务中的 `CATALINA_BASE` 和 JDK。
- `conf/server.xml` 中的 Connector、Host、`appBase`。
- `conf/Catalina/localhost/` 中的 Context 配置。
- 应用的 `META-INF/context.xml`、`WEB-INF/classes/` 配置，以及 JNDI 数据源。

普通 `portal.war` 常对应 `/portal/`，但 `ROOT.war`、Context 配置和代理路径会改变浏览器入口，以实际部署关系为准。[Tomcat Context 说明](https://tomcat.apache.org/tomcat-8.5-doc/config/context.html)

**进入下一步的结果：** 浏览器域名能追到前端目录或代理，代理能追到具体 JAR/WAR 与端口、上下文路径。

**三格回填：入口＝已登记；程序＝前端、后端及代理关系已对应；数据库＝连接参数已登记，待验证。**

### 02.5 先用现成前端，只改浏览器真正请求的地址

只有源码、没有可用构建产物时，才按 `package.json`、锁文件和原 Node 版本构建。先检查构建脚本，再使用对应包管理器；确认确实采用 npm 且存在匹配锁文件时，才在工作副本中执行：

```bash

```

```bash

```

打开浏览器开发者工具 **Network**，点击一个列表或详情，找实际接口请求：

- 请求已经是相对路径 `/api/`：先修 Nginx 代理，不替换前端全部字符串。
- 请求使用旧域名：能通过操作机 hosts 和原域名绑定恢复，就保留域名。

### 02.6 登录按阻断点选择：重算口令、短时验证码、单 class 调整

先从登录接口追到查询的账号表、账号主键和认证分支。以下方法分别解决不同问题，不是依次全部执行。

#### A．口令不明，但算法可复现：重算目标用户口令

保存目标账号原记录，确认代码是否使用用户名、明文、用户 salt、全局密钥、迭代次数或特定编码。

例如代码确实计算：

```text
MD5(用户名 + 明文口令 + 该用户的 salt)
```

就在本地调用原项目的摘要函数，按原字符编码、拼接次序、大小写输出重算。不要凭数据库字段长度猜算法。

将新结果交给原校验函数验证，通过后只更新该用户的口令字段。若字段带 `{bcrypt}` 等算法标识，保留完整存储格式。MD5 重算不是解密。

**本分支通过标志：** 正确临时口令通过、错误口令仍失败，目标账号进入正常权限范围。

#### B．登录读取 Redis 短信码：写入一个有期限的测试验证码

适用于验证码确实由本地 Redis 校验，外部短信发送只是交付渠道的情况。

从代码确认 Redis 实例、库号、完整键名、手机号格式、业务前缀、值类型和序列化方式。手机号、账号、用途、请求令牌都可能参与构造键。

只有确认值是普通字符串时，才使用以下形式。把 `DB_INDEX`、`EXACT_KEY`、`TEST_CODE` 换成代码对应值：

```bash
redis-cli -n DB_INDEX TYPE 'EXACT_KEY'
```

确认没有需要保留的现有值后：

```bash
redis-cli -n DB_INDEX SET 'EXACT_KEY' 'TEST_CODE' EX 120 NX
```

```bash
redis-cli -n DB_INDEX TTL 'EXACT_KEY'
```

看到 `OK` 且 TTL 为正数后，在两分钟内提交同一账号、同一用途的验证码。`NX` 未成功就先查已有键，不覆盖未知会话。若是 JSON、Hash 或 Java 序列化值，使用项目原来的写入函数，不把字符串强塞进去。`SET ... EX` 可在写入时同时设置过期时间。[Redis SET 说明](https://redis.io/docs/latest/commands/set/)

**本分支通过标志：** 正确验证码能用，错误验证码失败；成功后验证码按原逻辑消费或到期失效。

#### C．校验依赖外部服务，前两种均不适用：只调整一个 class

适用于副本中的特定校验依赖外部短信服务，且该判断确实集中在一个独立 class 的情况。先确认不是配置错误或 Redis 序列化错误。

操作顺序：

1. 保留完整原 JAR；另建待修改副本，记录两者哈希。
2. 反编译并定位实际加载的类及方法，确认它位于 `BOOT-INF/classes/`，还是某个依赖 JAR 内。
3. 使用原 JDK 版本、目标字节码级别和原依赖编译。只改该测试账号对应的验证码校验分支，保留账号状态、口令、角色与其他账号的校验。
4. 检查编译结果是否产生内部类或其他依赖变化。若需要同时替换多个类，就不把它称作“单 class 替换”。
5. 用归档工具仅替换副本中原位置的那个 class，保留包结构、启动清单和其他条目；有签名校验的包不能靠删除签名文件草率处理。
6. 停止旧实例，用原启动方式指向修改副本；从日志、加载路径和实际请求确认运行的是它。

**本分支通过标志：** 指定测试分支生效，其他账号和错误输入仍按原逻辑处理；恢复原 JAR 后，原校验行为恢复。记录这是“修改后副本可操作”，不是原认证流程完全恢复。

无论采用哪种方式，账号禁用和角色不足都按代码中的实际字段另查，不能靠跳过认证替代。

**三格回填：入口＝后台路径正确；程序＝实际登录分支已验证；数据库＝目标账号和会话已对应，旧业务记录待验收。**

### 02.7 用旧业务编号同时核对页面、接口和库

后台打开一条旧业务记录，记录编号、金额、状态。Network 中确认这条详情由哪个接口返回，再在数据库副本中按同一编号查询。

**三格回填：入口＝已验证；程序＝前端、代理、Java 实例已验证；数据库＝同编号旧记录的金额、状态已核对。**

### 03.4 把 Nginx 接到正确协议，不只是正确端口

同样叫“socket”，也可能使用不同协议。HTTP 代理对着 uwsgi 协议端口会失败；不要因此重装 Python。[uWSGI 协议说明](https://uwsgi.readthedocs.io/en/latest/WSGIquickstart.html)

```bash

```

```bash

```

| 现象 | 只查这一格 | 下一步 |
|---|---|---|
| 欢迎页、别的站 | 入口 | 核对 Host、端口、虚拟主机和已加载配置 |

### 03.5 用项目自己的认证实现重设一个账号

先确认真实登录路由。Django 不一定挂在 `/admin/`，也不一定用默认用户模型；Flask 没有通用管理员表和通用哈希方式。

保存目标账号原记录，查看登录代码和哈希器：

- 自定义 `salt` 字段：按该用户自己的 salt、原算法和参数重算。
- Django：使用项目设置中的用户模型和原密码哈希器。
- Flask：确认使用 Werkzeug、bcrypt、其他库还是自定义函数；使用项目安装的版本及原校验函数。

以**标准 Django PBKDF2 存储格式**为例，需要沿用该用户的原 salt 和迭代次数时，在已激活的原虚拟环境、原项目目录中进入：

```bash
python3 manage.py shell
```

逐行操作；`USER_ID` 换成已经确认的目标主键：

```python
from django.contrib.auth import get_user_model
from django.contrib.auth.hashers import identify_hasher
from getpass import getpass
u = get_user_model().objects.get(pk=USER_ID)
h = identify_hasher(u.password)
d = h.decode(u.password)
p = getpass("本次临时口令：")
new_hash = h.encode(p, d["salt"], d["iterations"])
h.verify(p, new_hash)
```

仅在输出 `True`、确认目标账号及原记录已保存后写入：

```python
u.password = new_hash
u.save(update_fields=["password"])
```

这段不套用于 bcrypt、Argon2 或自定义哈希器；它们使用各自的参数和编码接口。Django 支持配置不同哈希器，校验应与项目实际实现一致。[Django 口令管理说明](https://docs.djangoproject.com/en/stable/topics/auth/passwords/)

登录仍失败时，分别查验证码、账号状态、角色、会话存储与 Cookie。标准 Django 后台的 `is_active`、`is_staff` 与业务权限有关，不要直接给所有用户加超级管理员权限。

**进入下一步的结果：** 目标账号登录成功、错误口令失败、刷新后会话保持，业务页面可读。

**三格回填：入口＝登录路径正确；程序＝认证与会话已验证；数据库＝目标账号已对应，旧记录待核对。**

### 03.6 对一条旧业务记录，确认不是另一个空项目

打开旧记录详情，记下编号、金额、状态。到第 2 步确认的库中查询同一编号，核对金额单位、状态枚举和租户条件。

如果页面数据来自缓存，先核对接口原始响应和缓存来源，不直接清空整个 Redis。SQLite 项目还要核对服务实际打开的数据库绝对路径。

重新登录并再次打开同一条详情。只读到了 Django 欢迎页、调试首页、HTTP 200，或者项目显示运行中，均未达到这一结果。

**三格回填：入口＝已验证；程序＝原项目与运行环境已验证；数据库＝同编号旧记录的金额、状态已核对。**

## 04 Node.js：分清静态前端与真正后端


| 三要素 | 填表示例，现场按实际替换 | 从哪里确认 |

| 浏览器入口 | `https://app.test:443`，`/api/` 转给后端 | 网站设置、Nginx、浏览器 Network |

### 04.1 先看是谁处理请求，不凭 `package.json` 下结论

判断材料：

- 只有 `index.html`、CSS、JS，浏览器直接加载：这一部分按静态前端提供。
- 有 `package.json`：只能说明存在 Node 工具链，不能证明它是后端。
- 原进程执行服务器入口、SSR 服务或框架生产启动命令：才按 Node 服务恢复。
- 有 `dist`：查看内容；它也可能是后端编译后的 JavaScript，不一定是静态目录。

没有宝塔，查看进程及原服务：

```bash

```

```bash
systemctl cat app-api
```

原来使用 PM2 时，在原运行用户下查看：

```bash
pm2 list
```

```bash
pm2 describe app-api
```

不要用 root 的空 PM2 列表否定另一用户已有的项目。

**进入下一步的结果：** 明确哪些文件直接交给浏览器，哪个进程负责接口或服务端渲染。

**三格回填：入口＝待查；程序＝前端与后端职责已分清；数据库＝待查。**

### 04.2 读启动脚本和连接代码，填实后端配置

查看 `/srv/app/api/package.json` 的 `scripts`，并追到实际入口。核对 `.nvmrc`、`engines`、`packageManager`、锁文件和原服务记录；版本冲突时，以原可运行部署及日志进一步确认。

数据库参数可能来自：

- 项目配置文件或 `.env`。
- PM2 的环境配置。
- systemd 的环境文件。
- 宝塔 Node 项目的环境变量。
- 容器或原启动命令。

不要假定 Node 会自动加载 `.env`；看程序是否调用了对应加载方式。`NODE_ENV` 也不保证一定选择某个同名文件，要看代码。

记录实际数据库类型、主机、端口、库名或文件路径、账号。MongoDB 额外确认认证库 `authSource`，关系库确认 schema、表前缀和租户。

有宝塔用 **数据库** 检查原表；外部库从实际运行环境使用应用账号验证。例如：

```bash
mysql -h db.test -P 3306 -u app_user -p app
```

```sql
SELECT DATABASE();
```

SQLite 检查绝对路径；相对路径随工作目录变化可能连到空库。数据库域名可通过实际运行环境的 hosts 指向副本，硬编码 IP 则用原配置入口修改。

**进入下一步的结果：** 应用账号能读取旧记录，启动环境与连接代码使用同一套参数。

**三格回填：入口＝待查；程序＝启动脚本和环境已确定；数据库＝正确实例及旧数据已确认。**

### 04.3 保留现成依赖，避免一次安装把原环境换掉

已有 `node_modules` 且运行正常，先沿用。不要直接执行 `npm update`。

缺依赖或原生模块不兼容时，先确认错误：

- `Cannot find module`：缺包、工作目录错误，还是构建文件未生成。
- 原生模块 ABI 错误：核对 Node 版本、系统架构、原生模块版本。
- ESM/CommonJS 错误：核对入口、`type` 和原启动方式。
- 构建脚本顺带迁移、清库、种子初始化：先拆开这些动作，不在已有业务库上直接执行。

只有需要恢复依赖时，才在工作副本中按原锁文件安装。项目确实采用 npm 时可先执行：

```bash
npm ci --ignore-scripts
```

这会重建 `node_modules`；原依赖先保留。`--ignore-scripts` 会跳过安装生命周期脚本，某些原生模块随后需要按已核对的原流程单独构建。它也不等于把显式执行的 `npm start` 变成无操作。[npm ci 说明](https://docs.npmjs.com/cli/v11/commands/npm-ci/)

原项目用 pnpm 或 Yarn 就沿用对应版本，不生成一套新的 npm 锁文件。

有前端构建产物直接用；只有源码时，才按已核对的脚本生成前端产物。后端 TypeScript 也先看有没有原编译输出，缺失时才构建。

**进入下一步的结果：** 原入口及它需要的依赖、构建产物齐全，没有为了启动而改变数据库结构。

**三格回填：入口＝待接通；程序＝原版本依赖与产物已就绪；数据库＝原业务数据保持不变。**

### 04.4 只用一个管理器启动，并接上代理

有宝塔，在 **Node 项目** 按原环境启动并查看日志；然后到 **网站 → 设置 → 反向代理** 核对后端端口。不要再用 PM2 或终端启动第二份。

没有宝塔，沿用原管理方式。原来用 systemd：

```bash
systemctl start app-api
```

```bash
journalctl -u app-api -n 80 --no-pager
```

原来用 PM2：

```bash
pm2 start app-api
```

```bash
pm2 logs app-api --lines 80
```

以上两套只选实际使用的一套。已有进程就核对，不重复启动。

检查监听：

```bash

```

确认 Nginx 的目标地址、端口及路径前缀与后端一致。后端仅监听 `127.0.0.1`、由同机 Nginx 代理是正常方式，不必为测试开放所有网卡。

**进入下一步的结果：** 目标进程监听正确地址，原只读接口有响应，代理配置通过检查。

**三格回填：入口＝代理关系已建立；程序＝唯一目标实例在处理；数据库＝应用连接正常。**

### 04.5 从浏览器确认接口方向，再恢复登录

操作机 hosts 映射原域名，浏览器打开业务页，Network 中查看实际请求：

- 欢迎页、其他站：查入口域名与虚拟主机。
- 502：查后端监听、进程日志和代理目标。
- 接口 404：查路由及 `/api/` 前缀是否被代理保留或去掉。
- 前端请求旧 IP：只改当前实际加载的接口配置；有原域名可映射时优先保留。
- 请求返回 HTML 而不是 JSON：查是否误走 SPA 首页回退。
- 登录成功后又退出：查 Cookie 域、HTTPS、代理信任设置、会话库和系统时间。

前端现成 `dist` 修改后，在禁用缓存状态下确认 Request URL 已改变；仅改源码 `.env` 不代表运行中的前端已经改变。

登录处理顺序：

1. 找实际登录路由，确认它查哪张用户表或集合。
2. 保存目标用户原口令、salt、状态和角色相关记录。
3. 用原哈希实现按该用户自己的 salt、算法参数、编码重算；bcrypt、Argon2 等保留完整编码和原预处理逻辑。
4. 用原比较函数先验证，再只更新目标主键的一条记录。
5. 正确口令应通过，错误口令仍失败；再单独检查验证码、状态和权限。

不要把会员表当后台管理员表，也不要因会话失败反复修改口令。

**进入下一步的结果：** 浏览器请求到目标 Node 实例，目标账号进入业务页面并能保持会话。

**三格回填：入口＝前端与接口地址已验证；程序＝路由、认证和会话已验证；数据库＝目标账号已对应，旧记录待核对。**

### 04.6 按同一编号对页面、接口与数据库

选一条恢复前已有的订单或账务记录，在页面记录编号、金额、状态，再查看对应接口原始响应，最后查询数据库同编号记录。

关系库核对 schema、租户和金额单位；MongoDB 核对实际数据库、集合及 `_id` 与业务编号的区别。不要拿另一环境中恰好相同的展示编号验收。

页面与接口不同，查缓存或前端字段映射；接口与库不同，查运行中的环境变量、实际实例、租户和缓存。只修不对应的那一格。

重新登录后再次查看该记录，结果仍一致才通过。面板显示运行中、Node 输出“started”、首页 200 都只是中间结果。

**三格回填：入口＝已验证；程序＝目标 Node 实例已验证；数据库＝同编号旧记录的金额、状态已核对。**

| 三要素 | 填表示例，现场按实际替换 | 从哪里确认 |
|---|---|---|
| 浏览器入口 | `http://portal.test:8080`，必要时带原应用路径 | IIS 网站 → 绑定；应用和虚拟目录 |

- **应用程序池 → 高级设置**：运行身份、32 位选项、CLR 和托管管道。

物理路径不存在，先检查磁盘、盘符和共享路径。数据盘未接入时，不在同名空目录放一个新网站。

需要命令核对时，以管理员 PowerShell 执行：


```powershell

```


`Portal` 是示例 IIS 站点名，换成实际名称。

**进入下一步的结果：** 原绑定、业务路径、实际文件和应用程序池能对应起来。

**三格回填：入口＝绑定与应用路径已登记；程序＝实际目录、池已找到；数据库＝待查。**

### 05.2 认清程序类型，打开真正的连接配置

在 IIS 的 **内容视图、处理程序映射、模块** 中结合文件判断：

| 程序类型 | 实际配置位置与运行要求 |
|---|---|
| 经典 ASP | 从业务 `.asp` 页追 `include` 中的连接串；核对 ASP 功能、COM/ADO/OLE DB 提供程序及位数 |
| ASP.NET Framework | 查看站点及父级 `web.config` 的 `connectionStrings`、`appSettings`、外部 `configSource`；核对原 CLR、管道模式和程序集 |
| ASP.NET Core | 查看发布目录 `web.config` 的 `processPath`、`arguments`、`hostingModel`；连接串通常还要追 `appsettings.json`、活动环境文件和环境变量 |
| 静态 HTML | 由静态文件处理器提供；页面若调用接口，另记录那个接口的程序与库 |

ASP.NET Core 不按传统 CLR 版本选择运行时；通常使用“无托管代码”的应用程序池，并需要与发布方式匹配的运行时及 Hosting Bundle。`processPath` 指向 `dotnet` 还是程序自身 EXE，要与实际发布文件一致。[ASP.NET Core IIS 托管说明](https://learn.microsoft.com/en-us/aspnet/core/host-and-deploy/iis/)

不要统一打开“启用 32 位应用程序”。只有旧 COM、数据库驱动或程序位数确实需要时才调整；应用程序池身份也不要直接换成管理员。

**进入下一步的结果：** 明确处理请求的是 ASP、Framework、Core 还是静态处理器，连接配置的覆盖关系已查清。

**三格回填：入口＝已登记；程序＝类型、运行时和配置来源已确定；数据库＝连接目标已登记，待验证。**

### 05.3 先让正确身份读到正确数据库

打开连接串，分别记录：

- 服务器、实例或端口。
- 数据库名称。
- SQL 账号，还是 Windows 集成认证。
- 文件路径、驱动、加密和证书相关参数。

使用 SQL Server 管理工具连接副本，核对数据库状态和业务表。Windows 集成认证时，要进一步确认实际应用程序池身份是否有访问权限；管理员在管理工具中连接成功，不代表站点身份成功。

远程 SQL Server 使用命名实例时，核对实际 TCP 端口及实例解析方式。只改 hosts 不会自动解决实例发现和端口变化。

数据库驱动报证书或加密错误，核对原驱动版本、证书名称和连接串设置，不把所有 TLS 设置一律关闭。

需要测试已确认的 TCP 端口时：

```powershell
Test-NetConnection 192.168.56.20 -Port 1433
```

连接数据库后：

```sql
SELECT DB_NAME();
```

再查一条旧业务记录。

若是 Access 或 SQLite，确认程序真正使用的文件绝对路径、驱动位数、文件与目录权限；不要因相对路径错误生成一个空文件。SQL Server 数据文件按原实例和兼容版本恢复，不能把一个 MDF 文件当普通网页资源放进站点目录了事。

**进入下一步的结果：** 正确库有旧数据，并且应用实际使用的认证身份具备需要的读取权限。

**三格回填：入口＝待访问；程序＝运行身份已确认；数据库＝正确库及身份已验证。**

### 05.4 启动原应用程序池和站点，按子状态查失败

在 IIS 管理器中先启动目标应用程序池，再启动网站。不要为修一个站点先重启整台 IIS。

PowerShell 对应操作：

```powershell
Start-WebAppPool -Name "PortalPool"
```

```powershell
Start-Website -Name "Portal"
```

操作机 hosts 指向副本：

```text
192.168.56.10 portal.test
```

浏览器使用登记的协议、端口和应用路径。HTTPS 站点保留主机名并检查对应证书、SNI，不用 IP 访问结果替代域名结果。

失败时查看：

1. **网站 → 日志** 中配置的实际日志目录和站点 ID。
2. 对应日志行的 `sc-status`、`sc-substatus`、`sc-win32-status`。
3. **事件查看器 → Windows 日志 → 应用程序**。
4. 程序自身日志。

| 现象 | 只查这一格 | 具体下一步 |
|---|---|---|
| IIS 欢迎页、其他站 | 入口 | 核对绑定、主机名、端口和应用路径，再查命中的物理目录 |
| 404 | 程序 | 核对业务应用路径、路由、处理程序和 URL Rewrite |
| 403.14 | 程序 | 查默认文档或应用部署，不为显示目录直接开目录浏览 |
| 500.19 | 程序 | 按详细错误查配置行、缺失模块、重复配置或读取权限 |
| 503 | 程序 | 查应用程序池停止原因、身份凭据和快速失败保护 |
| Core 500.30、500.31、502.5 | 程序 | 查进程启动日志、运行时、Hosting Bundle、`processPath` 和位数 |
| 数据库登录、连接异常 | 数据库 | 查连接目标、运行身份和数据库日志 |

IIS 的状态码、子状态和系统错误码应一起看，不能只凭“500”判断是数据库故障。[IIS 错误排查说明](https://learn.microsoft.com/en-us/troubleshoot/developer/webapps/iis/site-behavior-performance/troubleshoot-http-error-code)

ASP.NET Core 确需开启 stdout 日志时，只短时启用，并给应用池身份授予日志目录所需写权限；取得启动错误后恢复原设置。

**进入下一步的结果：** 业务页由目标应用处理，不是默认欢迎页，程序日志没有阻断性异常。

**三格回填：入口＝目标绑定和业务路径已验证；程序＝目标池实际处理请求；数据库＝应用连接正常。**

### 05.5 区分 IIS 身份验证与网站自己的登录

先在 **网站 → 身份验证** 中查看启用了匿名、Windows 还是其他 IIS 身份验证方式，再判断浏览器显示的是哪一层登录：

- 浏览器弹出的 Windows 凭据框：先查 IIS 身份验证、运行环境和身份权限。
- 网站自己的登录表单：追网站代码、用户表和会话。
- IIS 管理员、Windows 管理员、数据库账号与网站管理员：四者不要混用。

需要重设业务口令时，保存目标账号原记录，查看原代码或程序集中的实际比较逻辑。传统 ASP、ASP.NET Membership、ASP.NET Identity 与自定义认证格式不同，不存在通用摘要。

使用该项目原提供程序或哈希实现，按目标用户自己的 salt、算法参数和编码重算；摘要嵌入版本、salt 和迭代参数时保留完整格式。先用原校验方法验证，再只更新目标账号。

口令通过但登录立即丢失，检查：

- Cookie 域名、路径、HTTPS。
- 应用是否意外跨了不同站点或应用边界。
- 原 `machineKey`、数据保护密钥和会话存储是否缺失。
- 应用程序池是否因异常持续回收。

不要重生成全部密钥来“试一下”，也不要把整个站点目录改成所有人完全控制。

**进入下一步的结果：** 目标账号完成网站登录，刷新仍保持会话，能打开原业务列表。

**三格回填：入口＝登录所在站点与路径正确；程序＝认证、密钥和会话已验证；数据库＝目标账号已对应。**

### 05.6 用旧记录确认不是连到了另一套库

在业务页面打开一条旧记录，记录编号、金额、状态。到实际连接的数据库，用同一编号查询；SQL Server 还要确认当前数据库及 schema，文件库确认绝对路径。

对照金额单位和状态映射，重新登录后再打开同一记录。

页面数据不符时：

- 请求去了另一个应用：查程序格。
- 应用连到测试库、默认库或另一实例：查数据库格。
- 浏览器打开了另一绑定：查入口格。

目标是页面与库中同编号记录的金额、状态一致，不是 IIS 显示“已启动”、应用池运行中或首页 200。

**三格回填：入口＝已验证；程序＝目标网站、应用池和程序已验证；数据库＝同编号旧记录已核对。**

## 06 静态站：恢复页面，并识别它背后的接口


| 三要素 | 填表示例，现场按实际替换 | 从哪里确认 |
|---|---|---|
| 浏览器入口 | `http://archive.test:80` | 网站域名、端口、原 Web 配置 |
| 实际程序 | Nginx 提供 `/srv/archive/dist/index.html` 及其引用资源 | 网站目录、实际响应文件、浏览器 Network |
| 实际数据库 | 纯静态：无；有接口：填写“接口程序 → 实际库”，未恢复前标待核对 | 页面请求、接口配置及后端连接配置 |

### 06.1 先确认材料确实能按静态文件提供

先给文件和相关后端、数据库副本做快照，限制外联。站点目录、接口地址和构建配置的修改只在副本进行，原文件另存。

有宝塔，先进入 **文件** 查看目录，再看 **网站** 中是否已有站点。面板账号只用于管理，不等于页面中某个业务后台账号。

找到真正的入口 HTML，查看它引用的脚本和样式：

- 根目录只有一层套一层的文件夹：继续找到包含入口与资源的那一层。
- 已有完整 `dist` 或导出目录：直接使用。
- `dist` 中是服务器入口 JavaScript，需要 Node 处理：这不是纯静态产物。
- 只有源码和构建配置：先确认原构建方式，之后才构建。

同时检查浏览器脚本是否发起 API、WebSocket、登录、表单或数据查询请求。首页没有请求，不代表详情页和登录页没有接口。

**进入下一步的结果：** 明确哪些文件能直接提供，哪些操作需要独立后端。

**三格回填：入口＝待查；程序＝静态入口与资源目录已找到；数据库＝尚待判断有无接口依赖。**

### 06.2 把站点目录指到入口所在层，不安装多余运行时

有宝塔：

1. 已有站点：打开 **网站 → 设置 → 域名管理、网站目录**，核对原域名和端口。
2. 没有站点：确认原目录、域名和端口后再添加，PHP 选择纯静态，不创建数据库。
3. **网站 → 设置 → 默认文档**：核对实际入口文件。
4. **软件商店 → 已安装**：沿用原 Nginx 或 Apache，不为静态页安装 PHP。
5. **文件**：确认站点用户能读取入口和资源，不把源码备份放进公开目录。

没有宝塔，使用已有 Web 服务的原站点配置。原配置确实缺失、且已确认采用 Nginx 时，可以建立最小静态站点：

```nginx
server {
    listen 80;
    server_name archive.test;
    root /srv/archive/dist;
    index index.html;

    location / {
        try_files $uri $uri/ =404;
    }
}
```

把它放进原 Nginx 已包含的站点配置目录，不覆盖全局配置。检查通过后再重载：

```bash
nginx -t
```

```bash
systemctl reload nginx
```

这是普通静态文件规则，还不是所有 SPA 的路由规则。

**进入下一步的结果：** 站点配置明确指向已有入口文件，配置检查通过。

**三格回填：入口＝域名和端口已配置；程序＝Web 服务与静态目录已对应；数据库＝待通过实际请求确认。**

### 06.3 打开原域名，先修资源路径，再修前端路由

操作机 hosts 指向站点副本：

```text
192.168.56.10 archive.test
```

使用登记的完整 URL 打开，不用双击 HTML 的 `file://` 结果代替网站运行结果。

浏览器开发者工具 **Network** 中检查 HTML、CSS、JS、图片和字体：

- **欢迎页或别的网站**：查入口格中的域名、端口及命中站点。
- **HTML 正常，资源 404**：查程序格；确认目录是否错了一层、文件名大小写、资源前缀、`base` 路径和子目录部署。
- **资源请求返回 200，但内容是 HTML**：查程序格中的错误回退规则；这不是资源正常。
- **HTTPS 页面阻止 HTTP 接口或资源**：核对原协议和代理，不把问题归结为文件缺失。
- **页面内跳转正常，刷新详情 404**：确认是否为 history 模式 SPA，再设置前端路由回退。

已确认是 SPA 时，可让前端路由回到 `index.html`；但 `/api/`、真实资源目录及下载路径应保留各自规则，不能把 API 404 也改成首页 200。

只有源码、没有可用产物时，才按原 Node 版本、包管理器和锁文件构建。先核对构建脚本、部署子路径和接口环境；在受控构建副本完成，再让网站目录指向生成的入口层。

**进入下一步的结果：** 首页、一个详情或深层路径直接刷新都正常，关键资源返回正确类型与内容。

**三格回填：入口＝原域名已命中；程序＝静态文件与页面路由已验证；数据库＝根据接口检查填写“无”或“待恢复”。**

### 06.4 有接口就追到它，不给静态页硬加数据库

依次点击登录、列表、详情、搜索和表单，观察实际请求。只改浏览器真正使用的接口地址：

- 相对路径 `/api/`：优先恢复原反向代理。
- 原域名：能映射到副本就保留域名。
- 写死旧 IP：定位当前加载的运行时配置或构建文件，只改对应地址。
- 地址藏在源码环境文件里：确认是否需要重新构建；修改源码不会自动改变已发布 JS。

然后按接口本身的类型恢复。静态页面仍由静态站点提供，不把整个前端改成 PHP、Java 或 Node 服务。

| 接口类型 | 在接口副本上完成的恢复动作 |
|---|---|
| PHP | 找原入口和框架版本；有宝塔就到网站设置核对运行目录、PHP 与伪静态；从生效配置接原库，先验证一条只读业务接口 |
| Java JAR/WAR | 找原服务、JDK、活动 profile 和外部配置；WAR 沿用原 Tomcat；将数据库域名映射到副本，启动后确认代理目标实际监听 |
| Python | 找原虚拟环境、启动模块和 settings；沿用 Gunicorn、uWSGI 或原 ASGI 服务；代理协议与原监听一致 |
| Node.js | 找真正的服务端入口、Node 版本和生效环境；沿用面板、PM2 或原服务中的一种启动方式；不要把前端 `package.json` 当后端 |
| IIS | 到接口所在 Windows 副本核对绑定、应用路径、物理目录和应用池；按实际程序配置连接数据库，再启动目标池和站点 |

每个接口都按同一条短链检查：

1. **配置里的业务账号能读取正确库的旧记录。**
2. **原运行方式能启动接口程序，并在日志中确认无阻断错误。**
3. **原只读接口能直接返回业务格式。**
4. **页面经过原域名和代理调用同一接口，返回同一数据。**

若接口程序或数据库材料缺失，把数据库格保留为“接口已定位，后端或数据待恢复”。静态文件能够浏览，并不代表业务系统完整。

需要接口登录时，先确定账号表及认证逻辑，保存目标用户原记录，按原算法与该用户自己的 salt 重算并用原校验函数验证。接口验证码、会话或来源限制分别查对应分支，不往静态 JS 中塞一个“通用管理员口令”。

**进入下一步的结果：** 纯静态站确认没有运行时业务接口；有接口的站点确认浏览器请求、后端实例与数据库副本对应。

**三格回填：入口＝页面及接口 origin 已确认；程序＝静态文件和实际接口处理者已确认；数据库＝无，或接口所连库已验证。**

### 06.5 验收分两种，别给纯静态站虚构数据库

#### 纯静态站

重新打开首页、一个深层页面和一份实际资源，检查：

- URL、页面内容和站点目录一致。
- 深层地址直接打开、刷新均正常。
- 图片、样式、脚本返回实际文件，不是被首页回退掩盖的 200。
- 页面应有的功能已检查，没有遗漏接口依赖。

如果业务数据来自静态 JSON，就按同一编号对照页面与该 JSON 的金额、状态，并把它记在“程序”格的数据文件说明中；它不是数据库。

**三格回填：入口＝已验证；程序＝页面、路径和资源已验证；数据库＝无，已确认。**

#### 带业务接口的静态前端

在页面打开一条旧业务记录，记录编号、金额、状态；在 Network 中找到该详情接口，再到接口实际连接的库查询同一编号。

核对三处：

- 页面显示。
- 接口原始响应。
- 数据库字段及金额单位、状态映射。

页面和接口不同就查前端映射或缓存；接口和数据库不同就查后端实际库、租户和缓存。静态首页 200、所有资源能加载，仅代表前端这一部分通过。

**三格回填：入口＝页面与接口已验证；程序＝静态前端和对应后端已验证；数据库＝同编号旧记录的金额、状态已核对。**
