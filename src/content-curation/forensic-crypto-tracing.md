## 01 实战路线：确定对象和证据范围

虚拟币取证先分清四个问题：**哪条链发生了什么交易、哪个平台账户发生了什么记账、哪些地址可能受同一主体控制、现实中谁实际操作**。公开交易记录通常只能直接回答第一项，后面三项需要钱包材料、平台账本、设备活动与支付记录补足。

接到材料后，先完成下面的顺序，再画资金流图：

1. 写清授权采集范围、目标地址或账户、资产、起止时间、材料完整度和需要回答的问题。
2. 保全镜像、手机备份、钱包状态文件、平台导出及链上响应；记录采集人、时间、工具版本、参数、文件大小和 SHA-256。
3. 从设备中找钱包地址、网络配置、交易哈希、平台 UID、订单号与聊天中的收款指令，建立候选表。
4. 按链和资产复核交易结果、转账事件、手续费、区块位置与查询覆盖范围。
5. 将链上交易和平台充提币记录对接，再用订单、支付流水、聊天与设备会话检验关联。
6. 对跨链、混币、离链划转和身份关联单独标记缺口；结论停在可复核的范围。

建议的工作目录如下。它是分析材料的组织方式，具体文件名以检材为准。

```text
evidence/
  device/                 镜像、手机备份、钱包状态文件
  chain/                  原始交易、回执、区块及分页响应
  platform/               UID、充值、提现、账内划转、订单和成交记录
  payment/                银行或支付机构流水
  communication/          聊天、邮件、通知与相关附件
work/                     解析副本及规范化表
output/                   清单、时间线、关联表、资金流图与报告
```

```bash
mkdir -p work output
find ./evidence -type f -print0 | sort -z | xargs -0 sha256sum > ./output/evidence-sha256.txt
find ./evidence -type f -printf '%p\t%s bytes\n' > ./output/evidence-files.txt
rg -n -i 'wallet|deposit|withdraw|txid|transaction|account|订单|充值|提现' ./work
```

检索用于定位已有文本副本；压缩、加密、数据库和二进制材料先按格式解析。动态数据库应连同日志文件和采集状态保全，不能把运行中的文件哈希变化直接解释为篡改。助记词、私钥和会话令牌保存在受控证据材料中，面向读者的资金图与普通报告使用证据编号和必要摘要。

## 02 用五张表承接资金流图

| 表 | 核心字段 | 用途 |
| --- | --- | --- |
| 链上事件表 | chain、网络、资产标识、tx_hash、区块哈希/高度、事件索引、from、to、原始数量、精度、执行结果 | 证明具体链上事件及数量 |
| 平台账本表 | 平台、UID、账本记录 ID、事件类型、资产、增减方向、数量、费用、状态、订单/成交/充提币 ID | 还原平台内部资金变化 |
| 对接表 | 链上事件 ID、平台记录 ID、充值地址、memo/tag、账户、有效时间段、关联条件 | 对接链与平台账户 |
| 关联证据表 | 地址/UID、设备、账号、记录位置、密钥或权限材料编号、独立印证、反例 | 区分地址控制、账户登记和实际操作 |
| 时间字典与事件线 | 时间原值、字段语义、单位、纪元、时区、UTC、精度、时钟误差、对象 ID | 解释先后关系及时间偏差 |

每条图边应能回到表中的具体行、数据库记录、日志位置或 JSON 字段。截图用于展示；原始响应、表格和解析规则用于复核。把重复截图或多个浏览器对同一交易的展示放在同一证据组，不能将它们当成多笔资金流。

## 03 充值地址、归集钱包与提现需要分别判断

### 03.1 充值地址不直接代表用户私钥控制

中心化平台可能给每个用户分配充值地址，也可能使用共享地址加 memo/tag，随后将资产归集到热钱包或冷钱包。进入交易所控制地址，只能先说明链上目的地；要确定入账到哪个 UID，需要平台对接信息。

复核充值时至少核对：网络、资产合约或原生币标识、地址、memo/tag、交易哈希、事件位置、金额、确认要求、到账状态和有效时间段。同一平台可能变更地址或账户绑定，当前标签不能自动回填历史归属。

归集是平台的钱包管理动作。若平台已确认某次充值记入账户 U，随后充值地址归集到热钱包 H，不能因此把 H 的全部余额、全部收款用户或后续所有提现都归到 U。

### 03.2 提现可能是批量付款

一笔链上交易可同时包含多个提现输出或多个代币转账事件；一个平台提现申请也可能经历审核、取消、重试、手续费调整及实际广播。关联时从提现记录 ID、目标网络/地址、实际到账数量、费用和链上事件位置逐项核对。

| 材料中的动作 | 应复核的对象 | 常见误判 |
| --- | --- | --- |
| 用户提交提现申请 | 平台申请及状态历史 | 将申请金额当成实际到账 |
| 平台显示已发送 | 广播记录及最终链上结果 | 把尚未确认或后来替换的交易当成最终结果 |
| 交易所热钱包批量转出 | 对应输出或事件、提现 ID | 将整笔批量金额算给单个用户 |
| 充值地址转入热钱包 | 归集记录与钱包管理关系 | 将热钱包全部资金认定为充值用户所有 |

## 04 平台账内划转、订单、成交与 P2P

平台内两个账户之间的划转可能只更新内部账本，不产生公开交易哈希。不存在链上转账不能否定已完成的账内划转；平台的内部记录 ID 也不能拿到区块链浏览器里当作交易哈希验证。

对平台材料按下列事件分组，保留原始状态：

| 类型 | 关键记录 | 判读边界 |
| --- | --- | --- |
| 充值/提现 | deposit_id、withdrawal_id、网络、地址、memo/tag、链上哈希、状态、数量和费用 | 链上成功与平台记账成功可能不同步 |
| 账内划转 | ledger_id、源/目标 UID、资产、方向、状态、关联业务 ID | 依赖平台账本，不能凭相同金额接出一条链上边 |
| 现货/币币交易 | order_id、fill_id、交易对、成交数量、价格、费用币种、实际结算 | 一个订单可多次成交；未成交委托不构成资产交换 |
| P2P/OTC | 订单、双方账户、托管/放币状态、付款方式、支付参考号、聊天及申诉记录 | 已标记付款不必然代表银行到账；已放币也不自动证明对价实收 |

将订单请求、订单修改、取消和实际成交分别统计。检查基础资产、计价资产和费用资产；买入 1 个单位 A 与支付若干单位 B 是同一兑换的不同记账方向，不能直接相加为“资金总额”。

P2P 关联需要核对币数量与法币金额、订单 ID 与支付流水号、双方身份信息、支付状态及时间范围。银行卡户名、平台认证姓名、手机持有人和实际操作者可以是不同人。付款凭证截图可能伪造或重复使用，优先与授权取得的银行/支付流水、平台状态历史及通信上下文交叉核对。

法币、虚拟币及平台兑付可能分阶段发生。时间接近、金额相似是候选条件；存在订单号、平台充提币记录、交易哈希或明确付款指令时，才能进一步解释为何属于同一业务。不能为拼成一条完整路径而强行让所有环节同秒发生。

## 05 跨链桥与兑换要建立两端对应关系

跨链时，源链上的一笔支出与目标链上的一笔收入通常是不同交易。协议可能采用锁定/铸造、销毁/释放或流动性池兑换，资产标识和数量也可能改变。先确认桥的具体机制与当时版本，再找关联记录。

1. 在源链原始交易、调用参数和回执日志中定位桥合约、目标链、接收人、nonce/message ID/transfer ID 等标识。
2. 保存桥浏览器或协议索引结果，记录查询时间、输入哈希、返回字段、页码和覆盖范围。
3. 在目标链找到对应消息处理或释放/铸造事件，复核目标交易、区块、实际接收地址、资产及数量。
4. 解释费用、汇率、滑点、分拆和退款；检查源链动作是否成功、目标链是否完成。
5. 建立“源事件 → 协议关联 ID → 目标事件”对接表，保留匹配条件和无法排除的候选。

只用时间与金额近似找到目标链记录时，写成候选跨链关联。桥服务存在批处理、多笔同额交易或路由中转时，金额接近不足以唯一匹配。桥合约收到资产也不等于接收人已在目标链到账。

同一个十六进制地址出现在两条 EVM 链上，不能省略 chain ID，也不能仅凭字符串相同就认定两笔资金属于同一业务。每一端都核对网络、资产、交易状态及相关签名或账户材料。包装代币、原生资产与兑换后的资产单独记账，不把两个链上的对应桥事件都累计为新增受害损失。

## 06 混币、CoinJoin 与隐私币的可见性边界

混币服务、协作交易和隐私币采用不同机制，不能用一张通用箭头图解释全部路径。

| 情况 | 可以保留的观察 | 需要限制的结论 |
| --- | --- | --- |
| 可识别混币存入 | 存入交易、金额、池或合约、时间、账户材料 | 不能直接认定某个近似时间的提款就是这次存入 |
| 疑似 CoinJoin/协作交易 | 多参与者共同构造交易的结构特征和候选分类 | 不能沿用“所有输入同一控制者”的朴素聚类 |
| 隐私币或隐私交易模式 | 公开可见结构、入口/出口服务及授权取得的终端/平台记录 | 不能假设公开账本显示真实发送者、接收者和金额 |
| 链上兑换后进入平台 | 已验证兑换、充值或提币事件 | 不能越过内部账本缺口接到任意同额提现 |

对混币出口，保留候选集合、过滤条件、时间范围、金额误差、排除理由与辅助证据。时间和金额模式可以指导进一步查询，不能单独证明唯一对应。使用隐私工具本身也不能直接推出违法目的。

Monero 等隐私币的公开可见字段与透明链不同；部分其他币种的隐私模式是可选的。必须按具体协议、交易类型和版本分析。终端钱包记录、合法取得的对手方或平台数据可能补足某些环节，旧版本研究结果不能直接宣称适用于当前网络。

## 07 归因结论分成观察、推断和印证

以下等级是分析报告的表达方式，用于提醒读者复核条件，不代替司法证明标准，也不把工具给出的数字自动变成法律意义上的置信度。

| 表达 | 例子 | 应附的材料 |
| --- | --- | --- |
| 直接观察 | 某链已确认交易中的事件从 A 转到 B | 原始交易、回执、区块位置、事件索引、数量换算 |
| 规则推断 | 按明确启发式，A 与 C 可能属于同一控制集 | 规则、适用链/版本、假设、反例、误聚类检查 |
| 多材料印证 | 平台充值记录将事件 X 记入 UID U，设备状态也记录该事件 | 对接字段、记录位置、时段、独立来源及冲突检查 |
| 待核实线索 | 浏览器给 B 标注某服务，或时间金额支持一条候选路径 | 标签来源/时点、候选条件及下一步验证所需资料 |

**链上地址不等于自然人。** 私钥/助记词或可用签名权限材料能支持控制能力关联，但仍需区分多人持有、导入账户、只读观察钱包、托管、多签、权限变更和被盗用情形。设备中发现一个地址，可以是收款方、联系人、浏览器缓存或观察账户，不能一律认定机主拥有它。

钱包账户名称和序号也不直接代表控制范围。统计账户时读真实对象结构与账户类型，按明确标识去重，核对导入/删除/观察账户；不能用最高的账户编号代替账户总数。由恢复材料离线派生候选地址时记录词表/算法、口令、路径、账户索引和地址格式，再与钱包状态和已知地址比较。成功派生一个地址只证明特定参数下的对应关系，不证明已找到全部历史账户或当时操作者。

## 08 标签与聚类结果应保存时点和版本

地址标签通常来自公开页面、测试交易、受控设备、平台信息或供应商推断。标签“相关”“使用”“控制”“属于某服务”表达的关系不同。黑客、受害者、托管平台和中转服务都可能出现在同一事件中，不能把相关事件标签自动当作所有权标签。

标签记录至少保留：目标链/地址、关系类型、标签文本、形成依据、提供者、取得日期、适用时间段、数据版本、复核状态和不确定性。聚类额外保存地址集合、算法/启发式及版本、账本截止区块、参数、例外处理和集合摘要；复核时核对成员变化，不能只比较界面中的群组名称。

共同输入、找零和行为模式都建立在假设上。CoinJoin、PayJoin、托管归集、批量支付或其他协作行为可能影响假设。一个错误合并会把两个控制集及其全部标签连接起来；发现异常巨大聚类、角色冲突或不合理桥接点时，回到触发合并的交易，保留撤销前后结果和理由。

无标签只表示当前材料没有识别；一个服务标记也不覆盖所有历史地址。不同供应商、一批不同时间的标签或不同算法结果不能合并成未经解释的“唯一真相”。已有人工可验证钱包材料时，用它检查聚类边界；无法取得真实对照时，保留该限制。

## 09 数量、时间与报告停止点

数量按 `chain + asset_id` 分组，以整数最小单位保存，展示数量为 `raw_amount / 10^decimals`。原生币、合约代币、同名仿冒币、包装资产和不同链分别记账。费用与转账金额分开；代币转账手续费可能由原生币支付，不能从代币数量中凭空扣除。

地址流入量、地址流出量、转移次数、期末余额、平台成交额和受害损失是不同口径。自转、中转多跳、重复导出、桥两端以及平台的增减两行都可能重复累计同一笔经济价值。只有定义了控制范围、去重方式、兑换与费用规则后，才能计算特定口径的净流量；存在缺口时列出已确认数量与待核实数量。

时间至少分开保留钱包本地创建/发起、节点或索引器首次观察、区块时间、平台到账、订单成交、支付到账和采集时间。区块时间不能直接当作点击发送的准确时间；手机时钟、服务器时钟和显示时区也需要校准。用交易/订单/会话标识连接事件，时间只提供相容性检查。

资金图到达混币、隐私交易、平台内部记账或未匹配桥事件时，可以标出已证实入口、候选出口及所缺材料。不要填补一条看起来完整、实际上不可验证的路径。报告每项结论注明链/账户/资产/时段、证据位置、计算口径、推断条件、冲突与覆盖范围；材料没有覆盖后续交易时，使用“在本次记录截止点仍可见的余额或位置”，不能宣称永远的最终去向。

## 10 交易图、地址图与资金归因模型

### 10.1 先决定图中的节点和边代表什么

**画得出一条路径，不等于已经证明同一笔经济价值沿这条路径移动。** 区块链保存交易及状态转换，调查者还需要选择图的模型。把不同模型混在一起，会将“引用关系”“实际转账”和“推测同一控制者”画成完全相同的箭头。

| 图的模型 | 节点与边 | 实用场景 | 不能直接推出 |
| --- | --- | --- | --- |
| Bitcoin 交易/输出图 | 交易与具体输出；边由后续输入引用的 `txid:vout` 建立 | 精确追踪某个输出何时被花费，处理一对多、多对多与批量付款 | 多输入到多输出中的唯一价值分配、付款人的自然人身份 |
| 地址交互图 | 地址；边汇总已验证的付款输出或事件 | 找到活跃对手方、反复交互、归集或拆分候选 | 地址就是完整钱包；每条边都是独立受害损失 |
| EVM 资产事件图 | 按网络和资产限定的地址；边关联具体日志或成功调用路径 | 追踪指定合约代币、NFT 或原生币的移动 | 顶层 `to` 总是最终收款人；授权事件就是转账 |
| 控制集/实体图 | 按明确规则合并的地址集合；边仍回指原始事件 | 检查疑似同一钱包的集合及其跨地址业务 | 聚类标签天然真实，集合成员历史上一直受同一主体控制 |

Bitcoin 图至少保留交易节点和输出序号，不能仅将多个输入地址直接连到全部输出地址，随后给每条边填上整笔交易金额。EVM 图按 `chain_id + tx_hash + log_index` 或明确的调用路径区分事件；一笔交易里出现两次 A→B，保存两条独立事件，汇总展示时另记事件数及求和规则。

同一对地址之间的多次转账不能被普通“每对节点只保存一条边”的结构覆盖。可保留事件级多重边，或先建立不可丢失的事件表，再生成按资产和时段汇总的图。交易数、转账事件数、对手方数和图中的度数分别计算；如果图删去低金额边、只显示若干跳或最活跃节点，明确记录过滤条件。图中的缺边可以来自展示裁剪，不能据此认定没有交易。

### 10.2 多输入、多输出为什么没有唯一的来源分配

构造一个可手算的 Bitcoin 场景：输入 A 为 60,000 sat，输入 B 为 40,000 sat；输出 C 为 70,000 sat、D 为 29,000 sat，手续费 1,000 sat。协议上可直接复核的是：两个前序输出被消费，新输出共 99,000 sat，差额为手续费。交易格式没有单独写明“C 中哪些 sat 必定来自 A”。

如果任务要估算 A 的资金在后续输出中的分配，先声明模型，再计算。下列结果是**同一事实材料下的不同分析假设**：

| 模型 | 本例给 C 的 A 来源数量 | 给 D 的 A 来源数量 | 手续费处理与限制 |
| --- | ---: | ---: | --- |
| 比例分摊（Haircut） | 42,000 sat | 17,400 sat | A 占输入 60%，本例同时分摊 600 sat 手续费；不能表述为协议证明的逐 sat 来源 |
| 先入先出（FIFO） | 60,000 sat | 0 sat | 本例按 A、B 的输入顺序及 C、D、费用的消耗顺序分配；费用最后由 B 承担，改变约定可能改变结果 |
| 接触标记（Poison） | C 被标记 | D 被标记 | 只表示输出与选定来源有图路径关联；把标记输出全额相加会扩大“相关数量”，不能当作 A 的实际数量 |

比例分摊仍要处理整数舍入和残余 sat；先入先出要固定输入、输出与费用的排序规则。多跳分析额外保存每一步规则、来源集合、已访问事件与守恒校验，不能边走边改变模型。把 A/B 的两个输入画成一个交易节点，再从交易连到 C/D，可以先表达协议事实；模型计算作为附表或不同样式的推断边显示。

**实战考点：** 识别拆分与归集只是第一步；还要检查输出引用、手续费、可能找零、协作交易、托管资金池与统计口径。绕一圈回到已访问地址时，不把每次经过都加为新增损失；达到平台或未匹配桥时，保留可证实边和缺口。选择某个模型不能补足身份、平台内部账本或跨链消息证据。
