# 用户认可的知识点讲解标准

## 要达到什么效果

读者看完一小段，就知道该打开哪里、执行什么、看哪个结果，以及不符合预期时往哪查。内容仍须全面，不能靠删除参数、命令、分支、例子和考点变得“简短”。

操作顺序：**遇到的问题 → 实际动作 → 看到的结果 → 原因与下一步。** 不先铺满术语体系，也不在每节重复固定理论模板。

## 用户喜欢什么

- 按实际取证或恢复顺序讲，保留排错过程，而不是把功能名排成百科目录。
- 标题能帮助定位问题；原有标题/层级/锚点需保留时，用节内加粗短句组织操作，不大范围改目录。
- 写清界面菜单、目录、文件、命令、参数和输出字段。不要只说“检查配置”“建立证据链”。
- 成功和失败都有下一步，一眼分清该查网络、服务、认证、数据库还是应用日志。
- 一段一件事；有必要才用表格。参数留在对应命令旁，风险留在对应修改前。
- 少交叉引用，正文当场讲清关键步骤；唯一完整专题保留必要导航，避免重复章节。

## 对照：同一个知识点怎样讲

### 不采用的写法

“依据技术栈核对部署边界，联结Web配置、后端运行时和数据层，形成环境恢复与证据验证闭环。”

这句话让读者自己猜要看什么文件、怎么分支、怎样判断完成。

### 采用的写法

**网站打不开，先看源码是什么项目。**

打开网站目录，先找入口和依赖文件。看到`index.php`，继续确认PHP版本和框架；看到JAR，先读原启动命令，不去配置PHP。`package.json`只说明用了Node相关工具，还要确认它是后端服务，还是只用于构建静态页面。

接着读原Web配置，看域名、监听端口、网站目录和代理目标。先尝试访问恢复副本的IP与实际端口：能打开正确站点就继续；进了欢迎页或其他站点，再检查域名匹配，不一上来就要求改hosts。

这个短例只说明写法，不替代网站重构原文。实际修改要保留各技术栈的路径、版本、路由和数据库细节。

短样例也要保留分支前提：只有已确认是PHP网站，才写“恢复PHP”。若开头只说“网站打不开”，后面就必须先判断技术栈，不能为了简短省成固定搭PHP。

## 更完整的认可样例

`examples/website-reconstruction-approved.md`是用户认可的PHP恢复案例，按“找文件 → 恢复环境 → 看访问结果 → 查数据库 → 找后台 → 核对认证 → 验业务数据”推进。它是内部写作标尺，不是第二篇公开知识文章。

使用时学顺序和解释方式，不把所有步骤再复制到其他章节。其他技术栈和取证主题应按自己的实际操作组织。

## 改写前后的核对表

每节建立：原知识点/考点 → 新稿位置 → 保留/纠错/合并理由。至少覆盖：

1. 适用场景、版本和前置条件。
2. 操作顺序、命令/菜单/工具和关键参数。
3. 证据位置、字段、输出解释、时间和对象对应关系。
4. 成功/失败分支、常见坑、风险与回退。
5. 原有示例、表格、代码、锚点及与其他章节的唯一归属。

语义查重看知识点，不看标题。正确完整的不重复写；分散的合并；冲突的修正原处；存疑的先保留并询问。

## 始终保留的技术判断

- 离线镜像、运行现场和仿真副本不是一个状态；历史日志与实验新日志分开。
- PHP/ThinkPHP、WordPress、Laravel、Java、Python、Node、静态站分别恢复真实依赖，不套固定伪静态。
- 原配置优先；系统Apache与宝塔Apache须区分实例；SSH进程、systemd服务、监听、配置、账户和认证分开。
- Linux root、MySQL root、面板账户和网站后台账户不是同一认证体系。
- 后台密码分析要跟着实际代码、salt、比较分支、session和角色走；MD5不叫解密；只改表或放行一个分支不代表整个后台已可用。
- HTTP200、服务“运行中”、命令退出0都不能单独证明业务恢复或历史行为。
- 案例提供的操作与官方行为冲突时，保留可核实细节并纠正错误，不为了像来源而恢复错误结论。

## 不采用的捷径

不批量替换几个词就声称全模块已改；不删掉“难讲”的考点；不堆砌跨页链接；不复制来源大段文字；不编造原题答案、截图、工具输出或已完成状态。
