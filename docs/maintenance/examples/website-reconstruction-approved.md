### 07.2 面板列表为空：从备份与操作记录找回 PHP 站点

服务器镜像已经仿真开机，也能进入宝塔，但网站打不开，面板里的站点列表还是空的。接下来从哪里查？

先把事情分开：**找回网站文件 → 让前台打开 → 找到后台 → 登录后核对数据。** 不急着重装宝塔，也不先改一堆密码。

本例讲的是已经确认使用PHP的网站。看到JAR、Python或Node.js后端时，应恢复对应程序，不照搬PHP和ThinkPHP设置。

【仅在副本/仿真/授权环境执行】开始前保存快照、原文件和数据库备份，记录哈希。后面的修改都留在恢复副本中；原始镜像继续只读保留。

#### 一、宝塔没有站点，先找网站文件

进入 **宝塔 → 文件 → `/www/wwwroot/`**，看原网站目录还在不在。

- **目录和文件都在：** 继续找原站点配置，记下域名、端口和网站目录。
- **`/www`整个目录几乎是空的：** 先查原挂载记录，确认数据盘是否已经挂上。
- **站点目录缺失：** 再查备份和操作记录。面板列表为空，只说明当前列表没有站点，不代表网站从未运行。

这时重点找三个位置：

```text
/www/server/panel/data/default.db   旧版面板常见数据库，先查看实际表结构
/www/backup/                       网站和数据库备份的候选位置
/www/wwwlogs/                      网站访问、错误日志的候选位置
```

把面板数据库完整复制后，用SQLite查看工具打开，先看有哪些表，再找删除、压缩、备份、移动文件的记录。若旁边有WAL/SHM文件，连同主库一致保全。表名随版本变化，不凭一个固定表名下结论。

**例如，操作记录写着“打包网站后移到backup目录”**，下一步就去对应路径找压缩包。文件夹不存在时，再查Shell历史里的`tar`、`zip`、`mv`和实际目的路径。找到备份后，还要找同一时期的数据库、上传附件及旧站点配置。

先记下压缩包的哈希、大小和时间。查看文件清单，检查绝对路径、`..`、软硬链接、设备文件、同名覆盖及解包体积，再解到一个新的空工作目录；这一步不运行包里的脚本或安装器。

**做到这里：你应当已经知道源码在哪里、是哪一版，以及它对应哪个数据库。** 不把几处“最新文件”直接拼成一个网站。

#### 二、文件找到了，再看网站需要哪些服务

**站点还在列表里：** 进入 **宝塔 → 网站 → 对应站点 → 设置**，核对网站目录、PHP版本和原站点配置。

**列表为空：** 先读保留下来的Nginx/Apache站点配置。宝塔管理的Nginx配置常见于`/www/server/panel/vhost/nginx/`，Apache常见于对应的`apache/`目录，最终以实际加载路径为准。

记下原域名、端口、目录和PHP设置，把检查后的源码恢复到副本中确定的位置。原Web配置仍在时先修复它；确需在面板补建记录时，进入 **宝塔 → 网站 → 添加站点**，选择已有源码目录和匹配的PHP，数据库选择“不创建”。补齐原Rewrite、证书等配置，检查是否生成了重复站点；不把已有数据库重新建成空库。

接着到软件管理页面，检查本例使用的Nginx、PHP和MySQL是否已安装、是否正在运行。服务未启动时先看报错，确认原版本和配置后，再在副本启动；不靠重装最新版解决所有问题。

这里最容易弄错两件事：

- **PHP版本：** 按原配置和依赖恢复，版本越新不代表旧网站越容易打开。
- **运行目录和伪静态：** 有些项目入口在`public/`，有些直接使用网站根目录；ThinkPHP、WordPress、Laravel分别读原来的规则，不统一选择ThinkPHP伪静态。

#### 三、尝试打开网站，看它停在哪一步

在恢复服务器查看当前IP：

```bash
ip a
```

再看站点实际监听端口。比如副本IP是`192.168.56.20`、HTTP端口是`8080`，就访问：

```text
http://192.168.56.20:8080/
```

这是地址示例，不是固定的恢复地址。

看到结果后再往下走：

- **出现原网站首页或登录页：** 前台已经有响应，接着找后台。
- **出现Nginx欢迎页或另一个网站：** 请求可能进了默认站点。回到原配置看`server_name`、端口和网站目录。
- **提示数据库连接失败：** PHP已经执行到连接数据库这一步，转到下一步查连接。
- **502、空白页或PHP报错：** 看这个站点的错误日志，再查PHP进程、版本、扩展或代理目标，不先改数据库密码。

**IP能打开正确网站，就先继续。** 如果原站点依赖域名，才在分析机hosts里把原域名映射到副本IP，并用原域名访问。单纯修改hosts不会替你修好端口和服务。

#### 四、数据库连不上，先把连接信息一项项对上

先找到网站自己的数据库配置。

在宝塔文件管理，或Notepad++的 **搜索 → 在文件中查找** 中，把目录选为网站源码目录，包含子目录。先找`config.php`、`database.php`、`.env`；没有命中，再按`DB_HOST`、`database`、`password`等内容搜索。

文件名只是线索。打开后继续看入口代码实际加载了哪个文件，避免改到备份配置。PHP的`include`、`require`可以指向其他文件；有配置缓存的项目还要核对正在生效的缓存。

找到配置后，逐项核对：

| 配置项 | 要跟什么对应 |
| --- | --- |
| 数据库地址 | 数据库真正所在的主机或容器 |
| 端口 | 该数据库实例的监听端口 |
| 库名 | 已恢复且包含目标表的数据库 |
| 用户名、密码 | 允许该应用连接的数据库账号 |

**网站与数据库在同一台普通主机上时，地址可能是`127.0.0.1`；站库分离或使用容器时，按实际连接关系填写。** 不因为虚拟机换了IP，就把所有数据库地址都改成虚拟机IP。

原配置使用`localhost`时还可能走Unix socket，先确认原连接方式，不把它与`127.0.0.1`机械互换。

保存原配置，只改已确认不匹配的字段，然后重新访问同一个页面。如果还报错，就看完整错误信息：

| 报错 | 接下来查哪里 |
| --- | --- |
| `2003`，连接不上 | 数据库是否运行，IP/端口是否正确，监听和网络是否可达 |
| `1130`，Host不允许连接 | 当前连接来源有没有匹配的允许项；此时数据库已返回拒绝信息 |
| `1045`，Access denied | 用户名、密码、账号对应的Host和认证配置 |
| `Unknown database`或表不存在 | 库名是否写错，是否连到空库，恢复是否完整 |

需要用Navicat看库时，新建对应的MySQL连接，先填已核实的数据库地址、端口和账号。网站的业务账号、MySQL root、Linux账号、宝塔账号是四回事。

**如果数据库只允许服务器本机连接，可以用Navicat的SSH连接方式：**

1. **常规页：** 填数据库地址、数据库端口和数据库账号。数据库在SSH服务器本机时，主机填`127.0.0.1`；如果在另一台机器或容器里，填从SSH服务器能访问到的真实地址。
2. **SSH页：** 填恢复服务器IP、实际SSH端口和Linux账号。
3. 点击测试连接。成功后打开目标库，确认原有表和记录都在。

不要为图省事直接把数据库来源改成“所有人”。先确认是连接地址问题，还是账号来源权限问题。

#### 五、前台打开了，再从日志找后台

进入 **宝塔 → 网站 → 对应站点 → 设置 → 网站日志**。不同版本的菜单名称略有差别，也可以直接打开该站点的访问日志。

先搜`admin`、`login`，记录命中的URL和时间，再访问恢复副本中对应的地址。200和302值得查看，但200可能只是提示页，302也可能跳回登录页；要以实际打开的页面为准。

如果日志没有明显线索，就在源码中找登录入口、路由和“后台管理”等页面文字。后台也可能用了自定义名称，不一定叫`admin.php`。

**旧URL返回404时先对版本。** 备份可能早于这条日志，也可能少了原Rewrite规则。保留旧路径和报错，不急着认定后台已经删除。

#### 六、后台地址找到了，怎样恢复登录？

先在数据库和登录代码中确认这个后台到底使用哪张账号表，再找对应管理员记录。前台特权用户和后台管理员可能来自不同表；表名带`user`不等于它一定管后台登录。

密码未知时，先用确认存在的副本账号提交一次错误密码，记下完整报错。假设页面提示“登录信息有误”，就在源码目录搜索这句话，查看命中位置上下文：

```text
查账号 → 计算密码摘要 → 比较密码 → 写入登录会话 → 跳转后台
```

现在再决定改哪里：

**方式A：按这个账号的规则重新计算密码字段。** 先备份该账号原记录，读出实际算法、拼接顺序和salt，再为副本测试口令生成对应值，只替换这个账号需要修改的字段。字段看起来是32位，不足以直接认定“就是一次MD5”。

如果salt是每个账号单独生成的，直接搬另一个账号的密码字段可能失败。要检查它是否还依赖独立salt、账号名或其他字段；使用`password_hash()`的存储串则可能已包含算法和salt，按对应验证函数处理。

**方式B：在副本临时改动已确认的密码判断。** 例如下面这段仅用于说明“成功分支”在什么位置：

```php
if ($candidateHash == $storedHash) {
    // 原代码：创建会话，进入后台
} else {
    // 原代码：提示密码错误
}
```

只有确认项目就是这种结构时，把这一处密码比较的`==`改为`!=`，错误密码才会进入原成功分支。账号查询、验证码、禁用状态和会话处理仍各自生效。若命中的是“密码不符就报错”的失败分支，应先读清整个if/else和return；改错位置会得到相反结果，不全站替换运算符。

用选定的副本账号测试后，继续打开一个需要登录的后台页面，看当前用户名、角色和数据范围。只出现“登录成功”提示还不够。结束时恢复原代码、账号记录和相关会话，再确认错误密码重新被拒绝。

#### 七、进入后台后，核对的是原有数据

选一笔已经存在的订单或一条已有用户记录，按下面顺序核对：

1. 在页面记下编号、账号、金额和状态。
2. 在数据库按同一个编号找到原记录，逐项比较。
3. 页面有筛选、分页或角色限制时，把这些条件记下来，再比较数量。
4. 对照目标时段的访问日志，记录代码备份、数据库备份和日志各自覆盖的日期。

只恢复出代码但缺少数据库、上传目录时，就分别记录哪些页面和数据已恢复。恢复期间生成的登录日志、会话、新账号和新密码单独登记，不当作历史使用痕迹。

**最后留下两组东西：原文件、原数据库和哈希；恢复用的配置、修改记录、页面截图及对应记录。** 这样既能说明网站怎样恢复，也能区分原来就有的数据和恢复过程中产生的变化。

#### 已复制材料的命令行查找

习惯命令行时，可以用下面一组命令找备份、配置和登录代码。`/work/backup-copy`是备份副本目录，`/work/extracted-site`是检查后解压出的源码目录；搜索只用于定位文本，不执行认证代码。

```bash
find /work/backup-copy -maxdepth 3 -type f \
  \( -name '*.zip' -o -name '*.tar.gz' -o -name '*.sql' \) -print
find /work/extracted-site -maxdepth 4 -type f \
  \( -name 'composer.lock' -o -name '.env' -o -iname '*database*.php' \
     -o -iname '*login*.php' \) -print
rg -l 'password|salt|password_verify|md5|hash|login' /work/extracted-site
```

find的深度限制用于首轮查找；未命中时继续检查更深目录。搜索结果只是候选文件，最终仍看实际入口和调用关系。
